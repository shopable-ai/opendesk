# OpenDesk 商业系统设计与模式组合

更新时间：2026-09-13

> 文档性质：Research / Business Design Baseline（商业设计研究基线）。本文件整理 2026-09-13 对话中关于预制自动化、低摩擦调用、免费获客、首发共建、外包供给与持续维护的推理。保存方案不等于批准全部模式，不代表商业验证成功，也不声明相关产品功能已经实现。金额、比例与评分均不能替代真实订单、成本和运行证据。

## 1. 目标需求与当前定位

让用户提出一个有明确结果的电脑任务后，优先直接使用已经验证的自动化能力；没有现成能力时，以可控成本完成开发、适配或定制，并在取得授权的前提下沉淀可复用资产。

核心商业链路：

```text
发现真实需求
→ 判断是否已有合格能力
→ 明确范围、报价、权限与验收
→ 自助运行或交付服务
→ 验证实际业务结果
→ 收款并核算全部交付成本
→ 经授权提取通用能力
→ 向后续客户重复交付
→ 维护、反馈、再次验证
```

用户提出的原始方向包括：提前做好常用脚本、其他人立刻调用、尽量减少使用摩擦、持续运行或生产能力、内部自研软件按需定制或驻场、借助外包与低价免费机制扩大需求和供给，以及首位客户出资后从后续使用收入中获得返还。

本轮讨论的名称是 **商业系统设计与模式组合推演**，不只是收费方式设计。

| 讨论内容 | 所属层面 | 核心问题 |
| --- | --- | --- |
| 提前做主流操作 | 产品规划与资产投资 | 先做什么，能否重复销售并覆盖维护？ |
| 一句话调用 | 产品体验与能力分发 | 如何匹配、配置、安全执行和验证？ |
| 24 小时运行 | 交付与运营 | 接单、生产、执行和人工支持分别承诺什么？ |
| 免费、低价 | 获客与补贴 | 补贴谁，换回什么，成本上限是多少？ |
| 首发出资后返还 | 成本共担与收益分配 | 返还条件、来源、上限和销量风险是什么？ |
| 外包、驻场 | 供给与交付组织 | 谁开发、验收、维护，谁对结果负责？ |
| 创作者分成 | 激励与平台治理 | 如何归因、结算、修复和更换维护者？ |

商业模式决定如何创造和获得价值；经营机制决定优惠、返还和分成规则；产品与运营架构负责兑现承诺。单独一个“首单免费”活动不是完整商业模式。

## 2. 当前建议：服务现金流与资产复用共同推进

建议的默认顺序：

```text
固定范围小额交付，获得现金流
→ 识别多个客户的重复需求
→ 沉淀标准场景包与维护方法
→ 扩大自助调用与可靠伙伴供给
→ 用真实交易决定是否建设平台
```

不是先做完整 Marketplace，再寻找用户；也不要求每家自动化公司最终都变成开放市场。

用户任务可分成四条交付路线：

| 路线 | 触发条件 | 对外体验 | 经营方式 |
| --- | --- | --- | --- |
| 已有能力直接调用 | 已有版本、环境、权限与业务范围匹配 | 完成必要配置和确认后运行 | 免费基础能力、授权或订阅 |
| 相似能力受控适配 | 有可复用基础，但存在配置或环境差异 | 先说明适配与验收，再运行 | 适配费、实施费或服务额度 |
| 缺失的公共需求 | 暂无能力，存在可验证复用需求 | 提交需求、报价、开发和验收 | 首发共建、联合预购或平台补贴 |
| 私有定制需求 | 客户要求专有业务逻辑或环境 | 私有交付、远程协助或驻场 | 项目费、部署费和维护费 |

Agent 辅助开发不等于未经验证即可上架或在客户生产环境执行。公共需求也必须有范围、预算和维护责任。

## 3. 七层商业系统任务树

- **L1｜客户与价值：为什么有人需要？**
  - 客户：个人办公用户、小企业、部门团队、软件厂商、自动化服务商。
  - 价值：减少重复劳动、缩短交付时间、减少错误、延长业务运行时间。
  - 产物：客户定义、任务问题、现有替代方式、购买决策人、不接的需求。
- **L2｜商品与资产：到底卖什么？**
  - 商品：一次结果、固定范围项目、场景包、应用操作包、托管服务、私有能力库。
  - 资产：脚本、应用适配、测试用例、兼容证据、配置模板与交付经验。
  - 产物：商品范围、交付单位、验收标准、公共与私有边界。
- **L3｜交易与收益：谁付钱，为什么付？**
  - 付款人：使用者、企业采购者、软件厂商、渠道商、联合采购组织。
  - 收费：项目、订阅、维护、结果、部署、授权、佣金。
  - 产物：价格假设、成本承担、付款节点、退款与失败责任。
- **L4｜增长与供给：需求与能力从哪里来？**
  - 需求侧：限额免费、试用、首发优惠、推荐、行业案例、渠道。
  - 供给侧：内部开发、Agent 辅助、业务专家示范、模块外包、维护者与伙伴。
  - 产物：获客实验、供应商试单、补贴预算及回报证据。
- **L5｜交付与运营：怎样真正完成？**
  - 交付地点：客户本机、远程协助、企业专机、托管环境、驻场。
  - 运营：环境检查、验收、异常接管、版本维护、客户支持。
  - 产物：服务边界、交接、运行条件、维护范围与支持时段。
- **L6｜产品与治理：需要哪些系统和规则？**
  - 产品：对话入口、能力目录、配置授权、执行记录、订单、工单和结算。
  - 治理：权限、安全、隐私、权属、兼容性、发布审核与维护者替换。
  - 产物：最小功能缺口、人工替代项、关键合同及审查事项。
- **L7｜经济与演进：怎样判断值得继续？**
  - 经济：订单贡献、获客成本、维护负担、复用成本、现金占用。
  - 演进：服务、标准方案、自助产品、合作网络、可选平台化。
  - 产物：继续、调整、停止或扩大的证据与条件。

完整性意味着每个新模式都有位置且可检查，不意味着七层同时完成。

## 4. 商品层级：销售业务价值，不用脚本数量代替价值

| 层级 | 示例 | 购买或使用对象 | 商业定位 |
| --- | --- | --- | --- |
| 原子操作 | 打开应用、点击按钮、读取字段 | 开发者 | 生产组件，未必独立收费 |
| 应用能力包 | 某软件的导出、查询和上传能力 | 开发者、实施团队 | 减少适配工作 |
| 业务场景包 | 下载订单、整理表格、生成报表 | 业务人员、小企业 | 可理解、可验收的商品 |
| 岗位方案 | 运营报表、采购资料整理 | 部门负责人 | 围绕持续工作组合多个流程 |
| 托管结果服务 | 按约定交付校验后的报表 | 不希望自己维护的客户 | 同时承担运行与服务责任 |
| 企业能力基础设施 | 私有目录、权限、审计、部署 | 企业信息化团队 | 管理与治理能力 |

技术上沉淀常用应用操作，商业上先覆盖一小类客户的高频、可验收任务。不要先做大量按钮动作，再寻找购买者。

Calculator 用于验证任务理解、能力选择、真实执行与结果读取的技术闭环，不等于商业需求或付费验证。文件保存不表示该技术链路已经通过实机验收。

主流软件不一定容易标准化，内部软件也不一定只能做一次。复用判断应看流程相似程度、配置差异、版本差异、测试条件与权属许可。

## 5. 模式地图：22 个可组合机制

下表工作量为小规模试点的相对负担，不是代码审查后的工期估算。“人工处理”可以减少后台开发，不能消除交付、财务或支持责任。

### 5.1 A 类：获客与首次开发成本

| ID | 模式 | 交换的价值 | 最少配套 | 开发 / 运营负担 |
| --- | --- | --- | --- | --- |
| A1 | 限额免费诊断与小样 | 用户看见可行结果，平台得到有效商机 | 需求表、范围、名额与成本上限 | 低 / 中 |
| A2 | 复用授权换首单优惠 | 用户立即少付费，平台取得约定通用部分的复用权 | 公私边界、交付范围、授权记录 | 低 / 中 |
| A3 | 首发共建、后续有条件返还 | 用户先获得功能，未来可能收回部分费用 | 收入定义、归因、账本、上限与期限 | 中高 / 高 |
| A4 | 多客户联合预购 | 多家分摊同一个标准版本的成本 | 共同需求基线、启动、退出与退款规则 | 低中 / 高 |
| A5 | 厂商、渠道或协会买单 | 用户免费或优惠，出资方获得服务或会员价值 | 赞助合同、适配包、权益范围和报告 | 中 / 中高 |
| A6 | 基础免费、便利与服务收费 | 用户低成本入门，为高级量级、维护或团队能力付费 | 权益、配额、升级、成本限制 | 中 / 中 |
| A7 | 示范或测试贡献换额度 | 业务专家提供经授权的知识与验证，获得优惠 | 示范、脱敏、授权与贡献验收 | 中 / 中高 |
| A8 | 推荐成交或内容获客奖励 | 推荐者获得奖励，平台获得实际付费客户 | 归因、有效订单、退款后调整 | 低中 / 中 |

A2 是返还模式的轻量替代，不必先有复杂分账。A7 吸引熟悉业务但不编程的人，不应要求其直接交付代码。A8 的获客佣金和作者的运行收入分成是两种机制。

所有免费机制都要明确免费对象、持续时间、运行费用及支持成本。基础安全、停止能力和必要权限控制不应成为付费后才获得的保护。

### 5.2 B 类：商品与收入

| ID | 模式 | 客户为什么付费 | 必要配套 | 开发 / 运营负担 |
| --- | --- | --- | --- | --- |
| B1 | 固定范围自动化小单 | 购买一个明确结果 | 报价、范围、验收、变更单 | 低 / 中 |
| B2 | 场景包订阅或授权 | 购买持续可用的标准能力 | 标准配置、兼容说明、版本与维护政策 | 中 / 中高 |
| B3 | 软件免费、实施与维护收费 | 购买安装、适配、培训和省心 | 安装检查、服务套餐、工单 | 低中 / 高 |
| B4 | 按合格结果或成功批次收费 | 为验证后的产出付费，不按点击次数付费 | 结果校验、计量、防重复收费、失败处理 | 高 / 中高 |
| B5 | 持续托管服务 | 购买持续结果，不自行维护机器和脚本 | 专用环境、调度、监控、接管、服务边界 | 高 / 很高 |
| B6 | 企业私有能力库 | 购买内部复用、治理和统一部署 | 私有目录、组织权限、版本、审计 | 高 / 高 |
| B7 | 品牌化小工具 / OEM 授权 | 服务商或厂商购买自己的产品入口 | 品牌配置、打包授权、更新、支持责任 | 中高 / 高 |
| B8 | 面向服务商或其他 Agent 的能力服务 | 团队购买交付工具，系统购买受控任务调用 | 接口、身份授权、预算、状态、计量 | 中高 / 高 |

B2 也可以是一次购买某版本、维护另收费，不能将有限收入和无限维护承诺绑定。B4 必须验证业务结果，例如字段、日期和完整性，而不是“脚本未报错”或“出现了文件”。运行资源成本与业务收费单位应分别定义。

按节省成本或新增收益分成可作为远期变体，但需要原始基线、变化归因、核算和争议处理，不把估算节省时间直接当成可结算收入。

### 5.3 C 类：供给与合作组织

| ID | 模式 | 组织方式 | 最少配套 | 开发 / 运营负担 |
| --- | --- | --- | --- | --- |
| C1 | 小额付费试单 | 用边界明确的真实任务验证合作能力 | 任务包、验收、付款节点 | 低 / 中 |
| C2 | 模块化外包 | 将业务分析、适配、测试与文档分工 | 输入输出契约、交接、集成验收 | 低中 / 高 |
| C3 | 现有脚本授权引入与迁移 | 经许可复用已有资产，而非全部从零开发 | 来源与许可检查、迁移、质量测试 | 中 / 中高 |
| C4 | 按应用签约维护者 | 长期负责某应用兼容与修复 | 范围、响应规则、备份维护者、版本记录 | 中 / 高 |
| C5 | 认证交付伙伴 | 伙伴实施、培训或驻场，平台提供工具和标准 | 认证、线索、规范、责任界面 | 中 / 高 |
| C6 | 开放创作者市场 | 第三方自主发布、销售和维护，平台抽佣 | 审核、授权、支付、分账、投诉、下架 | 很高 / 很高 |

低成本供给不建立在“多人免费做完、最后只选一个”上。优先小额付费试单、清楚验收、可复用工具和明确合作机会。

C5 可先于 C6。Repair Bounty（修复悬赏）是 C4/C6 的维护机制：依据经授权的失败证据提出修复任务，原维护者优先处理，修复经过回归、发布和观察。不能仅根据少量失败率变化自动认定根因并替换版本。

## 6. 五套完整经营组合

模式不是独立开发项目，需组合成包含客户、收入、交付和维护的业务。

| ID | 组合 | 链路 | 主要收入 | 建议定位 |
| --- | --- | --- | --- | --- |
| P1 | 现金流型自动化服务 | 免费小样 → 固定报价 → 复用优惠 → 官方或外包交付 → 维护 | 项目、实施、维护 | 优先验证 |
| P2 | 垂直场景自助产品 | 同类高频需求 → 标准场景包 → 自助配置 → 本机运行 → 更新 | 订阅、授权、有限服务 | 与 P1 共同推进 |
| P3 | 厂商赞助生态 | 厂商购买适配包 → 用户使用 → 联合推广 → 持续适配 | 厂商合同、维护、OEM | 有合作对象后试点 |
| P4 | 企业私有托管 | 企业购买持续结果 → 私有能力与专机 → 监控及接管 | 部署、周期服务、用量 | 有运行证据与支持能力后进入 |
| P5 | 创作者交易平台 | 需求 → 多供应商交付或发布 → 验证 → 交易复用 → 维护分成 | 佣金、平台服务 | 双边交易成立后投入 |

当前建议组合：P1 获得订单，P2 沉淀资产；获客优先 A1/A2，供给优先 C1/C2/C4。P3/P4 择机试点，P5 不是必然终点。此处为建议，未确认最终客户、价格和开发排期。

## 7. 首发共建与返还机制

### 7.1 保留原始想法，但拆清三类金额

原始想法：第一个客户先支付一笔金额，开发完成后别人付费使用，再逐步返还第一位客户的支出。

必须分别说明：

| 项目 | 含义 |
| --- | --- |
| 履约退款 | 没有按约定交付时如何退款 |
| 开发费用 | 已购买并交付的开发、适配或服务 |
| 后续返还 | 未来发生符合条件的复用收入后额外返还 |

不要将三者混为含糊的“押金余额”。将名称改成“赞助”不能替代合同、资金和责任设计。

可讨论的表达：首发共建价，符合条件的后续销售产生返还，累计不超过约定金额，不保证全额返还。未来销量不确定，不得承诺“首位用户最终一定免费”。

正式收款前，按实际经营地、支付服务、资金流和合同核实合规事项。本文件不是法律、税务或支付托管意见。

### 7.2 从轻到重的四个版本

| 版本 | 规则 | 特点 | 适合阶段 |
| --- | --- | --- | --- |
| V1 | 复用授权换即时优惠 | 用户立即受益，无后续返还账本 | 最早期 |
| V2 | 后续复用换服务额度 | 减少频繁现金付款，但必须说明不是现金 | 已有复用订单 |
| V3 | 已结算收入触发现金返还 | 设归因、总上限、期限和冲回规则 | 交易与财务稳定 |
| V4 | 多客户联合预购公共版本 | 共同承担首发成本 | 已有明确共同需求 |

平台额度只能按实际可用范围表述，不能将有限用途额度等同于等额现金。

### 7.3 返还可行性的算例

以下仅为说明计算方式，不是报价、销量预测或正式分配比例：

```text
首发返还上限：600 元
后续每笔合格订单的可分配贡献：20 元
其中用于返还的比例：30%
每笔返还：20 × 30% = 6 元
达到上限需要：600 ÷ 6 = 100 笔合格订单
```

比例设计并不证明存在足够后续收入。正式规则需要说明有效订单、收入归因、允许扣除的成本、结算窗口、退款冲回、反作弊、截止条件，以及停止维护时如何处理。

返还只能依据规则中明确的真实已结算收入，不能依赖继续收取新客户开发预付款维持承诺。

### 7.4 角色激励与风险分配

首发用户的返还可封顶于原约定金额；创作者、维护者和平台的长期报酬分别设计，不默认同一人永久负责维护。此前讨论的具体金额和百分比仅为示例，不作为已冻结定价。

没有后续销量的风险要明确由谁承担。不能一方面向首发客户保证回本，另一方面把全部风险转移给开发者或未来购买者。

联合预购需要一个共同标准范围；客户专属差异单独报价，避免多个低价项目被误称为一个可复用项目。

## 8. 24 小时与低摩擦的产品边界

### 8.1 四种 24 小时不能混合销售

| 类型 | 交付承诺 | 必要条件 | 持续工作量 |
| --- | --- | --- | --- |
| 接收需求与分发能力 | 随时提交和查询 | 可用入口、任务队列、响应说明 | 相对低 |
| 生产与测试候选脚本 | 内部持续扩大供给 | 隔离测试、预算、审核、失败归档 | 中高 |
| 无人值守业务执行 | 指定环境中持续运行 | 机器、会话、调度、监控、恢复、授权 | 高 |
| 全天人工异常处理 | 各时段有人接管 | 值班、升级、交接、响应承诺 | 很高 |

建议分别定价、分别验收。脚本已经写好不等于无人值守条件成立；macOS 和 Windows 的具体边界需依据本项目当前实现与实机证据验证。内部持续生产不代表候选脚本自动获得发布资格。

### 8.2 将“零摩擦”转成可验证目标

目标：用户不写代码、不找脚本、不处理坐标；首次完成必要设置后，重复任务无需重新配置。

```text
首次使用成本：安装、授权、账号、配置、首次验证
重复使用成本：输入任务、必要确认、等待结果、处理异常
```

必要授权、真实账号准备、业务参数和重要操作确认不能为了宣传零摩擦而省略。已有脚本降低开发等待，不自动消除首次配置和运行异常。

## 9. 共用功能底座与真实工作量

以下是业务需要的能力类别，不是对仓库缺失项的审计。先复用现有 Runtime、App、Catalog、Execution 与验证资产，再确认缺口。

| ID | 底座 | 小规模最小实现 | 持续工作 |
| --- | --- | --- | --- |
| F1 | 需求与商机管理 | 聊天或表单入口，人工分类台账 | 澄清、聚类、报价、跟进 |
| F2 | 能力目录与匹配 | 能力说明、参数、环境、版本、维护者 | 目录清理、匹配、兼容信息 |
| F3 | 安全执行与验收 | 权限、参数、确认、停止、结果证据 | 异常分析、实机验证、验收维护 |
| F4 | 标准交付包 | 契约、配置模板、安装、测试、交接 | 减少新客户适配成本 |
| F5 | 版本与维护 | 版本记录、兼容说明、工单、回退 | 回归、升级适配、修复、下架 |
| F6 | 订单、权益与结算 | 适当收款渠道与可核对台账 | 退款、账务、权益、分账、争议 |
| F7 | 供应商与伙伴管理 | 少量伙伴记录、人工派单验收 | 培训、质量、维护者替换 |
| F8 | 托管运行设施 | 专用环境、监控、调度、故障处理 | 容量、会话、权限、值班 |

总工作量：

```text
软件开发
+ 能力内容生产
+ 兼容与安全验证
+ 获客成交
+ 实施验收
+ 日常支持与修复
+ 财务和治理
```

“新增一个发布按钮”的开发量不能代表发布后所有版本与环境的维护成本。

实施原则：

- 后台报价、派单、对账可以先人工；权限、停止与真实结果验证不能靠台账替代。
- 通用 Runtime 与官方产品商业策略分离，不把商城、返还和渠道规则塞进通用执行核心。
- 公共组件、客户私有逻辑、账号数据、可分享测试证据分开管理；公开复用必须有授权。
- 企业内部复用本身也有价值，不强制所有付费成果公开。
- 商业收益模型不反向要求每次运行都使用模型；确定路径优先普通脚本，必要理解与异常才调用 Agent。

## 10. 经济核算与关键指标

### 10.1 核算边界

先记录实际收款、退款、模型与机器成本、人工交付、支持维修、渠道奖励、开发者分配及首发返还，避免把营业额当作利润。

用于内部实验的项目贡献口径可以是：

```text
已结算收入
－ 退款及支付相关成本
－ 交付与验收人工
－ 运行资源成本
－ 本期支持维护成本
－ 渠道、创作者、维护者和首发返还
＝ 项目贡献（管理口径）
```

采用何种税务或财务口径应另行确认；费用不得重复扣除。还需单列首次研发、固定开支和现金占用，不能因项目贡献为正就声称公司已经盈利。

### 10.2 需要真实证据的五个假设

| 假设 | 证据 | 反证 |
| --- | --- | --- |
| 有人愿意买 | 明确范围下的实际付款 | 只有点赞、报名，没有购买 |
| 可以重复销售 | 独立客户购买同一标准方案 | 每次都要重写主要逻辑 |
| 可以低成本交付 | 全流程工时与接管记录 | 开发快，但沟通、验收、支持不断扩大 |
| 可以持续维护 | 应用变化后的修复回归记录 | 首次成功后无人负责 |
| 可以形成正贡献 | 扣除完整成本后有余量 | 每增加一单，亏损反而增加 |

### 10.3 推荐指标定义

- 合格即时完成率：在事先声明的目标任务范围内，无需新增开发、无需工程师代操作且结果验证成功的任务数 / 真实有效需求数。
- 能力复用：独立客户是否重复购买或使用同一标准能力；参数变化与重写主体逻辑分开记录。
- 执行成功：按业务验收标准记录结果，不以进程退出码代替。
- 修复负担：从发现问题到恢复的时间、人工、受影响环境和回归情况。
- 单次及每客户贡献：将运行、支持和维护计入，不只计算脚本生成成本。
- 首发返还：实际现金返还和服务额度分开；未回本、部分回本、观察期未结束分别记录。

分母、任务范围和观察窗口先定义。必要的用户授权及确认可以保留，但工程师后台临时改脚本不得算作已有能力直接完成。

此前讨论中的覆盖率目标、脚本数、收入预期和主观高分不构成事实基线。

## 11. 如何继续推演新模式

使用组合维度，而不是不断添加孤立点子：

```text
客户类型
× 购买结果
× 实际付款人
× 首次开发成本承担者
× 供给组织
× 交付与运行地点
× 收费方式
× 资产权属
× 维护责任
```

| 改变维度 | 推导出的模式 |
| --- | --- |
| 用户付费改为厂商付费 | 厂商购买用户使用权益 |
| 办公用户改为实施团队 | 服务商购买交付工具与模板 |
| 脚本改为持续结果 | 托管业务服务 |
| 未来返还改为即时优惠 | 复用授权换首单折扣 |
| 从零开发改为授权引入 | 旧脚本资产迁移与资格验证 |
| 公共复用改为企业内复用 | 私有能力目录 |
| 平台交付改为伙伴交付 | 认证实施网络 |
| 聊天入口改为行业工具入口 | 品牌化小工具与受控系统调用 |

组合可行不等于经济成立。每个候选模式使用同一张模式卡：
