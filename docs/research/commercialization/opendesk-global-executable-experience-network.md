# OpenDesk 全球可执行经验网络战略

更新时间：2026-09-12

> 文档性质：Research / Strategy Input（研究 / 战略输入）。本文用于建立 OpenDesk 从 Desktop Automation Runtime（桌面自动化运行时）向 Global Executable Experience Network（全球可执行经验网络）演化的统一思考框架。它不是当前能力声明，也不自动进入正式 Roadmap；任何 Marketplace（市场）、Creator Economy（创作者经济）、共享执行数据、收益分成或云端能力都必须经过产品、隐私、安全、合规和真实付费验证。

## 1. 核心战略命题

- **长期命题**
  - Turn human computer work into executable software（把人的电脑工作变成可执行软件）。
  - Solve a digital task once, make the successful experience reusable for later users（一个数字任务成功解决一次，让后来用户优先复用已有成功经验，而不是从零重新探索）。
- **核心价值变化**
  - 第一阶段：一个人做过一次，自己不再重复。
  - 第二阶段：一个人做过一次，团队不再重复。
  - 第三阶段：一个 Creator（创作者）解决一次，其他用户可以安装复用。
  - 第四阶段：一个环境或版本问题被修复一次，相同环境用户共同受益。
  - 第五阶段：执行、失败、恢复和适配持续沉淀，网络整体成功率提升。
- **核心差异**
  - Agent（智能体）负责新任务、变化和异常。
  - Recipe / Workflow（配方 / 工作流）负责已知、稳定、重复路径。
  - 平台价值不应停留在“AI 会操作电脑”，而应进入“AI 第一次解决后，把经验编译成可复用资产”。

## 2. 推荐战略模型：1 + 7 + T

### 2.1 M｜Evolution Maturity（整体演化成熟度）——唯一主等级

- **M0｜Desktop Runtime（桌面执行运行时）**
  - 可靠观察、点击、输入、窗口、OCR / Vision（视觉）、Accessibility（无障碍）、文件、网络、Execution（执行）。
- **M1｜Personal Automation（个人自动化）**
  - 用户把自己的重复操作变成 Script / Action / Workflow（脚本 / 动作 / 工作流）。
- **M2｜Agent-Learned Automation（Agent 学习型自动化）**
  - Agent 完成新任务并提炼出可重复执行路径。
- **M3｜Reusable Automation Asset（可复用自动化资产）**
  - 不再只是 `.js`；形成 Procedure（过程）、Recipe、Verification（验证）、Recovery（恢复）、Compatibility（兼容性）和 Metadata（元数据）的正式资产。
- **M4｜Shared Organizational Capability（组织共享能力）**
  - 一个人学会，团队 / 企业可复用；SOP 逐步变成 Executable SOP（可执行 SOP）。
- **M5｜Creator Economy（创作者经济）**
  - 用户既是 Consumer（消费者）也是 Creator（创作者）；可创建、分享、发布、出售 Automation（自动化资产）。
- **M6｜Adaptive Automation Network（自适应自动化网络）**
  - Workflow、版本适配、失败修复、验证规则和 Recovery 可共同演进；一个用户验证过的兼容修复可以帮助其他匹配环境用户。
- **M7｜Digital Labor Platform（数字劳动力平台）**
  - 商品从“脚本 / Workflow”上移为岗位能力和持续业务执行，例如客服、运营、ERP、财务等 Digital Worker（数字员工）。
- **M8｜Global Executable Experience Network（全球可执行经验网络）**
  - 用户提出目标时，系统优先搜索、匹配、组合和适配世界上已经验证的执行经验；只有未知部分继续由 Agent 探索。

## 3. 平台核心对象不能只有 Script

建议后续设计至少区分以下对象，具体 Schema（数据契约）需另行设计：

- **Automation（自动化本体）**
  - 描述“做什么”，不与按钮、快捷键、UI 或 Agent 强绑定。
- **Procedure（语义过程）**
  - 人和 Agent 都可理解的业务步骤、前置条件、后置条件、失败停止条件。
- **Recipe / Implementation（Recipe / 实现）**
  - 某个环境下的确定性执行实现。
- **App Profile / Adapter（应用画像 / 适配器）**
  - 某应用、平台、版本、语言、界面的可重用操作知识。
- **Verification / Oracle（验证 / 结果判定）**
  - 判断动作完成不等于业务成功，必须定义成功 Oracle（判定依据）。
- **Compatibility Profile（兼容画像）**
  - OS、App Version（应用版本）、Locale（语言区域）、权限、界面 Variant（变体）、依赖。
- **Package（自动化包）**
  - 可安装、可版本化、可签名、可授权、可升级的分发单位。
- **Execution Evidence（执行证据）**
  - 运行结果、验证结果、错误分类和允许共享的匿名化兼容信息。

## 4. 平台用户角色

- **Consumer（使用者）**
  - 搜索、安装、配置、运行 Automation。
- **Creator（创作者）**
  - 通过人工开发、Recorder、Agent-to-Recipe 等方式创造 Automation。
- **Maintainer（维护者）**
  - 维护版本、兼容性、失败修复和升级。
- **Verifier（验证者）**
  - 在特定环境验证 Automation 是否真实可用。
- **Organization Publisher（组织发布者）**
  - 在企业内部发布私有 Automation / SOP。
- **Platform（平台）**
  - 负责 Registry（注册中心）、搜索、版本、信誉、分发、权限、计费、收益分成和安全边界。

同一个用户可以同时是 Consumer、Creator、Maintainer 和 Verifier。

## 5. Automation 生命周期：平台飞轮的最小闭环

- **Discover Need（发现需求）**
  - 用户提出目标，或系统识别重复工作。
- **Search Existing Capability（搜索已有能力）**
  - 先查本地、团队、企业、公共 Registry，不默认从零创建。
- **Create / Learn（创建 / 学习）**
  - 无匹配资产时，人工、Recorder 或 Agent 完成第一次任务。
- **Verify（验证）**
  - 验证业务结果，而不是只确认鼠标事件已发送。
- **Distill（提炼）**
  - 去掉探索、错误、重复和临时步骤；参数化输入、配置和 Secret（密钥）。
- **Package（打包）**
  - 形成可安装、可版本化、可描述支持环境的 Automation Package。
- **Publish（发布）**
  - Private / Team / Enterprise / Public / Paid（个人 / 团队 / 企业 / 公开 / 付费）不同范围。
- **Discover & Install（发现与安装）**
  - 后续用户按目标、应用、版本、行业、评分和成功率搜索。
- **Bind & Adapt（绑定与适配）**
  - 检查当前环境；优先复用已有 Adapter / Compatibility Patch，必要时只对差异部分调用 Agent。
- **Execute（执行）**
  - 稳定路径优先使用低成本 Recipe；不确定部分升级 Agent。
- **Observe & Verify（观察与验证）**
  - 保存本地 Evidence；只有经过授权且脱敏的数据才能成为共享网络信号。
- **Repair & Improve（修复与改进）**
  - 新版本、失败场景、恢复路径形成候选 Patch / Variant。
- **Reward（收益）**
  - Creator、Maintainer、Verifier 是否获得收益，需要根据贡献、质量和实际使用设计激励模型。

## 6. 需要形成的三类飞轮

### 6.1 Creator Flywheel（创作者飞轮）

- 更多用户
  - → 更多真实需求
    - → 更多 Creator 产生 Automation
      - → Automation 更丰富
        - → 用户更容易找到现成解决方案
          - → 更多用户进入
            - → Creator 获得更多收益
              - → 更多高质量供给。

### 6.2 Execution Flywheel（执行飞轮）

- 更多运行
  - → 暴露更多真实环境和失败
    - → 更多 Compatibility / Recovery 知识
      - → 更高成功率
        - → 更高价值任务愿意进入平台
          - → 更多运行。

### 6.3 Economic Flywheel（经济飞轮）

- 用户为节省时间 / 完成业务结果付费
  - → Creator / Maintainer 获得收入
    - → 更多专业人员持续维护高价值 Automation
      - → 资产质量提高
        - → 用户 ROI 提升
          - → Marketplace GMV / Usage / Outcome 收入增加
            - → 平台继续投入 Runtime、兼容和分发能力。

## 7. 平台价值的关键跃迁

- **从 Code Sharing（代码共享）到 Experience Sharing（经验共享）**
  - 用户不必理解源码即可继承成功路径。
- **从 Experience Sharing（经验共享）到 Capability Sharing（能力共享）**
  - 同一个 Automation 可以被 Button、Hotkey、Scheduler、HTTP、MCP、Agent 等不同入口调用。
- **从 Capability Sharing（能力共享）到 Collective Adaptation（群体适配）**
  - App / OS / Version 差异成为 Adapter / Compatibility Layer，而不是要求每个用户重写 Workflow。
- **从 Automation Marketplace（自动化市场）到 Digital Labor Economy（数字劳动力经济）**
  - 交易对象逐步从脚本、Package、Workflow 上移到持续岗位能力和业务 Outcome。

## 8. 必须提前冻结的共享边界

- **Shared Automation Core（共享自动化核心）**
  - 可公开或交易的 Procedure、Recipe、通用 Locator、Verification、Compatibility 信息。
- **Organization Overlay（组织覆盖层）**
  - 企业自己的审批、业务规则、私有 App Profile 和内网配置。
- **User Config（用户配置）**
  - 用户自己的参数和偏好。
- **Secrets（密钥）**
  - 密码、Token、Cookie、Credential 等不得进入公共 Package 或共享执行数据。
- **Runtime Context（运行上下文）**
  - 订单、客户、文件、业务数据默认保持本地 / 私有；共享必须显式授权、最小化并脱敏。

核心原则：**经验可以共享，秘密和业务数据不能因为“改进网络”而默认共享。**

## 9. 平台是否成立的关键指标

- **Reuse Rate（复用率）**
  - 新任务有多少可以直接复用已有 Automation / Procedure / App Profile。
- **Adaptation Cost（适配成本）**
  - 从已有 Workflow 到新用户环境平均需要多少人工 / Agent 成本。
- **Agent Escape Rate（Agent 升级率）**
  - 重复执行中有多少比例仍需要 Agent 介入。
- **Verified Success Rate（已验证成功率）**
  - 不是“脚本退出 0”，而是业务 Oracle 判定成功。
- **Compatibility Coverage（兼容覆盖率）**
  - OS × App × Version × Locale × Variant 的覆盖程度。
- **Creator Earnings（Creator 收益）**
  - Creator 是否真的能通过优质 Automation 获得持续收入。
- **Time-to-First-Value（首次价值时间）**
  - 新用户从提出需求到第一次成功执行需要多久。
- **Network Learning Rate（网络学习率）**
  - 新失败 / 新版本被成功修复后，有多少后续执行能够直接受益。

## 10. 当前阶段的战略约束

- 当前不因为终局巨大，就立即建设完整 Marketplace、云端账户体系、全球 Registry、支付结算和 Creator 分成。
- 当前更重要的是验证最小闭环：
  - 真实任务能否可靠完成；
  - 第一次成功能否沉淀为高质量资产；
  - 第二个不同环境用户是否可以低成本复用；
  - Version / Environment 差异能否局部适配而不是重做；
  - 用户是否愿意分享；
  - Creator 是否存在明确收益动机；
  - 平台是否能在不泄露业务数据的前提下获得兼容改进信号。
- 优先顺序保持：
  - 现金流验证
    - → 真实 Workflow
      - → 资产化
        - → 小范围共享
          - → 复用 / 适配验证
            - → Creator 激励验证
              - → Marketplace / Network。

## 11. 下一阶段应系统设计的工作包

后续正式平台设计至少需要独立回答：

- **P1｜Platform Product Model（平台产品模型）**
  - 用户为什么上传、为什么下载、为什么付费、为什么持续维护。
- **P2｜Automation Asset Model（自动化资产模型）**
  - Automation / Procedure / Recipe / Adapter / Verification / Package 的边界和版本关系。
- **P3｜Create-to-Publish Pipeline（创建到发布链路）**
  - Recorder / Agent-to-Recipe / Manual Authoring 如何进入同一发布流程。
- **P4｜Discovery & Matching（发现与匹配）**
  - Goal、App、OS、Version、Locale、行业、信誉、成功率如何参与搜索和匹配。
- **P5｜Install / Bind / Adapt（安装 / 绑定 / 适配）**
  - 如何检测用户环境、选择已有 Adapter、局部 Agent Adaptation（Agent 适配）和验证。
- **P6｜Version & Compatibility Network（版本与兼容网络）**
  - App 改版以后如何产生 Patch、验证、灰度和共享收益。
- **P7｜Trust / Verification / Reputation（信任 / 验证 / 信誉）**
  - 谁验证、验证什么、如何防止虚假成功率和恶意 Package。
- **P8｜Security / Privacy / Permissions（安全 / 隐私 / 权限）**
  - Secret、用户数据、企业数据、本地 Evidence 和共享遥测如何隔离。
- **P9｜Creator Economy（创作者经济）**
  - 定价、免费 / 付费、License（授权）、分成、退款、维护责任、贡献归因。
- **P10｜Marketplace & Distribution（市场与分发）**
  - Public / Private / Enterprise Registry、搜索、安装、升级、下架。
- **P11｜Execution Feedback Loop（执行反馈闭环）**
  - 失败、Recovery、Compatibility、Agent 修复如何变成候选资产，同时避免自动污染公共版本。
- **P12｜Business & Flywheel Validation（商业与飞轮验证）**
  - 用最小 MVP 验证 Reuse、Creator Supply、Buyer Demand、Adaptation Cost、Repeat Usage 和 Revenue。

## 12. 当前最重要的战略假设

平台是否值得成为下一层核心方向，最终取决于以下假设是否成立：

- **H1**：真实桌面 / 跨应用任务具有足够高的重复率，可以从第一次 Agent 探索转为低成本 Recipe。
- **H2**：不同用户环境的差异主要可以局部适配，而不是每个用户都从零重做。
- **H3**：用户愿意安装别人创建的 Automation，并信任其在本机执行。
- **H4**：一部分用户愿意把成功经验发布给别人。
- **H5**：Creator 可以因为共享和维护高质量 Automation 获得足够收益，从而持续创造供给。
- **H6**：运行数据可以在严格隐私与授权边界下提高 Compatibility、Recovery 和 Verification，而不是制造安全风险。
- **H7**：随着资产和执行增长，平台成功率、复用率和供给质量能够形成正向网络效应。
- **H8**：OpenDesk 的长期优势可以从 Runtime Engineering（运行时工程）迁移到 Executable Experience Moat（可执行经验护城河）。

这些假设必须按阶段验证；任何单项未成立，都可能改变 Marketplace、Creator Economy 或 Global Network 的最终产品形态。
