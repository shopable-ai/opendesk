# 自动化软件竞品与商业模式研究

更新时间：2026-08-31

> 文档性质：Research / 商业化决策输入。本文研究自动化底层框架、桌面自动化产品、RPA 平台、Creator / Recorder 与 Marketplace 如何获得收入。它不是 OpenDesk 当前能力声明，也不是最终商业决策。

## 0. 2026-08-31 Computer Use / Agent / Recorder 二次重扫补充

2026-08 的竞争环境已经不能只用“传统 RPA / Macro Recorder / 底层自动化库”描述。当前需要同时跟踪：

```text
Computer-Use Driver / Desktop Runtime
AI Computer-Use Tool / Model Contract
AI Recorder / Demonstration-to-Skill
Agent-authored RPA / Workflow-as-Code
Personal Agent OS / AI Workspace
Enterprise Agentic RPA
Browser Agent / Cloud Computer Infrastructure
Vertical Business Automation
```

详细技术与产品重扫见：

- [`../desktop-automation/2026-08-31-computer-use-agent-competitor-rescan.md`](../desktop-automation/2026-08-31-computer-use-agent-competitor-rescan.md)

本轮新增或升为一级跟踪的对象：

| 对象 | 类型 | 与 OpenDesk 的关系 | 当前研究结论 |
|---|---|---|---|
| `clawdesk/clawdesk` / Agent2OS | Personal Agent OS | 同名 + 产品层中高重叠 | 必须进入一级竞品和 Naming 风险跟踪；不应无边界复制其模型、Channel、Memory、Agent OS 能力 |
| Cua Driver | Computer-Use Driver | 直接技术竞品 | MCP / CLI / SDK、Accessibility、截图、后台执行、effect/verification contract 都值得重点比较 |
| Peekaboo | macOS Computer Use | 直接技术竞品 / 可集成候选 | macOS 原生 UI Automation 已高度产品化，应研究 Provider/Adapter 集成而非全部重复造轮子 |
| Agent Desktop Harness | Windows Computer Use + RPA-as-Code | 直接技术竞品 | Agent 探索 → Workflow Source → Validate → Run → Evidence 的闭环与 OpenDesk 高度相关 |
| OpenAI Codex Computer Use + Record & Replay | Computer Use + AI Recorder | Recorder 直接产品竞品 | “演示一次 → reusable skill”已经成为成熟产品入口 |

| Automation Anywhere EnterpriseClaw | Enterprise Agent Runtime | 企业上层竞品 | 本地 Agent、files/apps/browser/terminal、fleet/governance 是企业化方向参考 |

### 当前商品形态修正

过去更像：

```text
Library
→ Macro Recorder
→ RPA Platform
→ Vertical SaaS
```

现在更合理：

```text
Driver / Runtime
→ Agent Tool Surface
→ Recorder / Skill Compiler
→ Workflow / Durable Execution
→ Agent OS / Enterprise Control Plane
→ Business Solution / Outcome
```

因此 OpenDesk 的商业研究也应区分：

- **Driver 商品**：兼容、权限、跨平台、后台执行、稳定 contract；
- **Creator / Recorder 商品**：把演示和 Agent 探索变成可复用资产；
- **Workflow Runtime 商品**：长期执行、调度、恢复、审计、容量；
- **App / Business Package 商品**：特定软件与业务流程兼容性；
- **Enterprise 商品**：权限、治理、Fleet、支持、SLA；
- **Outcome 商品**：直接为客服、订单、报表、运营等结果付费。

### 对商业路线的新增判断

1. Recorder 仍然值得做，但竞争标准已从“宏录制”升级成 `demonstration → semantic flow → reusable skill/routine → replay/recovery`。
2. Durable Execution 不只是技术优化，而是无人值守、企业 Bot、Agent Routine 能否收费的基础设施。
3. `clawdesk/clawdesk` 证明“ClawDesk”这个名称本身已经存在明显 GitHub / SEO / 产品识别冲突；正式公开发行前需要独立 Naming / Trademark / Domain Clearance。
4. OpenDesk 更适合把 Agent OS / Model Provider / Messaging Channel 视为上层生态，通过 MCP / HTTP 接入，而不是全部内建。
5. 传统底层库仍有参考价值，但 Cua Driver、Peekaboo、ADH、Codex Record & Replay、UiPath Delegate 已更能代表 2026 下半年的竞争上限。

## 1. 核心结论

1. **底层自动化能力使用量可以很大，但通常离直接收入很远。** Windows API、AutoHotkey、PyAutoGUI、RobotGo、pywinauto 等主要承担基础设施、语言、SDK 或执行原语角色；大量核心能力免费或开源。
2. **“底层免费”不等于“自动化没有商业市场”。** 收入通常向上迁移到：预编译发行包、Recorder / IDE、OCR / AI 插件、企业支持、无人值守机器人、流程治理、业务解决方案、定制实施、Marketplace 和垂直行业 SaaS。
3. **离业务结果越近，付费能力通常越强。** `click()`、窗口控制、UIA 本身弱；“自动完成客服问题”“减少漏单”“找到竞品机会”“完成报表/发货/退款”等更容易产生预算。
4. **仍然存在“为开发者框架直接付费”的反例。** nut.js 当前直接对预构建核心包收费，说明开发者会为“省安装/兼容/维护成本”的底层产品付费；但这种模式更像专业开发工具，不应被当成 OpenDesk 最大市场。
5. **对 OpenDesk 更有价值的路线是：底层 Runtime 作为基础设施，向上研究 Recorder、Creator、Automation Package、App Profile、Business Solution 和垂直自动化。**

## 2. 自动化产品的“离钱距离”

| 层级 | 典型内容 | 典型产品 | 直接付费能力 | 对 OpenDesk 的意义 |
|---|---|---|---|---|
| L0 系统原语 | Win32、UIA、AX、CGEvent | Windows API | 很低 | 依赖/集成，不作为商品 |
| L1 Runtime / Library | mouse、keyboard、window、screen | AutoHotkey、PyAutoGUI、RobotGo、pywinauto | 低 | 可免费、开源或内部使用 |
| L2 开发工具 | Recorder、Inspector、OCR、AI、Debugger、预编译包 | Macro Recorder、nut.js Solo | 中 | 可成为 Creator Pro |
| L3 自动化平台 | Workflow、Bot、调度、日志、治理 | Power Automate、UiPath | 中高 | 只选择必要能力，不完整复制 |
| L4 业务解决方案 | 客服、订单、财务、ERP、内容运营 | UiPath Business Solutions、电商 SaaS | 高 | OpenDesk 优先研究 |
| L5 业务结果 | 成功解决客服、减少漏单、增长收入 | outcome-based AI / 垂直 Agent | 很高 | 最终收费应尽量靠近这一层 |

## 3. 底层框架到底怎么赚钱

### 3.1 AutoHotkey

**已验证事实**

- AutoHotkey 官方将其定义为免费、开源的 Windows 宏与自动化工具。
- 核心仓库采用 GPL-2.0 许可证。
- 官方核心产品不是按许可证、席位或调用量收费。
- 市场上长期存在使用 AutoHotkey 为企业或个人编写定制脚本的付费需求；Freelancer 等平台可以看到桌面流程、文件处理、数据录入等具体项目。

**商业模式判断**

AutoHotkey 本体更接近“免费语言 + 免费 Runtime + 社区生态”。真正产生收入的主体经常不是框架本身，而是：

- 定制脚本开发；
- 自动化咨询与实施；
- 将脚本包装为独立 EXE / 小工具；
- 企业内部节省人工时间形成的间接价值；
- 第三方 IDE、Recorder、模板、培训或服务。

**对 OpenDesk 的启示**

AutoHotkey 证明“免费 Runtime 可以支撑很大的生态”，但并没有证明“Runtime 本身是最好的收费对象”。OpenDesk 如果做公开底层，也应把它看作分发、生态和上层产品的基础。

参考：
- https://github.com/AutoHotkey/AutoHotkey
- https://www.autohotkey.com/
- https://www.freelancer.com/jobs/autohotkey/

### 3.2 PyAutoGUI

**已验证事实**

- PyAutoGUI 是 BSD-3-Clause 开源库。
- 官方 README 提供 Patreon 捐助入口，而不是商业许可证。
- 它封装 Windows API、macOS Cocoa、Linux X11 等平台差异，为 Python 提供鼠标、键盘和 GUI 自动化接口。
- 市场上存在基于 PyAutoGUI 的自动化定制项目，但项目通常按“完成某个业务自动化”收费，而不是按 PyAutoGUI 调用收费。

**商业模式判断**

主要是：

- 捐助；
- 作者个人品牌、教育/内容的间接价值；
- 第三方定制开发；
- 与 OpenCV、OCR、Web 自动化等组合后提供业务项目。

**对 OpenDesk 的启示**

“简单 API + 大量使用”可以形成影响力，但未必形成框架公司。OpenDesk 不应仅通过扩大 JS API 数量来期待商业价值自动出现。

参考：
- https://github.com/asweigart/pyautogui

### 3.3 RobotGo

**已验证事实**

- RobotGo 是 Go 生态的跨平台 GUI / RPA / computer-use 库。
- 当前核心代码主要采用 Apache-2.0 许可，仓库约万级 Star。
- 截至本次研究，未从官方公开材料确认稳定的“RobotGo Core 订阅 / 商业许可证”收入模式。

**当前可确认的变现路径**

- 作为其他商业软件的嵌入式依赖；
- 开发者以 RobotGo 承接定制自动化；
- 进一步包装成 Runtime、Agent、RPA 或垂直软件；
- 咨询、集成和支持服务。

**未知项**

RobotGo 作者/维护团队是否存在未公开的企业合同、赞助或定制收入，本轮没有足够公开证据，不应猜测。

**对 OpenDesk 的启示**

RobotGo 与 OpenDesk 的关系更适合定义为“可买/可集成的底层执行能力”，而不是商业模式模板。

参考：
- https://github.com/go-vgo/robotgo

### 3.4 pywinauto

**已验证事实**

- pywinauto 当前采用 BSD-3-Clause 许可证。
- 核心项目聚焦 Windows GUI Automation，支持 Win32 / UIA 等语义化桌面控制路径。
- 未从官方仓库确认核心库的商业订阅或商业许可证。

**商业模式判断**

与 PyAutoGUI 类似，价值更多流向：

- Windows 自动化项目；
- 测试自动化；
- RPA 咨询；
- Legacy 系统自动化；
- 在更上层产品中作为基础能力使用。

**对 OpenDesk 的启示**

语义控件能力技术价值很高，但仍然可能只是“商品中的原材料”。OpenDesk 应建设统一 locator / verification 层，而不应将“支持 UIA”本身当作主要付费卖点。

参考：
- https://github.com/pywinauto/pywinauto

### 3.5 Windows API / Win32 / Windows SDK

**已验证事实**

- Windows SDK 向开发者提供 OS 级 API、headers、libraries 和工具；Win32 API 本身不是按调用收费的 SaaS API。
- Microsoft 的收入来自整个 Windows / Microsoft 商业生态，而不是开发者每调用一次 Win32 API 付费。
- Microsoft Store 为非游戏应用提供应用购买、订阅、广告等商业化；开发者可使用自己的商业系统并保留非游戏应用 100% 的收入，若使用 Microsoft commerce，当前应用费率约 15%、游戏约 12%。

**商业模式判断**

这是典型的“底层平台能力免费/低摩擦 → 扩大生态 → 在 OS、分发、企业服务、商店和其他产品层变现”。

**对 OpenDesk 的启示**

不要试图对每个 `mouse.click`、`window.focus`、UIA primitive 单独建立价值叙事；更合理的是用基础能力降低上层商品生产成本。

参考：
- https://learn.microsoft.com/en-us/windows/apps/get-started/
- https://learn.microsoft.com/en-us/windows/win32/api/
- https://learn.microsoft.com/en-us/windows/apps/publish/get-started

## 4. 直接为自动化工具付费的代表产品

### 4.1 nut.js：开发者愿意为“可维护的底层包”付费

当前官方公开方案包括：

- Core：约 20 美元/月或 220 美元/年；
- Solo：约 75 美元/月或 825 美元/年；
- Solo 在 Core 之外增加 OCR、图像匹配、UI element inspector、screen recording、AI SDK 等。

这说明底层框架并非绝对无法收费。真正付费点不是“API 所有权”，而是：

- 预构建二进制与依赖；
- 跨平台兼容；
- 快速发布；
- OCR / AI / Inspector 等高级插件；
- 降低工程维护成本。

参考：
- https://nutjs.dev/pricing/core
- https://nutjs.dev/

### 4.2 Macro Recorder：Recorder 是成熟的直接付费产品

当前官方模式：

- Standard：约 99.95 美元；
- Professional：约 149.95 美元；
- Enterprise：约 249.95 美元；
- 一次性永久许可证，包含约 12 个月更新维护；后续维护可续费。

高级卖点包括 SmartClick、OCR / Image Recognition、Smart Record、Scheduler、Variables、AI Support 等。

**关键启示**：普通用户会为“我录一次，电脑以后替我做”付费。Recorder 与 Creator 的商业距离明显比底层 Runtime 更近。

参考：
- https://www.macrorecorder.com/shop/

### 4.3 Ui.Vision：开源核心 + 企业支持 / 更新治理

当前官方模式：

- 核心 RPA 免费且允许商业使用；
- Pro：约 299 美元/年；
- Enterprise：999 美元+/年；
- Enterprise Player、批量许可证和更新管理继续向企业收费。

付费主要买：

- 支持；
- 企业更新管理；
- 多机器 / Player 分发；
- 企业级运维便利。

**关键启示**：Open Source 和商业化不冲突，收费层可以放在“可靠运营和组织使用”上。

参考：
- https://ui.vision/rpa/x/pricing

### 4.4 Microsoft Power Automate：按用户、Bot、托管运行环境收费

当前公开价格示例：

- Premium：15 美元/用户/月，包含 attended desktop flows；
- Process：150 美元/bot/月，面向 unattended automation；
- Hosted Process：215 美元/bot/月，增加 Microsoft 托管虚拟机。

**关键启示**：企业愿意为“无人值守 + 运行容量 + 管理”持续付费，而不是只为 Recorder 付费。

参考：
- https://www.microsoft.com/en-us/power-platform/products/power-automate/pricing

### 4.5 UiPath：平台订阅 + Enterprise + Marketplace + Services

UiPath 的商业化不依赖单个桌面动作，而是把开发、机器人、调度、治理、审计、AI、流程优化和企业支持组合成平台。

更值得 OpenDesk 注意的是 Marketplace：

- 支持 Free / Paid listing；
- Paid 当前适用于 Custom Activities、Business Solutions 等类型；
- 付费 listing 可自定义价格，订阅期固定为 12 个月并包含更新/支持；
- Marketplace 已有 1500+ 可复用 RPA listings；
- Business Solution 还可继续销售 setup、customization、premium support。

**关键启示**：自动化资产可以成为商品，但 Marketplace 应建立在足够多的真实业务资产之后，而不是先造市场再找需求。

参考：
- https://docs.uipath.com/marketplace/automation-cloud/latest/user-guide/introduction-to-uipath-marketplace
- https://docs.uipath.com/marketplace/automation-cloud/latest/user-guide/submit-a-listing-pricing
- https://docs.uipath.com/marketplace/automation-cloud/latest/user-guide/how-to-submit-a-business-solution

## 6. 对 OpenDesk 商业模式的当前推导

### 6.1 不优先依赖的收入

当前不应把主要希望放在：

- 对 Mouse / Keyboard / Screenshot API 收费；
- 对 MCP tool 数量收费；
- 对 JavaScript Runtime 本体收费；
- 单纯复制 AutoHotkey / PyAutoGUI 的功能后收费；
- 先做完整跨平台 Runtime，再等待自然产生商业用户。

### 6.2 可以逐步验证的收入层

建议从近到远验证：

1. **垂直业务自动化实施**：先帮助真实商家完成一个有 ROI 的工作流，快速产生收入和需求反馈。
2. **垂直自动化产品订阅**：把重复实施沉淀为某个 App 的 Automation Package。
3. **Recorder / Creator Pro**：当内部录制/生成工作流已经稳定，再卖给第三方 Creator。
4. **App Profile / Enterprise Package**：企业为特定软件兼容、版本维护、稳定性和支持付费。
5. **Automation Marketplace**：供给足够多以后，允许第三方发布和售卖 Workflow / Business Solution。
6. **Outcome-based**：对可以明确验证成功的业务流程，探索按成功处理次数、节省量或业务结果收费。

### 6.3 建议的产品层次

```text
OpenDesk Runtime
  → 基础设施 / 可能免费或开源

Recorder + Creator
  → 提高自动化资产生产效率

App Profile + Workflow Package
  → 可复用商品

垂直 Agent / Business Solution
  → 直接解决业务问题

Marketplace
  → 放大第三方供给和分发
```
