# 客服应用场景：OpenDesk 框架复用、缺口与最小落地

更新时间：2026-09-14。审查基线：`master` / `e61ae707dfbfff8ab2e26c19e6eb243590cc82cf`；写入前再次读取分支，基线未变。

配套[商业方案](../../research/commercialization/knowledge-customer-service-automation.md)明确：知识库 × 智能客服是 OpenDesk 的应用业务之一，不是把通用底座改造成客服平台。

本轮交付是文档与定向静态评估。读取了下列 API 文档、相关架构及 Webhook／Execution 部分源码，未全量审计、构建或运行 Runtime／真实客服测试。文档存在、源码存在、测试通过、生产可用是不同证据等级。下列“待补齐／待核验”不等于断言整个仓库不存在同类能力。

## 1. 结论

**需要完善的是“外部业务如何可靠调用、授权、验证和维护现有自动化”，不是重新开发 RAG、客服 SaaS、数据库或通用工作流引擎。**

优先级：已有资产定位→一个受控只读接入→一个批准后的真实写入→按客户需要增加可靠异步接入→同类客户复用。

最需要明确的六组合同：业务能力调用、知识与对象上下文、审批、业务防重与恢复、桌面执行归属、独立业务结果与回填。先在场景应用／集成层组合已有能力；只有跨入口共享资源或生命周期确有缺口，才进入 Runtime。

### Webhook 边界必须保留

当前 `Webhook.listen()` 是同步等待业务 handler 完成的本地短处理入口。只绑定 loopback；凭据只授权当前 listener。`source` 标签不能代替租户身份。去重仅为同一 listener 的 `source + deliveryId`，且有保护窗口；超时后的 `RESULT_UNKNOWN` 不能当作未执行，不能释放实际仍在运行的 handler。

不能在原 P0 handler 内启动未追踪桌面后台任务后立即返回“成功”，也不新增虚构的 `mode` 参数。需要长任务、断线后查询和重启恢复时，使用已有业务系统的可靠任务层；确需新增时作为独立集成合同设计。HTTP 202 不等于持久收件，更不等于业务完成。

## 3. 四层职责：哪些属于框架，哪些不属于

- 外部系统／客户已有服务：消息渠道、知识库、客户身份、ERP／CRM 原有业务与审批。
- 场景应用／集成层：消息与对象映射、候选能力白名单、业务参数校验、审批记录、业务任务台账、结果回填与费用统计。
- OpenDesk Runtime／宿主：普通 JS 执行、输入输出、取消与资源清理、桌面操作、网络和文件边界；跨入口桌面资源归属在证据确认后补齐。
- 开发与资格工作流：业务合同、数据来源、应用定位、代码候选、独立验证、发布与维修；复用现有 Agent／Human-to-Recipe 和质量合同。

退款政策、产品兼容表、客户折扣、ERP 字段、客服话术归场景与客户配置，不归 Runtime。业务运行状态机不因名叫 workflow 就新建一套 `workflows/customer-service/` 专业方法体系。

### CS-02：把普通 JS 包装成“可调用业务能力”，而不是再造执行语言

复用 `Execution.input` 与现有 bridge。由受信宿主把能力标识映射到固定 Recipe；模型／Webhook 正文不能提供任意 script、路径、shell 命令、批准标识或自报资格。

最小内部描述应能表达：业务目的、输入／结果形状、支持环境、前置状态、预览、实际副作用、所需审批、执行边界、验证方式和人工兜底。优先接续现有 Definition／Candidate／Qualification 设计；没有完整通用 Catalog 时用维护者明确登记的固定清单，不先建设注册中心。

这是受信产品入口的限制，不是把 OpenDesk JavaScript Runtime 改成只能执行白名单，也不是声称任意恶意 JS 已被沙箱化。

### CS-03：知识是依据，不是权限

检索结果保留文档标识、来源片段、版本／时间和适用范围。正式政策需业务批准；实时订单／库存按本次授权查询；兼容性判断、优惠与退款例外不得仅凭向量相似度执行。

租户与客户归属由认证上下文和可信映射确定，不能相信用户提交的 tenantId 或截图。检索前做权限过滤；图片、文档与历史对话都当作不可信数据，不把其中的操作指令升级为工具授权。

原 RAG 若已具备这些能力就复用，缺哪项补哪项，不要求所有知识模块迁入 OpenDesk。

### CS-04：审批不是一个永远有效的按钮

预览明确“哪位客户、哪个订单、哪个动作、具体字段、影响和结果”。批准绑定参数摘要、目标、能力版本、政策版本与有效期；权限或对象变化则作废。

等待较长人工审批时保存待确认状态，不长期占住桌面或任意 JS 调用栈。后续授权运行重新校验对象状态，不假装能从任意脚本行安全恢复。局部低风险同步确认可复用 Dialog／已有 UI，但按钮点击本身不能代替业务授权记录。

### CS-05：可靠任务不是再加一个 SQLite 或 Webhook

先确定一个业务状态权威源，复用原客服／RAG 服务的数据库与任务系统；本地交付确需时，可用已存在 SQLite API 建独立业务库。不要并行维护本地与服务器两套可写权威状态。

最小台账关联：外部事件、业务任务、业务对象、已批准动作、能力版本、executionId、尝试次数、结果引用、回填状态与最后错误。名字是业务字段候选，不是新 Runtime 枚举。

区分 delivery 去重和业务防重：不同消息或不同 deliveryId 仍可能要求同一动作；同一订单也可能有合法的多次不同申请，不能只按订单号永久去重。

执行前记录意图，执行后独立核验并记录结果。崩溃可能发生在外部系统已提交、台账尚未更新之间：恢复必须用业务关联标识查询；无法判断则人工处理，不承诺跨外部 GUI 的 exactly-once。相同业务键但参数不同应报冲突。

外部长期自动事件需要可靠收件、持久任务、幂等 claim、有限重试、积压上限和失败告警。结果回填可用持久待发送记录（outbox）；回填失败只补回填，不重做原业务。网页按钮触发的首个受控样例不要求先建完整异步平台。

### CS-06：一条 listener 串行，不等于整台桌面串行

必须核验 CLI、HTTP、Scheduler、App 等入口实际共享的交互桌面资源归属。Scheduler 的 store runner 锁、同一个 Webhook 的 single-flight、业务订单锁，分别保护不同对象。

首个试点可以限定一个受控执行节点、一个调度方和一个 GUI 写入任务；明确禁止其他自动化争用。同一交互桌面默认串行，不把换进程或开两个窗口当隔离。纯 API 查询只有在资源独立且权限明确时才可并行。

需要跨入口支持时，优先复用现有锁／owner／取消机制并补真实验收；确有缺口再做宿主级通用资源治理，不先发明公共 `DesktopLock` API。超时或取消请求不证明实际任务停止，不能仅凭租约到期启动第二个有副作用的 worker。

人工改变焦点、登录过期、屏幕锁定、弹窗、分辨率／窗口变化应被检查；无法安全继续则停止／接管。权限 granted 不等于当前操作必然可用。一次 GUI Execution 保持一个实际目标，不在其内部偷偷启动多个独立 Executions；跨目标由明确外层顺序组织并验证组合。

### CS-07：独立验证与回复必须共享事实

至少分开记录：Runtime 是否完成、实际动作是否成功、业务是否仍待处理、结果是否回填、回复是否发送。业务状态可表达已核验成功、未开始、等待、部分完成、未知和失败，但不冒充现有 Runtime 状态枚举。

验证从目标系统重新读取订单、申请号、状态与关键字段；不能从 expected 值、点击日志或执行器自述推断。没有独立 API 时可重新打开详情核对 UI，说明证据强度与限制，不宣称与独立后台记录等价。

正确示例：“申请已登记，编号 X，等待审核。”错误示例：仅建单后回复“退款已到账”。报价流程也要区分“建议／草稿”与“正式提交”。

### CS-08／09：交付安全与持续升级

单客户可先独立进程／账户／业务目录／数据库；多客户不得仅靠进程变量中的 tenantId 共享已登录桌面。凭据由可信运行方注入或引用现有安全存储；未审查的 securestore 不能直接被宣布为通用客户 Secret API。

日志只记录必要业务元数据；请求体、截图、环境和模型输入都需要外发策略、脱敏、访问与保留边界。源码配置不保存真实客户数据或凭据。终端不显示不代表 artifact 未保存。

保留 request／task／execution 关联、能力与政策版本、阶段耗时、审批／复核工时、重试、人工接管、模型用量和维修工时。指标先写结构化记录，不先做复杂经营看板。

发布复用现有 Candidate／Qualification 方向与 App／受保护包交付能力，逐项核验兼容范围。新版本不能中途改变已批准任务；未知副作用未对账时，不能通过回滚代码重跑业务。维护合同区分兼容修复和新增需求。

## 5. 最小实施顺序与验收

### 第一步：既有 RAG 接入＋只读业务样例

目标链：已有客服／RAG→明确客户与对象→受控调用一个固定查询 Recipe→从目标系统读取→结构化返回→客服侧显示真实结果。

先定位原实现与目标系统。可先用普通 HTML 样机确认预览、错误、待确认和结果展示的交互，但样机／mock 通过不代表 RAG 接通或真实桌面成功。无可用真实接口时记录阻塞，不自造一个新 RAG 冒充复用完成。

验收：正确对象读取、错误身份拒绝、参数错误拒绝、未知能力拒绝、目标不可用返回明确状态、结果可关联 execution 和实际证据。只读也需控制敏感数据范围。

### 第二步：一个批准后的可验证写入

优先选择待审核售后申请或报价草稿等单一动作；先确认没有隐式资金／出库副作用。

验收：预览准确；无批准不写；参数／版本变化后旧批准失效；重复点击不重复写；提交后超时先查询；重启后未知状态不盲重试；验证真实编号和字段；回填失败不重做；取消不虚报回滚；桌面争用被阻断或安全拒绝。

首个付费写入需要最小持久操作记录与人工兜底，不以“只是试点”为由忽略重复副作用风险。

### 第三步：长期事件与持续维护

有客户需求才增加远端验签／认证、可靠收件、结果查询、outbox、告警、恢复和服务部署。优先接已有业务工作流；不能为方便把本地 Runtime 管理／script 接口暴露公网。

验收覆盖重复与乱序事件、签名失败、过载、进程退出、恢复、取消后的迟到结果、外部写入成功但回填失败。公开 webhook 文档也会要求处理重复、乱序和异步负载；这是接入设计参考，不是要求引入特定支付产品。[外部参考 1]

### 第四步：第二客户复用

再验证应用能力、客户配置、凭据、资格与数据隔离；统计新增开发、兼容维修、复核和支持成本。通过复用与经济性证据后再抽取通用 Connector／能力包，不提前做 Marketplace。

## 6. 框架真正可能需要修改的地方

当前应先做定向验证，不直接批准以下改造：

1. 若现有各入口无法共同保护同一交互桌面，补宿主级资源归属、取消后释放和争用错误；这是可反哺其他自动化场景的通用能力。
2. 若严格 bridge 不能可靠关联业务结果、取消与 artifact，补现有执行合同及对应测试；不另造平行任务执行 API。
3. 若入站、外发、日志或 artifact 边界无法满足已确认交付要求，补通用安全与观测机制；不把所有企业权限管理塞进 Runtime。

其余优先放场景应用、已有 RAG／客服服务、Connector 和 Recipe 内。一个客户特有功能不因需要编码就升级为框架公共接口。只有实际复用、稳定语义与现有组合不足同时成立，再按已有 Runtime API 扩展规范评估。

## 7. 不新增与不重复建设

不新增完整客服 UI／工单 SaaS、通用 RAG／向量数据库、第二套 Scheduler、第二个 Execution 管理类、通用 Agent 编排引擎、客服专属 Runtime namespace、任意生产代码生成执行、跨平台 WindowTarget 路由、通用审批平台和多租户云控制平面。

不以“持续升级”为由恢复在线自我授权与自动发布；不以缺少真实 RAG 位置为由重做；不把设计合同、示例或源码存在写成生产 PASS。
