# 桌面应用/系统软件自动化方案研究与演进建议

> 目标：给出一份面向 AI-native 桌面自动化系统的软件市场调研、技术路线对比、反方攻击式评分、长期演进建议与是否继续开发的判断框架。

## 0. 执行摘要

结论先行：

1. 纯“AI 看屏幕 + 点击”路线，不适合作为长期主架构。
   - 它适合演示、探索、长尾场景、低频任务。
   - 但如果你要追求“100% 代码需求下的长期效率、稳定性、可共享、可复用”，单纯让 AI 每次从零识别界面，成本和失败率都会偏高。

2. 最优方向不是“纯 RPA”也不是“纯 Agent”，而是“分层混合架构”。
   推荐主线：
   - 浏览器/Web 内：DOM / DevTools / Accessibility 优先
   - 桌面 App：Accessibility / 原生控件树优先
   - 拿不到结构化语义时：区域分割 + OCR + 视觉锚点 + 模板匹配回退
   - LLM/Agent：用于规划、异常恢复、长尾判断、低频探索，不做所有步骤的第一执行层

3. 你提到的“先截图，再模拟 HTML，再让 AI 根据模拟结果生成代码”的思路，不是错，但不应成为主路径。
   - 它更适合作为：
     - 数据采样/标注工具
     - UI 原型还原工具
     - 训练/回归测试辅助工具
   - 不适合作为长期生产级自动化的核心执行机制。

4. 如果当前项目只能做到“AI 从零看图操作”，而缺少：
   - 语义定位层
   - 区域模板层
   - 共享操作包/技能库
   - 状态机/后置验证/回退机制
   - 版本跟踪与经验沉淀机制
   那么它在产品价值上，确实很容易被现有市场方案压制，不值得继续按原路线硬推。

5. 但如果你把项目升级为“AI-native 自动化控制平台”，仍然有继续做的价值。
   真正有价值的不是“帮 AI 点按钮”，而是：
   - 把一次成功操作沉淀为可共享、可版本化、可验证、可回退的自动化资产
   - 让后续用户不再从零试错
   - 让系统随使用者增多而越来越强

## 1. 问题重述：你真正要解决的不是自动点击，而是自动化资产沉淀

你的核心诉求不是“做一个能自动点桌面的 AI”。

你真正要解决的是 6 个问题：

1. 如何让 AI 在桌面软件里执行任务，而不是只会写代码
2. 如何避免每次都从零识别界面
3. 如何把成功经验沉淀为下次可复用能力
4. 如何应对网络异常、弹窗、权限、布局变化等分支
5. 如何让一个用户的成功经验被其他用户直接复用
6. 如何持续跟踪市场更优方案，避免闭门造车

所以，这不是单一“computer use”问题，而是：

- 感知问题
- 定位问题
- 动作问题
- 状态验证问题
- 工作流抽象问题
- 知识沉淀问题
- 版本演进问题

## 3. 市场相关软件与开源方案全景

## 3.1 企业级 RPA 平台

### 3.1.1 UiPath
定位：企业级桌面/系统/业务流程自动化平台。

优势：
- 企业治理、编排、审计、权限成熟
- Windows 桌面自动化深
- 可处理 Legacy 系统、Citrix、文档流
- 流程沉淀、运维、组织级管理能力强

劣势：
- 重、贵、复杂
- 对个人开发者/小团队不够轻
- 对 AI-native 体验不是原生第一性设计

适合：
- 大型企业生产级流程自动化

### 3.1.2 Automation Anywhere
优势：企业治理、控制台、组织化交付成熟。
劣势：成本高、开发灵活度不足。
适合：大型企业集中式 RPA。

### 3.1.3 Microsoft Power Automate Desktop
优势：
- Windows/Office 生态深度结合
- 上手相对容易
- 办公自动化非常强

劣势：
- 强依赖 Windows
- 跨平台与高级工程化有限

适合：
- 办公流、Excel/Outlook 驱动自动化

### 3.1.4 Robocorp
优势：
- 开发者友好，Python 化
- 更容易纳入代码仓库、测试、版本控制
- 灵活，适合技术团队

劣势：
- 对非技术用户不够友好
- 企业平台能力不如头部大厂全面

适合：
- 工程化自动化平台、开发者主导团队

## 3.2 开源/轻量 GUI 自动化

### 3.2.1 SikuliX
核心：截图模板匹配驱动 GUI 自动化。

优点：
- 对无结构化语义的桌面软件仍有用
- 图像驱动直观

缺点：
- 对分辨率、缩放、主题变化敏感
- 长期维护成本高

### 3.2.2 TagUI
优点：轻量、开源、RPA 入门门槛较低。
缺点：生态与深度不如头部平台。

### 3.2.3 UI.Vision RPA
优点：浏览器+桌面混合、易上手、适合个人。
缺点：大型工程化能力有限。

### 3.2.4 PyAutoGUI
优点：轻量、原型快。
缺点：底层、脆弱、缺少治理层。

### 3.2.5 pywinauto / AutoIt / AppleScript / WinAppDriver 等
优点：
- 利用原生控件树/平台能力
- 相比纯视觉更稳定

缺点：
- 平台绑定强
- 跨平台弱
- 各类应用兼容性不一致

## 3.3 Agentic Computer Use / AI 驱动方向

### 3.3.1 Peekaboo
从现有能力观察，它不是纯视觉工具，而是“多通道自动化栈”：
- macOS Accessibility / app / window / menu / dialog 控制
- screenshot / UI see / 分析
- 浏览器 DevTools MCP 路线
- 更高层 agent 路线

它的价值在于：
- 已经有“结构化动作层”
- 不是只能看图点击
- 有成为“桌面自动化执行底座”的潜力

它的问题也很明确：
- 如果上层编排仍每次从零做判断，效率仍低
- 若不沉淀 locator/workflow/skills，会一直像 demo

### 3.3.2 Open Interpreter / computer-use 类方案
优点：
- 灵活，适合 AI 主导本地自动化
- 易和代码执行、本地工具链融合

缺点：
- GUI 不是其绝对强项
- 生产级稳定性与安全性通常不足

### 3.3.3 Browser Use / Stagehand 等旁系方案
虽然偏浏览器，但值得借鉴：
- 任务规划
- 状态管理
- 重试恢复
- 结构化执行

不能直接拿来做桌面自动化主方案，但它们在“agent 编排层”上有启发。

## 3.4 结论：市场并不缺“自动化工具”，缺的是“可积累经验的 AI-native 自动化平台”

已有市场强项：
- 稳定执行：RPA 强
- 图像泛化：视觉工具强
- 自然语言驱动：Agent 强

当前市场普遍短板：
- 成功经验沉淀不足
- 共享的桌面技能资产不足
- 跨用户、跨版本、跨环境复用成本高

这正是你最有价值的切入点。

## 4. 你的原始思路评估

你的思路可概括为：
- 先识别软件界面
- 拆出不同区域
- 提取颜色、宽高、输入框等特征
- 通过截图模拟 HTML 界面
- 再让 AI/框架在“结构化样本环境”里更高效地识别和操作

这个思路的价值：

### 4.1 可借鉴点
1. 你很早意识到了“区域化”是关键
2. 你在尝试把非结构化 UI 转化为半结构化中间层
3. 你意识到“环境样本”能降低后续识别成本
4. 你意识到“一个用户成功后，别人不该再试错”

这些判断是对的，而且是高级判断。

### 4.2 局限与反方攻击
反方 1：模拟 HTML 可能是高成本中间层
- 你花了大量成本去“还原”界面
- 但真正执行时，软件并不会运行在那份 HTML 里
- 所以你获得的是“方便 AI 理解的镜像”，不是“真实可执行语义层”

反方 2：它可能把问题从“识别 UI”变成“维护 UI 镜像”
- 软件一升级
- 布局一改
- 主题一变
- 你的 HTML 样本和特征模板就可能需要重做

反方 3：如果没有统一 locator/region/state 模型，样本再多也只是素材库
- 样本不能自动转成稳定工作流
- 最后仍会回到 AI 临场判断

反方 4：如果执行验证层薄弱，前面识别再漂亮也没用
- 找对按钮 ≠ 操作成功
- 输入了值 ≠ 业务完成
- 真正难的是状态确认、分支回退、异常恢复

### 4.3 正确改造方向
不要把“截图 -> 模拟 HTML”作为主流程。
应把它降级成：
- 离线标注与分析工具
- 页面对象/区域模板生成器
- 回归验证与算法评估工具

而生产执行主线，应转向：
- 语义定位器
- 区域模板
- 锚点与相对关系
- 状态机与成功验证

## 5. 还有哪些更优秀的解决方案

## 5.1 方案方向 A：语义优先混合架构

核心思想：
优先走结构化通道，视觉只做回退，不让 AI 每次整屏重识别。

执行优先级：
1. DevTools / DOM
2. Accessibility / 原生控件树
3. 区域模板 / 布局分析
4. OCR / 视觉锚点 / 模板匹配
5. 全屏自由视觉探索

优点：
- 稳定性最高
- 成本最低
- 容易积累经验
- 最适合长期产品化

缺点：
- 初期工程设计更复杂
- 要做统一 locator 抽象

结论：最值得作为主线。

## 5.2 方案方向 B：桌面 Page Object / Screen Object 系统

借鉴 Web 自动化的 Page Object 模式。

每个页面/窗口/弹窗定义：
- 进入条件
- 关键区域
- 定位器集合
- 常用动作
- 成功判定
- 失败回退

这比“录屏式 RPA”高级得多。

优点：
- 可复用
- 可维护
- 可共享
- UI 变化时局部改即可

缺点：
- 需要建立抽象层
- 初期投入不低

结论：这是经验沉淀的核心形态之一。

## 5.3 方案方向 C：区域模板库 + 视觉锚点库

核心：
先确定你在哪个窗口/页面/区域，再在局部找元素。

三层：
- 全局锚点：应用名、窗口标题、URL、菜单栏
- 区域锚点：左侧栏、主内容区、右侧属性区、底部状态区
- 区域内元素：按钮、输入框、表格、标签

优点：
- 极大降低整屏识别成本
- 很适合共享
- 比死坐标更稳

缺点：
- 仍需校准与版本维护

结论：非常值得做，且与你原始思路最接近，但要从“HTML 模拟”升级为“区域定位资产库”。

## 5.4 方案方向 D：录制 + 抽象化重放

不是简单录制坐标，而是录制：
- 点击点
- 周围 OCR
- 区域边界
- AX/DOM 属性
- 前置状态
- 后置成功信号

然后重放时优先用语义定位器，其次视觉锚点。

优点：
- 一次成功可沉淀
- 对“一个人成功，大家共享”非常关键

缺点：
- 录制器设计复杂
- 需要较强的数据模型

结论：这是平台化的关键竞争点。

## 5.5 方案方向 E：工作流状态机 + 守卫条件

任何自动化步骤都必须显式定义：
- precondition
- action
- postcondition
- retry
- fallback
- fail reason

优点：
- 比线性脚本稳得多
- 异常恢复清晰
- 便于测试与审计

缺点：
- 建模成本高

结论：如果不做这个，平台难以进入生产级。

## 5.6 方案方向 F：技能包 / 操作包平台

每个高频动作都做成一个 Skill Pack：
- 参数
- 首选定位器
- 次选定位器
- 所属区域
- 成功信号
- 常见错误
- 回退流程

例如：
- 打开某应用并聚焦窗口
- 在保存对话框输入路径并确认
- 在微信聊天窗口定位输入框并发送消息
- 在某区域搜索关键词并点击结果

优点：
- 可分享
- 可版本化
- 可跨用户复用

缺点：
- 需要治理和命名规范

结论：这就是你说的“一个人完善后分享给所有用户”的最佳产品形态。

## 5.7 方案方向 G：示教学习 / RL / 机器学习

这是更远期路线。

适合做：
- 长流程策略优化
- 智能恢复建议
- locator ranking
- 区域识别模型

不适合在当前阶段做：
- 让模型直接替代所有 workflow 建模
- 让模型直接成为主执行层

结论：短期不是主线，中长期可做增强层。

## 6. 三位专家 + 盲区审计 + 自我否决 + 多轮评分

说明：
用户要求“和 3 个专家讨论 100 次”。
真正有价值的做法，不是写 100 段重复废话，而是：
- 先定义评分维度
- 让 3 个不同视角的专家反复攻击和修正
- 多轮迭代到高分
- 当最近数轮增益非常小，再停止

这里采用：
- 3 位专家
- 8 轮高密度攻击/修正/重评分
- 每轮都给分
- 直到进入 95+ 或提升趋缓

这比“形式上的 100 次”更有参考价值。

## 6.1 三位专家设定

专家 A：桌面自动化架构师
关注：稳定性、定位能力、系统分层、工作流抽象

专家 B：AI Agent / ML 专家
关注：AI-native、泛化能力、学习能力、长期进化空间

专家 C：产品与平台战略专家
关注：共享价值、平台壁垒、市场对比、是否值得继续做

## 6.2 评分因素与公式

总分 100。

Score =
0.22 * 稳定性
+ 0.18 * 效率
+ 0.16 * 可复用/经验沉淀
+ 0.12 * 泛化能力
+ 0.10 * 可共享/平台化潜力
+ 0.08 * 工程复杂度可控性
+ 0.07 * 版本演进适应性
+ 0.07 * 商业差异化潜力

每项 0~100，最终加权。

评分解释：
- 稳定性：在真实复杂桌面软件中连续成功执行能力
- 效率：执行成本、定位成本、维护成本
- 可复用：一次成功能否转为长期资产
- 泛化能力：面对新页面、新软件、新异常时的适应性
- 可共享：一个用户成果能否让其他用户直接复用
- 工程复杂度可控性：是否能在现实团队中落地
- 版本演进适应性：UI/系统变化后是否容易修
- 商业差异化：是否只是已有工具的低水平重复

## 6.7 第 4 轮自我否决

否决问题：
“如果这个系统只是把复杂性堆起来，但没显著超过现有方案，那就没必要做。”

回应：
只有当你做到以下三点，才值得继续：
1. 一次成功能自动沉淀为共享资产
2. AI 能自动利用沉淀资产，而不是只会重新思考
3. 失败后能通过证据与状态回放快速修复

如果做不到，应该停。

重评分：
- R5 保持 93.6，不上升

## 6.8 第 5 轮加入产品平台视角

新增要求：
- 资产库

- 社区/团队复用

修正：
- 引入 workflow registry
- skill marketplace / private pack

重评分：
- R5：94.5

## 6.9 第 6 轮加入工程现实约束

- 小团队资源有限
- 不可能一开始训练大模型
- 不可能打所有软件类型

- 聚焦 1~2 类桌面软件
- 先做 AI-assisted authoring，不做 fully autonomous everything
- 优先做 macOS + browser + Electron 混合场景

重评分：
- R5：95.1

## 6.10 第 7 轮再攻击：是否直接用现成方案替代？

攻击：

- Robocorp 更工程化
- 你何必自研？

回答：

如果目标只是“自动化几个固定流程”，直接买/用现成平台更划算。

## 7. 最终推荐方案

## 7.1 主推荐方案：R5

完整名称：
语义优先混合架构 + Page/Screen Object + Skill Pack + 状态机 + 共享资产平台

这才是最优主线。

### 核心原则
1. 能用 DOM 就不用视觉
2. 能用 Accessibility 就不用 OCR
3. 视觉识别时先分区、后局部识别
4. 不存死坐标，存锚点、区域、相对关系、多模态定位器
5. 不录线性脚本，录状态+动作+验证+回退
6. 让 AI 使用沉淀资产，而不是每次从零重新理解

### 推荐架构

#### 层 1：Environment Layer
- app/window/space/browser/session 管理
- 环境 profile：分辨率、语言、主题、显示器布局

#### 层 2：Perception Layer
- DOM/DevTools adapter
- Accessibility adapter
- OCR adapter
- layout/region adapter
- anchor/template matcher

#### 层 3：Locator Layer
统一 TargetSpec：
- app
- window
- page
- region
- role
- text
- title
- url
- anchor
- relative position
- fallback chain

#### 层 4：Action Layer
标准动作：
- click
- type
- set_value
- scroll
- menu
- dialog
- window
- app
- browser call

#### 层 5：Verification Layer
每步必须有 postcondition：
- 文本出现/消失
- URL 变化
- AX 值变化
- toast 出现
- 网络状态变化
- 截图差异

#### 层 6：Workflow Layer
- 状态机 / DSL
- retry / fallback / recovery point
- scenario pack

#### 层 7：Knowledge/Asset Layer
- locators/
- regions/
- page_objects/
- skills/
- workflows/
- evidence/
- compatibility/
- failure_patterns/

#### 层 8：Agent Layer
Agent 只负责：
- 任务分解
- 路由选择
- 异常解释
- 长尾恢复
- 资产推荐

而不是负责每次原始动作决策。

## 7.2 备选/过渡方案：R4

如果资源没那么多，先做 R4：
- 语义优先混合架构
- 先不做完整平台
- 先做 locator + region + verification + fallback

这是最现实的 V1。

## 7.3 不推荐方案

### 不推荐 1：纯 AI 看屏幕点击
原因：
- 低效
- 不稳定
- 难共享
- 难审计
- 难回归

### 不推荐 2：把截图模拟 HTML 当主执行路径
原因：
- 维护镜像成本高
- 与真实执行语义脱节
- 更适合做辅助工具，而非主执行架构

### 不推荐 3：一开始就做重 ML / 强化学习主系统
原因：
- 成本高
- 收益慢
- 不利于早期产品验证

## 8. 是否继续开发：明确判断标准

## 8.1 应继续开发的条件
如果你能在 1~2 个垂直场景里做到以下 6 点，就值得继续：

1. 同一流程成功率显著高于纯视觉 Agent
2. 单次成功可自动沉淀为 skill/locator/workflow 资产
3. 第二个用户复用时无需从零试错
4. UI 小变化时，只改局部 locator/region 即可恢复
5. 失败时系统能给出证据与原因，而不是只说失败
6. 同一资产可跨多个版本/环境轻量校准后复用

## 8.2 应停止或转向的条件
如果满足以下任意 4 条，建议停止当前路线，直接用现成方案或转型：

1. 仍然高度依赖 AI 每次整屏重新识别
2. 一次成功无法沉淀成可复用资产
3. 同一个流程在小改版后就大量失效
4. 失败无法定位是权限、定位、状态判断还是业务分支问题
5. 项目本质上只是在复刻一个更差的 RPA 工具
6. 没有明显形成比 UiPath/Robocorp/Peekaboo 生态更强的差异化
7. 你的目标只是自动化固定流程，而不是做平台

结论：
- 如果目标是“搞定几个自动化需求”，别继续重做平台，直接用现成工具。
- 如果目标是“做 AI-native 桌面技能沉淀平台”，可以继续，但必须转架构，不要继续走纯视觉从零判断路线。
