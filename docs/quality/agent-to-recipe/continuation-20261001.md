## 网页端和本地材料的差别

网页端取得的是版本化源码、文档和测试资产。本地任务材料位于 `.runtime/automation-authoring/calculator-completion-20261001/`；Human 材料另在 `.runtime/tests/human-to-recipe/partial-authoring/`。这些目录未推送。网页端引用打不开时，应明确写证据不可访问，而不是复制文档中的数字、重建历史或自动运行验证。

本地新任务可以静态读取 `progress.json`、`last-check.md`、根 `stage-review.md` 首屏和具体失败文件，但要核对范围与时间：根报告可能仍绑定较早的 S2 → S3 放行，并未纳入后来 17:35 的失败。最新版生成器源码不等于根报告已经更新。

静态 Git 审阅还发现 `tests/workflows/artifact-calculator-production.test.js` 的部分历史候选场景无条件依赖本地 `.runtime` manifest、源快照和 `dist/opendesk`；干净网页端或新检出不一定具备这些材料。这是待处理的测试可移植性缺口，不能通过提交运行产物解决，也不能假装整个测试集已通过。本次没有执行该测试。

## 下一轮怎样推进

继续只做静态工作流维护。先选择一个妨碍人理解或下游消费的具体缺口，固定其要求、实际成果正文、来源和版本，解释错误如何产生及为何归属该责任层，然后修改对应方法、交接或人工视图。不要重新开始 Calculator 生产，不为更新报告启动任何 Node、测试、Runtime、render 或桌面脚本。

先解决读者能否逐阶段判断成果内容与错误，再处理报告同版链接、声明范围和测试可移植性。所有暂时不能证明的行为继续标为未验证；原始评分、Gate、阶段编号与唯一 checker 不另建一套。只有用户以后明确恢复执行授权，才能开展相应验证。

新任务使用现有 `master`。先核对本地修改和远端最新版本；不创建或切换分支，不使用 reset、force push 或清理来覆盖并行成果。同一任务根只有一个进度写入者，同一桌面只有一个注册任务操作拥有者。静态协作不意味着获准刷新运行状态或抢占 Calculator。
