# Desktop Reset Clock：设计交叉评审记录

- 日期：2026-10-11
- 本轮变更：根据用户反馈，默认取消 Go 采集服务、SQLite 与 Cookie 采集方案；HTTP/HTTPS feed 优先
- 对象：[当前唯一方案](../../plans/desktop-reset-clock.md)
- 文档状态：**DESIGN_REVIEW；运行验收 NOT_TESTED**
- 评审方式：三个独立 AI 子任务分别研究来源语义、架构可靠性与价格，主代理汇总、交叉质疑并修订
- 本记录不是外部人类专家签字、商业认证、产品完成度证明或正式能耗 / 环保审计
- 用户要求：提高方案质量，目标至少 95 分；先确认方案，再写代码

## 1. 最新评审结论：最小化优于过度建设

用户明确补充：**采集可以由其他系统完成，当前 Go 程序不必编写 X 爬虫、后台存储与任务调度；若现成 HTTP 数据源请求成功，则不继续叠加采集复杂度。**原先由桌面项目自行建设集中 Go 采集服务、SQLite、LLM 提取、审核后台和 CDN，作为 MVP 默认路径属于过度建设风险。

评审决定：以**外部可信数据生产者 → HTTPS JSON Feed → Go 桌面状态 / 时区 / 提醒**为默认架构。额外转换、上游巡检、付费鉴权等按缺口有条件启用。原来的 X 读取与成本章节不再是默认实现承诺。

重要限定：HTTP 200 不等于业务数据有效，HTTP 304 仅在有合法缓存时复用；401/403 不绕过访问限制；上游是否持续采集不能由客户端请求成功自动推断。读取与语义责任分开，Cookie 不是默认方案。

当前是方案评审，缺少真实源 URL、协议样本、两平台运行和 30 天成本；任何 95 分结论仍待实测和独立核验。

## 2. 风险审查与权衡

| 维度 | 原设计风险 | 新决策与原因 |
|---|---|---|
| 架构复杂度 | 预设云端 Go 采集、DB、LLM、审核、CDN | 最小只读 HTTPS Feed + 本地缓存；现成源可直接实现核心价值 |
| 来源变化 | 强耦合 X API 与 tibo 单账号 | 客户端只理解版本化事件，不依赖 X；来源生产者可替换 |
| Cookie | 自动登录易触及凭据暴露与访问限制 | 只用获得授权且提供方支持的会话；默认公开 feed 或合法 Token，不采集用户浏览器 Cookie |
| 成功判定 | HTTP 状态 200 容易被误写为成功数据 | HTTP/Schema/证据分别确认；304 检查已有缓存；拒绝访问就记录失败 |
| 新鲜度 | 只有“最后帖子时间”容易误报来源故障 | 本机请求时间、生产者上游检查时间、事件更新时间分开 |
| 误提醒 | 旧公告、模糊时间或更正没有独立生命周期 | 未核实则禁止精确提醒，更正撤销旧计划 |
| 成本 | 自建源维护预算被误当固定成本 | 按外部提供方合同、客户端轮询、发行、客服和支付实测重新报价 |
| 商业 | 0.99 定价过早固化 | 先验证来源许可、时效、用户使用意愿，再确定币种与实际周期 |

HTTP 缓存依据：[MDN 条件请求](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests)；X 使用与认证边界：[X Developer Policy](https://docs.x.com/developer-terms/policy)。本表为工程审查意见，不构成法律合规结论。

## 4. 95 分如何评，谁来评

### 4.1 两个不同的评分

1. **设计评审分**：检查问题、决定、契约、失败处理、取舍和验收方法是否完整且自洽。评审者逐条引用方案和发现记录；不能因措辞详尽而加分。
2. **发行验收分**：检查实际源码、真实样本、端到端、两平台、费用与交易是否达到承诺。没有运行证据的项不得按通过计分。

两个分数各自满分 100。达到设计 95 不代表产品 95，更不代表 95% 的用户适用率或模型准确率。当前不发布人为凑出的总分；目标是经过独立复核达到不低于 95，且关闭相应硬门槛。

### 4.2 权重

| 维度 | 分值 | 设计审查要点 | 发行证据 |

## 5. 样本与准确性验收

### 5.1 先建立可复核数据集

- 真实原文与上下文需来自允许的数据路径，记录获取日期、来源版本与权限。
- 历史真实样本、合成反例和在线观察分别统计。
- 初始建议至少 100 条规格样本，覆盖普通帖子、公共预告、完成、banked grant、规则变化、多效果、玩笑、否定、回复、重发、编辑和模糊时间。
- 每条标注事件类别、适用范围、时间精确度、原文依据、是否允许通知，以及正确修订关系。
- 有歧义的真样本经过人工裁决；不能把模型自己的输出当答案。
- 同一公告组的原帖、回复与改写不跨开发集和保留评测集，防止看似独立的重复样本抬高成绩。
- 样本不足时继续人工审核 Beta；合成反例通过不替代真实来源准确性。

### 5.2 指标与停止规则

自动发布的建议目标为：真实保留集事件级精确率至少 99%，召回率至少 90%；同时关键错误为零，包括编造明确时间、误判全局适用和把赠送机会当作已到账重置。所有比例同时报告分子、分母、样本来源、拒绝 / 待审核比例与不确定性。

这是验收目标，当前没有达到该目标的结果。少量样本零误报不足以证明长期 99% 准确，不能靠大量容易负例稀释少数危险误报。稀有事件没有足够可复核真样本时，保留人工发布，不上线相应自动模板。

召回不能只统计被规则筛中的帖子，须抽检被过滤内容，以发现前置规则漏报。运行中出现关键语义错误，应停用相关自动模板、纠正已发布事件，并把反例纳入回归。

## 6. 场景演练与成本审计

最小反例链：一条有时区的明确预告 → 修改时间 → 延迟完成声明 → 撤回其中一个效果 → 客户端休眠后恢复。核查同一事件 ID、递增修订、旧任务取消、来源时间和实际通知内容。

另测分页中断、429、预算耗尽、模型失败、提示注入、部分上传、坏签名、CDN 旧包、主机时钟跳变、先退款后收到迟到支付事件等关键行为。

成本记录至少包含：

| 数据 | 用途 |
|---|---|
| 计费资源与 API 请求分别统计 | 防止请求数与资源数混算 |
| 独立候选 / 修订与模型调用 | 核查重复处理、规则过滤和提取费用 |
| 人工审核、发行维护、故障与客服工时 | 检查低价是否依赖未计价劳动 |
| 全部活跃用户、付费用户与免费比例 | 计算分发和支持成本 |
| CDN 命中、请求、鉴权与对象操作 | 验证共享缓存是否节省实际账单 |
| 支付路径、退款、费率、签名预算 | 用实际渠道替换估算 |
| 订阅意愿、持续使用、无公告期反馈 | 判断持续服务价值 |

每个结果带源码提交、配置、时间窗口和环境。原始日志、截图、账单脱敏文件归 .runtime/；正式记录只整理必要证据与结论。

## 7. 当前关闭程度与下一步

本轮可确认：已把架构简化为外部数据来源与 HTTP 客户端，分离了请求、上游与事件新鲜度，并明确 HTTP/Cookie 拒绝和边界。旧三路设计研究是背景，不应误称本次有新的真人专家签字或完整联调。运行门槛仍待验证。

本轮不可确认：现成 HTTP feed 是否可用、X / 第三方数据许可、事件准确率、桌面真实效果、30 天实际成本、收费发行或总分达到 95。

下一步优先取得一个现成数据接口 URL 或明确采用手工 JSON fixture；确认来源生产者是否提供可信最近检查时间和允许的访问认证，再决定是否开发薄适配。价格币种与年付假设仍待确认。
