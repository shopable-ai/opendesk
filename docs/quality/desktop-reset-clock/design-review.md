## 1. 评审结论

用户补充的中心数据服务要求改变了原设计的主路径。正确边界是：**公共来源公告 → 服务端提取与审核 → 共享事件 feed → 桌面本地换时和提醒**。个人账户额度作为可选适配，不能用公共帖子替代。

当前方案已补充集中增量读取、事件类型与状态、时间不确定性、编辑撤回、可信缓存、预算保护、Beta 人工成本、收费与阶段门槛。它已经具备可供决定下一阶段的结构。

当前不能确认产品达到 95 分。缺少准确来源确认、正式 API 样本与使用范围验证、真实费用记录、双平台桌面结果、支付及发行证据。以下明确区分“设计已处理”和“实现已验证”。

## 4. 95 分如何评，谁来评

### 4.1 两个不同的评分

1. **设计评审分**：检查问题、决定、契约、失败处理、取舍和验收方法是否完整且自洽。评审者逐条引用方案和发现记录；不能因措辞详尽而加分。
2. **发行验收分**：检查实际源码、真实样本、端到端、两平台、费用与交易是否达到承诺。没有运行证据的项不得按通过计分。

两个分数各自满分 100。达到设计 95 不代表产品 95，更不代表 95% 的用户适用率或模型准确率。当前不发布人为凑出的总分；目标是经过独立复核达到不低于 95，且关闭相应硬门槛。

## 5. 样本与准确性验收

### 5.1 先建立可复核数据集

- 真实原文与上下文需来自允许的数据路径，记录获取日期、来源版本与权限。
- 历史真实样本、合成反例和在线观察分别统计。
- 初始建议至少 100 条规格样本，覆盖普通帖子、公共预告、完成、banked grant、规则变化、多效果、玩笑、否定、回复、重发、编辑和模糊时间。
- 每条标注事件类别、适用范围、时间精确度、原文依据、是否允许通知，以及正确修订关系。
- 有歧义的真样本经过人工裁决；不能把模型自己的输出当答案。
- 同一公告组的原帖、回复与改写不跨开发集和保留评测集，防止看似独立的重复样本抬高成绩。
- 样本不足时继续人工审核 Beta；合成反例通过不替代真实来源准确性。

### 5.2 指标与停止规则

自动发布的建议目标为：真实保留集事件级精确率至少 99%，召回率至少 90%；同时关键错误为零，包括编造明确时间、误判全局适用和把赠送机会当作已到账重置。所有比例同时报告分子、分母、样本来源、拒绝 / 待审核比例与不确定性。

这是验收目标，当前没有达到该目标的结果。少量样本零误报不足以证明长期 99% 准确，不能靠大量容易负例稀释少数危险误报。稀有事件没有足够可复核真样本时，保留人工发布，不上线相应自动模板。

召回不能只统计被规则筛中的帖子，须抽检被过滤内容，以发现前置规则漏报。运行中出现关键语义错误，应停用相关自动模板、纠正已发布事件，并把反例纳入回归。

## 6. 场景演练与成本审计

最小反例链：一条有时区的明确预告 → 修改时间 → 延迟完成声明 → 撤回其中一个效果 → 客户端休眠后恢复。核查同一事件 ID、递增修订、旧任务取消、来源时间和实际通知内容。

另测分页中断、429、预算耗尽、模型失败、提示注入、部分上传、坏签名、CDN 旧包、主机时钟跳变、先退款后收到迟到支付事件等关键行为。

成本记录至少包含：

| 数据 | 用途 |
|---|---|
| 计费资源与 API 请求分别统计 | 防止请求数与资源数混算 |
| 独立候选 / 修订与模型调用 | 核查重复处理、规则过滤和提取费用 |
| 人工审核、发行维护、故障与客服工时 | 检查低价是否依赖未计价劳动 |
| 全部活跃用户、付费用户与免费比例 | 计算分发和支持成本 |
| CDN 命中、请求、鉴权与对象操作 | 验证共享缓存是否节省实际账单 |
| 支付路径、退款、费率、签名预算 | 用实际渠道替换估算 |
| 订阅意愿、持续使用、无公告期反馈 | 判断持续服务价值 |

每个结果带源码提交、配置、时间窗口和环境。原始日志、截图、账单脱敏文件归 .runtime/；正式记录只整理必要证据与结论。
