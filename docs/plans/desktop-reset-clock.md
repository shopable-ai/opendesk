## 1. 用户要求与本轮修正

用户要求使用 Go 开发 macOS / Windows 桌面应用，显示当前时间、计算时差、提醒 Codex 重置信息，并显示在系统桌面背景中。价格目标为每人 0.99/月、首次免费；先作为仓库 demo，先确认方案，再开发代码。

用户补充了决定架构的核心要求：**由服务端定时获取 X 上指定 tibo 账号的内容，分析并提取重置相关信息，然后分发给客户端，避免每个用户重复访问目标平台。**同时要求重新评估价格，并通过多角色讨论和审计提高质量。

本次据此替换原方案的主数据路径：

| 决定 | 本版方案 |
|---|---|
| 主数据来源 | 服务端集中处理指定来源的公共公告 |
| 主要产品承诺 | 说明公告讲了什么、适用于谁、是否有明确时间，并换算和提醒 |
| 个人额度 | 可选后续本地适配，不是接收公共公告的前置条件 |
| 桌面端联网 | 读取本产品事件 feed；不携带 X / 模型密钥，不各自爬取 X |
| 技术形态 | 一个 Go 服务、SQLite、本地审核入口、对象存储 / CDN；两平台 Go 客户端 |
| 商业判断 | 同时计算源数据、提取、分发、支付、发行、维护和客服；先验证再锁定价格 |
| 质量要求 | 以 95/100 为分阶段验收目标，保留硬门槛与未验证项 |
| 本轮交付 | 更新唯一方案与 README，增加交叉评审记录；不写应用源码 |

以下仍是建议，不能当作已批准的规则：

- 0.99 的币种尚未确定；本文经营算例全部假设 USD。
- “tibo”候选为 [@thsottiaux](https://x.com/thsottiaux)，准确账号须由用户给出或确认。
- 首次免费建议为 30 天完整试用，无需绑卡，不自动扣款。
- 第一种收费方案建议为 US$11.88 的一年服务授权，一次支付、到期主动续购，月均 US$0.99。
- 建议本人两台活跃设备，Mac / Windows 共用；允许释放旧设备。
- Go 承担业务逻辑；桌面窗口适配允许少量 Objective-C / Win32 代码。
- 当前尚无真实 API 接入、实时采集、桌面运行、支付或外部专家认证的证据。

## 2. 产品定位与最小范围

建议工作名为 **Reset Clock**。收费价值是持续识别有用公告、审校时间与范围、纠正变更、可靠提醒以及双平台兼容维护。

### 2.1 公告与个人额度必须分别表达

公共来源的发言不能直接证明某个人的账户余额、正常滚动额度窗口或兑换状态。应用应保持三种来源：

| 来源 | 能表达的内容 | UI 必须标注 |
|---|---|---|
| 公共公告 | 某来源宣布一次重置、发放可使用的重置机会、调整规则或倍率 | 来源、公告状态、适用范围、原帖时间、核查状态 |
| 手动提醒 | 用户自己输入的目标时刻 | 手动设置 |
| 可选个人额度适配 | 本地官方客户端实际返回的个人窗口与时间 | 当前账户、读取时间、实际返回值 |

公共公告不得覆盖手动提醒或个人额度。没有确定下一次事件时，显示“暂无确定的下一次重置”；不能根据以往间隔编造一个循环倒计时。

到达预计时刻，只能说明“预计时间已到”。作者说已经完成时，显示“来源已宣布完成”。只有个人账户适配取得相应实测结果时，才能显示该账户当前额度；不能把前两者当作账户已恢复。

### 2.2 首版功能

| 功能 | 首版行为 |
|---|---|
| 当前时间 | 本地 12/24 小时，默认显示到分钟，秒显示可选 |
| 公告卡片 | 事件类型、范围、预告 / 完成 / 更正 / 待确认、来源链接 |
| 时间换算 | 有明确时刻才精确换算；不明确时展示窗口或原文时间说明 |
| 提醒 | 已批准且符合范围的事件才触发；支持提前提醒、到时、免打扰 |
| 手动时间 | 日期、时间、来源时区或持续时长；与自动公告分别保存 |
| 桌面显示 | 可被普通应用遮挡、不抢焦点、锁定后点击穿透 |
| 托盘 / 菜单栏 | 查看公告、刷新、设置、编辑位置、隐藏、退出 |
| 本地持久化 | 配置、可信事件缓存、通知去重、权益缓存 |
| 运行状态 | 显示来源检查时间；区分无新公告、来源停更和离线 |
| 商业 Beta 后 | 试用、购买 / 恢复授权、两设备、到期与退款 |

先支持一个经过确认的公共来源频道。任意账号自助监控、多账户、团队、多产品、云同步和个性化模型任务不进入首版。

### 2.3 桌面信息结构

紧凑组件优先三行：当前时间；最相关公告状态；明确的本地生效时间或“时间待确认”。详细证据、时区和历史在托盘展开页或设置中查看。

用户可选择自己的套餐以筛选公告。这个选择只用于匹配已知适用范围，不证明账户符合资格。来源范围未知时不能默认全体用户；精确提醒要等范围与时间满足发布规则。

设置只保留“公告与提醒”“桌面显示”“授权与关于”。工程诊断如协议版本、模型、缓存哈希留在主动打开的诊断页。

## 3. 来源验证与访问方式

### 3.1 目前证据与未知项

OpenAI 官方论坛 2026 年 5 月活动将 Tibo Sottiaux / Thibault Sottiaux 介绍为当时的 Codex 负责人，可以支持名字与 Codex 的关联；它本身不能代替用户确认要监控的具体 X 账号。[来源：OpenAI Forum](https://forum.openai.com/public/videos/event-replay-codex-is-for-everyone-why-codex-matters-beyond-code-2026-05-13)

本轮定位到候选账号及原始帖子链接，部分原站搜索摘要可读，但直接打开 X 原帖出现 403。因此：

- 已完成的是来源研究，不是实时采集验证。
- 搜索摘要、第三方转载或跟踪站不作为生产事实源。
- 账号确认后固定稳定用户 ID，用户名作为可变展示属性。
- 第一阶段必须取得正式数据路径下的真实响应，核查回复、引用、编辑、长帖及线程上下文。
- 无法确认来源与可用数据时，继续做带模拟数据的技术 demo；不以实时数据服务收费。

### 3.2 集中读取策略

首选官方支持的指定用户发帖接口，当前文档为 GET /2/users/{id}/tweets。使用增量游标与分页；不要把 mentions 或账号的首页关注流当成本人发帖。接口提供 since_id、分页及时间过滤；字段和支持能力以实际接入版本的官方文档与真实响应固定。[来源：X Get Users Posts](https://docs.x.com/x-api/users/get-posts)

建议初始周期为每 5 分钟一次，任务加抖动并串行处理同一来源。该值是待运行数据调整的预算参数，不是服务时效承诺。

- 每页成功后先持久化；整个扫描范围的分页完整结束后才提交完成游标。
- 中途超时、预算不足或页数达到上限，保存未完成扫描，恢复后继续，不跳过中间内容。
- 原帖 ID 按字符串保存，避免大整数经过浮点数转换。
- 新增 / 新修订幂等入库，未变化内容不重复提取。
- 不默认排除回复；先用真实样本验证回复是否包含关键进度。
- 另设有界复查，核查仍会触发提醒的活跃来源帖；单靠 since_id 无法完成编辑、删除和纠正维护。
- 限制上下文深度、帖子数与总字符；没有完整上下文时进入待审核，不无限扩张采集。
- 单独维护 API 流控状态；X API 限流窗口重置不属于用户的 Codex 重置事件。

### 3.3 数据使用与保留

X 的开发者政策对经 API 向第三方再分发内容设置限制，指南也要求采用支持的访问方式与数据处理流程。正式接入阶段须核实本产品的商业用途、正文展示、派生事件、保留 / 删除和第三方模型推理是否处于获得的权限范围。[来源：X Developer Policy](https://docs.x.com/developer-terms/policy)、[Developer Guidelines](https://docs.x.com/developer-guidelines)

设计上只向客户端提供必要事件字段、简短自有说明及原帖链接，不建设公开原文归档 API。**提取成结构化字段不自动证明已经获准商业再分发。**未经确认的处理路径保持未启用。

内部原文只按确有必要的范围保存，访问受控；保留期限和删除时限在数据接入门槛确定。删除 / 纠正需传播到事件、CDN 和客户端。某次不可访问不等于作者正式撤回：先暂停该证据驱动的自动行动，再核对是访问故障、删除还是更正。

不把浏览器 cookie 池、绕过登录、轮换账号或无限重试作为数据供应方案。来源不稳定时公开显示状态，不用旧缓存假装实时。

## 4. 事件语义与数据契约

### 4.1 先分类，再解释时间

下表是自拟规格示例，不是经本系统核实的当前公告。

| 语义 | 事件类别 | 正确行为 |
|---|---|---|
| 指定某日某时统一重置 | 公共重置预告 | 时间与范围有证据后可设置预计提醒 |
| 今天结束前重置 | 模糊时间预告 | 保留时间窗口；时区未知则待确认，不编造午夜 |
| 发布者称重置已全部生效 | 公共重置完成声明 | 展示作者声明；不证明每个账户余额 |
| 给付费用户一次可自行使用的重置机会 | banked grant | 提醒查看可用机会；是否需领取及如何使用以官方说明为准，不当作当前额度已重置 |
| 恢复某套餐的五小时限制 | 规则变化 | 说明规则，不生成统一重置时刻 |
| 重置一次，同时短期提高倍率 | 多效果公告 | 分开重置与倍率有效期，关联同一公告组 |
| 某人说自己的额度刚恢复 | 个人经历 | 不触发公共重置提醒 |
| 引用旧公告并否认 / 开玩笑 | 非事件或待复核 | 补上下文，不只按关键词发布 |

一个帖子可以产生多个效果，多个帖子也可以更新同一事件。例如预告和完成回复应关联到同一事件组。词语相似不意味着效果相同。

### 4.2 内部字段

下列是拟定内部契约，不是已经发布的 OpenDesk API：

| 字段组 | 规则 |
|---|---|
| source_account_id / post_id / post_url | 稳定来源与原文定位；ID 为字符串 |
| source_version / evidence_post_ids | 编辑链、原帖和相关上下文证据 |
| source_published_at / fetched_at | 分开发帖时间与本次采集时间 |
| event_id / event_group_id / revision | 稳定语义事件、公告组、递增修订 |
| event_type / effects | 重置、赠送、规则、倍率等；一帖多效果可表达 |
| workflow_state | candidate / review_required / approved / rejected，表示内部审核 |
| announcement_state | announced / propagating / author_confirmed，表示来源所述进展 |
| lifecycle_state | active / superseded / withdrawn / expired / unverifiable |
| audience / product_scope | 套餐、区域、条件等；未知保持 unknown |
| effective_at / effective_window | UTC 明确时刻或时间窗口；不能确定时为空 |
| time_expression / time_basis | 原始时间表达、解释依据、时区和歧义 |
| evidence_status / evidence_spans | 关键字段的依据与缺失；不使用模型自评分冒充事实概率 |
| last_poll_success_at | 频道时间线最后成功检查；空结果也可成功，但不能替代旧帖复查 |
| evidence_checked_at | 该事件关键证据最后成功复查；与频道抓取及 feed 重签分别计算 |
| notify_until / revalidate_before | 允许首次通知的截止点、自动行动前需再次核查的截止点 |
| supersedes / tombstone | 更正、替换和撤销关联；使客户端取消旧计划 |
| extractor_version / reviewer / reviewed_at | 可追踪提取器与审核记录；不在公开 feed 暴露个人审核信息 |
| approved_evidence_hash / approved_revision | 批准绑定确切证据与事件版本；关键证据变化使旧批准失效 |

严格区分事件事实、来源声明和系统审核。“审核通过”表示证据满足本产品的发布规则，不表示代替 OpenAI 对每个账户作保证。

### 4.3 时间解释

- 绝对时刻统一存 UTC，额外保留 IANA 时区与解释依据。
- 明确相对时长以原帖发布时间为基准，不以采集时间或用户打开时间为基准。
- “稍后”“今晚”“EOD”“下一小时内”通常只支持范围或未知状态。
- 账号所在地、用户所在地和服务器时区都不能自动补成作者的精确时区。
- 时间缩写如 PST 与相应日期的夏令时用法存在冲突时保留原文并要求确认。
- 预告到期不自动变成已完成；没有后续证据时显示“预计时间已过，等待更新”。
- 不从不定期的活动公告推断正常五小时 / 每周额度重置周期。

## 5. 服务端与分发架构

### 5.1 单服务起步

首版推荐一个 Go 进程、一个本地持久磁盘上的 SQLite 数据库，以及对象存储 / CDN。内部模块拆分职责，部署不拆微服务。

SQLite WAL 适合该单机方案，但仍是单写者，不能放在网络文件系统上假设多机共享写入。未来有确切多实例需求时再评估 PostgreSQL。[来源：SQLite WAL](https://www.sqlite.org/wal.html)

建议模块：

| 模块 | 职责 |
|---|---|
| source / collector | 账号、游标、分页、复查、速率与预算 |
| extraction | 规则、可关闭模型、结构校验、版本 |
| review | 人工批准、纠正、撤回、理由 |
| events | 语义事件、适用范围、有效期与修订 |
| publisher | 持久发布任务、事件快照、签名、版本推进 |
| entitlement | 订单、试用、设备、到期、短期服务访问凭证 |
| operations | 来源健康、积压、成本、备份和恢复 |

抓取记录与处理任务事务落库。外部网络请求不持有长写事务。发布任务使用数据库 outbox，失败可重放；无需先引入 Redis、Kafka 或独立任务集群。

### 5.2 提取与审核

处理顺序：规则过滤 → 必要上下文 → 可选模型生成结构化候选 → Go 验证 → 审核 → 批准发布。

- 同一内容版本只提取一次；修改规则或模型时显式重处理并记录版本。
- 确切模板可由规则处理；模型用于语言归类、时间表达和证据抽取，可随时关闭。
- 模型调用限制输入、输出、重试和预算；不对每个客户端重新分析。
- 原文、引用、链接和其中的命令全部作为数据。模型没有发布、付费、Shell 或任意 URL 访问权限。
- Schema 校验覆盖枚举、长度、来源、时间、证据及范围。没有证据不能靠模型的高分通过。
- 首个公开 Beta 对所有会触发系统通知的候选人工确认。审核入口可先是受保护的简单页面 / 管理 CLI。
- 批准绑定事件 revision 和关键证据哈希。发现原帖 / 关键上下文变化后先使旧批准失效，发布暂停 / 替换状态并取消旧计划，再重新审核；新版本不得自动继承旧批准。
- 将来只允许经评测通过的明确模板自动发布。模糊时间、否定、引用冲突、未知范围和敏感更正继续人工处理。
- 运营者不在线时宁可等待核查；Beta 不承诺全天候即时人工服务。

### 5.3 版本发布与可信缓存

发布不可变版本事件包，再更新短缓存 latest 清单。清单包含 schema_version、单调 feed_version、事件包地址与哈希、key_id、issued_at、expires_at、来源健康与 last_poll_success_at；每个事件单独保留 evidence_checked_at。

- 先完成并校验对象上传，再移动 latest；失败保留旧的完整版本。
- 旧发布任务不得把最新版本回退；修改已发布内容要生成新修订。
- 定义唯一的签名字节格式，例如对原始 payload 字节签名，避免两端 JSON 重排不一致。
- 客户端校验签名、哈希、版本和有效期；公钥随程序发行，轮换有明确重叠期。
- 签名只证明由本产品发布且内容未改，事实准确仍由来源与审核决定。
- 完整有效事件快照使客户端可以对账；更正和撤回保留必要 tombstone，客户端取消旧计划。
- 首次安装只显示当前摘要，不默认回放历史通知。

事件包内容按频道共享，不混入邮箱、个人授权、设备或账户数据。若收费包含实时 feed，商业版在 CDN 边缘验证短期服务访问凭证后才读共享缓存，源站对象禁止绕过入口直读；验证成功后的公共事件使用规范化缓存键。用户权益响应单独处理且不得进入共享缓存。具体 CDN 能力与成本在实现前选定并验证。

低频权益检查与事件轮询分离，不能每次刷新时都穿透数据库。开源客户端的本地付费开关不能充当服务端访问控制；也不承诺公开消息绝对无法被用户转述。

### 5.4 延迟与请求预算

初始参数建议：来源每 5 分钟检查，客户端每 5 分钟检查 latest，latest 缓存最多 60 秒；启动、唤醒、网络恢复合并一次刷新。空闲模式可退到每 15 分钟检查。

自动路径的延迟由源轮询、提取 / 发布、缓存、客户端轮询和系统通知共同组成。仅这些轮询等待就可能接近 11 分钟，外加处理时间；不能写成“实时秒到”。人工审核时间另计。

1000 个活跃客户端实例如果全天每 5 分钟检查一次，按 30 天计算约 864 万次请求；15 分钟一次约 288 万次。这是固定轮询请求基线，不是总请求上界，还需计算启动、唤醒、重试、鉴权和新版本下载。1000 位用户若两台设备都全天在线，5 分钟轮询约为 1728 万次/月。条件请求减少传输，不能假定所有 CDN 的 304 响应和鉴权操作免费。

客户端每秒显示时钟不需要每秒联网。默认不常驻 WebSocket / SSE，也不每分钟重新渲染壁纸图片。

## 6. 桌面客户端与 Go 边界

### 6.1 业务逻辑

Go 管理 feed 校验、事件筛选、时间换算、调度、去重、配置和权益。UI 只消费显示模型。

Go 的 time / tzdata 提供时区转换所需能力。入口包含时区数据兜底；当地时间的重复或不存在要显式处理，不能只相信一次日期构造就已经消除歧义。[来源：Go time](https://pkg.go.dev/time)、[Go time/tzdata](https://pkg.go.dev/time/tzdata)

- 时差按事件日期算，不固定写死两个城市相差几小时。
- 每次刷新按绝对目标减当前时间重算，避免计数器累计漂移。
- 休眠、改时、时区切换、网络恢复时重算并刷新适用状态。
- 自动通知共同要求 workflow_state=approved、lifecycle_state=active、范围符合、feed 与关键证据未失效。unverifiable / withdrawn / superseded / expired 的旧计划取消。
- 精确到时 / 提前提醒还必须有确定的 effective_at。仅有完成声明或赠送机会时，可按经核实的公告时间发消息通知，不虚构到账时刻或未来倒计时。
- 通知按语义事件及提醒种类去重；只修改描述的 revision 不再次弹窗。
- 改期 / 撤回时原子替换本地计划，任务执行时再次检查当前有效版本。
- 休眠补偿受 notify_until 限制，只补仍有意义的一条，不回放一天的消息。
- 通知提交成功不代表用户实际看见；权限、免打扰与无可靠回执分别表达。
- 应用常驻是首版提醒前提；退出或关机不承诺后台继续提醒。

### 6.2 桌面背景验收定义

“显示在系统桌面背景中”以行为定义：普通应用在上；显示桌面时可见；不抢焦点；锁定时图标可点击；从托盘进入编辑后可拖动；断开屏幕后位置可恢复。

macOS 优先用公开原生窗口接口验证层级、点击穿透、Spaces / Stage Manager 与全屏行为。Windows 单独验证 Win+D、Explorer 重启、虚拟桌面、缩放与多屏。

Windows IDesktopWallpaper 提供壁纸相关能力；它不是任意实时组件的通用嵌入接口。将自有窗口挂到 WorkerW / Progman 的实现依赖 Shell 结构，SetParent 的公开性不等于该组合有稳定承诺，并有 DPI 兼容风险。[来源：IDesktopWallpaper](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-idesktopwallpaper)、[SetParent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent)

透明卡片优先原生绘制；设置页可用 Wails。Wails 关于 macOS 透明 WebView 的文档提示涉及 private_mac_apis，因此不能仅凭 CSS 透明就认定原生桌面效果可行。GUI 框架与版本经过技术验证后再固定。[来源：Wails Private macOS APIs](https://v3.wails.io/guides/build/private-macos-apis/)

Wails 设置页与自建原生窗口必须归属同一个明确的主线程 / 原生事件循环，由统一生命周期管理。不能并行启动两套 AppKit 主循环，或从任意 goroutine 更新原生窗口；技术验证时确定与所选框架的集成方式。

某平台无法达到上述行为时记录 BLOCKED 并调整产品范围，不能以置顶浮窗替代“桌面模式已通过”。

### 6.3 资源与能耗预算

以下是待测目标，不是已有成绩：

- 默认到分钟显示，按内容变化重绘，不持续运行 60 FPS 动画。
- 常驻 Go 核心、托盘、原生卡片空闲平均 CPU 目标低于单核 0.5%，至少观察 5 分钟。
- 常驻内存先按 100 MB 评估；设置 WebView 等所有子进程单列并报告总占用。
- 唤醒 / 屏幕变化后目标 2 秒内恢复本地正确显示，网络新内容另计。
- 连续 24 小时无明显内存增长、重复通知或持续失败重试。
- 记录进程唤醒、请求量、缓存命中和模型调用，检查集中处理是否真实降低总资源消耗。

CPU / 请求量可以验证效率；没有相应测量不能宣称通过正式能耗或环保认证。

### 6.4 个人额度作为后续独立适配

官方 Codex App Server 提供额度读取及相关更新能力，可用于未来的可选个人功能；实际支持取决于客户端版本、账户模式和返回字段。[来源：Codex App Server](https://learn.chatgpt.com/docs/app-server)

该功能在本机读取，OpenAI 凭证、会话和代码不上传到本产品服务器。不得把公共公告替代成个人账户数据，也不硬编码所有账户都有相同窗口。它不进入集中公告 MVP 的关键路径，当前不扩大 OpenDesk Browser RPC 白名单。

## 7. 可靠性、纠错与运维

### 7.1 三个时间不能混淆

| 时间 | 表达什么 | 禁止的推断 |
|---|---|---|
| effective_at / source_published_at | 事件何时发生、作者何时发布 | 从获取时间重新解释历史相对时间 |
| last_poll_success_at / evidence_checked_at | 频道何时成功查询、事件关键证据何时复查 | 频道查询成功或重签 feed 就算旧公告已复查 |
| issued_at / fetched_at | feed 何时发布、客户端何时收到 | HTTP 200 或 CDN 命中就代表消息仍新鲜 |

建议来源连续三个 5 分钟周期未成功时显示“来源暂不可更新”。频道查询成功不能延长旧事件的 evidence_checked_at；驱动提醒的关键来源必须单独复查。公开自动提醒还须满足事件核查截止与 feed 有效期，初始最长事件证据未核查窗口建议 30 分钟，在 Beta 用误报与可用性结果校准。超过窗口，保留最后内容供查看，暂停新的自动公告通知；手动提醒和本地时钟继续运行。

缓存失效、事件撤回和授权到期是不同状态，不共用一个模糊的“过期”。

### 7.2 失败与恢复规则

| 场景 | 必须处理 |
|---|---|
| X 429 / 服务故障 | 遵守重试提示、指数退避、抖动和有界重试；不推进缺失范围的游标 |
| 预算达到上限 | 暂停相关外部请求，保留队列，显示来源状态 |
| 模型超时 / Schema 错误 | 候选留待处理；不发布空结果或自造时间 |
| 同一内容重复到达 | 幂等落库；不重复模型调用和提醒 |
| 作者编辑 / 后续纠正 | 关联旧事件，生成新修订，取消旧通知计划 |
| 来源暂不可见 | 标为 unverifiable，暂停依赖该证据的自动行动；核查后再决定撤回 |
| 采集后崩溃 | 数据与任务持久化后恢复；完整扫描完成才推进游标 |
| 发布中崩溃 | outbox 重试；先不可变内容，再最新指针，不回退版本 |
| 客户端拿到坏签名 / 旧版本 | 拒绝新包；仅保留仍有效的可信缓存 |
| 停机一天后恢复 | 补全数据，但过期通知只进历史，不集中补发 |
| 系统改时 / 夏令时变化 | 重算时间并提示重大时钟异常；不继续递减旧数值 |
| 权益服务暂不可用 | 按原已验证权益的有限宽限处理，不无限延长付费期 |

每月和每日预算都应有本地上限；平台可用时同时配置账户消费上限。80% 用量预警是建议参数。监控包括最后成功采集、扫描滞后、待审核年龄、提取失败、来源复查、发布版本、实际资源计费及人工工时。

单机备份必须使用 SQLite 支持的备份 / 一致性方法，不能只拷贝运行中的主文件忽略 WAL。记录恢复步骤并实际演练。后台管理、签名密钥与源凭证访问受限，日志不输出密钥、支付凭据或个人账号内容。

### 8.2 X 当前公开费率与计费口径

截至 2026-10-11 核查，X 官方公开按量预付 credits 方案：Post 读取 US$0.005 / 返回资源，User 读取 US$0.010 / 返回资源；不是每次请求固定收上述费用。同一 UTC 日资源重复读取有计费去重说明，但属于软保证，跨日重读不能假定免费。具体价格和权限以实际控制台为准。[来源：X Pricing](https://docs.x.com/x-api/getting-started/pricing)

因此，一个账号每 5 分钟轮询不等于每 5 分钟把最近 100 条重新计为有效新消息。费用按实际返回和计费资源记录，包括补采、跨日复查和上下文；第三方账号不套用只针对自己数据的优惠。一次性赠额不计入持续经营收入。

集中架构让源数据与提取成本主要随来源及内容增长，而不是随每位用户增长；分发和客服仍随活跃用户增长。

### 8.3 成本公式

定义：

- N：处于有效付费服务期的用户，按用户月折算；年费收入不只计当月实际活跃者。
- M：全部活跃用户，含试用；D：活跃客户端实例，反映两设备和轮询负载。
- Rp / Ru：实际计费 Post / User 数，包含复查与补采。
- I / O：模型输入 / 输出 token，包含重试；pi / po 为选定模型每百万 token 单价。
- F：托管、存储、日志、发行等固定现金费用。
- H：固定维护、复核与故障处理工时；w 为计入预算的小时单价。
- cd：每活跃客户端实例的增量分发成本；cs：每付费用户客服成本。
- B：退款、异常流量及试用支持等储备。

月成本的参数化形式：

~~~text
X 费用 = 0.005 × Rp + 0.010 × Ru
模型费用 = (I × pi + O × po) / 1,000,000
月运营成本 = X 费用 + 模型费用 + F + H × w + D × cd + N × cs + B + 支付费
~~~

B 中的试用支持按实际活跃试用人数计入，不用有效付费人数替代。下表每人分发 / 试用储备须由实际 D/N、免费用户比例与账单验证。

没有新相关内容不必调用模型。模型选择留到真实样本评测后；本文的小额模型预算是可替换假设，不是供应商报价。

### 8.5 Beta 人工必须另算

“所有通知候选人工确认”不能直接套用上表低工时：

~~~text
H = 发行维护工时 + 独立候选及修订数量 × 单次复核分钟 / 60 + 纠错故障工时
~~~

例如 60 个候选每个 2 分钟，已经用完 A 档全部 2 小时，尚未做其他维护。Beta 单列审核预算、候选数、等待时间与工时；日审核容量上限由可投入工时决定，超出进入等待并显示状态，不能为了提速跳过审核。免费 Beta 的未计价劳动不能证明未来服务有利润。

只有明确模板的自动发布经过验收后，才用实测结果降低人工假设；不预先把人工记为零。

### 8.6 支付后的贡献与保本

示例采用 Stripe 美国境内卡公开基础费率 2.9% + US$0.30 / 笔；月度订阅另按 Billing 0.7% 举例。实际主体、地区、卡种和产品不同会改变费率。[来源：Stripe Pricing](https://stripe.com/pricing)、[Stripe Billing Pricing](https://stripe.com/billing/pricing)

年度方案必须实际使用一次性支付、没有创建 Billing 订阅，才采用下表纯支付费率。仅关闭续费但仍创建订阅，不自动免去 Billing 费用。

另假设每付费用户每月 US$0.15 变动储备：客服 0.10、分发 / 试用 0.02、退款等 0.03。它是敏感参数，不是保证足够的成本标准。

| 对照 | 实际每月 US$0.99 | 一次性 US$11.88 / 年 |
|---|---:|---:|
| 示例支付计费 | 3.6% + 0.30 / 月 | 2.9% + 0.30 / 年 |
| 支付费后月均金额 | 0.65436 | 0.93629 |
| 变动储备 | 0.15000 | 0.15000 |
| **用于覆盖固定预算的月均贡献** | **0.50436** | **0.78629** |

~~~text
年付月均贡献 = (11.88 × 0.971 − 0.30) / 12 − 0.15 = 0.78629
月付月均贡献 = 0.99 × 0.964 − 0.30 − 0.15 = 0.50436
保本人数 = 向上取整（固定预算 / 每人月均贡献）
~~~

此处未按每笔支付分币舍入，属于数学估算。

| 情景 | 现金预算：年付 | 现金预算：月付 | 加既定人工：年付 | 加既定人工：月付 |
|---|---:|---:|---:|---:|
| A | 49 | 76 | **112** | **175** |
| B | 70 | 109 | **197** | **307** |
| C | 122 | 189 | **376** | **586** |

这些人数是无余量的运行保本下界，不是商业成功线。B 档约 200 位年付用户只覆盖所列预算；任何额外获客或研发摊销都要提高目标。年费按未来服务期摊销，不能当收款月全部利润。

US$0.10 客服假设相当于每月 2% 用户各需 12 分钟支持、人工 US$25/小时。若发生在 20% 用户，单项就约 US$1/用户/月，已超过 0.99 标价。试用用户也需要支持；在真实模型中用全部活跃人数与实际免费 / 付费比例计算，不能固定用 0.02 覆盖无限免费流量。

如果 0.99 指人民币，以上结论无效，须按该币种、开户主体和支付渠道重算。

### 8.7 定价结论与验证顺序

建议保留“月均 US$0.99、年付 US$11.88”为首轮价格假设，暂不锁定长期价，也不因有服务器就任意翻倍。

连续记录至少 30 天的数据和维护成本，并向目标用户验证：公告是否频繁且有用；错过后损失什么；时间与范围判断是否确实省事；无新公告的一周是否还愿意订阅。小规模付费 Beta 也必须先验证来源及数据使用条件、交付可用的端到端服务，并通过最小支付 / 退款 / 权益闭环，清楚展示适用范围；常规可售发行仍受阶段 6 门槛约束。目标与样本记录在质量报告中，不能用免费安装量冒充付费意愿。

若实际用户规模无法覆盖人工与服务承诺，应缩小运营范围、调整后续售价，或保留为免费 demo，停止扩大商业投入。

### 8.8 最小交易与权益闭环

使用适合销售主体的托管支付页。优先复用已可用的支付基础；开户资格、费率和地区在商业阶段确认，不在文档阶段创建真实商品。

服务端验证支付事件，验签、去重、处理乱序并核对订单；不能信任客户端返回 URL。支付成功才签发对应期限的服务权益。试用、已付费、暂不可验证、到期、撤销分开表达。

提前购买保留约定剩余试用时间并展示实际日期。全额退款与权益撤销联动。两设备可恢复与释放。建议权益验证允许最长 7 天离线宽限且不超出已付费截止；公共公告的来源新鲜度仍按第 7 节独立执行，不能靠授权宽限延长来源可信期。配置不因到期或退款而删除。

本地 7 天宽限不延长 CDN 访问令牌。云端凭证建议最多 1 小时并有明确时钟容差；过期时权益服务不可用，客户端只能降级，不自行声明宽限绕过鉴权。退款或释放设备后停止签发新凭证；现有凭证的最迟访问终止按 TTL 与容差说明，若采用更快的边缘撤销也须实测。不能承诺撤销请求后所有离线设备立即失效。

## 11. 验收矩阵与 95 分门槛

详细权重、证据口径和阻断项以 [设计评审](../quality/desktop-reset-clock/design-review.md) 为评审依据。本方案定义业务验收行为：

| ID | 场景 | 必须结果 |
|---|---|---|
| SRC-001 | 精确来源和 API | 稳定账号 ID、实际字段、权限范围有证据 |
| SRC-002 | 分页中断 / 重启 | 恢复不漏帖；不提前推进扫描游标 |
| SRC-003 | 回复 / 引用 / 旧帖重发 | 保留上下文与原始时刻；历史不回放成新公告 |
| EVT-001 | reset / banked grant / 规则 / 倍率 | 正确区分，多效果可表达 |
| EVT-002 | 私人经历 / 否定 / 玩笑 / 未知范围 | 不升级为全局重置，不自动精确通知 |
| EVT-003 | EOD / 缺时区 / 相对时间 | 不捏造精确时刻；相对量基于原帖时间 |
| EVT-004 | 编辑 / 更正 / 删除 / 不可见 | 区分原因、修订关联、旧计划取消 |
| EVT-005 | 预告到期 / 完成声明 | 不自动等同个人账户已恢复 |
| EXT-001 | 模型超时 / 提示注入 / 无证据高分 | 不能发布或执行源文本指令；待审核可恢复 |
| PUB-001 | 部分上传 / 崩溃 / 重放 | 最新指针只指向完整版本，发布不回退 |
| PUB-002 | 坏签名 / 旧包 / 到期 | 拒绝新包；只保留允许的可信内容 |
| PUB-003 | 无新内容 / 上游停止 / CDN 命中 | 来源状态正确，分发成功不冒充采集成功 |
| TIM-001 | 时区 / 跨日 / 夏令时歧义 | 同一时刻转换一致，歧义有明确处理 |
| TIM-002 | 休眠 / 改时 / 重启 | 重算正确，不补发无意义历史通知 |
| NTF-001 | 重复抓取 / 文案修订 / 改期 | 语义去重，取消旧计划，必要纠正可提醒 |
| NTF-002 | 免打扰 / 权限拒绝 | 表达已知结果，不假称用户已收到 |
| GUI-001 | 两平台桌面 / 图标 / 焦点 | 满足第 6.2 节，含真实可见证据 |
| GUI-002 | 多屏 / 缩放 / 桌面切换 / Explorer | 恢复与降级状态清楚，无不可见丢窗 |
| OPS-001 | X / 模型预算耗尽与恢复 | 消费可封顶，有界重试，数据不丢 |
| OPS-002 | SQLite 备份与恢复 | 可恢复游标、事件和待发布任务 |
| PERF-001 | 常驻性能与请求量 | 24 小时记录，含所有相关进程，不假定节能 |

| PAY-002 | 支付乱序 / 退款 / 两设备 / 离线 | 服务端状态决定权益，恢复幂等 |
| PAY-003 | 付费 feed / 缓存 | 先鉴权再读缓存，个人数据不混入共享响应 |
