# OpenDesk 商业验证推进计划

更新时间：2026-09-13

> 文档性质：Plan / Validation（商业验证计划）。本计划承接已保存的商业设计研究，不批准全部候选模式、不自动创建工程排期，也不表示已经完成访谈、订单、收入、外包或实机验证。阶段以产物和证据推进，不用日历时间或主观高分代替验收。

研究基线：[OpenDesk 商业系统设计与模式组合](../../research/commercialization/opendesk-business-system-design.md)。
研究导航：[商业化研究](../../research/commercialization/README.md)。
长期战略：[全球可执行经验网络](../../research/commercialization/opendesk-global-executable-experience-network.md)。

## 1. 目标需求

把“可以怎样赚钱、怎样低价获客、怎样扩大能力供给”的多种设想，收敛成可以报价、交付、收款、维护和重复销售的小规模业务闭环。

最终需要得到：

```text
明确的首批客户
+ 1—3 个有边界的候选场景
+ 一种优先经营组合
+ 可交付与可验收的商品
+ 有完整成本记录的付费试点
+ 跨客户复用或明确停止的证据
+ 仅为该闭环补齐的产品功能
```

当前建议主线：固定范围小单（B1）获得现金流，重复需求沉淀标准场景包（B2），用实施维护（B3）补足服务；获客优先限额小样（A1）与复用授权换优惠（A2）；供给优先小额付费试单（C1）、模块外包（C2）和明确维护者（C4）。这些是候选建议，不是已验证经营事实。

## 3. 后续推进任务树

- **S0｜保存研究基线与状态**
  - 输入：当前对话方案、现有商业研究与目录规则。
  - 工作：区分用户目标、候选建议、来源线索和未验证假设；建立交接。
  - 输出：商业设计正文、本计划、研究导航。
  - 门槛：核心模式不遗漏；不把建议写成承诺；下一消费者明确。
  - 状态：本轮完成文档固化；不等于完成商业验证。
- **S1｜选择首批客户与任务**
  - 输入：基线、现有行业研究、能够合法获得的任务证据。
  - 工作：选定客户范围，比较任务频率、现有做法、预算、可验收性、复用与风险。
  - 输出：1—3 张场景卡、候选比较表、一条首选或明确阻塞项。
  - 门槛：知道为谁做、谁付款、完成什么；未知项和证据获取方式明确。
  - 下一消费者：经营组合与报价设计。
- **S2｜形成可报价商品与完整经济假设**
  - 输入：场景卡、现有能力边界、初步交付与维护信息。
  - 工作：组合获客、收费、供给、运行、权属和维护；核算完整成本。
  - 输出：模式卡、报价草案、验收合同要点、成本假设、付费实验卡。
  - 门槛：范围、付款、失败、变更和维护责任清楚；不以免费或返还掩盖成本。
  - 下一消费者：最小产品交付与试点销售。
- **S3｜补齐最小交付与测量能力**
  - 输入：选定商品、验收标准与当前仓库真实证据。
  - 工作：分类“直接复用 / 配置适配 / 必须开发 / 可人工处理 / 外部依赖”。
  - 输出：功能缺口表、任务分解、验收用例、交付包与运行记录格式。
  - 门槛：权限、停止和真实结果校验可用；不能只靠营销页面或聊天演示交付。
  - 下一消费者：受控的付费试点。
- **S4｜完成小规模付费试点**
  - 输入：可交付商品、已确认范围与必要授权。
  - 工作：真实报价、成交、交付、验收和收款；记录全部工时与异常。
  - 输出：订单记录、结果证据、完整成本、客户反馈与支持记录。
  - 门槛：不能将愿意试用、点赞或内部测试写成付费验证。
  - 下一消费者：重复销售与维护验证。
- **S5｜验证复用与持续维护**
  - 输入：首单资产及第二个独立客户或后续真实复用需求。
  - 工作：记录配置差异、适配工时、维护成本、成功结果与复购。
  - 输出：复用报告、贡献核算、维护记录及继续/调整/停止决定。
  - 门槛：区分“同一客户重复运行”与“跨客户复用”；少量成功只属于初步信号。
  - 下一消费者：有选择的产品化与伙伴扩展。
- **S6｜按证据追加能力**
  - 输入：已验证的订单、复用、成本、供给或托管需求。
  - 工作：选择标准包、伙伴、返还试点、厂商合作、私有库或托管服务。
  - 输出：明确批准的专项目标与验收标准。
  - 门槛：每项投入有业务触发条件，不将整个模式库一次性转成开发待办。

S1/S2 的访谈与方案可迭代，S3 不要求先建设全部后台。任一阶段发现核心假设被否定，应返回对应假设，而不是默认继续扩大投入。

## 4. 下一轮应做什么

下一轮建议止于 **S1：首批客户与 1—3 个场景选择**，必要时补 S2 的模式草案。不继续从零枚举商业模式，不立刻建设 Marketplace、现金返还系统或 24 小时托管后台。

下一轮必须交付：

| 产物 | 内容 | 不应出现 |
| --- | --- | --- |
| 场景候选比较 | 客户、任务、付款人、现有方法、频率、结果、可复用性、风险 | 没有证据却声称需求已经成立 |
| 1—3 张场景卡 | 输入、输出、前后条件、人工确认、验收、不做范围 | 只有应用名称，没有业务结果 |
| 优先组合建议 | 从 A/B/C 与 P1—P5 中选择，说明排除项 | 把所有组合都设为 P0 |
| 验证问题与获取方式 | 哪些通过访谈、演示、报价、付款或实机测试验证 | 用推测补出客户、预算或订单 |
| 初步功能分类 | 需要哪类能力、哪些可人工处理、哪些需查当前代码 | 把方案需求表当成代码缺失事实 |

可以基于现有材料先产出候选，不需要因为缺少真实客户信息而停止全部整理；但没有证据的字段统一写“未知/待验证”，不能把候选选择称为已完成商业决策。

## 6. 从商业模式映射到产品功能和工作量

只有选定商品后，才进行当前代码核对。

| ID | 功能或工作 | 为什么需要 | 当前状态 | 处理类别 | 一次工作量 | 持续工作量 | 验收 | 证据 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 待填 | 待填 | 对应模式/场景/风险 | 待核对 | 复用/配置/开发/人工/外部依赖 | 待估 | 待估 | 待填 | 待填 |

工作量至少分开：产品工程、脚本内容、跨平台与环境验证、售前获客、实施验收、维护支持、财务治理。不能只报代码行数或只计算 Agent 生成时间。

### 6.1 小规模阶段先做与后做

| 现在必须可靠 | 可以人工或简单台账 | 有触发证据再建设 |
| --- | --- | --- |
| 安全执行、权限、停止、真实结果校验 | 需求归类、报价、派单、客户跟进 | 完整商城和开放创作者市场 |
| 参数与环境边界、错误提示 | 合规渠道收款后的对账 | 自动分账与现金返还系统 |
| 版本与交付记录、失败定位信息 | 少量伙伴审核、工单分配 | 大规模伙伴管理后台 |
| 私有数据与公共资产隔离 | 手动核算成本和复用情况 | 全天无人值守托管与人工值班 |

收费、渠道和返还机制不应侵入通用 Runtime 核心。人工处理是阶段性交付方式，不是降低必要安全或隐瞒实际人工参与。

### 6.2 与 Calculator 技术线并行

```text
技术线：对话 → 参数 → 匹配 → 确认 → 确定性脚本 → UI 实际结果 → 证据
商业线：客户 → 场景 → 商品 → 报价 → 交付 → 收款 → 成本 → 复用
```

技术线测试证明执行链路，商业线测试证明交易价值，两条线不能互相代替。客户发现和模式筛选不必等待所有平台功能完成；但对外承诺的功能必须有相应运行证据。

### 7.2 推荐顺序

| 实验 | 需要回答的问题 | 有效信号 | 不算通过 |
| --- | --- | --- | --- |
| E1 任务发现 | 谁正在重复做这件事，结果有什么价值？ | 具体流程、频率、现有成本和付款人 | 泛泛表示喜欢自动化 |
| E2 有边界的小样与报价 | 客户是否为约定商品付费？ | 对明确范围的实际购买 | 免费注册或只看演示 |
| E3 首单交付 | 是否能可靠完成且成本可核算？ | 结果验收、收款、工时与异常记录 | 只运行成功一次，没有业务验收 |
| E4 独立客户复用 | 低价是否来自真正复用？ | 标准能力复用、适配量、完整贡献 | 换个客户就重写主要逻辑 |
| E5 维护与支持观察 | 持续收益是否覆盖维护？ | 支持、升级修复、返工和续费记录 | 只看首单收入 |

## 8. 扩大、调整和停止规则

| 发现 | 应采取的动作 |
| --- | --- |
| 大量兴趣但没有明确购买 | 调整客户、任务价值或报价，不先扩大脚本数量 |
| 每个客户差异都很大 | 维持定制服务或缩小标准范围，不强行宣传标准包 |
| 执行成功但支持成本高 | 改进环境约束、配置与提示，重新定价或限制服务 |
| 维护成本吞噬贡献 | 缩小兼容范围、明确维护收费，或停止该场景 |
| 私有权属不允许外部复用 | 提供私有交付，不将客户成果偷偷加入公共目录 |
| 有真实重复订单且维护可承受 | 产品化对应标准包与自助配置 |
| 有稳定外包和交付需求 | 扩大伙伴机制，再评估专门后台 |
| 有可归因、已结算复用收入 | 才评估有条件返还试点 |
| 有企业实际托管需求与可靠性证据 | 单独评估托管服务和支持承诺 |
| 供需双方与治理成本已经可核算 | 再判断开放市场是否优于受控伙伴网络 |

没有通过只意味着需要调整或停止相应实验，不应否定整个长期愿景；也不应为了维护愿景而忽视实际失败。

## 9. 文档与证据如何继续保存

### 9.1 文件职责

- 研究正文：维护候选模式、推理、边界与假设，不堆积原始订单资料。
- 本计划：维护当前阶段、比较表、模式卡、实验摘要和下一决策。
- 研究导航：指向正文和计划，不复制全文。
- 后续工程目标：只有批准了具体需求，才进入所属技术架构、计划与实现文档。

早期直接更新本计划的表格即可，不需要立即创建大量空文档。候选卡或验证报告增长到影响阅读时，再在同主题目录按职责拆分；不要建立多份相互冲突的最终版文件。

真实客户姓名、合同、付款明细、账号、原始截图和敏感业务数据默认不写入仓库。公开或共享文档仅使用经授权、脱敏的摘要与证据编号；原始材料保存在适当受控位置。不能默认仓库适合保存客户隐私。

### 9.2 状态标记

| 状态 | 含义 |
| --- | --- |
| 用户目标 | 用户明确表达的目的，不是市场事实 |
| 候选建议 | 设计上可考虑，尚未验证 |
| 待验证假设 | 需要指定证据的问题 |
| 已观察事实 | 有时间、范围和来源支持的观察 |
