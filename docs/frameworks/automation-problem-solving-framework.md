# 自动化任务求解方法（Automation Problem-Solving Framework）

## 0. 定位与使用方式

本文回答：**面对一个真实业务目标，怎样把人的经验判断变成可解释、可验证、可交接的解决步骤？**

先看[框架总导航](README.md)。本文属于“执行与解题方法”，不是新的 Runtime、业务编排系统或 API 清单。

方法来源是[自动化总体框架](automation-framework.md)、[应用自动化开发框架](app-development-framework.md)，以及[示范到自动化执行方法](demonstration-to-automation-pipeline.md)中的任务合同、业务分段、泛化和第 10 节千牛案例。本文将分散的判断整理成可选用的模式；新增的分类、步骤模板与对照用例是方法建议，不是源码已实现声明。

默认先用普通 JavaScript Recipe／应用 helper 落地。没有明确选择 Recorder 路线时，不要求先建立 IR、Compiler、Skill Registry 或独立 Workflow Runtime。

<a id="strategy-space"></a>

### 0.1 先看总地图：自动化求解策略空间

**本文是“自动化求解策略空间（Automation Solution Strategy Space）”的唯一总框架正文，也可称“求解框架宇宙”。** 下列八问是阅读、选择和审阅的方法导航，不是八个执行阶段，也不要求每次逐项展开全部方法。八问帮助读者找到当前问题；后文六类解题模式说明怎样分析和处理；S1—S12 规定阶段责任、成果、验收和接续。Calculator 只是其中一条简单路径。

```text
自动化求解策略空间
│
├─ 1. 要完成什么？这是什么类型的任务？
│   ├─ 目标与成功标准：最终应得到什么结果
│   ├─ 输入输出与授权：数据从哪里来，允许改变什么
│   ├─ 任务结构：单动作、多步骤、条件分支、循环
│   ├─ 规模与范围：单对象、多对象、批量、多窗口、跨应用
│   └─ 风险与持续时间：副作用、部分成功、长期运行、中断
│
├─ 2. 我要操作或读取谁？
│   ├─ 应用、账号或工作区、当前窗口
│   ├─ 页面、模式、状态和相关区域
│   ├─ 业务对象：哪条记录、哪个联系人、哪份文档
│   └─ 界面目标：该对象对应的按钮、字段、结果区
│
├─ 3. 当前子目标需要什么能力？
│   ├─ 观察、定位、读取
│   ├─ 输入、动作、必要的状态准备
│   ├─ 等待、验证、恢复或停止
│   ├─ 集合处理（按需）：搜索、分页、滚动、去重、结束条件
│   └─ 每项能力的输入、输出及下游依赖
│
├─ 4. 有哪些候选方案？各自怎样组合？
│   ├─ 可复用资产：已有应用操作、helper、App Adapter
│   ├─ 执行接口：高层 UI / Locator，或必要的底层组合
│   ├─ 观察方法：原生属性、文字 / OCR、图像等
│   └─ 必要空间处理：区域、锚点、相对几何、坐标映射
│
├─ 5. 当前证据足以确认目标吗？
│   ├─ 身份范围：正确应用、账号、窗口和业务对象
│   ├─ 匹配依据：identifier、role / name、字段值、文字、图像
│   ├─ 关系约束：父区域、锚点、标签关联、对象与动作的关系
│   └─ 证据检查：唯一性、新鲜度、完整性、冲突与未知
│
├─ 6. 为什么选择这个方案？
│   ├─ 硬条件：业务语义、身份、范围、授权、失败和验证边界
│   ├─ 能力依据：完整契约、Runtime 支持、当前环境验证
│   ├─ 合格方案比较：复用收益、兼容性、维护成本
│   └─ 选择记录：选中理由、未选理由、证据和未验证范围
│
├─ 7. 怎样安全执行？出问题后怎么办？
│   ├─ 动作前：确认前置、实际输入、当前目标及必要权限
│   ├─ 按需观察 / 定位 / 读取 / 等待；需要时取得本次坐标
│   ├─ 执行动作：有界、顺序明确，保存真实回执
│   ├─ 动作后：按需等待或读回，核对正确对象的实际结果
│   ├─ 跨对象 / 窗口：数据交接、共享桌面输入顺序、逐对象进度
│   └─ 失败分流：未执行、部分完成、效果未知、已确认结果
│       └─ 按证据决定补观察、安全接续、定向维修或停止
│
└─ 8. 怎样沉淀，并证明以后还能用？
    ├─ 可复用规则：操作策略 / 应用操作
    ├─ 按需封装：内联、helper、App Adapter 或应用模块
    ├─ 业务数据：参数、运行时读值、转换与每次重新获取
    ├─ 适用边界：版本、环境、依赖、备用策略与失效条件
    └─ 资格证据：局部、组合、Fresh Run、重复、变参、兼容与失败测试
        └─ 只声明已验证范围，变化后定向重验
```

任务结构、规模、范围、风险和持续时间可以同时成立，不是互斥的任务分类。对象范围按应用实际关系建立，不强制每个任务都有完全相同的包含层级。第 7 问中的观察、读取、等待与验证按当前操作需要组合、循环；纯读取不强加写动作，也不因图上只写一次就省略动作后的核对。

**每次必须判断**目标、授权、输入来源、验证与安全停止；**按需选择**OCR、图片定位、分页、App Adapter、模块等。没有分页需求就不填写分页方案；主方法无法安全继续且没有可靠备用时停止，不强制每个操作拥有多个策略。本地图覆盖方法类别，不声称枚举了所有应用的全部解法。API 已公开、Runtime 已实现和当前范围已实测仍分开记录，不能由导航中的名称推断支持状态。

| 当前问题 | 从哪里深入 | 本文与它的边界 |
| --- | --- | --- |
| 对象、业务分段、准备、定位、结果、恢复怎样判断 | 本文后续六类解题模式 | 保留既有方法，不再建立第二套分类阶段 |
| OpenDesk 有什么能力，怎样选方法并读契约 | [能力发现](../../workflows/agent-to-recipe/design/capability-discovery.md)、[Agent API 入口](../api/agent/README.md) | API 正文与发布状态不由总地图维护 |
| 应用中的目标与操作怎样可靠落实 | [应用操作建模](../../workflows/agent-to-recipe/design/application-operations.md)、[应用开发框架](app-development-framework.md) | 操作策略、兼容与切换方法由应用工程拥有 |
| 重复结构、分页和滚动怎样处理 | [结构化界面集合读取](../architecture/desktop-automation/structured-ui-collection-reading.md) | 不复制 segmentation、continuity、merge、end detection 算法 |
| 多窗口与跨应用怎样交接 | [多应用自动化原语](multi-application-automation-primitives.md)、[动作目标模型](../architecture/desktop-automation/action-target-model.md) | 不另造输入、焦点或副作用状态机 |
| 什么进入 App Adapter，什么留在 Recipe | [应用适配层合同](../architecture/desktop-automation/app-adapter-contract.md) | 应用映射与操作不接管整个业务控制流 |
| 模块是否可用，代码怎样组织 | [Runtime 模块边界](../api/runtime.md)、[recipe-build](../../workflows/agent-to-recipe/skills/recipe-build/SKILL.md) | 模块是可选组织方式，不是全部 Recipe 的前提 |
| 怎样评分、验证及返修 | [验证计划](../../workflows/agent-to-recipe/design/validation-plan.md)、[WORKFLOW](../../workflows/agent-to-recipe/WORKFLOW.md) | 本地图不新增 Gate、评分体系或运行报告 |

<a id="method-selection"></a>

### 0.2 选择方法：先排除不合格，再比较合格方案

不能把 API 层级、观察来源和业务封装混成“Accessibility → OCR → Image → Coordinate”的固定优先级。选择时分别回答四个问题：

| 维度 | 实际要判断什么 | 不能混成什么 |
| --- | --- | --- |
| 执行入口 | 已有应用 helper、高层 UI、Scope/Locator 调用或必要底层组合 | 观察证据的可靠性排名；Locator 不是固定夹在 UI 与 Accessibility 之间的一层 |
| 观察来源 | 原生属性、OCR 文字、图像/模板、布局或人工证据 | 对象身份本身；文字相同不证明业务对象相同 |
| 目标绑定 | identifier、role/name、父区域、锚点、相对关系及唯一性 | 单次坐标、最高匹配分或默认首候选 |
| 业务封装 | helper、应用操作、App Adapter、业务步骤、Recipe | 第二套通用 Runtime 或强制模块层级 |

**候选应是完整的组合方案，而不是名词之间的排名。** 一个候选可以组合“已有应用 helper＋高层语义动作＋原生结构预检”；另一个可以在相应能力和证据成立时组合“图像定位＋当前区域/坐标映射＋输入接口”。比较的是它们能否保留同一业务语义、对象范围、验证与停止条件，不是“Accessibility 和 Geometry 谁更好”。这些只是组合方式示意，不表示本次已有两条可执行路径，也不要求每次同时实现它们。

**识别线索不等于充分的身份证明。** `identifier`、`role/name`、`native value`、文字或图像都需要与当前范围、业务关系及证据有效性结合。两个区域显示同一个数值，不能仅凭值相同确认哪一个是本次结果区；知道坐标也不能单独证明该位置当前对应的业务对象。先核对身份、范围、必要关系、唯一性和新鲜度，再在确需坐标操作时取得本次临时位置。固定几何仍可在有证据的限定范围使用，但不升级为永久身份。

```text
写出当前操作必须保留的业务约束
→ 列出少量有理由的候选
→ 排除不能满足身份、范围、授权、失败语义与验证硬条件的方案
→ 在合格候选中优先复用最合适的已验证高层能力
→ 没有已验证能力时先形成待验证候选，不执行尚未读清契约的调用
→ 读取选中方法的完整契约及必要公共约束，冲突时修订选择
→ 在原授权和预算内开展最小现场验证，取得实际证据
→ 保存选择、支持范围、证据和失效条件，交下游消费
```

目标身份不成立、必要权限缺失或动作结果不能安全确认，不能用调用方便、维护成本低等优点抵消。API 成熟度、应用版本/语言/主题/窗口/DPI 敏感性和维护成本用于比较合格候选，不产生第二套选型总分。

下沉必须有具体理由，例如高层方法无法表达必要父区域、读取不能绑定指定结果对象、当前 Runtime 不提供该能力，或已有实测证明当前方法不适用。高层能力并非天然正确，低层组合也并非天然更可靠。Runtime 内部已经负责的 provider 协调不在 Recipe 中重新实现；具体责任核对 [Desktop UI API](../api/desktop-ui.md)。

未选是 rejected，不等于 failed；文档存在不等于 Runtime pass；待验证候选不能当已验证备用。初次探索允许明确 unknown，不要求调用者在 S2 之前已经完成所有选型或提供最终 JS。

### 0.3 一次选择应交出什么，而不是填写整张宇宙

八问的答案应能追到下列实际成果，而不只是八段“已完成”文字。按当前阶段及请求范围检查：尚未发生的动作、读取或验证保留未运行/未知，不要求 S2 提前交出最终代码或资格。具体可读文件、模板与裁剪方式见[本次成果与人工检查](#case-tailoring)，这里不再复制一套文件清单。

| 阅读问题 | 应能直接看到的内容 | 沿用的成果位置 |
| --- | --- | --- |
| 1. 目标与任务类型 | 原始目标、成功标准、输入输出、授权、任务形态和关键未知 | TaskContract / WorkPlan |
| 2. 操作或读取谁 | 需求指定的业务对象，以及现场应用/窗口、区域和界面目标的实际关系 | TaskContract 的对象要求；AppProfile 与观察证据 |
| 3. 当前需要什么能力 | 当前子目标所需观察/操作、输入来源、预期输出与下游依赖 | WorkPlan；已形成时的 Business Steps / SemanticProcedure |
| 4. 候选怎样组合 | 少量候选的执行入口、观察方法、目标绑定和必要封装，不以名词排列代替方案 | 当前工作包的能力选择材料及所引契约 |
| 5. 证据是否足够 | 当前对象依据、唯一性、新鲜度、完整性、冲突及尚缺哪些证据 | 原始 observation / evidence；AppProfile 的主张来源与限制 |
| 6. 为什么选它 | 硬条件核对、选中/未选理由、实际验证状态、适用范围和消费者 | 实际选择记录；需长期消费时按合同收敛的 capabilityDecisions 与应用规则 |
| 7. 怎样执行和接续 | 实际动作/读值、结果比较、副作用状态、停止点与下一安全动作 | 对应 Execution / 示范 / 局部验证或资格运行记录，不混淆证据用途 |
| 8. 怎样复用和证明 | 参数与运行时数据、规则/依赖版本、冻结候选、声明范围、测试结论和重验条件 | SemanticProcedure、AppProfile/helper、CandidateManifest、QualificationRecord |

这是既有产物的阅读清单，不是新的 schema。S2—S6 在原工作包记录实际选择；S9 按[共享合同](agent-to-recipe-skill-contract.md)收敛需要长期消费的 `capabilityDecisions`；S10 维护 AppProfile 操作规则，S11 实现固定上游。规则改变影响既有选择时发布有来源的增量并定向更新引用，不维护互相漂移的第二份选择。

操作策略沿既有 `AppProfile.operations`、目标、几何、验证规则与普通 helper 表达。策略的条件化执行、备用资格、副作用 unknown、部分完成和环境重验见[应用操作建模](../../workflows/agent-to-recipe/design/application-operations.md)。无可靠备用时 stop / human handoff 合法；有待确认副作用时先对账，不能换接口重做。

### 0.4 复杂任务怎样从地图开始

下面是**方法示例，不是已实现的微信 API 或真实运行记录**。面对“给指定联系人发送文字和附件”，先固定账号、收件人身份、内容、文件、授权和成功强度，再检查获准的已有应用操作。随后选择查找会话的方法，消除同名歧义，核对当前会话，准备并核对实际草稿与附件，满足发送门禁后发送一次，再核对实际结果。输入框变空不证明送达，结果未知不自动重发。

“打开会话”“设置草稿”“发送草稿”是待落实的应用操作意图；只有实际 helper/API 及其合同、范围和证据存在时才可生成调用。搜索、打开、滚动、切页会改变应用状态，不全部视作无副作用观察。批量任务逐对象记录成功、失败和未知；共享桌面输入按实际焦点与执行约束组织，不能默认并行点击。

复杂案例的第二条基准线优先使用**沙盒记录跨页查找 → 读取指定真实字段 → 写入另一文档 → 另存新文件并核验**，补充列表、多对象、跨应用数据与部分成功接续。具体应用、数据和权限须在执行前固定；未选定时只保留设计范围，不伪造运行资产。其验证计划见[复杂应用第二基准线](../../workflows/agent-to-recipe/design/validation-plan.md#complex-golden-case)。该案例不替代真实消息发送、附件或长期运行专项验证。

### 0.5 能力状态与证据强度分开

| 表述 | 所需依据 | 不能据此声称 |
| --- | --- | --- |
| 已公开 API / 已实现能力 | 对应版本 canonical contract / 实现来源，分别标明 | 当前任务现场已经通过 |
| 当前范围真实验证 | 同版本、同输入/环境范围的 action、observation、verification | 所有应用、平台和未来版本都可靠 |
| 设计方法 / 推荐模式 | 本文或专项方法的适用条件与边界 | 宿主会自动执行、策略已安装 |
| 尚待实现 / 尚待验证 | 具体缺口、责任和解除条件 | 未运行算通过、备用路径已可用 |

这些是阅读时的证据分类，不新增 Runtime 状态枚举。公开状态、实现状态和验证状态可以同时记录且不同。正文不保存某轮 PASS；每次实际结果仍进入既有 execution、Profile 验证、Qualification 或质量记录。方法文件的静态审阅不能替代阶段独立评分或 Fresh Run。

### 0.6 从总地图到本次成果：裁剪、封装与人工检查

**先判断本任务需要什么，再判断所需方法是否已验证。** “不需要分页”是任务裁剪；“需要分页但不知道结束条件”是阻塞缺口，两者不能互换。未采用一种定位方法，不代表删除业务要求；requested 中失败或未运行的场景不能事后改成 excluded。地图不要求逐项填写所有方法，更不要求同时实现 UI 树、OCR、图像与坐标四套程序。

初始需求、预算、方法偏好及 Unknown 在 S1 已有合同/计划中表达；S2—S6 取得现场事实后，按来源修订原记录。S8 固定业务步骤与数据关系，S9 收敛有来源的复用边界；S10 补应用操作规则，S11 只实现这些固定输入。后续阶段不能把最终代码倒填为早期观察。

| 需要看清的决定 | 正式内容由谁维护 | 本次人工首先看什么 | 下游怎样使用 |
| --- | --- | --- | --- |
| 本次采用哪些任务形态，哪些不需要、哪些未知 | TaskContract/WorkPlan，后续经批准的 Procedure scope/分支 | `operation-plan.md`；S9 `procedure.md` | 不漏业务要求，也不强加分页、批量或策略集合 |
| 每步为什么存在、输入输出及能力边界 | S8 Business Steps、S9 dataDependencies/capabilityDecisions | `business-steps.md`、`procedure.md` | S10 知道工程需求；S11 不重猜 producer/consumer |
| 选中方法、适用环境、主备与停止条件 | AppProfile/operation rules/helper；与 S9 固定决定一致 | `app-profile.md`、`operation-rules.md` | 只有实际存在且符合条件的路径进入代码 |
| 哪些内联、哪些复用，入口与依赖是什么 | S11 exact source/CandidateManifest/sourceMapping | `candidate-summary.md` 和所引源码 | S12 验同一候选及实际路径，不把模块名字当实现 |
| 默认、备用、变化和未知分别证明到哪一层 | 阶段 acceptance、原始 evidence、Qualification | `stage-review.md`、`qualification-summary.md` | 找首错、回原责任、只重验受影响部分 |

这些文件名沿用[Calculator 产物链](../../workflows/agent-to-recipe/cases/calculator-artifacts.md)的人机双层约定。实际路径和 hash 仍来自本次正式引用；视图从同版权威产物生成，不要求再建 `solution-design.json`、能力注册库或第二份总报告。

**可直接使用的正文格式：** [SemanticProcedure 模板](../../workflows/agent-to-recipe/skills/procedure-synthesize/templates/semantic-procedure.md)承接裁剪、业务能力与数据关系；[应用操作模板](../../workflows/agent-to-recipe/skills/application-engineer/templates/operation-rules.md)承接条件化执行；[Candidate 模板](../../workflows/agent-to-recipe/skills/recipe-build/templates/candidate.md)承接代码与实际入口。[Calculator 方法样本](../../workflows/agent-to-recipe/skills/procedure-synthesize/examples/calculator.md)展示填写后的关系，只供教学/维护及允许的评审使用，不是隔离 Producer 的答案输入或本次 Actual。

方法偏好可以来自执行前提示词，但必须明确它是偏好还是不可变需求。先守授权与硬约束，再检查候选适用性与证据，最后在合格集合中应用用户偏好和默认值；显式强制要求不能悄悄降成偏好，无法满足就保留冲突并返回责任方。获准策略配置应记录有效取值、来源与实际消费者；默认值改变也要评估资格影响，不能让配置存在但不生效。

“框架设计能力”首先是业务合同与责任边界，不是文件数：一次简单任务保留内联或少量 helper 即可；多个消费者确实共享同一操作时再封装。操作的目的、输入输出、前后条件、失败及副作用合同不因改名为 `clear()`、`sendMessage()` 就消失。可复用模块的导入不得自动操作桌面；具体生成与验证要求见 [recipe-build 正确性检查](../../workflows/agent-to-recipe/skills/recipe-build/references/validation.md)。此要求是作者约束，不宣称 Runtime 会自动沙箱拦截所有副作用。

## 一、求解主线：先消除不确定性，再执行动作

```text
明确结果与授权边界
→ 绑定业务对象
→ 拆分子目标和数据依赖
→ 建立可操作状态
→ 选择最小必要观察与操作
→ 验证实际结果
→ 决定继续、停止、恢复或保存可复用成果
```

这不是替代主流程文档的第二套 12 阶段。它是在任意业务步骤中反复使用的判断顺序：此刻还不知道什么，用什么证据确认，确认以后才允许做什么。

| 判断层 | 例子 | 不能直接推出什么 |
| --- | --- | --- |
| 观察事实 | 区域中出现绿色、某段文字或某个图标 | 不直接证明某个业务状态 |
| 应用状态解释 | 在已确认版本、页面和上下文中，该信号支持“待发货”的假设 | 不直接证明当前订单身份或发货许可 |
| 业务操作资格 | 对象、状态、输入和任务授权均满足该动作条件 | 不代表动作一定成功，仍需结果验证 |

屏幕、OCR、网页文字和外部 API 返回内容都是待验证数据，不能成为新的执行授权。订单状态、文案内容或弹窗提示不能自行扩大用户给定的业务范围。

## 二、六类解题模式

| 模式 | 关键问题 | 主要产出 | 什么时候用 |
| --- | --- | --- | --- |
| 1. 业务对象与操作资格判断 | 要处理谁？现在允许做什么？ | 对象依据、状态判断、允许与禁止动作 | 多账号、多会话、多订单、提交或发送前 |
| 2. 业务分段与数据交接 | 哪些子目标独立？下一步依赖什么？ | 步骤合同与可验证输出 | 长任务、外部查询、分阶段执行 |
| 3. 可操作状态准备 | 当前界面怎样变成可观察、可操作的起点？ | 已确认的起点状态 | 弹窗、列表位置、焦点、视图切换 |
| 4. 分层观察与相对定位 | 从哪个范围，用什么证据找到目标？ | 当次候选、关系约束与临时位置 | 重复按钮、动态布局、窗口移动 |
| 5. 动作与结果分别验证 | 实际发生了什么？达到哪一级证明？ | 结果、证明依据和不确定性 | 输入、发送、保存、跨系统写入 |
| 6. 有界恢复与经验泛化 | 哪一步可以重做？什么知识能复用？ | 恢复边界、复用规则与失效条件 | 超时、漂移、重复运行、失败重入 |

六类是分析方法，不是六个必须实现的模块。同一业务步骤可以组合多个模式；不要为了套分类，把一次简单任务扩展成大型工程。

## 三、模式 1：业务对象与操作资格判断

**适用问题。** 窗口正确但对象可能错误；界面显示一种状态，但不确定当前动作是否被允许。

**使用依据。** 主流程第 10 节区分千牛窗口、订单状态和缺少稳定会话／订单身份的风险。窗口标题、颜色与位置是观察线索，不是完整业务身份。

**判断与步骤。** 先明确用户指定的对象和操作；检查当前应用、账号、窗口、页面及业务对象；将识别依据与未确认项分开；在发送、提交、删除等写操作前重新确认会变化的条件。

| 输入 | 输出 | 有效条件／失效条件 |
| --- | --- | --- |
| 任务目标、允许动作、对象线索、当前观察 | 已确认对象或“无法确认”；状态依据；操作资格 | 切换账号、会话、订单、页面或对象状态后重新确认；窗口未变不代表业务对象未变 |

**完成与停止。** 只有足够证据将对象与任务绑定，且满足动作资格，才能进入写操作。没有稳定 ID 时要记录实际依据与限制；证据不足则停止，不凭空制造 `orderId` 或把屏幕行号当永久身份。

**跨场景例子。** 千牛中区分当前订单与其他订单；文本编辑器中区分目标文档、同名标签页和目标保存位置。后者是设计对照，不是已验证案例。

## 四、模式 2：业务分段与数据交接

**适用问题。** 一长段脚本混合取数、查询、写入和提交，任何一步失败都只能从头运行；或者下一步不知道前一步到底确认了什么。

**使用依据。** 主流程的 Business Step／Skill 归纳要求目标、输入输出、前后置与验证；千牛代码自然出现复制商品信息、查询文案、准备输入、发送和发货等组合。

**判断与步骤。** 按“可独立解释、可独立验证的业务子目标”分段，不按动作数量或函数长度分段。先画清数据依赖，再决定执行顺序。一个只读查询结果与一个写操作结果要分开返回；错误文字不得冒充准备好的业务内容。

| 输入 | 输出 | 有效条件／失效条件 |
| --- | --- | --- |
| 总目标、数据来源、子目标依赖 | 每步输入、输出、完成证据、失败语义与下一步入口 | 上游对象、输入、数据版本或授权变化，下游相关成果必须重新核对 |

**完成与停止。** 下一步能够只凭明确输出及必要的新观察继续，而不依赖隐含全局变量、旧窗口焦点或一次截图。前一步“函数返回”不是交接成功；必须检查其结果是否满足下一步的输入合同。

**跨场景例子。** 商品信息查询后才准备消息；读取文档内容后才生成报表。普通函数与返回对象通常足够；确需跨次执行时再保存必要数据，不先引入调度器。

### 最小业务步骤说明模板

这是文档模板，不是新的强制 JSON schema 或 Runtime 类型。

| 项目 | 应说明什么 |
| --- | --- |
| 子目标 | 这一步让什么业务状态发生变化，或消除什么未知项 |
| 输入 | 业务数据、目标身份、必要配置；来自哪个上游步骤 |
| 前置与授权 | 哪些条件必须成立；允许哪些副作用 |
| 观察依据 | 读哪些区域或系统信息；不足时如何补观察 |
| 执行方式 | 先复用什么接口；哪些规则属于应用适配 |
| 输出 | 下一步需要的最少数据，不把所有屏幕或日志一并传递 |
| 验证 | 哪个来源证明了哪个结果；仍有什么没有证明 |
| 有效性 | 哪些上下文、时间、数据或版本变化会让输出失效 |
| 失败与重入 | 写入是否可能发生；哪些只读部分可重做；何时必须先核对结果 |
| 交接与留存 | 下一步是什么；需要保存什么；隐私与清理要求 |

## 五、模式 3：可操作状态准备

**适用问题。** 操作目标尚不可见、焦点不对、列表位置不可预测，或者弹窗改变了当前操作路径。

**使用依据。** `qianniu.js` 的 `getOrderBlock` 使用聚焦、`PageUp` 和 `End` 建立作者认为可处理的列表状态。应提炼其目的，不能学习“总是按两次或三次”这个偶然实现。

**判断与步骤。** 明确希望到达的状态及识别条件；选择最小准备动作；重新观察并确认状态。准备、探索、错误重试与正常业务步骤分别标记，不把探索路径录成每次必做步骤。

| 输入 | 输出 | 有效条件／失效条件 |
| --- | --- | --- |
| 所需前置状态、当前界面、允许准备动作 | 已确认起点，或具体阻塞原因 | 窗口、页面、列表内容、焦点和弹窗变化后重新观察 |

**完成与停止。** 有状态证据才继续；等待到期、状态矛盾或恢复可能产生额外业务写入时停止。固定 sleep 只能是显式节奏控制，不能证明准备完成。

**跨场景例子。** 订单面板显示目标记录；文件管理器进入指定目录并显示目标文件。不能为了识别方便，擅自关闭用户窗口、改变业务数据或丢弃未保存内容。

## 六、模式 4：分层观察与相对定位

**适用问题。** 同屏有多个“编辑”“发送”按钮；窗口移动或列表滚动后，历史位置失效。

**使用依据。** 总体框架区分对象、定位信号与坐标；千牛案例包含“窗口 → 右侧订单区 → 订单块 → 操作按钮”的分层观察，以及手工 offset 换算。

**判断与步骤。**

```text
确认窗口和业务上下文
→ 选当前有效区域
→ 识别参照物与候选
→ 应用方向／矩形／其他已明确支持的约束
→ 检查唯一性、新鲜度与坐标来源
→ 只在动作前解析当次位置
```

| 输入 | 输出 | 有效条件／失效条件 |
| --- | --- | --- |
| 对象描述、范围规则、参照物、定位证据 | 候选及筛选依据；当次位置；未解决的歧义 | 窗口、布局、DPI、滚动、对象上下文或来源变化后重算／重新识别 |

**方向与矩形。** “同行右侧且距离有限”是常用约束；复杂位置可明确给出参照物旁的矩形。矩形只是查找范围，不能在没有目标时点击中心。关系匹配仍有歧义时停止，不默认选最近、最高分或第一个。

**规则与快照。** Geometry 的普通点和区域是快照，不自动跟随窗口。可复用的是“区域怎样计算”的规则；下一次操作需要同一窗口的最新 bounds。窗口未动但业务内容变化，同样需要重新识别。未知来源的图片只能做图片分析，不能自动产生当前桌面的可执行点。

**跨场景例子。** 联系人同行的“编辑”；文件列表中对应文件的操作按钮。位置关系只能缩小候选，不能代替业务对象确认。

**接口落点。** `UI.findText / findTexts / tapText`、Geometry 和现有截图／OCR 能力是相关入口。`region / relativeTo` 代表该模式的接口设计方向，本方法不声明其已发布；应核对[Desktop UI API](../api/desktop-ui.md)、[类型](../../types/UI.d.ts)、当前源码及本地任务结果。布局快照语义见 [Geometry API](../api/geometry.md)。

## 七、模式 5：动作与结果分别验证

**适用问题。** 点击或输入没有抛异常，却可能点错、未接收、保存失败，或者只完成部分业务步骤。

**使用依据。** 总框架要求动作后观察；千牛案例将点击后直接返回 true、主流程不始终检查结果列为实现债务。

**判断与步骤。** 在动作前指定成功证据和观察范围；执行一次动作；再观察并核对对象、内容和状态。返回结果说明“证明到哪一层”，而不是把不确定性藏在 true／false 中。

| 证据层次 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 工具返回／事件发送 | 调用链到达对应阶段，按该接口合同完成或失败 | 目标控件已正确接收，更不能证明业务完成 |
| 界面状态变化 | 观察到目标区域发生预期变化 | 后端已提交、消息已送达或文件内容已正确持久化 |
| 目标值／业务结果核对 | 在明确对象、来源与合同下核对相应结果 | 未被该来源覆盖的业务结果 |

| 输入 | 输出 | 有效条件／失效条件 |
| --- | --- | --- |
| 动作目标、预期结果、验证来源与期限 | 已确认结果、失败原因，或结果不确定；对应证据 | 对象或结果版本变化后重验；验证器不可用不等于成功 |

**变化、稳定、出现、完成。** 区域变化说明画面不同；采样稳定说明在给定采样和容差下暂未变化；目标出现说明观察到了匹配对象；业务完成必须满足任务成功条件。它们不能互相替代。候选 `UI.waitRegion` 属于区域观察组合，不是通用业务成功判定；其 API 和取消合同尚需单独确认。

**完成与停止。** 结果不确定时先核对已发生的效果，不自动重发、重输或再次提交。不把剪贴板变化直接等同于复制了正确字段；不把输入框清空等同于消息送达。

**跨场景例子。** 核对正确会话中的消息；核对正确文件的保存位置及内容。读取、字段校验与独立结果证明仍按应用能力和风险决定。

## 八、模式 6：有界恢复与经验泛化

**适用问题。** 目标消失、环境变化、观察失败、动作结果不确定；重复运行时不知道哪些成果还能使用。

**使用依据。** 主流程将探索、重试和 Recovery 与正常路径分开，并要求多示范、扰动验证和重新认证。千牛固定矩形兜底不能升级为通用规则。

**判断与步骤。** 先判断失败发生在观察、定位、动作还是验证；再确认是否可能产生副作用；只在已明确安全的边界重新执行。补观察与重新定位不等于允许再次发送或提交。

| 失败类型 | 下一步原则 |
| --- | --- |
| 只读观察暂时失败 | 有界重新观察；保留失败原因，不当成“目标不存在” |
| 目标歧义或身份失效 | 缩小范围、补证据或停止；不自动选择另一个对象 |
| 业务动作可能已经发生 | 先核对结果；无法确认时停止并交由人工，不盲目重做 |
| 权限不足或取消 | 停止后续动作；按实际支持的资源清理合同处理 |
| 规则因应用变化失效 | 提出局部修订，重跑相关验证；不追加 magic number 掩盖问题 |

| 输入 | 输出 | 有效条件／失效条件 |
| --- | --- | --- |
| 失败阶段、已完成结果、可能的副作用、当前观察 | 恢复范围、停止理由、待补证据或可复用规则 | 输入、环境、业务规则或验证条件变化后，相关结论重新检查 |

**经验怎样提炼。** 将一次运行中的内容分别标为业务规则、应用识别约定、环境配置、可变输入、派生值、临时观察、探索噪声和未经验证的假设。长期保留规则与适用条件，不把坐标、旧颜色或偶然重试次数当成知识。

**跨场景例子。** 消息发送状态未知时先核对会话；文件保存状态未知时先读取目标结果。没有可靠 fallback 时，停止或人工接管就是合法的失败去向，不要求每个关键目标都具有替代动作。

## 九、从千牛案例到步骤合同

详细源码事实仍以主流程文档第 10 节为案例正文，本文只保留必要对应关系。

### 9.1 源码所支持的事实

| `getOrderBlock` | 聚焦、PageUp／End、局部截图、色块与固定兜底 | 可提炼状态准备和区域搜索；固定兜底与默认首候选是待改进实现 |
| `clickCopyGetProduct` | 检查剪贴板变化，并按复制出的标题查询商品内容 | 可提炼“取数 → 查询 → 交接”；不是已经取得稳定 productId／orderId |
| `inputChatMsg`、`clickSendMessage` | 粘贴、点击、等待后返回 true | 体现输入与发送动作；不构成正确控件回读或消息送达证明 |
| `handleCopyAndSend` | 检查查询结果，准备内容；发送路径随后调用发货动作 | 体现业务组合；发送、发货的资格与验证必须分别明确 |

这里不复制源码中的业务内容、账户信息、接口地址或敏感数据。

### 9.2 改进后的交接示例

下面是设计建议，不是当前函数已具备的返回合同，也不要求马上增加新的 SDK。

| 步骤 | 输入 | 输出与交接门槛 | 不满足时 |
| --- | --- | --- | --- |
| 确认处理对象 | 任务要求、当前上下文 | 对象确认依据与允许动作 | 身份不足即停止 |
| 准备业务数据 | 已确认对象、合法查询线索 | 可用内容、数据来源、适用对象 | 查询失败或对象不符，不进入输入 |
| 准备并核对草稿 | 目标会话、内容 | 正确位置中的草稿与验证结果 | 读回或焦点不确定即停止 |
| 发送并验证 | 已核对草稿、发送许可 | 发送结果或明确“不确定” | 不自动重发 |
| 可选发货 | 当前订单依据、最新资格、独立发货许可 | 已核对的订单状态变化 | 不能由发送调用成功隐式授权发货 |

表中的对象、结果字段需要应用真实提供；缺少可靠来源时应保留未知。只要求发送消息的任务，不得自动添加发货步骤。

## 十、成果保留：不是每次从零开始，也不是永久复用旧状态

| 成果 | 可保留的内容 | 下次继续前必须检查 |
| --- | --- | --- |
| 业务规则 | 条件、参数来源、允许动作和版本 | 任务范围、业务规则或授权是否变化 |
| 应用知识 | 页面识别依据、布局规则、参照关系 | 软件版本、主题、语言、页面和对象上下文 |
| 中间业务数据 | 必要查询结果、适用对象、来源与时间 | 数据是否过期，是否仍对应当前对象 |
| 已完成步骤结果 | 哪一步经什么证据确认完成 | 是否可重入；不能把“已发送”当作可重做动作 |
| 临时 UI 观察 | 当前截图、bbox、坐标及来源 | 重新观察和映射；不得作为永久点击地址 |

短任务先用函数返回值交接。跨阶段或跨次执行确有需要时，才将必要数据和验证摘要保存到既有运行产物目录；不复制完整桌面、不默认保留正文或 Secret。恢复入口先验证前置条件，不只是从文件中的某个行号继续。

## 十一、从模式发现 SDK 缺口

```text
具体场景
→ 反复手写且易错的步骤
→ 可跨场景复用的机制
→ 现有 API 能完成到什么程度
→ 最小缺口与归属
→ 合同、失败边界、示例与验证
```

| 内容 | 默认归属 |
| --- | --- |
| 平台资源、真实输入、权限和执行生命周期 | 现有 native owner |
| 区域计算、候选筛选、公开 API 的少量组合 | Geometry／UI 等现有命名空间或 JS helper |
| 应用页面、标签含义、快捷键习惯 | 应用 helper／适配代码 |
| 订单资格、内容生成规则、发送或提交决策 | 普通 Recipe 与业务验证代码 |

一个候选至少说明两个不同类型场景，才能讨论进入通用层；这些用例只是设计依据，不能替代实际验证。扩展方式继续见 [Runtime API 扩展与定制框架](runtime-api-extension-framework.md)。

## 十二、如何检查方法有没有真正落地

| 检查项 | 完成判据 |
| --- | --- |
| 目标与授权 | 能用业务语言说明成功结果和禁止副作用 |
| 对象与状态 | 观察、状态解释、操作资格分别有依据 |
| 步骤粒度 | 每步有独立目标与可核对输出，不是机械分组 |
| 交接与有效性 | 下一步知道收到什么、证明了什么、何时失效 |
| 定位与来源 | 规则可复用，坐标按当前来源计算；歧义停止 |
| 超时与取消 | 说明真实支持范围，不能以外层 Promise 结束冒充 native 已停止 |
| 副作用与恢复 | 不确定写入先核对，不自动重发、重输或再次提交 |
| 通用性 | 至少一个跨类型对照场景，且不把业务字段搬进 SDK |
| 验证 | 分开报告确定性、集成、真机和业务结果证明；缺失证据明确列出 |

第二个对照场景可选择“在文本编辑器中替换指定内容并保存”：同样需要确认目标文档、准备输入数据、核对草稿、保存并检查实际文件，但不使用千牛的颜色、订单状态和发货规则。这是方法对照，不是该场景已经执行成功的声明。

方法完成的标志不是多了多少名词，而是：读者知道值得做什么、为什么这样拆、每步交出什么、什么时候不应继续，以及真正缺少哪一小块通用能力。
