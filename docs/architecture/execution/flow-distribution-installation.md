## 1. 最终方案

采用：**单文件交付、统一目录安装、宿主管理信任与授权、复用既有 Runtime 执行。**

```text
开发者完成自动化
→ 交付 .js / .odpkg / .odflow
→ 用户双击 .odflow，或把文件拖入 OpenDesk
→ 宿主校验、确认信任、取得必要授权、安装与注册
→ Flow 出现在 Script Runner
→ 用户明确运行
→ 现有 Execution / Goja 执行业务
```

普通用户不需要操作安装目录、公钥、Content Key、License 文件路径、设备私钥或资源相对路径配置。首次未知发布者确认、必要的登录/购买和 OS 权限仍由用户决定，不能把自动安装理解为自动替用户同意。

| 问题 | 决策 |
| --- | --- |
| 分发模型 | 对外接受三种文件，正式安装后一律一个 Flow 一个目录 |
| `.js` | 明文单脚本；直接导入，不强迫开发者建项目或写 Manifest |
| `.odpkg` | 现有受保护单脚本载荷；不承担 Flow 资源安装职责 |
| `.odflow` | 新增已签名的 ZIP 类分发/安装容器；正式发布、资源和商业交付的首选 |
| 公钥位置 | 允许随包携带；通过信任判断后由宿主登记，包内公钥不是信任根 |
| 授权与密钥 | 宿主按身份精确解析授权；每包独立 Content Key；设备私钥由 OS 安全存储管理 |
| 安装位置 | App 数据根下 `flows/<installId>/`；没有 `<version>/` 层 |
| 资源根 | 宿主绑定的 Flow root；与 shell cwd、下载目录、可执行文件位置无关 |
| 市场 | 复用相同格式、安装器、Trust Store、授权解析器和 Runtime |

本次落文只增加实施所需的明确约束：信任作用域、安装事务与恢复、运行中更新、资源上下文、旧目录迁移以及可执行验收要求；不改变上述选定模型。

## 2. 格式与安装目录

### 2.1 三种格式的职责

`.js` 不提供发布者认证或源码保密。直接导入时，OpenDesk 自动生成本地 Manifest、安装标识和安装记录；这些记录不能标记成发布者签名。

`.odpkg` 沿用现有加密、验签、设备绑定授权和内存加载机制。裸 `.odpkg` 只有在能够从已信任存储或可信注册信息解析公钥时，才可以自动验证；缺少公钥时明确说明缺少发布材料，不能静默信任包内声明或要求普通用户挑选 key。陌生客户的完整交付应使用 `.odflow`。

`.odflow` v1 必须签名，不再增加面向普通用户的“未签名 `.odflow`”安装路径。轻量未签名分享继续使用 `.js`。它不是新语言、第二套加密算法、独立 Runtime 或可以改写官方界面的宿主插件。

免费不等于没有解密机制。免费受保护 Flow 可以自动取得免费设备授权；不能靠内置全局 Content Key 实现“免费免激活”。保留既有 CLI 格式兼容，但没有可用合法密钥时必须明确不可运行。

现有 `.mjs` 等入口不因本设计被删除；本轮三种交付类型不是整个 Runtime 的格式白名单。

### 2.2 单一正式布局

```text
<appDataRoot>/
├── flows/
│   ├── <installId-A>/
│   │   ├── flow.json
│   │   └── simple.js
│   ├── <installId-B>/
│   │   ├── flow.json
│   │   └── main.odpkg
│   └── <installId-C>/
│       ├── flow.json
│       ├── flow.sig
│       ├── main.odpkg
│       ├── assets/
│       └── trust/
├── flow-data/
│   └── <installId>/
└── flow-state/
```

正式 OpenDesk 默认 App 数据根是 `~/.opendesk/apps/com.opendesk.desktop/`，Windows 的 `~` 指该用户主目录。实现必须复用 App 数据根解析逻辑及已有显式覆盖机制，不在 JS、Go、Scheduler 中分别硬编码第二个根。

`installId` 是宿主管理的稳定本地标识，不使用包提供的字符串直接拼接磁盘路径，不随版本改变。逻辑 Flow 身份绑定已验证的发布者身份与 `flowId`；显示名称不承担身份或路径职责。未知发布者自称相同 `publisherId`，不因此成为已有发布者。裸脚本使用本地身份，不获得官方/市场身份。

安装内容、可写业务数据、宿主状态分开。宿主状态记录逻辑身份、内容摘要、安装位置、信任/授权引用和状态，不复制第二份可执行 Manifest。签名 Manifest 在安装后保持原始字节，宿主不能向其中追加本地绝对路径。

已有授权存储保持现有 `os.UserConfigDir()/OpenDesk/protected-recipe` owner，不为目录名称统一而强制搬迁。这里的“全局”指当前 OS 用户的 OpenDesk 全局，不是所有系统用户共享授权。

## 3. `.odflow` 最小结构与完整性

普通已签名 Flow：

```text
hello.odflow
├── flow.json
├── flow.sig
├── main.js
└── trust/
    └── publisher.pub
```

受保护、带资源的 Flow：

```text
order-export.odflow
├── flow.json
├── flow.sig
├── main.odpkg
├── assets/
│   └── export-template.xlsx
└── trust/
    ├── publisher.pub
    └── license-issuer.pub
```

使用跨平台 ZIP 文件容器，不使用 macOS 专属目录包作为交付格式。v1 只接受一个根目录入口；授权公钥仅在需要该授权路径时携带。

### 3.1 Manifest 的最小职责

| 字段组 | 内容 |
| --- | --- |
| 格式与身份 | `schemaVersion`、`flowId`、`name`、`version` |
| 发布者 | `publisherId`、`publisherKeyId` |
| 运行 | `entry`、`minimumRuntimeVersion`、支持平台 |
| 完整性 | 文件相对路径、SHA-256、实际大小的清单 |
| 授权附加信息 | 受保护 Flow 的 `productId`、License issuer key 标识及获准用途 |

这是待实现格式的字段职责，不代表仓库已有对应 JSON Schema。实施时一次性冻结具体字段形状、必填项、限制和错误码，并由 writer、reader、签名验证器和测试共同使用同一契约；不得在各入口自行解释。

内层 `.odpkg` 的 `publisherId`、`productId`、`packageId`、`publisherKeyId`、`contentKeyId` 以已验签内部 Manifest 为准；外层不得重新授权一个不匹配的包。v1 默认外层与内层为同一发布者、同一获准签名身份，不引入第三方重新包装委托。

### 3.2 签名规则

`flow.sig` 对原始 `flow.json` 字节加明确的 Flow 格式域标识后进行 Ed25519 签名。不得与 `.odpkg`、License 或轮换声明复用签名消息域。具体字节编码必须写入格式契约和固定测试向量。

`flow.json` 的文件清单覆盖入口、资源和公开信任材料；不包含 Manifest 自身及签名文件，避免循环依赖。其他普通文件必须与清单完全一致，多、少、改任何一项均失败。拒绝重复 JSON 字段和未知格式版本；明确未知字段处理规则，不静默忽略安全语义。

读取公钥可用于候选验签，但成功不能直接改写 Trust Store。公钥是否具有发布/授权用途由外部信任记录、可信委托或用户明确批准决定。

`.odflow` 自身不提供资源加密。`assets/` 中内容可读；需保护的业务 JavaScript 应在构建时合入 `.odpkg`，不能把明文 helper 放在资源目录却宣称全部源码受保护。

构建器按显式文件清单打包；签名私钥、License 私钥、裸 Content Key、设备私钥、Token 和开发环境文件都不属于分发输入。公开材料必须用 public-key parser 验证，不能把私钥 PEM 改名成 `.pub`。秘密材料应位于发布输入树之外，不依赖扫描器识别任意字节是否为秘密。

## 4. 发布者信任

```text
包内公开材料
→ 候选公钥与签名验证
→ 官方根 / 市场证明 / 已有 pin / 用户确认
→ 宿主信任记录
→ 安装及后续运行校验
```

信任记录至少绑定发布者身份、公钥指纹、key ID、用途、信任来源、作用域、状态以及必要的轮换序号。不能只按发布者名称或 `publisherId` 字符串认人。

| 场景 | 行为 |
| --- | --- |
| 官方 Flow | 由发行应用内可信根或可信根签署的记录认证；包自称官方不生效 |
| 市场开发者 | 验证市场发布者证书/签名注册记录，绑定身份与公钥；认证不等于代码安全承诺 |
| 未知开发者首次安装 | 显示“未认证发布者”；默认只批准当前 Flow，单独提供信任此发布者的明确选择 |
| 已信任开发者 | 身份、获准密钥及用途匹配才免重复信任确认；新增权限和购买仍独立处理 |
| 同名或同 ID 换了公钥 | 不覆盖既有身份、Flow、pin 或授权；要求合法轮换或重新确认 |
| 已知撤销 | 按撤销策略拒绝，不能自动退回未知发布者继续安装 |

单 Flow 批准不能因底层保存公钥 pin 就隐式升级为信任该发布者全部代码。若现有 key provider 只检查 key 文件存在，需要新增信任作用域检查；其结果必须传递到真正执行边界。

UI 必须区分“密码学验签成功”“发布者身份已认证”“当前用户批准”“有权运行”。Manifest 中未认证的名称、网址、图标均当作不可信显示数据处理。

### 4.1 轮换与撤销

正常轮换声明绑定发布者、旧/新指纹、用途、递增序号和适用状态；由当前获准旧密钥授权，并验证新密钥持有证明，或由已有可信上级根重新认证。严格区分 retired 与 revoked；不能仅因旧 key 被退休就接受任意新 key。

旧密钥遗失、已撤销或疑似泄露时，不允许只靠包带的新公钥静默恢复；需要可信上级恢复或用户重新确认。官方信任不能由普通未知发布者确认代替。

Publisher 与 License issuer 分别轮换。可以借鉴 TUF 的角色、信任根与防回滚思想，但首版不要求搭建完整 TUF 仓库。离线设备无法即时获知新的服务端撤销，必须如实定义缓存有效期、在线刷新点和最大离线窗口，不能宣称离线即时撤销。

## 5. 授权与密钥管理

| 材料 | 长期 owner | 客户端行为 |
| --- | --- | --- |
| Publisher 私钥 | 发布者或其受保护签名服务 | 不交付到客户设备 |
| License issuer 私钥 | 授权发行方 | 不交付到客户设备 |
| 每包 Content Key / DEK | 发布者密钥库或受托授权服务 | 通过设备绑定加密信封交付；原生宿主内存解封 |
| Publisher / Issuer 公钥 | 包可携带；宿主信任存储管理认可状态 | 按身份、指纹、key ID 和用途解析 |
| License / Entitlement | 宿主授权存储 | 核对签名、主体、产品、包、设备、时间及撤销/防重放状态 |
| Device 私钥 | OS 安全存储 | 仅原生授权 owner 使用；不作为 JS 全局、环境值或普通 API 返回 |

macOS 复用 Keychain owner；Windows 复用 current-user DPAPI owner并补目标平台验证。不引入 `content.key` 旁置，也不引入所有 Flow 共用的 `global.key`。OS 保护不是对本机管理员或同用户恶意进程的绝对隔离承诺。

### 5.1 产品授权与 Package 密钥分离

```text
一次产品登录/激活
→ 产品权益：哪些 Flow、哪些版本、几个设备、多久有效
→ 安装某个 Flow
→ 自动取得该 Package 的设备授权信封
→ 用该 Package 的独立 Content Key 运行
```

一个产品可以包含多个 Flow；不同受保护包仍使用独立随机 DEK。不得把现有精确验证放宽成只检查 `productId`。包对产品的归属由可信发布及授权记录决定，不由包作者填一个同名产品 ID 就获得授权。

现有精确绑定 `publisherId / productId / packageId / contentKeyId / deviceId` 保留。上层产品权益协调可以自动取得现有包级授权，尽量不破坏 P1/P2 格式；同一购买不等于复用同一个 DEK。

离线可以批量导入已经签发的多个包授权；尚未发放的新包密钥不能离线凭空产生。新版本换 Package/Content Key 后由权益策略决定能否取得新信封。

### 5.2 激活服务与凭据

激活地址来自已验证的发布者/市场配置，按来源和产品作用域绑定。未知配置不得在确认前触发网络请求。市场登录凭据不能发送给包任意声明的地址；使用受限、适合目标 audience 的凭据。

延续现有 HTTPS、响应签名、设备绑定和防重放边界；不跟随恶意重定向或访问未经批准的本地/私有服务。参考授权服务只能证明集成合同，不可当成生产计费 SaaS。

激活可能已经占用远端设备名额，而本地安装提交失败：需要可恢复的幂等激活标识、补偿或明确待恢复状态，重试不能重复消耗名额。不能伪称本地文件事务可以回滚已经发生的远端副作用。

## 6. 统一安装链路

### 6.1 用户入口

必须支持 `.odflow` 双击、OpenDesk/Script Runner 实窗文件拖放，以及“安装 Flow…”文件选择。托盘拖放只是增强，不是唯一入口。不抢占系统 `.js` 默认关联；裸 `.js` 通过拖入/选择安装。

macOS 文档类型/打开事件和 Windows 文件关联/启动参数都进入同一原生安装服务。宿主未启动时启动宿主；已启动时转交现有实例。安全传递文件参数，不用 shell 字符串拼接路径，不把打开文档转换成执行脚本。

### 6.2 状态链路

```text
接收文件
→ 受限解析、私有暂存
→ 路径/条目/Manifest/平台/Runtime 兼容性检查
→ 全文件清单与外层签名验证
→ 必要的 .odpkg 内层签名及身份一致性验证
→ 发布者信任判断与用户确认
→ 产品授权、设备授权及密钥可用性判断
→ 事务式提交安装目录、安装记录与 Catalog
→ Runner 刷新
→ 等待用户明确运行
```

安装和授权检查不得执行业务 JavaScript。受保护包需要解密可用性验证时，直接调用原生验证/解密 owner并清理内存，不创建可执行源码快照。

用户取消时不注册可运行 Flow，不增加超出明确批准范围的全局信任。签名错误、内容不一致、身份冲突不得安装到正式目录。

缺少授权时可明确选择“安装，稍后激活”，其状态是 `needs-activation`，不是 ready。其他状态至少区分安装中、可运行、被阻止、需要修复；状态名称可沿用现有枚举，但语义不得合并成“成功”。无人值守触发不能弹窗偷偷获得信任或自动忽略待激活状态。

### 6.3 ZIP 与文件系统防线

| 风险 | 必须满足的约束 |
| --- | --- |
| Zip Slip / 路径逃逸 | 拒绝绝对路径、`..`、盘符、UNC、非法分隔符及不合法路径；实际写入也使用目录受限的安全访问 |
| 链接逃逸 | 拒绝 symlink、hardlink 描述、reparse point 和其他特殊文件；防止暂存/目标父路径被链接替换 |
| 跨平台别名 | 拒绝大小写/Unicode 规范化冲突、Windows 保留名、尾点/尾空格、ADS 路径及控制字符 |
| 重复/覆盖 | 重复文件和文件-目录冲突均拒绝；不向现有 Flow 直接解压 |
| 大小与炸弹 | 限制压缩包、实际解压总量、单文件、文件数和深度；以实际读取计数，不信任 ZIP header |
| 内容与签名 | 文件清单完全匹配；CRC/截断/结构异常/签名失败均拒绝；验证前绝不执行业务 |
| 检查使用竞态 | 不采用“检查路径安全后按普通路径再次打开”作为安全保证；优先符合项目 Go 版本的受限目录 API |
| 安装钩子 | 不执行 `postinstall.js`，不调用包内程序来完成安装或授权 |

限制值由宿主统一定义并测试边界；包不能自行提高限制。避免为了首版提前加入自解压、嵌套安装包或任意插件执行能力。

### 6.4 更新、恢复与卸载

同逻辑 Flow 保留 `installId`。同版本同摘要为幂等重复安装；同版本不同摘要拒绝普通更新；降级需要明确批准且不能绕过信任/授权防回滚。

运行期间绑定该次安装内容并持有运行租约；更新和卸载不能替换本次运行后续还需读取的资源。等待相关 execution 结束后再提交更新，不增加正式版本目录。

私有 staging、事务 journal 和短期回滚区由宿主管理，均不出现在 Runner 中；它们是事务工具，不是 `flows/<id>/<version>/` 的长期并存机制。用互斥、提交顺序和重启恢复保证目录与索引一致，不能假设跨平台非空目录替换天然原子。

故障注入覆盖解压、验证、激活、目录提交、索引提交和恢复点。失败应保留旧版本或恢复到明确不可运行状态，不留下被误识别为 ready 的半安装版本。

卸载一个 Flow 不删除其他 Flow 共用的发布者信任、产品权益或设备身份。可写数据是否保留由明确策略/用户选择决定；卸载本身不默认等于停用整个产品。

## 7. Flow 资源上下文与运行

拟新增只读上下文：

```javascript
Flow.root
Flow.resolve("assets/export-template.xlsx")
Flow.dataDir
```

这是实现目标，不是当前可调用 API。原生宿主从经过验证的安装记录/开发上下文绑定它，不从用户可伪造的 `source` 标签或 Manifest 的绝对路径推导。

`Flow.root` 是本次运行的资源根；`Flow.resolve` 只解析包内合法相对资源；`Flow.dataDir` 是该 Flow 的可写业务数据根。包资源与 `Execution.artifactDir`、snapshot、shell cwd、OpenDesk 可执行文件位置分开。

`Execution.scriptPath/scriptDir` 保持实际入口及其父目录的既有语义，不为迁就 Flow root 改成虚构路径。对安装后的入口，受保护脚本仍指向 `.odpkg`，不是解密后的临时 `.js`。

`Flow.resolve` 返回路径不意味着所有通用 File/Command 调用获得沙箱保护。宿主内部资源读取必须执行受限访问；对外语义应明确路径解析与强制文件访问隔离的区别。不用 `os.Chdir()` 修改整个宿主的 cwd 来模拟每次执行工作目录。

未安装的开发脚本不应被偷偷安装；保留当前直接脚本执行语义。需要开发态 Flow 上下文时显式建立，未绑定时返回明确不可用状态，不猜测安装身份或伪造授权。

### 7.1 唯一执行链路

```text
已验证 Flow / 安装记录
→ 信任与内容完整性预检
→ 已有文件加载入口
→ 普通脚本，或 .odpkg 验签/授权/内存解密
→ 既有 Execution / Goja
```

Runner、CLI、AI 和 Scheduler 的 Flow 调用应复用同一解析与加载 owner。内部可以扩展调用面，但不得为每个入口复制一套找资源、找 key 或解密逻辑。现有不支持受保护文件的 transport，在安全接入前必须明确拒绝，不能绕过授权转为明文内联。

Script Runner 从 Flow Catalog 获得稳定身份、显示名称、状态和入口，不再把“文件名以 `.js` 结尾”作为正式 Flow 能力边界。保留播放器式运行/停止/上一个/下一个/名称/列表，不重新设计整个界面，不显示扩展名来冒充友好名称。

### 7.2 不落地受保护源码

必须沿加载结果的可信 ProtectionInfo 传递保护状态，而非仅依赖用户文件名或丢失标记的包装对象。

Protected execution 不自动输出明文 `script_snapshot.js`、临时源码、source preview、源码片段错误页或解密缓存；系统日志/错误/artifact 只输出安全 metadata。不能仅去掉 Runner 的扩展名限制而保留原有明文快照路径。

授权失败、撤销、解密失败时业务 JavaScript 零执行。校验成功与失败、语法错误、业务异常、停止/取消等路径都必须测试宿主泄露面。公开脚本与授权受保护脚本的业务结果应等价。

禁止向 JS globals、Execution.env、子进程参数、日志或 artifact 注入 Content Key/设备私钥。原生 key buffer 用后清理；清理不等于对 Goja 内部副本、OS paging 或管理员内存提取的绝对控制。

安装完整性也不是恶意脚本沙箱；签名和授权不证明自动化安全。对第三方 Flow 拥有的 File/Command/桌面操作能力必须如实说明。包不得通过安装器覆盖官方 Shell、UI、菜单、品牌配置或其他发布者文件。

## 8. Flow 市场复用

市场负责开发者身份认证、包发布记录、发现、购买、产品权益和更新信息；交付同一 `.odflow`。安装时校验可信商品记录与包摘要、发布者、Flow 和版本一致。

保留开发者签名，市场证明通过独立证书或签名 metadata提供。文件从市场下载后经邮件转发，仍按同一规则验证；不能把下载来源直接当作无限信任。

首版需要实现可测试的市场信任证明和产品权益接入边界，不以真实市场、支付系统或生产密钥尚未配置为理由阻塞本地安装闭环。测试根/测试授权服务仅在隔离验收环境注入，不能进入生产默认信任或提供通用绕过开关。没有真实官方根配置时不得把测试 key 标为 OpenDesk 官方。

### 11.2 独立结果与泄露检查

测试使用可预测的资源读取/业务输出作为 Oracle；拒绝路径使用不可伪造的执行计数或副作用文件证明零执行。不能把“返回 JSON”“出现日志”“测试 mock 收到调用”当作业务完成。

受保护脚本包含不主动打印的唯一源码标记；检查安装输出、执行 artifact、宿主日志、源码预览和受控临时目录中是否出现该标记或测试秘密。构建输入区本来就有测试明文/测试 key，必须与被测输出隔离，不能扫描到 fixture 后误报，也不能因为输出日志没有标记就忽略快照目录。

临时测试 key/授权服务/设备状态在隔离环境中生成并清理；不读取生产私钥，不复用真实客户授权，不改变用户现有 Flow/产品名额。测试隔离支持不得演变为生产的信任/授权绕过开关。

### 11.3 运行与证据

实际测试数据、截图、日志、包、授权和临时秘密写入 `.runtime/tests/flow-distribution/` 或既有 runner 分配的证据目录；可复用测试源码/非秘密 fixture进入版本控制。

提供从仓库根目录可直接复制的一行命令，并原样验证；使用当前源码对应的 OpenDesk 主程序与匹配 UI host，不能用过期构建验收。Node-only mock 测试不等于 OpenDesk Runtime 或原生 UI 通过。

macOS/Windows 分别列明源码、build、Runtime 和 native/live 证据；没有目标设备就标记未验证。不能以跨编译代替 Windows 文件关联/DPAPI/拖放真机，也不能因没有另一 OS 就停止所有可执行开发。未经授权不启动 VM/Wine 或下载系统镜像。
