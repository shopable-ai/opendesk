# OpenDesk 对话工作台｜产品需求与实施设计

状态：产品设计 v0.3，2026-09-13。本文是拟实施合同，不是新 UI、通用 Catalog、自动组合、远程分发或真实桌面验收已经完成的证明。本次文档复核基线为 `master@9b06d8fedf385e0753e0d45d9b24cb12e6926e05`；实施前重新读取真实文件，不覆盖并行修改。第 3 节保留此前 Calculator 源码复核记录，不表示本次范围修订重新测试了代码。

**v0.3 范围修订：本产品界面是对话式助手，不把「手选任务 → 查看说明 → 填写参数」整合为另一条必需用户入口。该方式作为独立使用形态另行评估，不进入本助手 P0.1/P0.2 的功能清单或验收门槛；不因此删除或改造现有 Script Runner。后台能力目录可以保留，共用执行能力不等于必须共用一个界面。**

继续沿用 v0.2 的首期顺序：**先完成新建对话、对话列表、对话界面与持久化，再接入已存在的任务程序。复杂脚本的生产与组合近期由本地 Codex 配合 Recorder 完成，不是聊天框必须具备的能力。** 本文长期设计不应全部展开成本轮任务；当前下一轮只实施 P0.1。

## 1. 产品决定与边界

产品仍是 OpenDesk；「AI 助手」是对话工作台的用户名称；Calculator 是首个能力与回归案例，不是产品边界。

```text
生产侧：真实任务 + Recorder 示范 / 已有资产
  → 本地 Codex 按已有工作流理解、参数化、提取可复用方法
  → 普通 JS 任务程序与固定依赖
  → 独立验证适用范围 → 明确发布
  → 本地后台能力目录；以后可增加服务器分发

使用侧：对话中描述目标
  → 从后台目录查找已发布任务
  → 对话澄清 / 提议参数 / 展示当前任务依据
  → 参数校验、可信预览、授权与执行
  → 普通 OpenDesk JS → 实际步骤、实际结果与证据

没有匹配程序：会话内说明能力缺口 → 后续可保存生产交接需求
  → 不生成未经验证的代码并立即执行
```

「手选程序、填写参数再运行」与对话式使用是不同体验，不在此主链路增加第二个入口。未来独立使用形态可以复用相同的执行服务，但不要求本助手提供任务商城、脚本选择器或参数表单。对话内对当前请求进行必要的候选消歧、参数摘要审阅和确认，不等同于建设手选任务页。

近期不建设万能聊天编程 Agent，不让模型临时选择一串细小动作直接操纵桌面；也不要求工作流全部完成后才能交付会话界面。未来可以增加聊天内作者态或已限定的动态判断，但必须保留普通运行与生产/验证/发布的边界。

一个任务程序可以很复杂、依赖多个模块，也可以只接收少数参数；「通用」指在明确的应用、版本、平台、布局与输入范围内复用，不代表任意应用状态都可靠。

## 2. 需求任务树

- **普通用户通过对话使用已有能力**
  - 新建、切换、重命名、归档与恢复对话；关闭重开仍可查找历史。
  - 自然语言描述目标，在同一对话中澄清、补充和修改要求。
  - 查看当前任务的目标应用、实际操作影响、参数、程序版本和真实执行结果。
  - 停止、修正要求、查看错误；不要求输入终端或脚本路径，不强迫先选择程序和填写表单。
- **开发者生产可复用程序**
  - Recorder 保存示范与证据；Codex 消费已有任务包，不从零重建所有工作流。
  - 先得到一个可验证的完整任务，再提取确实可复用的方法。
  - 从实际代码形成输入输出、支持范围、依赖与验证说明，经资格与发布后进入后台目录。
- **多个方法组合成完整任务**
  - 基础 Runtime 操作由现有 API 承担；应用方法表达稳定业务步骤。
  - 任务脚本组合方法；更大业务仍是普通 JS 任务脚本，不新增复杂执行 DSL。
  - 数据显式传递，前后置条件与副作用检查不能因拆分丢失。
- **执行可检查、可验证**
  - 看真实源码、实际入口、参数绑定和步骤证据；不展示替代性的伪代码冒充执行代码。
  - 区分结构合法、意图正确、目标正确、执行正确、结果已观察。
  - 模型回复、UI 消息和历史记录不能反向成为执行授权。
- **分阶段产品化**
  - 会话基础不依赖模型安装、任务库非空或桌面权限授予。
  - 先本地后台目录，后服务器分发；存放在哪里与在哪台机器执行分别定义。
  - 助手接入既有 App Shell，不把不同工具的使用页面合并，不造平行主程序。

## 3. 当前代码复核：能证明什么，不能证明什么

以下是 v0.2 保存的源码复核记录，没有真实 Codex、Calculator、Windows/macOS UI 的本轮运行证据，也未重跑全部 mock 测试。实施时仍须以最新源码为准。

| 对象 | 源码事实 | 对产品设计的含义 |
| --- | --- | --- |
| `planner.js` | 只返回固定任务 envelope，不生成 JS、Shell、路径或坐标 | 当前验证的是现有程序参数化调用，不是临时生产自动化的能力 |
| `task-contract.js` | 限定字段、两个 task、按钮字符、表达式形状、数字长度与乘数格式；预览从校验后的参数生成 | 结构校验不是自然语言意图正确性证明；预览要让用户能复核关键参数 |
| `index.source.js` | 按 task 调用 `pressAndRead` 或 `twoStage`，使用任务内 signal/progress | 新助手复用既有校验和执行逻辑，不重新写另一套 Calculator 接线 |
| `calculator.js` | `twoStage` 先实际读取 firstResult，再形成 multiplier 各位、×、firstResult 各位、= | 当前第二段没有直接用模型预测值；需在界面展示这一动态数据绑定 |
| Calculator 读数与边界 | 检查 active window/身份/尺寸；Accessibility 需完整且只有一个 numeric staticText；连续两次相同才返回 | 这些是检查机制，不证明所有布局、语言、应用版本或输入都已通过 |
| 两阶段限制 | firstResult 只允许可重新输入的 1–12 位非负整数字符串 | 负数、超长等结果会停止；不能把任务描述成任意数学计算器 |
| 模块校验 | Calculator 底层按键检查与上层 envelope 语义校验粒度不同 | 对话接入不能直接绕过完整任务合同调用底层模块；复用安全门不意味着新增手选 UI |
| `index.js` | 构建时生成的 classic-script bundle，包含来源模块摘要 | 不等于本次规划新生成脚本；查看源文件还须对应实际 bundle 版本 |
| 现有消息/UI | 内存消息拼接，最多 60 条；已有取消和旧确认保护 | 不能只增加一个「新对话」按钮就声称实现多会话和运行历史 |

源码依据：[planner](../../examples/ai-workflows/chat-calculator/planner.js)、[task contract](../../examples/ai-workflows/chat-calculator/task-contract.js)、[calculator](../../examples/ai-workflows/chat-calculator/calculator.js)、[UI/controller](../../examples/ai-workflows/chat-calculator/index.source.js)、[session](../../examples/ai-workflows/chat-calculator/task-session.js)、[实际 bundle](../../examples/ai-workflows/chat-calculator/index.js)。

例如用户要求第二次乘以 6，而模型给出合法数字字符串 7，现有 envelope 校验并不与原请求进行语义比较；它只能判定 7 是允许的乘数。这是校验职责的边界，不是已通过一次错误执行的测试结论。产品应提供显式参数绑定、会话内的关键值审阅与需求修订，以及代表性自然语言测试，不能用第二个模型说「正确」替代验证，也不因此要求建设参数表单。

## 4. 第一阶段：先完成真正的多会话工作台

### 4.1 页面与必须交付的功能

```text
OpenDesk · AI 助手
  左侧：新建对话 / 最近对话 / 已归档对话
  中间：当前会话标题 / 消息列表 / 输入框 / 发送与停止
  辅助：模型连接状态与必要设置
  后续 P0.2：当前任务卡，以及按需打开的代码、参数和结果详情
```

不在侧栏增加任务库、手选任务、参数表单或脚本商城。第一阶段只要求会话基础真实成立，任务详情随第二阶段接入；不要显示尚不可用的执行、代码查看或自动运行按钮来冒充实现。

| 功能 | 明确行为 |
| --- | --- |
| 新建对话 | 创建独立 ID、消息与草稿；不启动模型，不运行脚本，不自动继承上一会话的确认 |
| 对话列表 | 按最近活动排序，显示标题和活动状态；支持切换、重命名、归档及恢复 |
| 标题 | 默认从首条请求确定性截取，可手动修改；不强制多调用模型生成标题 |
| 消息 | 按独立消息对象保存角色、文本/任务引用与状态；长内容可滚动或分页 |
| 持久化 | 重开 App 恢复会话、草稿和已发生事实；不会恢复后自动重跑 |
| 连续交流 | 当前会话历史和其他会话隔离；后续任务澄清绑定原 task/request |
| 停止 | P0.1 停止当前模型请求；后续明确区分桌面 Run 的停止，不把全局退出伪装为单任务取消 |
| 未连接模型 | 仍可新建、浏览历史、修改标题和保存草稿；发送时给出真实配置/连接提示 |
| 暂无匹配能力 | P0.2 接入执行后，在当前对话解释限制；P0.1 不要求先建立任务目录或生产入口 |

首期不要求手选入口、参数表单、附件、语音、联网搜索、会话分支、云同步、批量执行、在线脚本生产或自动组合。可以先使用分页会话/消息列表；分页只限制视图，不截断持久化历史，不能把 60 条文本拼接扩大为另一种不可追溯存储。

模型连接使用已有受控 Agent/LLM owner：已连接时应能返回本次真实回复并支持取消，未配置或不可用时状态诚实。普通聊天不拥有文件/命令/桌面操作权，不因接入 Agent backend 就自动开放作者工具。测试适配器只用于明确标注的测试，不作为默认产品回复。

### 4.2 最小数据关系

```text
Conversation
  → Message
  → Task（后续当前目标，可没有）
      → PlanRevision（后续已校验方案，可没有）
          → Run（后续一次执行尝试，可没有）
              → Step events / Observations / Artifacts
```

P0.1 只需实际实现会话、消息、草稿、请求归属与持久化；Task/Plan/Run 的边界为后续接入预留，不强制本轮创建空壳框架。普通文本消息不需要创建 Run。一个任务可以修订和多次运行；一次重试对应新 Run。消息编辑、重新生成、重命名和归档不能改写真实运行事实。

发送时冻结 conversationId、messageId、requestId；异步回包按这些身份归属原会话，不能写入回包时正在选中的会话。切换会话不取消原请求；停止后迟到回包不能被标成有效完成或形成可执行新任务。后续 Run 事件还需 taskId、runId、sequence 与计划修订引用。

P0.1 可限制一个在途模型请求；切换和新建仍可用，其他草稿可保存；再次提交时明确告知占用，不做隐形队列。后续桌面执行首期同样串行，多会话不等于同时抢占鼠标。

P0.1 优先归档而非复杂删除；归档活动会话须先提示并停止请求或明确拒绝，不留下不可见且不可取消的请求。未来删除活动会话需先处理活动任务并明确运行证据的保留/删除策略，不能留下无法停止的运行。崩溃后的活动请求显示「已中断」，未来未知 Run 显示「已中断/待核验」，旧确认失效，不显示成功或自动补发。

## 5. 脚本的正确拆分粒度

### 5.1 三层即可，组合任务不另造执行系统

| 层 | 内容 | 默认消费者 |
| --- | --- | --- |
| Runtime 基础能力 | 查找、点击、键盘、窗口、文件等已有 API | 应用方法 |
| 应用操作模块 | 查找联系人、打开并核验会话、准备消息、提交消息等普通函数 | Codex 和任务程序 |
| 任务程序 Recipe | 完成用户目标的 JS 入口；可组合多个方法或其他受控业务模块 | Chat Runner，经后台目录解析 |

更复杂业务依然是第三层的 Recipe。例如「读取报表后给指定人发送摘要」可以复用报表和消息模块，但它是一个需要独立验证的新任务，不因两个模块分别可用就自动具备组合资格。

**拆分的是职责和可复用函数，不是每次点击都成为一个独立 .js 程序、Skill、CLI 子进程或目录条目。** 同一应用的若干小方法可以先放一个模块；只有形成稳定复用边界时再拆文件或公共库。先做完整任务，再提取共用方法，不先设计万能动作语言。

### 5.2 可组合方法的最小合同

| 要点 | 必须说明 |
| --- | --- |
| 输入与来源 | 用户参数、上一方法返回值、现场观察或显式配置；不得读未知全局变量 |
| 前置条件 | 目标应用/账户/会话、允许界面状态与所需资源 |
| 返回值 | 可被下一方法使用的业务对象或观察值；不能只有 console.log |
| 后置验证 | 如何确认动作真的达到下一方法需要的状态 |
| 副作用与失败 | 是否发送/覆盖/删除，错误如何停止，哪些状态属于未知 |
| 取消、超时与重试 | 共享同一任务上下文，是否允许重试，哪些动作禁止自动重试 |

以上可以通过普通函数签名、已有合同说明和测试表达；不要求给每个函数建立一份大型 JSON schema。公开任务边界仍必须使用既有输入/输出合同。

同一桌面任务默认在同一个受管 Execution 内调用模块方法，共用授权目标、取消、截止时间、步骤记录和桌面资源占用。不为 search/open/send 每一步启动一个 OpenDesk；也不复制现有 Execution/Command owner。

前置检查不是永久通行证。窗口、会话和输入内容在实际副作用前仍需核对。UI 句柄或现场会话对象只属于当前 Run；不得跨重启直接恢复旧句柄。跨 Run 使用上一结果时传持久化 Observation 引用，再做适用性/时效检查。

模块 import 不得触发桌面动作；固定依赖版本/内容。维护者构建可以打包，但当前 classic 入口应保持可运行；不能把 Node ESM 的测试通过当作 OpenDesk 的 .js 入口通过。

## 6. 微信例子：组合的是业务语义，不是裸点击

以下为设计示例，不表示仓库已有这些微信方法，也不假定任何 UI 身份字段一定可读取。

```text
用户目标：给指定联系人发送指定文本

任务程序
  → 检查目标应用与当前发送账户
  → 在已授权范围内查找联系人
  → 根据可验证身份信息消除同名歧义
  → 打开并核验目标会话
  → 准备消息并检查是否覆盖已有草稿
  → 展示确切账户、收件人、正文与附件
  → 获得绑定此次发送内容的确认
  → 发送前重新核对会话与草稿
  → 提交一次发送动作
  → 观察客户端结果，记录能证实的状态
```

推荐的应用方法边界可为 `findRecipient`、`openVerifiedConversation`、`prepareMessage`、`submitMessage`、`observeSubmission`；名称仅表示拟议模块函数，不是 OpenDesk 公共 API。单个方法内部可以执行多次点击或读取。

`findRecipient` 不得默认选择同名搜索结果中的第一人；信息不足时交给用户确认或停止。`openVerifiedConversation` 返回基于现场观察的目标会话信息，后续方法消费该结果，而不是再次猜测姓名。`prepareMessage` 不隐式发送；已有草稿的覆盖也是需要说明的影响。

联系人查找、导航和草稿填写本身也有影响；准备阶段要处于明确允许的范围。最终确认绑定实际账户/目标/内容；等待期间发生变化则旧确认失效。批准发送以后不应再调用模型重写正文。

一次鼠标点击返回，不等于消息已送达。客户端出现本次发送记录，可作为相应的本地可观察证据，但不能无依据升级成收件人已收到或已读。前后快照和时间边界要能区分旧的相同内容，不能仅搜索到相同文本就宣称本次成功。

发送后超时、崩溃或读数失败可能处于「已提交但结果未知」。记录这类状态并核验，不自动重发。runId/idempotency key 能防重复发起本地命令，不能让没有幂等协议的外部 UI 保证 exactly-once。更大的组合任务失败时保留已完成前缀；不能因最后一步失败重跑全部发送动作，也不自动撤回消息作为补偿。

助手从后台目录解析完整的「发送文本消息」任务，在当前对话展示其依据。作者使用应用方法库；不要把所有底层方法都暴露给普通聊天模型任意组合。需要单独发布「查找联系人」时，它也应有独立业务合同、范围和验证，而不是因为函数存在就自动公开。

## 7. Codex + Recorder 的最小生产闭环

复用已有 Human-to-Recipe / Agent-to-Recipe / Existing Assets 合同，不新增平行工作流：

```text
需求与允许范围
→ 已有任务包 / 一次真实示范 / 对应应用证据
→ Codex 整理业务步骤，去掉探索和无关操作
→ 普通 JS 完整任务，参数化输入、Config 和 Secret 引用
→ 需要时提取可组合应用方法
→ 验证不同参数、状态变化、取消及失败边界
→ 冻结候选和依赖，独立 qualification
→ 用户/维护者明确 publish
→ 后台目录可发现
```

允许先交付一个完整 JS 入口，不把「必须拆成很多文件」作为门槛。录制出来的 raw/basic 脚本是生产输入，不因为可以回放一次就自动成为可公开任务。

最小可交付的逻辑内容：实际入口与依赖、支持范围与输入输出、所需权限/模型/副作用说明、来源和验证引用。沿用 CapabilityDefinition/CandidateManifest/QualificationRecord/CatalogEntry 的引用方向，不把可写 `qualified: true` 当资格，也不让 Candidate 反向引用下游资格造成循环。

内部方法先通过同包 exports、源码和说明被 Codex 复用；近期无需另建一个巨大方法注册平台。跨多个任务抽出共享库后，固定依赖闭包并验证组合；库升级不得悄悄替换正在运行或已确认的版本。

没有任务时，助手后续可保存包含需求、目标应用、示例输入/结果要求与已有证据引用的生产交接包。材料由用户明确交给本地 Codex；不要假装已自动启动其本地会话。生产完毕后刷新后台目录形成新的计划和确认，不偷偷恢复原请求执行。此交接属于后续阶段，不阻塞 P0.1 会话基础。

## 8. 后台能力目录：服务对话解析，不是手选页面

### 8.1 单一对话式使用链路

```text
当前会话自然语言请求
→ 宿主过滤可信目录 / 查找候选
→ 会话内澄清目标、必要时消除候选歧义
→ 提议参数并解析已发布版本
→ 结构与业务语义校验
→ 绑定参数来源和代码闭包
→ 当前就绪检查
→ 当前任务可信预览 / 用户确认
→ 最终现场检查 → 执行 → 真实结果
```

模型只看经宿主过滤的公开任务说明与 schema，不把所有源码塞入每次模型上下文。少量任务先用名称、别名、应用和关键词；有实际规模需求再加语义检索。相似度用于排序，不用于签发权限或证明适用性。

找不到时返回缺口；缺参数时在当前对话澄清；多个可能对象时在当前任务内说明区别并请用户确认；未安装或环境不适用时说明受阻原因。不能默认运行最相似的程序，也不强迫用户跳到另一个选择页重新开始。

用户修改要求产生新的计划修订，原确认失效。参数摘要和代码详情是对本次请求的审阅工具，不是另一个手选运行入口。纯确定性 Recipe 的实际执行不必依赖模型；自然语言解析和任务本身的模型调用仍按既有 modelPolicy 分别管理，不能宣称整个对话链路都离线可用。

### 8.2 可发现说明必须绑定实际代码

后台目录从现有发布合同投影：名称/id/version、做什么/不做什么、输入字段和输出、平台/应用适用范围、权限与副作用、入口和依赖引用、资格/发布/撤销状态、后续的安装状态。模型说明、参数摘要与实际验证器同源，不各写一份漂移的合同。

描述可以由 Codex 根据源码辅助生成，但发布时需交叉检查「字段 → 导出参数 → 实际用途 → 输出」；不能仅相信模型自报。目录只读取受信 metadata，不通过 import/eval 任意用户脚本来获得说明。一个小型随产品发布的本地清单即可开始，不要求先做网络市场，也不要求有可浏览任务库的页面。

未来另行建设手选运行或快捷任务产品时，可以共享现有安全校验和执行服务；那是独立范围，不进入本助手的交付条件。已有 Script Runner 的开发者任意脚本入口保留，但它不绕过普通助手的可信任务门。能力卡片若仅用于展示示例问法，也不是本轮必需组件，不能借此重新引入任务选择器与参数表单。

## 9. 代码、参数与正确性可视化

### 9.1 不只提供「查看主脚本」

建议详情按三层呈现：业务步骤 → 本次参数与数据绑定 → 真实文件/依赖。技术详情提供概览、参数、源码、实际入口、步骤记录、结果证据；开发预览版显著可见，正式版默认折叠。这些是 P0.2 的执行透明度目标，不强制在 P0.1 创建没有真实数据的详情页。

以当前 Calculator 为例：

```text
calculator.twoStage
  buttons ← 本次用户请求 / 用户在对话中明确修订的按钮序列
  multiplier ← 本次请求或明确修订中的第二次乘数
  firstResult ← 本次 Run 的第一次显示区读取（运行前未产生）
  第二段输入 ← multiplier 各位 × firstResult 各位 =
  finalResult ← 本次 Run 的第二次显示区读取
```

执行前显示 firstResult 的来源占位，不填模型预测数字；执行后显示实际值、实际形成的第二段按钮和对应步骤。用户可看到 `calculator.js` 的业务函数、`index.source.js` 的调用接线，以及 `index.js` 的实际 bundle；不是每次都要生成一份新实现。

组合任务的「本次执行程序」包括真实入口、实际依赖文件/导出/版本、实际走过的步骤；不能只展示一个包装函数隐藏其调用代码。预览由程序描述中的步骤说明形成，并与运行事件/测试校核；不要求任意 JS 静态分析能推导全部控制流，也不为此新增脚本解释器。

参数出处至少区分用户输入、明确默认值、已保存配置和具体 Run/Observation；未知来源不直接执行。「用刚才的结果」必须绑定可识别观察，多义时澄清。敏感正文的模型修改应显示出来，审批以后禁止静默再生成。

### 9.2 五种正确性分别验收

| 正确性 | 依据 |
| --- | --- |
| 任务选择正确 | 目录范围、会话内关键意图确认与必要的候选消歧 |
| 参数正确 | 同源结构校验、业务语义校验、关键值和来源展示、代表性语言测试 |
| 程序正确 | 实际入口和固定依赖的独立测试与适用资格 |
| 当前执行正确 | 目标账户/对象/窗口、必要状态、现场检查与实际步骤 |
| 结果可证实 | 真实观察、业务后置条件与诚实的未知/部分完成状态 |

源码可见帮助检查，不单独证明正确。结构化输出只是第一道门。测试 expected 可以作为独立 oracle，但不能成为业务脚本输入或结果来源。

### 9.3 文件安全与所见即所执行

真实文件只读查看、复制、复制路径、在文件管理器显示和受控编辑器打开；路径由宿主的受信文件引用解析，不执行模型提供的 Shell。初期不内置直接修改生产脚本的 IDE；修改形成新候选和新验证。

计划和确认绑定精确参数、目标/影响范围、能力版本和实际入口/依赖摘要。变更使旧确认失效；执行使用已固定的代码内容/不可变部署，不先查可变路径 hash 后又读取另一份字节。源码和 bundle 映射缺失时明说未验证一致，不能伪装。

摘要证明内容一致，不证明发布者可信或代码安全。原始模型日志、Secret、用户隐私和内部指令不因为开发模式就默认显示或导出。展示代码不执行代码，折叠状态不改变授权。

## 10. 本地与服务器：先分清存储、分发和执行

近期只要求本地受信后台目录。服务器阶段可以承载目录、版本和程序包；这不意味着服务器能够直接操作用户本地的微信或计算器。安装与分发可由独立管理流程负责，不因服务器存在就把手选目录页塞回助手。

```text
服务器目录（未来）
→ 经授权确定固定版本
→ 下载到暂存区
→ 验证发布来源、包完整性、路径与依赖闭包
→ 检查 Runtime/平台/资格适用范围
→ 明确安装到本地后台目录
→ 本地现场预检与授权
→ 本地 OpenDesk 执行
```

系统状态区分可发现、未安装、已安装但受阻、当前可用、需升级/重验、已撤销；助手在相关任务消息中解释必要状态。不能把任何下载包视为已资格化能力，也不从模型输出 URL 直接拉代码执行。签名/摘要只证明相应身份或内容，不替代安全审查与本地就绪检查。

多用户版本需要认证、访问控制、版本撤销、依赖锁定和升级回退；任务运行中不热更新其依赖。共享目录是代码/描述共享，不默认上传私有聊天、凭证或执行证据。

若以后增加远程执行节点，必须单独声明执行机器、会话/账户、安全连接和授权；不得把任务目录功能悄悄扩展成远程桌面控制。云同步、多租户、网络方法市场不阻塞 P0.1/P0.2。

## 11. 服务、文件与现有主应用整合

### 11.1 最小责任划分

| 模块责任 | 内容 |
| --- | --- |
| Conversation Store/Controller | 会话、消息、草稿、归属、切换与保存 |
| View/Renderer | 消息与当前任务卡展示，发送用户意图 |
| Task Service | 复用既有规划/解析、校验、授权、运行、取消与真实状态 |
| Artifact Store | 代码引用、参数、运行记录与证据的安全存取 |
| 现有 Catalog/Permission/Agent/Execution owners | 继续拥有其权威协议，不由助手重写 |

这些是责任边界，不要求独立进程、微服务或一对一文件。首期可以少量模块，避免一开始建立几十个空壳。

产品模块维持拟议 canonical 路径 `apps/opendesk/assistant/`，建议包含入口、controller、view.html/view.css 与会话存储；任务服务和产物存储随 P0.2 接入。Calculator 和其他应用模块属于能力资产，不在助手里复制按键表。示例保留为薄入口/固定回归；发行包不能运行时依赖仓库 examples 路径。

由现有 App Shell 创建一个助手 controller，并统一分发助手打开 action；优先复用当前已存在的 AI/助手入口。没有入口时，在系统托盘/主菜单增加「AI 助手」，作为本轮正式可达入口，不要求用户输入启动命令。重复打开使用同一个逻辑助手实例；实际接线以实施时最新 App 源码为准，本文不把拟议 action 名当作已实现接口。

若 Script Runner 或 Recorder 已有助手快捷按钮，只连接同一入口，不嵌入第二套聊天界面。本轮不要求给两者新增按钮或合并它们的操作页面，也不在助手侧栏添加手选任务页。首次打开、复用、关闭后重建可独立验收，不必同时完成候选/脚本数据交接。

首期保留 Script Runner 默认启动与全部旧菜单。助手成熟后再决定普通用户默认首页，不立即覆盖主产品行为。未来 Runner 可传脚本/版本引用，Recorder 可传候选/证据引用；未发布候选不能直接进入普通任务执行，跨工具生产交接不阻塞本轮。

### 11.2 生命周期与资源

重复打开复用助手窗口，关闭后以当前 ui 合同允许的新 window id 重建。窗口销毁不卸载 App 全局 action listener。P0.1 切换会话不取消原模型请求；关闭助手窗口默认停止活动请求并保存状态，再次打开恢复历史但不自动重发。

后续切换会话不改变活动 Run；隐藏/最小化运行必须有清晰状态与托盘停止入口；关闭活动助手窗口首版默认请求停止并保留记录。退出整个 App 走现有统一取消和子进程清理。

未来桌面互斥必须覆盖助手、Script Runner、Recorder 回放和计划任务；仅在一个会话禁止双击不够。资源等待后最终预检与授权有效性需再检查；未知状态 fail closed。不把停止等同撤销，不在未实现安全检查点前显示暂停/继续。该桌面执行协调不作为纯会话 P0.1 的前置开发任务。

### 11.3 持久化

使用既有产品路径服务的 appDataRoot，不写安装包，不硬编码个人路径。拟议位置：

```text
<appDataRoot>/assistant/
  conversations/<id>/conversation.json
  runs/<runId>/plan.json
  runs/<runId>/manifest.json
  runs/<runId>/events.jsonl
  runs/<runId>/result.json
  runs/<runId>/artifacts/
```

P0.1 只落地所需会话数据，不为后续 Run 预建假记录。小规模可先用版本化 JSON/JSONL 和单写入者、原子替换/恢复协议；不能假装未发布的 File API 已支持事务。实现时核对当前文件能力；无法保证完整写入则补最小能力，不直接并发覆盖整份索引。会话数增长后可替换存储，不改变会话/Run 身份。

写入失败必须显示；后续执行时还需停止需要持久证据的关键提交。崩溃恢复不重发模型请求或重放副作用。日志有界、历史有保留/删除政策，执行证据与普通消息清理分开处理，导出先脱敏。`.runtime/` 是开发证据路径，不是普通用户必须认识的目录。

## 12. UI 技术选择与执行策略

### 12.1 首轮 UI

继续优先使用当前 Custom UI 做薄界面，但第一交付是有独立数据模型的会话产品，不是原示例改标题。`ui.createWindow()` 禁止任意业务 script/inline handler/远程 URL，`ControlHandle.update()` 是允许字段的非结构更新；不能假定 React、任意 DOM 增删、details、代码高亮或虚拟列表已经可用。实施前以最新 API/类型/源码核验这些边界。

可先利用经实机验证的 button/text/value/visible 等受限状态做有界分页会话和消息视图，保持独立消息语义；折叠/代码详情采用实际支持的控件。若必要交互无法由当前 surface 合理承载，补充窄而可测的 UI 能力；不要反复销毁主窗口模拟消息刷新，也不要把所有消息长期挤进一个文本标签就算验收通过。

后续富交互可以采用受信、随包交付的 Web renderer，并评估 assistant-ui。v0.2 保存的官方参考包括 ExternalStoreRuntime 与 Threads；这些只是后续评估线索，不是本轮必须安装的依赖。OpenDesk 的 Run/授权依然由 Task Service 所有，前端 thread 状态不是第二套执行引擎。

不整套 fork LibreChat，不放开所有普通 Custom UI HTML 的脚本权限。受信应用前端通过受控 submit/revise/approve/cancel/read-artifact 桥接，不直接取得 File/Command/mouse/eval。模型内容按数据净化，限制导航和资源来源；浏览器调试入口若存在，需本地绑定、认证及 Origin/CSRF/DNS rebinding 等防护。

前端工具可用于维护者构建，不变成用户必须安装的 Node、Docker 或开发服务器，也不表示更换 OpenDesk JavaScript Runtime。WebView2/平台可用性按实际能力诊断；Windows Runtime 可用不等于当前 Calculator 或拟议微信任务已支持 Windows。

### 12.2 运行模式

保留仅规划、审阅后执行、未来已授权安全任务自动运行三种模式的设计。P0.1 只实现会话，不增加未接通的执行模式选择器；P0.2 默认审阅后执行。自动模式必须等到精确资格、参数子域、权限/就绪、目标/影响范围、预算/超时、桌面资源与取消保护可验证后才启用。

发送、删除、覆盖、付款、安全设置等敏感动作仍需相应强确认；模型自报低风险无效。暂停仅在安全恢复合同实现后开放。重新生成回答、再次运行任务、打开历史、展开代码分别走不同动作；后三者中的只读操作不隐式运行。

## 13. 分阶段实施与完成标准

| 阶段 | 可独立验收的最小交付 | 不作为本阶段前提 |
| --- | --- | --- |
| P0.1 会话基础 | 新建/列表/切换/重命名/归档恢复、消息和草稿、持久化、真实连接状态、取消与会话归属、可从主菜单打开的独立助手；已有受控模型适配 | 手选任务页、参数表单、任务目录实现、通用脚本生产、微信自动化、自动组合、自动执行 |
| P0.2 对话调用已有任务 | 后台小目录供对话解析、会话内任务卡与澄清、完整校验、实际代码/参数、确认/停止、运行记录；Calculator 在其已验证范围接入 | 手选运行体验、在线编程、远程执行、复杂检索 |
| P0.3 生产接入与组合 | Codex+Recorder 交接、应用方法提取、第二个真实任务、组合合同/依赖锁定/独立资格；非危险场景先验收 | 万能方法市场、运行时任意 DAG |
| P1 分发与高级体验 | 受信服务器分发、富聊天、满足条件的自动模式、成熟后主首页调整 | 把独立手选/快捷任务产品合并进助手，或全部一次性交付 |

手选运行作为独立使用方式另行评估，不是本表被延期后仍必须实现的一项助手功能。现有 Script Runner 不因本表改变。UI/store 可以使用明确标注的测试适配器验证异步、失败与长消息；mock 不能对用户展示成真实模型/桌面成功。第一阶段的交付分数只代表会话基础，不代表完整自动化产品已经满足发布标准。

### 95 分以上的评价口径

设计评估与实现验收分开。设计评估采用：需求/范围 20、组合与复用 20、执行可信度 25、会话体验 20、分发演进 15，总分 100，目标至少 95。发布验收按所发布阶段逐项提供真实证据；没有实机证据不能填写虚假的产品通过分数。

越权发送、错误收件人、重复副作用、会话串线、隐藏执行或伪造真实结果属于硬失败，不能用其他项目得分抵消。Windows/macOS 的实际支持范围分别验证。现有 golden 与历史 mock 不自动转移到新模块、新组合或扩大后的输入域。

## 14. 本版变更与交付边界

本版更新同一产品文档，不建立平行架构或第二套 schema。继续保留真实代码可见性、受限 UI、主应用生命周期、权限、安全自动运行与分发边界，以及 v0.2 的作者先行供给、方法级组合和参数正确性区分。

v0.3 取消 v0.2 的「双入口必须一起建设」决定：同步移除主链路、需求、侧栏、P0.2 和 T01 验收中的手选任务/参数表单要求。后台能力目录继续服务自然语言路由；手选运行只作为独立使用方式另行评估，不混进助手，也不被删除出已有 Runner。

近期交付顺序保持：**P0.1 对话基础 → P0.2 对话调用已有任务 → P0.3 Codex/Recorder 生产与组合接入 → 服务器分发和高级体验。** 当前执行提示词只实施 P0.1：真实入口、新建对话、对话列表、消息与草稿、保存恢复、受控回复和取消；不能以长期设计为由扩大为完整自动化平台。

本次只修改设计文档，未创建 assistant 实现模块，未修改现有 Calculator bundle、默认首页或执行确认策略；未执行真实 Codex、微信或 Calculator 测试。后续实施必须交付实际代码、必要测试与本阶段证据，不仅输出方案或审计报告。
