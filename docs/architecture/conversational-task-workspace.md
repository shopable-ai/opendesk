# OpenDesk 对话工作台｜产品需求与实施设计

状态：拟实施产品设计，2026-09-13。本轮交付需求与设计文档，不代表新界面、代码查看器、自动执行、通用 Catalog 或发布验收已经实现。

源码检查基线：`master@99df0ef902f98b56a3bcf0fa10c8f8d2e7d201ce`。其他会话可能继续修改 master；实施前重新读取当前文件，不覆盖并行改动。

## 1. 产品决定

**产品是 OpenDesk，主要交互页面是「AI 助手」，内部称为对话工作台；Calculator 是首个可测试能力，不是产品名称、专用聊天协议或主界面架构。**

目标不是把「规划 → 执行」两个按钮做漂亮，而是建立一个普通用户能完成任务、开发者能追踪执行依据、能力能持续增加的桌面产品入口。

```text
OpenDesk Desktop / 统一 App Shell
  → AI 助手：描述任务、澄清、查看方案、授权、执行与结果
  → Script Runner：脚本资产、参数化运行与开发者工具
  → Recorder：采集示范、生成候选与能力生产
  → Scheduler / Runtime Log / Permissions / Inspector：复用既有入口

AI 助手
  → 受控规划与能力解析
  → 宿主生成可信任务卡
  → 冻结参数、实际代码版本与授权范围
  → 确认或满足既有授权的自动运行策略
  → 普通 OpenDesk JavaScript
  → 真实 Observation、执行事件与结果
```

近期增加独立 AI 助手模块和入口，保留 Script Runner 默认启动及旧入口；完成产品验收后，再将 AI 助手切换为普通用户默认首页。不要在 Recorder 内塞一个专属聊天系统，也不要另造第二个 App Shell 或额外 Demo 首页。

## 2. 需求整理

### 2.1 已明确的需求

- **产品定位**
  - 面向大量普通用户，不要求理解脚本路径、终端、坐标或 JavaScript。
  - 交互接近聊天应用，但价值是完成本机任务，不只是生成回答。
  - Calculator 只是首页的第一个能力卡片与回归样本；增加其他能力不应修改聊天页面主流程。
- **执行透明度**
  - 用户能知道将操作什么、影响什么、目前做到哪一步、结果来自哪里。
  - 实际存在的代码必须有真实文件可查看；开发阶段显著展示，发布阶段可默认折叠。
  - 区分已有代码、本次参数、构建产物、将来真正生成的候选代码；不制造虚假的「AI 已生成脚本」。
- **聊天与操作体验**
  - 支持新会话、历史会话、连续澄清、修改要求和任务状态。
  - 规划摘要、执行步骤、代码、日志可以按层级展开，不能把所有信息堆在消息正文里。
  - 不同阶段提供对应动作，不再只能「规划后执行」。
- **运行策略**
  - 既支持审阅后执行，也为经授权的安全任务提供规划后自动运行。
  - 随时能停止；取消规划、拒绝方案、停止执行不能混成无法解释的一种行为。
  - 自动运行不能绕过资格、权限、参数校验、现场检查和高风险确认。
- **主产品整合**
  - 先有独立可维护的产品模块，再接入当前 App Shell、Script Runner 和 Recorder。
  - 统一会话、运行、产物和生命周期，避免每个入口复制一套聊天/执行实现。

### 2.2 本文新增的设计建议

用户提出的折叠「思考」区域、自动执行、第三方聊天 UI 都是可评估手段，不是必须原样实施的约束。本文选择：

1. 用「处理过程」展示可公开的规划摘要和真实执行事件，不声称展示模型完整内部思考。
2. 采用「薄聊天界面 + OpenDesk 自有任务服务」，先复用受限 Custom UI 完成产品闭环，不整套引入 LibreChat。
3. 开发预览版默认展开代码来源与参数，正式版默认收起但保留明显入口；可见性不改变权限。
4. 默认审阅后执行；自动运行是明确启用、范围受限的独立策略，不是把执行按钮删除。
5. 本机单用户产品先成立；大量安装用户不等于首版就需要云端多租户、账户系统或网络能力市场。

## 3. 当前实现事实与复用边界

| 范围 | 实际检查结果 | 产品差距 / 处理 |
| --- | --- | --- |
| 规划 | `planner.js` 明确要求不生成代码、Shell、路径、坐标，只返回固定 JSON envelope | UI 应写「已解析任务 / 已选择现有能力」，不能写「已生成代码」 |
| 执行 | `index.source.js` 按两个 TASK_IDS 调用 `pressAndRead` / `twoStage` | 保留确定性执行，后续由可信 Catalog 接管能力路由 |
| 启动入口 | `index.js` 是构建时生成的 classic-script bundle，头部保存模块 SHA-256 | 必须区分「开发源码」与「实际加载入口」，不是每次规划生成的新脚本 |
| 状态机 | `task-session.js` 已有确认、取消、迟到结果抑制、重复执行保护 | 不能声称当前完全没有取消；需补全会话、修订、运行记录与各状态操作 |
| 聊天记录 | `index.source.js` 把消息拼接进一个文本控件，内存最多保留 60 条；规划接收当前 request | 是聊天外观的单任务演示，不是已完成的持久化多轮会话产品 |
| 代码查看 | 当前 Chat 没有文件产物面板；Recorder 文档已有读取 `File.read(scriptFile)` 并显示真实内容的做法 | 复用文件查看交互与安全路径处理，不重新让模型解释一份「类似的代码」 |
| 产品入口 | `apps/opendesk/main.js` 和 `app-controller.js` 已集中管理 Runner、Scheduler 等 | AI 助手接入同一个 controller；窗口不能拥有全局 action listener 生命周期 |
| UI 技术 | `ui.createWindow()` 为受限 HTML/CSS；禁止业务 `<script>`、inline handler 和远程 URL | React/assistant-ui 不能直接放进当前 content.html；需另行建设受信应用前端承载面 |
| 平台 | 当前 Calculator 模块针对 macOS Calculator，示例文档限制特定布局 | Windows Runtime 支持不等于此 Calculator Recipe 已支持 Windows |

源码依据：[规划器](../../examples/ai-workflows/chat-calculator/planner.js)、[UI 源码](../../examples/ai-workflows/chat-calculator/index.source.js)、[实际入口](../../examples/ai-workflows/chat-calculator/index.js)、[状态机](../../examples/ai-workflows/chat-calculator/task-session.js)、[Recorder 说明](../custom-ui/README.md)、[主应用](../../apps/opendesk/main.js)、[App Controller](../../apps/opendesk/app-controller.js)。

## 4. 主界面与信息层级

### 4.1 页面结构

```text
┌──────────────────────────────────────────────────────────────────┐
│ OpenDesk · AI 助手             连接状态    执行模式    设置          │
├───────────────┬──────────────────────────────────────────────────┤
│ 新建会话       │ 今天需要完成什么任务？                           │
│ 最近会话       │ [计算器] [其他已发布能力] [浏览能力]               │
│               │                                                  │
│ AI 助手        │ 用户：先算 25×4+10，再将结果乘以 6                │
│ 脚本库         │                                                  │
│ Recorder       │ 任务卡：计算两次并读取结果                        │
│ 计划中心       │ 目标：本机计算器；开始前会清空当前计算输入          │
│               │ ▾ 处理过程：已匹配能力，等待确认                   │
│               │   已解析参数 → 已校验 → 待运行                    │
│               │ [修改要求] [查看代码与参数] [确认并运行] [取消]    │
│               │                                                  │
│               │ 结果卡：显示区实际读取的 firstResult / finalResult │
├───────────────┼──────────────────────────────────────────────────┤
│ 权限 / 帮助    │ 输入任务或补充要求…                  [发送]       │
└───────────────┴──────────────────────────────────────────────────┘
```

这是目标信息结构，不是当前实现截图，也不要求首版一次实现所有侧栏页面。小窗口收起左栏，代码详情独立打开；不强迫固定三栏挤压聊天区。

### 4.2 三层展示

| 层级 | 默认内容 | 交互 |
| --- | --- | --- |
| 业务层 | 用户请求、任务目标、影响摘要、当前状态、实际结果 | 普通用户不展开技术详情也能完成任务 |
| 过程层 | 已解析参数、选中的能力、前置检查、执行步骤、验证结果 | 进行中展示当前阶段；完成后可折叠；失败自动展开相关步骤 |
| 开发层 | 实际代码文件、本次参数、代码版本、运行日志和证据 | 开发预览版显著可见；正式版保留「查看代码与参数」 |

折叠状态只是视图偏好，不触发规划、运行、暂停或授权变化。用户手动展开后不要因下一次状态刷新又折叠。

「处理过程」使用真实宿主状态与可公开的规划摘要，不伪造推理流，不展示内部指令、凭证或未经筛选的供应商日志。没有流式模型接口时显示真实阶段与本地耗时即可，不为刷新动画反复调用模型。

### 4.3 状态对应的操作

| 状态 | 主要操作 | 规则 |
| --- | --- | --- |
| 空闲 | 发送、选择能力卡片、切换会话 | 能力卡片可填充请求或打开表单，不默认触发桌面动作 |
| 规划中 | 停止规划 | 输入区可保留草稿；P0 不承诺运行中插入新指令 |
| 需要澄清 | 补充信息、取消 | 补充信息绑定原任务，不作为孤立新请求 |
| 待审阅 | 确认并运行、修改要求、查看代码、取消 | 修改已提交需求会产生新修订，旧确认失效 |
| 自动运行已放行 | 查看依据、停止 | 显示为何无需再次确认及本次影响；不可仅以倒计时充当授权 |
| 执行中 | 停止执行、查看进度/代码/日志 | 停止不等于撤销已完成副作用；未实现安全检查点前不显示「暂停/继续」 |
| 已完成 | 复制结果、使用结果继续提问、再次运行、保存为快捷任务 | 再次运行生成新 Run；不能复用旧确认直接重放副作用 |
| 失败/受阻 | 查看原因、打开修复入口、重新规划、经校验重试 | 业务副作用不自动无限重试；重试边界必须明确 |
| 缺失能力 | 查看支持范围、申请定制、进入作者态 | 不在普通执行过程中偷偷生成任意代码并运行 |

草稿输入和「修改已提交任务」要分开；输入下一条草稿不应悄悄修改正在运行的参数。P0 可以仍禁止在活动任务中提交新任务，但必须解释原因。

## 5. 代码与文件可见性

### 5.1 必须展示的四类对象

| 对象 | 来源 | 正确标签 |
| --- | --- | --- |
| 可读业务源码 | 产品交付的原始模块 | 「现有能力源码」 |
| 实际执行入口 | 当前 Runtime 实际加载的 bundle / 模块 | 「实际加载入口」 |
| 本次执行输入 | 宿主通过校验并冻结的 envelope / arguments | 「本次参数」 |
| 新生成代码（未来作者态） | 真正写入磁盘的候选 Recipe 与依赖 | 「新生成候选，尚未发布」 |

当前 Calculator 应让开发者能看到 `calculator.js`、`index.source.js`、`index.js` 的不同角色以及本次 JSON 参数，不需要为每次普通调用重新生成一份计算器实现。

**不得为了满足「有代码可看」，展示一段未实际执行的伪代码并标成实际脚本。** 可读伪代码可以存在，但必须明确标注「流程说明，非执行文件」。需要导出调用脚本时，由宿主模板生成，标明「导出入口」，保留精确依赖与使用前提；未经重跑不能标成已验证独立 Recipe。

### 5.2 代码详情面板

默认提供「概览 / 本次参数 / 源码文件 / 实际入口 / 执行日志 / 结果证据」。每个真实文件显示路径、相对展示名、版本或内容摘要、来源以及是否属于本次执行快照。

操作包括只读查看、复制内容、复制路径、在文件管理器中显示、用编辑器打开。外部打开必须调用受控宿主动作，不拼接模型提供的 Shell 命令。首版不内置可直接修改生产脚本的 IDE。

开发模式可以展开更多日志，但不能放宽执行权限。编辑源码必须走「创建候选副本 → 校验/资格 → 新版本」；正在运行的快照和已发布原件不允许被聊天窗口就地改写。

### 5.3 所见与所执行一致

可信任务卡应绑定 plan revision、精确参数、能力版本、实际入口与依赖摘要、目标范围、影响范围和授权策略。确认前后任一关键项变化，都必须使旧确认失效。

对 bundle 入口，不能只显示仓库里后来被修改的 `calculator.js`：构建发布时保留源码映射/源文件快照与摘要，运行时记录实际 bundle 版本。映射缺失则明确「仅能确认 bundle，源码映射未验证」，不能假装二者一致。

执行前校验并固定实际读取的代码字节/不可变部署版本；不能先检查可变路径的 hash，再在可被替换的路径上重新读取执行。Hash 本身不证明发布者可信，也不替代安全审查和资格验证。

UI 返回只是展示，不是执行唯一真相；最终参数、授权与执行绑定由任务服务掌握。

## 6. 执行模式与自动运行

### 6.1 三种模式

| 模式 | 体验 | 默认与边界 |
| --- | --- | --- |
| 仅规划 | 返回方案、参数、影响与代码来源，不执行 | 适合调试与了解能力 |
| 审阅后执行 | 方案完成后由用户确认 | 首轮产品默认 |
| 已授权安全任务自动运行 | 规划和宿主检查通过后直接执行 | 仅在用户明确启用且全部放行条件满足时可用 |

自动运行条件必须同时满足：已发布且资格适用的精确能力版本、受允许的参数子域、明示的目标与副作用、当前权限与环境就绪、有效授权、桌面执行资源可获得、预算与超时限制满足。模型自报「低风险」不构成放行依据。

涉及发送消息、付款、批量删除、覆盖文件、改变安全设置等敏感副作用，必须执行更严格的确认策略；不能因用户选了自动模式就全局跳过。当前 Calculator 开始前会清空输入，首次启用自动模式也应明确这一影响。

### 6.2 自动运行主链路

```text
提交请求
→ 受控规划 / 澄清
→ Resolver 与宿主语义校验
→ 冻结计划和实际代码引用
→ 生成可信预览
→ 策略判断：仅规划 / 待确认 / 可自动运行
→ 获取执行资源并重新检查现场状态
→ 执行与验证
→ 持久化真实结果
```

「过程面板收起」与「系统获准执行」是两件事。取消信号必须优先于慢 UI 刷新，迟到规划结果不能在用户停止后触发自动运行。

新建/修复能力沿已有 Authoring → Qualification → Publish 边界运行；发布完成不自动执行原请求，不沿用开发前的旧确认。普通运行策略不能覆盖这一边界。

## 7. 会话、任务与运行服务

### 7.1 最小对象关系

```text
Conversation：会话与用户消息
  → Task：一个业务目标
    → PlanRevision：一个冻结方案版本
      → Run：一次实际执行尝试
        → Events / Observations / Artifacts
```

一个会话可能有多个任务；一个任务可能多次修改；一次重试是新的 Run。不能用一段拼接文本同时充当会话数据库、执行计划和审计记录。

「把第二次乘数改成 7」应明确绑定当前任务及旧乘数，产生新计划。「用刚才的结果」应解析为明确 run/observation 引用；多义时询问，不把自然语言历史中的某个数字直接作为实际结果。

消息编辑、重新生成和会话分支只能改变未来请求，不能改写已发生的运行事实。重连/重新打开窗口恢复状态，不重放执行命令。

### 7.2 职责拆分

| 模块 | 职责 |
| --- | --- |
| View / Renderer | 展示消息、任务卡、代码和按钮，发送用户意图 |
| Conversation Controller | 选择会话、草稿、修订关系、将状态投影为 UI |
| Task Service | 规划、路由、授权、运行、停止、串行控制、持久化状态 |
| Artifact Store | 参数、实际代码引用/快照、日志、证据、安全读取与保留策略 |
| Capability / Permission / Agent / Execution owners | 复用现有权威能力，不在 Chat 再造另一套实现 |

这些名称是内部责任划分，不要求每项立刻对应独立进程、公共 API 或服务端框架。

UI 通过结构化事件更新，不通过解析模型文本「执行成功」来判定任务完成。事件至少携带 conversationId、taskId、runId、sequence、type 和可显示数据；终态与结构化结果由宿主产生。

### 7.3 存储边界

产品文件写入既有产品路径服务解析出的用户数据根，不依赖仓库存在，不写入安装包，也不硬编码某个用户的绝对目录。以下为拟议布局，不是新增路径 API：

```text
<appDataRoot>/assistant/
  conversations/<conversationId>/conversation.json
  runs/<runId>/
    plan.json              # 冻结任务与参数、计划修订
    manifest.json          # 代码/依赖引用、Runtime/平台、授权摘要
    events.jsonl           # 有界、结构化运行事件
    result.json            # 真实结果/失败；不是模型预测
    artifacts/             # 必需证据与确实生成的文件
```

已有受信部署中的不可变源码可按内容寻址复用，不必为每条消息复制整套 Runtime。开发 `.runtime/` 仅作为开发证据位置，不是正式用户必须认识的目录。

实现必须考虑原子写入、磁盘失败、崩溃后不自动重跑、schema 迁移、容量上限与删除策略。日志/截图/用户文件可能含敏感内容；仅保存必要数据，凭证用引用，不默认写入日志。导出诊断包先脱敏；未知类型拒绝或需要额外确认。临时会话也不能绕过执行授权或销毁仍在运行任务的必要状态。

## 8. 主应用集成与目录规划

### 8.1 建议新增的产品模块

先创建独立模块，而不是把产品源码继续堆在 `examples/ai-workflows/chat-calculator/index.js`：

```text
apps/opendesk/assistant/
  index.js                 # 产品模块入口，无 import 即执行桌面任务的副作用
  controller.js            # 会话与视图协调
  view.html                # 当前受限 HTML
  view.css                 # 当前受限 CSS
  task-service.js           # 复用/提取现有任务状态机并补齐产品行为
  conversation-store.js    # 会话持久化
  artifact-store.js        # 真实文件与执行快照
```

这是拟议文件地图，本轮没有创建空壳源码来冒充实现。实际实施允许在职责清晰的前提下合并小文件；不要仅为设计名词制造目录层级。

Calculator 的能力代码归属既有 Capability/Recipe 资产层；不要在 assistant/ 再复制一套计算器按键表。提取无副作用模块并复用后，保留示例为薄入口或独立固定回归案例。正式发行包不得运行时 import 仓库的 examples 路径。

当前公开 `.js` 启动方式需要受控 bundle；迁移时保留真实 loader 合同，源码变更后同步重建 bundle 并做公开命令回归。不要把 Node 的 ESM 测试成功当成当前 Runtime 入口一定可运行。

### 8.2 接入现有入口

`apps/opendesk/main.js` 创建一个助手控制器，由现有 `app-controller.js` 分发一个产品 action（例如待实施的 `assistant.open`）。Script Runner、Recorder 和系统托盘只调用这个入口，不创建各自的会话服务。

Runner 向助手移交 script/recipe 引用与版本；Recorder 移交 candidate/evidence 引用。未经资格/发布的录制结果不能在普通助手里自动变成生产能力。

打开同一主视图优先复用窗口；已关闭窗口按照当前 ui contract 使用新的 window id 重建。窗口隐藏/关闭不能卸载 App 全局 listener，也不能销毁 Runner/Scheduler 的共享服务。

切换会话/页面不改变正在运行任务。最小化/隐藏后继续执行需有明确产品约定及托盘停止入口；首版点击关闭活动助手窗口默认请求停止当前任务并保留历史，不能无提示继续操作桌面。退出整个 App 走统一取消与清理。

### 8.3 桌面资源互斥

多个会话不意味着可以同时控制同一个桌面的鼠标和焦点。AI 助手、Runner、Recorder 回放和计划任务必须使用同一个执行资源协调边界；仅在 Chat 内禁止重复点击不够。

规划可在有界预算内独立进行；真实桌面动作首版串行，资源占用明确显示「等待桌面可用」。未实现跨入口互斥前，不宣称多会话并发自动化安全可用。这里复用 Lifecycle 总纲，不再另造一套 Desktop Lock 机制。

## 9. 自建 UI 与第三方方案

### 9.1 本轮决策

**先用当前 Custom UI 做轻量产品界面；任务服务与视图解耦。首轮不整套 fork LibreChat，不为使用 React 而放开现有受限 HTML 的脚本限制。**

理由不是「第三方不好」，而是当前最关键缺口是可信任务卡、实际代码来源、会话/运行分离、授权策略和产品生命周期。换聊天外壳不会自动补齐这些能力。

用户提到的「libra」未提供项目地址，不能确认具体所指。下表把 LibreChat 作为明确名称的候选进行比较，不认定两者是同一个项目。

| 方案 | 可借鉴/复用 | 当前取舍 |
| --- | --- | --- |
| 当前 Custom UI 自建薄视图 | 已有窗口、控件、事件、权限、分发与生命周期 | P0.5 优先；仅实现真实支持的控件与交互，复杂富文本能力不伪装已存在 |
| assistant-ui | React 聊天组件、外部状态适配、消息操作、工具结果和附件的适配模式 | 富交互前端的优先评估候选，不可直接嵌入当前受限 HTML |
| LibreChat | 完整聊天产品的信息架构、会话动作、独立 Artifacts 面板 | 优先借鉴 UX；作为完整自托管应用引入会增加不属于当前桌面任务产品的部署和集成责任 |

官方依据：assistant-ui 的 [ExternalStoreRuntime](https://www.assistant-ui.com/docs/runtimes/custom/external-store) 允许既有状态与回调驱动 UI；LibreChat 的 [Artifacts](https://www.librechat.ai/docs/features/artifacts) 将生成内容放入独立视图，[本地部署](https://www.librechat.ai/docs/local/docker) 则面向自托管应用，不能等同于一个零依赖桌面聊天控件。以上检索日期为 2026-09-13；具体选定版本仍需检查许可证、依赖和供应链。

### 9.2 当前 HTML 能力门

以 [ui API](../api/ui.md) 为准：HTML 内容不运行任意业务脚本，不可直接访问 File、Command 等 Runtime 全局。当前窗口底层使用 WebView，不代表公开契约允许 React 或任意 DOM 编程。

首轮折叠/详情采用已支持的控件能力；不能假定 `<details>`、任意结构更新、Markdown 高亮、动态虚拟列表、拖拽上传或事件类型已支持。若当前控件无法合理承载长会话，先完成独立任务/产物详情视图，并明确产品差距，不能把拼接文本演示包装成完整聊天工作台。

### 9.3 富交互前端的后续路径

当需要长会话消息列表、丰富任务卡、附件、代码高亮和分支导航时，评估受信的应用前端承载面，而不是放开任意脚本的 createWindow：

```text
随产品交付、版本固定的 Web UI 资源
→ 明确受信的应用前端承载面
→ 窄的、结构化、可授权的 bridge
→ 同一个 OpenDesk Task Service
```

前端只能发送 submit、revise、approve、cancel、read-artifact 等受控业务意图；不能取得任意 File、Command、eval 或鼠标接口。模型生成的 Markdown/HTML/代码视为数据，禁止进入特权桥；展示代码不执行代码。

必须验证来源隔离、导航拦截、内容净化、命令幂等、敏感字段脱敏和打包资源完整性。若另行提供浏览器调试入口，服务只绑定受控本地地址，实施认证、Origin/CSRF/DNS rebinding 等防护；不能把整个桌面控制端口公开出去。生产用户不应被要求启动 npm、Docker 或开发服务器。

Node/前端打包工具可以属于维护者构建链，不因此变成 OpenDesk JavaScript Runtime 的运行依赖。不要把接入 React 解释为把当前 Runtime 换成 Node/Electron。

## 10. 可以借鉴的聊天功能与优先级

| 优先级 | 功能 | OpenDesk 特有要求 |
| --- | --- | --- |
| P0.5 | 清晰的用户/助手消息、发送与停止、可信任务卡、进度、代码/参数详情、错误修复入口 | UI 由任务事件驱动，失败与结果不能来自模型自述 |
| P0.5 | 基本会话保存、继续澄清、修改已提交要求、运行历史 | 任务修订与执行尝试分离，旧确认失效 |
| P0.5 | 能力卡片、连接/权限状态、主 App 入口 | 只显示实际受支持范围，缺失后端提供可操作引导 |
| P1 | 受限自动运行、快捷任务、会话搜索、导出诊断 | 以资格与安全门通过为前提，不用评分抵消安全缺口 |
| P1 | 附件、代码高亮、长会话、分支、富结果卡 | 需要宿主/UI 能力与数据安全专项验证 |
| 后置 | 多模型快捷切换、云同步、协作、多租户、网络能力市场 | 不阻塞本地产品最小闭环，模型仍由现有 Agent/LLM owner 适配 |

「重新生成回答」与「重新运行桌面任务」必须使用不同文案及调用通道；恢复会话、切换分支、展开代码均不能重跑任务。

## 11. 面向大量用户的发布底线

普通用户只需要安装并启动 OpenDesk、完成必要的模型连接与系统权限引导、选择任务并执行。当前依赖本机 Codex CLI 的方式可以作为开发者路径，但不能把「自行配置 PATH、终端登录、查日志」作为大众产品唯一 onboarding。

近期复用现有 Agent backend/profile：区分 Runtime 支持、程序发现、配置、真实认证和测试调用结果；页面给出连接向导与错误修复，不把 configured 显示成已成功登录。另一模型通道只有在已实现并验证后才出现在产品选择器中。

在大规模发布前必须覆盖：安装包自包含 UI/必要源码资源、平台明确支持范围、模型/权限前置诊断、运行超时和停止、资源互斥、版本锁定及回退、错误码和脱敏诊断、数据保留与删除、中文输入与键盘可访问性、窗口缩放和长文本、升级后历史数据可读取。

接入非测试应用前，至少增加一个经独立资格化的第二能力，验证 UI/Task Service 不再包含 Calculator 专属分支。macOS 与 Windows 要分别给出实际支持/受阻/不支持状态，不做虚假平台对称。

## 12. 实施顺序与最小交付

### A. 产品模块化与可见性

交付：独立 assistant 产品入口、现有能力适配、任务卡、真实参数和代码文件查看、结构化运行记录、原示例命令回归。

先保持「审阅后执行」。只有 UI 改名、不提供真实代码依据与运行记录，不算完成。

### B. 会话与主应用整合

交付：基本会话持久化、连续澄清/任务修订、同一控制器接入主菜单/Runner/Recorder、窗口复用和关闭重建、停止与退出回归。

不复制已有 Agent、权限、Recorder 生成或 Runtime 执行协议。

### C. 受限自动运行

前提：可信 Catalog/资格、授权绑定、现场预检、取消竞态与跨入口互斥已经可验证。

交付：明确开关与授权范围、宿主策略判定、运行前最终预检、可见的停止入口、高风险确认和失效保护。任何前提缺失则保留手动确认，不做假自动模式。

### D. 富聊天与主要首页

交付：在真实 UI 能力评估后选择继续原生薄视图或建设受信 Web renderer；完善长会话、附件、代码高亮等必要功能。产品验收通过后，将 AI 助手切为默认首页；Script Runner/Recorder 保留原功能与菜单。

这四步按依赖推进，不要求全部做完才能获得第一版可用产品，也不能把最后一步的设计当成本轮实现。

## 13. 验收矩阵

| 编号 | 场景 | 必须看到的证据 |
| --- | --- | --- |
| P01 | 输入两阶段 Calculator 请求 | 宿主参数与预览一致；两次结果真实读取；第二段绑定本次 firstResult |
| P02 | 查看代码 | 界面内容来自实际文件；源码、bundle、本次参数标签正确；摘要可核对 |
| P03 | 修改待确认任务 | 产生新修订；旧确认/按钮不能启动旧方案 |
| P04 | 停止规划及迟到结果 | 停止后不执行，不因迟到 envelope 进入自动运行 |
| P05 | 停止桌面执行 | 已在途单次动作边界明确；不再提交新的动作；终态与日志一致 |
| P06 | 重复点击/断线重连/恢复历史 | 同一授权请求不重复提交执行；恢复视图不自动重跑 |
| P07 | 自动模式 | 仅资格、策略和现场全部满足才放行；高风险/未知条件转确认或阻塞 |
| P08 | 代码或参数被更换 | 旧确认无效；运行使用冻结版本，不发生查验后可变路径替换 |
| P09 | 主入口与窗口生命周期 | Runner/Recorder/托盘打开同一助手；关闭重建；全局菜单仍工作 |
| P10 | 跨入口桌面冲突 | Runner/助手/计划任务不能同时争抢同一桌面；占用状态可解释 |
| P11 | 环境与平台 | 缺 CLI、未认证、权限不足、布局不适用、Windows 未支持均有真实状态 |
| P12 | 数据/渲染安全 | 敏感信息不默认进日志/导出；模型 HTML 不执行；文件路径越界被拒绝 |
| P13 | 中文与长会话 | 输入法回车不误发送，长消息可读，滚动和按钮可达；有真实实窗证据 |
| P14 | 第二能力 | 能力卡片/路由扩展不改聊天主流程；各平台资格范围独立 |
| P15 | 发行包与升级 | 无源码仓库仍可打开界面与代码详情；无需开发服务器；历史数据迁移通过 |

质量目标可采用 95/100：业务闭环 25、执行可追溯 20、安全与生命周期 25、UI 可用性 15、分发与维护 15。未完成实机验收不填虚假分数；任一关键安全门失败不得用其他项目加分抵消。
