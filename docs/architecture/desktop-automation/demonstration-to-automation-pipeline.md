# Agent 驱动的示范到自动化生成主链

## 状态与定位

- 文档性质：下一阶段架构基线 / 研究结论。
- 上位架构：`agent-first-recorder.md`。
- 配套框架：`docs/frameworks/automation-framework.md`、`app-development-framework.md`、`capability-development.md`。
- 本文不重新发明一级架构，而是把 Recorder 从“真实执行”到“高质量可重复自动化”的具体执行步骤补完整。
- 本文描述目标架构与开发方法，不代表所有能力已经实现。

## 一、一级主链：冻结

当前一级结构没有严重架构错误，建议冻结：

```text
任务来源：Agent / 人工 / 脚本
↓
真实任务执行
↓
多模态证据采集
↓
界面与状态重建
↓
元素、动作与语义落地
↓
行为规律归纳
↓
统一自动化模型
↓
工作流 / 技能合成
↓
健壮性工程
↓
编译生成
↓
真实回放与验证
↓
修复 / 晋级正式技能
```

核心目标不是生成普通宏，而是：

> 从一次真实成功的业务操作中，保留可核验证据，理解状态与目标，提炼真正有效的行为规律，最终生成接近人工编写质量、可重复执行、可验证、可维护的自动化程序。

## 二、最关键的十个执行步骤

1. 先让 Agent 真实完成一次任务。
2. 同时记录动作、语义、状态和证据。
3. 理解应用、窗口、页面、区域和元素。
4. 把语义目标对应到真实 UI，而不是只保存坐标。
5. 把完整执行轨迹提炼成真正有效的成功路径。
6. 把具体步骤抽象成业务步骤和可复用技能。
7. 把具体值提取成变量和参数。
8. 生成能够重复执行的代码。
9. 优化定位、坐标、验证、恢复和代码可读性。
10. 真实回放，通过后才晋级为正式自动化。

## 三、第一次运行：先真实完成任务

第一次运行的第一目标不是立即写出完美代码，而是先真正完成用户任务，并确认业务结果成立。

执行过程中同步保存：

- 用户目标与当前子目标；
- 当前准备完成什么操作；
- 操作目标是什么；
- 实际调用了什么工具或执行了什么动作；
- 动作前状态；
- 动作后状态；
- 预期变化；
- 实际变化；
- 是否成功；
- 是否重试；
- 是否进入恢复路径；
- 支撑以上判断的真实 Evidence。

原则：

```text
真实 Evidence
> 工具调用和实际结果
> Agent 的结构化提示
> Agent 的自然语言说明
```

Agent 提供的语义非常有价值，但只能作为提示、候选或假设，不能自动成为事实。

## 四、记录对象：不是鼠标键盘，而是完整操作经验

普通宏可能只记录：

```text
点击坐标
等待
输入文字
再次点击坐标
```

OpenDesk Recorder 应逐步形成：

```text
动作前状态
+
操作目标
+
实际动作
+
动作后状态
+
结果
+
验证
+
Evidence
```

例如不只记录“点击某坐标”，而要尽可能知道：

```text
当前处于联系人搜索状态
↓
目标是联系人搜索输入框
↓
输入联系人名称
↓
搜索结果发生变化
↓
选择目标联系人
↓
聊天区域切换到对应联系人
↓
通过页面状态和内容验证成功
```

这类完整经验才是后续行为归纳和技能生成的学习基础。

## 五、优先从浏览器 Recorder 建立简单环境下的完整链路

不要一开始从微信、千牛等复杂桌面软件推导全部架构。

优先顺序：

```text
可控网页测试环境
↓
真实浏览器网页
↓
简单桌面程序
↓
结构化桌面程序
↓
动态桌面程序
↓
复杂业务软件
↓
跨应用长期工作流
```

浏览器拥有 DOM、事件、节点属性、文字、层级关系等结构化信息，最适合先研究清楚：

> 怎样把“一次录制得到的粗糙轨迹和代码”，逐步优化成长期稳定、可读、可维护、可验证的自动化代码。

浏览器场景的核心处理链：

```text
真实操作
↓
记录 DOM / 事件
↓
确定实际操作元素
↓
生成多个候选定位方式
↓
判断候选的唯一性和稳定性
↓
删除容易变化的定位方式
↓
组合更可靠的定位条件
↓
转换成有业务语义的步骤
↓
删除探索和无效操作
↓
识别变量
↓
形成工作流
↓
生成高质量可读代码
↓
真实回放
↓
验证结果
```

核心判断：

```text
当前唯一
!=
长期稳定
```

普通 Recorder 的 Selector 和代码质量经常较低，本质上是因为它只需要找到“这一次操作的节点”，而长期自动化需要判断“哪些身份特征跨运行仍然稳定”。

## 六、从 Browser 原理迁移到 Desktop

桌面端不能假设只有坐标，也不能假设永远能够获得完整 UI Tree。

默认逐级使用：

```text
结构化接口 / Accessibility
↓
角色、名称、文字和稳定标识
↓
页面、区域、父级和 Anchor
↓
OCR
↓
布局与相对空间关系
↓
图像 / 模板
↓
视觉模型
↓
坐标回退
```

因此：

```text
语义目标
!=
Locator

Locator
!=
坐标

坐标只是最终动作位置
```

一次目标应尽可能保存多个候选识别信号，而不是永久固化一个坐标。

## 七、先建立 UI 状态，再频繁操作

第一次进入陌生软件或陌生页面时，可以进行较完整的窗口分析：

```text
应用
└── 窗口
    └── 页面 / 状态
        └── 区域
            └── 元素
```

例如先识别：

- 左侧导航区域；
- 列表区域；
- 主内容区域；
- 输入区域；
- 按钮；
- 输入框；
- 文本和图标。

然后保存可复用的状态与布局信息。后续重复操作优先复用已有模型，只重新观察发生变化或置信度不足的区域。

## 八、控制截图和在线大模型成本

不能把正常路径设计成：

```text
每执行一步
→ 截全屏
→ 上传在线视觉模型
→ 重新理解整个桌面
```

建议按成本逐级升级：

```text
已有结构化信息和缓存
↓
Accessibility / DOM / 窗口信息
↓
OCR / Layout / 图色
↓
局部区域截图
↓
较大窗口区域视觉分析
↓
完整窗口视觉模型
↓
全屏视觉模型，仅困难情况
```

同时遵循：

- 初次进入陌生状态可以进行较完整分析；
- 已知状态优先使用缓存；
- 局部变化只分析局部区域；
- OCR、Layout、图色可以解决时，不请求在线大模型；
- 结构信号不足、歧义、抽象和修复时，再使用 Vision / Agent；
- 正常稳定回放尽量不依赖在线大模型。

## 九、窗口相对坐标和 Geometry 必须成为通用基础能力

长期自动化不能主要依赖一次运行的全局屏幕坐标。

至少需要统一理解：

```text
屏幕坐标
显示器坐标
窗口坐标
窗口内容区坐标
区域坐标
元素坐标
归一化坐标
截图坐标
```

目标应该逐渐从：

```text
click(1532, 827)
```

转变为：

```text
目标应用
└── 目标窗口
    └── 当前页面
        └── 目标区域
            └── 目标元素
                └── 元素内部动作位置
```

执行时再完成各坐标空间之间的转换。

窗口截图、区域截图、相对坐标、坐标转换、目标定位与最终坐标解析应成为 OpenDesk 通用自动化基础能力，而不是只存在 Recorder 内部。

## 十、完整执行轨迹必须经过有效路径提炼

Agent 第一次探索可能包含：

- 看界面；
- 尝试错误目标；
- 返回；
- 搜索；
- 输入错误内容；
- 修正；
- 重试；
- 最终成功。

这些不能全部进入正式脚本。

需要经过：

```text
完整执行轨迹
↓
动作归组
↓
识别探索行为
↓
识别错误和无效动作
↓
识别恢复动作
↓
提取真正成功路径
↓
合并连续操作
↓
形成最小必要步骤
```

正式自动化保留的是“完成任务所必需的可靠步骤”，不是第一次探索过程的录像。

## 十一、从具体动作抽象为业务步骤和技能

例如：

```text
点击搜索框
输入联系人名称
等待搜索结果
选择联系人
验证聊天页面
```

可以逐渐抽象为：

```text
打开联系人(contactName)
```

再把：

```text
聚焦消息输入区
输入消息
发送
验证消息出现
```

抽象为：

```text
发送消息(message)
```

最后形成：

```text
发送消息给联系人(contactName, message)
```

判断是否应该形成 Skill，至少考虑：

- 是否具有明确业务语义；
- 是否有稳定输入和输出；
- 是否可以独立验证；
- 是否可以在其他工作流中复用；
- 是否具有相对稳定的开始和结束状态。

## 十二、在成功路径稳定后提取变量和参数

一次具体执行中，需要进一步判断：

```text
什么是流程结构？
什么只是本次运行的具体值？
```

例如：

- “张三” → 联系人变量；
- “你好” → 消息变量；
- 文件路径 → 文件变量；
- 日期 → 日期变量；
- 搜索关键词 → 搜索变量。

逐渐形成：

```text
稳定动作结构
+
可变输入参数
```

不参数化的结果更接近录像；经过可靠参数化以后才开始接近可复用 Skill。

## 十三、先生成正确可回放代码，再优化到人工质量

第一阶段先确保：

- 能够重复执行；
- 能够真正完成任务；
- 能够验证最终结果；
- 失败时不会继续假装成功。

第二阶段再进行代码质量优化：

- 整理函数边界；
- 提取变量；
- 使用业务语义命名；
- 优化 Locator；
- 减少固定坐标；
- 减少固定 sleep；
- 增加前置状态检查；
- 增加动作后验证；
- 增加明确的失败处理；
- 增加有限恢复；
- 删除录制产生的冗余步骤；
- 保留必要注释和来源关系。

最终目标不是：

```text
click
sleep
click
type
```

而是形成可读的：

```text
确认当前状态
↓
定位业务目标
↓
执行可验证动作
↓
确认业务结果
↓
必要时进入有限恢复
```

## 十四、统一自动化模型位于代码之前

不要长期保持：

```text
Raw Trace
↓
Flow
↓
JavaScript
```

目标结构应逐渐演进为：

```text
原始证据
↓
完整操作经验
↓
语义行为
↓
统一自动化模型
↓
可执行工作流模型
↓
生成代码 / Skill / Playbook
```

统一自动化模型至少需要逐步表达：

- 应用；
- 窗口；
- 页面 / 状态；
- 区域；
- 元素；
- 目标；
- 多候选 Locator；
- Geometry；
- 变量；
- 可验证动作；
- Skill；
- Workflow；
- 条件和分支；
- Recovery；
- Evidence；
- Confidence；
- Provenance。

JavaScript 是可重新生成的交付物，而不是自动化知识的唯一 Source of Truth。

## 十五、真实回放与晋级

生成自动化后必须重新进入真实环境执行：

```text
识别应用
↓
识别当前状态
↓
解析变量
↓
定位目标
↓
解析最终动作位置
↓
执行动作
↓
重新观察
↓
验证动作结果
↓
继续下一步
```

失败时：

```text
定位失败
├── 尝试其他可靠候选
├── 更新状态 / 区域
├── 重新观察必要范围
└── 必要时再请求 Vision / Agent

验证失败
├── 判断动作是否真正失败
├── 判断 UI 是否发生预期外变化
├── 执行有限恢复
└── 无法证明成功时立即停止
```

只有经过真实 Replay + Verification 的结果才能晋级为正式 Skill。

## 十六、从简单到复杂的验证路线

### Level 1：可控 HTML Benchmark

验证：

- 事件记录；
- DOM 元素身份；
- 多 Selector 候选；
- Selector 优化；
- 动态位置；
- 输入和点击；
- 变量提取；
- 代码生成；
- 回放验证。

### Level 2：真实浏览器应用

增加：

- 动态 DOM；
- 异步状态；
- 滚动；
- Dialog；
- 多候选元素；
- 长期稳定 Selector。

### Level 3：简单桌面应用

优先：

- Calculator；
- Settings；
- Text Editor。

验证：

- 窗口身份；
- Accessibility；
- 窗口相对坐标；
- OCR；
- 动作后验证。

### Level 4：普通结构化桌面应用

验证：

- 多区域；
- 多输入框；
- 列表；
- Tab；
- Dialog；
- 多页面状态。

### Level 5：动态桌面应用

验证：

- Resize；
- 滚动；
- DPI / 坐标变化；
- 动态布局；
- 虚拟列表；
- 自绘 UI；
- 不完整 Accessibility。

### Level 6：复杂业务应用

例如微信、千牛。

验证：

- 多区域；
- 多状态；
- 动态列表；
- OCR / Vision；
- 强业务验证；
- Recovery；
- 高风险动作保护。

### Level 7：跨应用、长期运行工作流

验证：

- 多应用切换；
- 多窗口；
- Clipboard / File；
- Checkpoint；
- Retry / Recovery；
- 长时间运行和状态恢复。

每一级都必须重复：

```text
真实执行
→ 理解
→ 生成
→ 回放
→ 验证
```

当前一级没有稳定证明之前，不用更复杂应用代替基础能力验证。

## 十七、需要逐步补齐的通用基础能力

优先检查并完善：

- 窗口截图和指定窗口区域截图；
- 多坐标空间及统一坐标转换；
- 窗口相对、区域相对、元素相对动作；
- Accessibility / DOM / OCR / Layout / Image 的统一 Evidence 表达；
- 页面、区域和元素状态模型；
- State / Layout Cache 与失效机制；
- Target Candidate Set；
- 多 Locator 解析与排序；
- 独立 Verifier / Oracle；
- Evidence、Confidence、Provenance；
- 可验证动作；
- Variable / Parameter 模型；
- Skill / Workflow 模型；
- Recorder 生成物到正式运行时 API 的稳定编译接口。

这些通用能力应优先进入 OpenDesk Automation Framework / Runtime 的公共基础层，而不是在每个具体应用脚本和 Recorder 中重复实现。

## 十八、工程原则

后续实现必须长期遵循：

1. Evidence 高于 Agent 自述。
2. 坐标不是元素身份。
3. 当前唯一的 Selector 不等于长期稳定的 Selector。
4. 一次目标优先保存候选集合，而不是单一定位结果。
5. 第一次运行优先真正完成任务，同时保存足够信息。
6. 正式脚本只保留有效路径，不复制探索过程。
7. 操作经验比裸 Event 更适合作为行为学习单位。
8. 稳定路径优先使用传统规则、结构化接口和缓存。
9. OCR、Layout、图色能够解决时，不调用在线视觉模型。
10. Vision / Agent 主要处理结构不足、歧义、抽象、诊断和修复。
11. 正常稳定回放尽量不依赖在线大模型。
12. 未能独立证明成功的关键步骤不能晋级正式自动化。
13. JavaScript 是派生产物，不是唯一事实源。
14. 先完成 Browser Recorder 的低噪声闭环，再逐步增加 Desktop 不确定性。
15. 复杂应用用于后期综合验证，不能替代基础能力 Benchmark。

## 十九、千牛反向案例分析计划

`qianniu.js` 等已运行过的真实应用代码适合作为反向案例，但案例结论必须以实际源码为依据，不能凭印象写入正式架构。

后续读取真实源码后，重点反向检查：

- 哪些代码表达真实业务语义；
- 哪些代码已经形成应用 / 窗口 / 页面 / 区域模型；
- 哪些定位依赖稳定结构；
- 哪些定位依赖 OCR、图色或相对布局；
- 哪些地方仍使用脆弱固定坐标；
- 哪些 sleep 可以改成状态等待；
- 哪些动作已经有业务验证；
- 哪些动作执行后直接假定成功；
- 已有哪些 Recovery；
- 哪些逻辑应该由通用 OpenDesk API 提供；
- 哪些逻辑应该由 Recorder 自动归纳；
- 哪些内容只能留在千牛 App Profile / Skill 中。

在没有读取源码前，本节只定义分析方法，不把千牛经验作为已经验证的架构事实。
