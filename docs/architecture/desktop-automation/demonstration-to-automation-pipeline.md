# Agent 驱动的示范到自动化生成主链

## 0. 结论与总框架

本文回答一个核心问题：**怎样把 Agent / 人的一次真实业务操作，逐步转换成长期稳定、可重复、可维护、可验证的自动化程序。** 当前一级架构没有严重问题，建议冻结；下一阶段重点完善二级执行链和基础能力。

### 一级主链

**任务来源；真实任务执行；证据采集；界面与状态重建；目标语义落地；行为规律归纳；统一自动化模型；工作流 / 技能合成；健壮性工程；编译生成；真实回放与验证；修复 / 晋级正式技能。**

### 二级执行链

1. **任务与执行上下文绑定**：明确用户目标、任务输入、应用、窗口和执行会话。
2. **Agent 真实完成一次任务**：第一次运行优先把业务真正做成功，不要求同时生成完美代码。
3. **同步采集证据**：记录动作、动作前后状态、窗口、结构化 UI、截图、OCR、布局、输入上下文和验证结果。
4. **重建 UI 状态**：形成“应用、窗口、页面 / 状态、区域、元素”的结构。
5. **目标语义落地**：把“搜索框、发送按钮、联系人张三”等语义对应到真实 UI，保存多个候选识别方式，而不是只保存坐标。
6. **构造完整操作经验**：形成“动作前状态 + 操作目标 + 实际动作 + 动作后状态 + 结果 + 验证 + 证据”。
7. **提炼有效成功路径**：区分业务动作、探索、错误、等待、重试和恢复，只保留真正完成任务所需要的步骤。
8. **行为抽象与参数化**：识别变量、重复模式、技能边界、前置条件、后置条件、分支、恢复和完成条件。
9. **构造统一自动化模型**：统一表达应用、状态、目标、定位候选、几何关系、变量、可验证动作、技能、工作流、恢复和证据。
10. **健壮性工程**：消除脆弱固定坐标、固定等待、单一定位和弱验证，补充候选定位、状态等待、失败分类和有限恢复。
11. **编译与代码生成**：先生成能正确回放的程序，再优化成接近人工编写质量、可读、可维护的代码。
12. **真实回放与晋级**：重新执行并独立验证；无法证明成功就停止，通过多次真实验证后才能晋级正式技能。

### 最核心的关系

- 一次演示不等于自动化。
- 演示 + 真实证据 = 完整操作经验。
- 操作经验 + 状态理解 + 目标落地 = 可复用行为。
- 可复用行为 + 参数化 + 验证 = 统一自动化模型。
- 统一自动化模型 + 健壮性工程 + 真实回放 = 正式自动化技能。

### 从简单到复杂

**可控 HTML → 真实浏览器 → 简单桌面应用 → 普通结构化桌面应用 → 动态桌面应用 → 千牛 / 微信等复杂业务应用 → 跨应用长期工作流。** 每一级都重复“真实执行、理解、提炼、生成、回放、验证”。

### 当前开发优先级

- **P0 正确性门禁**：关键动作未经独立验证，不能晋级正式自动化。
- **P1 浏览器 Recorder Benchmark**：先完成低噪声环境下“录制、理解、提炼、参数化、生成、回放、验证”的完整闭环。
- **P2 完整操作经验模型**：原始 Trace 不再直接变成最终 Flow。
- **P3 Target + State + Geometry 公共能力**：补齐状态、目标、多定位候选、窗口 / 区域 / 元素相对坐标和局部截图。
- **P4 有效路径提炼 + 行为归纳 + 统一自动化模型**：把一次具体操作真正转成可复用行为。
- **P5 高质量技能 / 工作流 / 代码生成**：先正确可回放，再优化到人工质量。
- **P6 简单桌面应用**：Calculator / Settings / Text Editor。
- **P7 普通和动态桌面应用**。
- **P8 千牛 / 微信等复杂业务应用综合验证**。

## 1. 文档定位与边界

- 上位文档：`agent-first-recorder.md`；配套框架：`docs/frameworks/automation-framework.md`、`app-development-framework.md`、`capability-development.md`。
- 本文描述目标架构和开发方法，不代表所有能力已经实现。
- 千牛案例基于历史真实代码 `examples/app/qianniu.js`，历史提交 `008d9d9726d4ab9ec215a73f6d30ec7e0f7e763e`；用于校准架构，不用于证明当前 Recorder 已完成。
- Recorder 目标不是宏录制，而是把一次真实成功操作转成可核验、可参数化、可重复执行的自动化知识和程序。

## 2. 第一次运行：先真实完成任务，再提炼

第一次运行优先顺序是：**理解任务、探索界面、完成业务、确认结果**。不要求 Agent 一边探索一边直接写出最终高质量代码，但必须同步留下足够信息。

- **目标信息**：用户目标、当前子目标、预期业务结果。
- **语义信息**：准备操作什么、为什么操作、目标对象是什么。
- **实际动作**：工具调用、点击、输入、滚动、窗口切换、等待等。
- **状态信息**：动作前状态、动作后状态、实际变化。
- **结果信息**：是否成功、是否重试、是否进入恢复路径。
- **真实证据**：窗口信息、结构化 UI、截图、OCR、Layout、工具结果和独立验证。

可信度原则：**真实证据 > 工具实际结果 > Agent 结构化提示 > Agent 自然语言说明。** Agent 的语义信息很有价值，但默认只能作为提示、候选或假设，不能自动成为事实。

## 3. Recorder 的学习单位：完整操作经验

普通宏可能只记录“点击坐标、等待、输入、再次点击”。OpenDesk 应记录：**动作前状态 + 操作目标 + 实际动作 + 动作后状态 + 实际结果 + 验证 + 证据**。

例如联系人操作应表达为：当前处于联系人搜索状态；目标是搜索输入框；输入联系人名称；搜索结果刷新；目标变成结果中的联系人；打开联系人；通过聊天区域标题或内容确认已经切换成功。

因此后续行为归纳的基本输入不应只是裸 Event，而应是带状态、目标、结果和证据的完整操作经验。

## 4. UI 状态、目标与坐标

### UI 状态结构

建议统一按以下层级理解桌面：**应用 > 窗口 > 页面 / 状态 > 区域 > 元素。** 第一次进入陌生应用或陌生状态时进行较完整观察，建立页面、区域、关键元素和状态模型；后续优先复用缓存，只重新观察发生变化或置信度不足的部分。

### 目标定位原则

桌面端不能假设只有坐标，也不能假设永远存在完整 UI Tree。默认优先级是：**结构化接口 / Accessibility；角色、名称、文字、稳定标识；页面 / 区域 / 父级 / Anchor；OCR；布局与相对空间关系；图像 / 模板；视觉模型；最后才是坐标回退。**

关键判断：

- 语义目标不是 Locator。
- Locator 不是坐标。
- 坐标只是目标在当前状态下投影出的最终执行位置。
- 一个目标应保存多个候选识别信号，而不是永久固化一个坐标。

### 坐标与几何关系

至少需要统一处理：屏幕坐标、显示器坐标、窗口坐标、窗口内容区坐标、区域坐标、元素坐标、归一化坐标、截图坐标。长期自动化应表达“目标应用、目标窗口、当前状态、目标区域、目标元素、元素内部动作位置”，运行时再完成坐标转换。

窗口截图、区域截图、相对坐标、坐标转换、目标定位和最终动作位置解析应成为 OpenDesk 通用自动化基础能力，而不是由每个 Recorder 或应用脚本重复手写。

## 5. 有效路径提炼与行为归纳

Agent 第一次探索经常混合：看界面、错误点击、返回、搜索、错误输入、修正、固定等待、重试、恢复和最终成功。正式自动化不能把这些全部复制进去。

有效路径提炼至少包括：

- 动作归组；区分业务动作、状态准备、探索、错误、等待、重试、恢复。
- 删除无效探索和错误路径；保留真正完成业务所需的成功路径。
- 合并连续操作；例如连续键入合并为一次输入。
- 识别常量和变量；例如“张三”成为联系人参数，“你好”成为消息参数。
- 识别重复行为和技能边界；例如“点击搜索框 + 输入联系人 + 选择结果 + 验证页面”抽象为“打开联系人(contactName)”。
- 推断前置条件、后置条件、分支、完成条件和有限恢复策略。

核心原则：**正式脚本保存的是完成任务所需的可靠行为，不是第一次探索过程的录像。** 不参数化的结果更接近录像；经过可靠参数化后才开始接近可复用技能。

## 6. 浏览器 Recorder：先解决简单环境下的核心问题

浏览器拥有 DOM、事件、节点属性、文字和层级关系，最适合先研究“怎样把一次粗糙录制变成长期稳定代码”。浏览器建议处理链为：**真实操作；记录 DOM / Event；确定实际元素；生成多个候选选择器；判断唯一性和稳定性；淘汰脆弱选择器；组合可靠定位；转换成业务步骤；删除探索和无效操作；识别变量；形成工作流；生成可读代码；真实回放；验证结果。**

重点不是“这一次能不能找到节点”，而是“哪些身份特征跨运行、跨状态变化仍然稳定”。因此：**当前唯一不等于长期稳定。**

浏览器阶段优先验证：事件记录、DOM 元素身份、多候选 Selector、动态 ID / Class、重复元素消歧、文字 / Role / Test ID、异步状态、滚动、Dialog、变量提取、步骤归纳、代码生成和真实回放。

## 7. 感知预算：减少截图和在线大模型消耗

正常路径不能设计成每一步都截全屏并上传在线视觉模型。建议按成本逐级使用：**已有结构和缓存；Accessibility / DOM / 窗口信息；OCR / Layout / 图色；局部区域截图；较大窗口区域视觉分析；完整窗口视觉分析；全屏视觉分析仅用于困难情况。**

执行原则：

- 初次进入陌生状态可以进行较完整分析；已知状态优先使用缓存。
- 已知目标区域后优先局部截图，局部变化只分析局部。
- OCR、Layout、图色可以解决时，不调用在线视觉模型。
- 结构不足、歧义、复杂自绘界面、抽象和修复时，再升级 Vision / Agent。
- 正常稳定回放尽量不依赖在线大模型。

## 8. 统一自动化模型、代码生成与验证

长期结构不应停留在 `Raw Trace → Flow → JavaScript`。目标应逐渐形成：**原始证据；完整操作经验；语义行为；统一自动化模型；可执行工作流模型；生成代码 / Skill / Playbook。**

统一自动化模型至少逐步表达：应用、窗口、页面 / 状态、区域、元素、语义目标、多候选 Locator、Geometry、变量、可验证动作、技能、工作流、条件 / 分支、恢复、证据、置信度和来源。

代码生成分两步：

- **先正确可回放**：可以重复执行、真正完成任务、能够验证结果、失败时不会继续假装成功。
- **再优化成人工质量**：整理函数边界、业务语义命名、提取变量、优化 Locator、减少固定坐标、减少固定 sleep、增加状态检查、增加动作后验证、增加明确失败处理和有限恢复、删除录制冗余。

JavaScript 是可重新生成的交付物，不是自动化知识的唯一事实源。

真实回放时依次完成：识别应用和状态；解析变量；定位目标；解析最终动作位置；执行动作；重新观察；验证结果。定位失败时尝试其他可靠候选、更新状态 / 区域、重新观察必要范围，必要时才请求 Vision / Agent；验证失败时判断动作和业务结果，执行有限恢复，无法证明成功则停止。

## 9. 从简单到复杂的 Benchmark

- **Level 1 可控 HTML**：事件、DOM 身份、多 Selector、动态位置、输入 / 点击、变量、代码生成、回放验证。
- **Level 2 真实浏览器**：动态 DOM、异步状态、滚动、Dialog、多候选元素、长期稳定 Selector。
- **Level 3 简单桌面应用**：Calculator、Settings、Text Editor；验证窗口身份、Accessibility、窗口相对坐标、OCR、动作后验证。
- **Level 4 普通结构化桌面应用**：多区域、多输入框、列表、Tab、Dialog、多页面状态。
- **Level 5 动态桌面应用**：Resize、滚动、DPI / 坐标变化、动态布局、虚拟列表、自绘 UI、不完整 Accessibility。
- **Level 6 复杂业务应用**：微信、千牛；验证多区域、多状态、动态列表、OCR / Vision、强业务验证、Recovery、高风险动作保护。
- **Level 7 跨应用长期工作流**：多应用、多窗口、Clipboard / File、Checkpoint、Retry / Recovery、长时间运行和状态恢复。

复杂应用用于后期综合验证，不能替代基础能力 Benchmark；基础能力没有稳定证明前，不应通过千牛或微信的单次成功声称 Recorder 架构已经成熟。

## 10. 千牛历史代码反向案例：已完成验证

### 已验证的正确经验

历史 `qianniu.js` 已经自然出现：确认 `AliWorkbench.exe` 和窗口标题；按窗口或局部区域截图；使用像素颜色、颜色相似度和色块查找判断状态 / 按钮；根据局部色块位置、截图偏移和窗口原点计算最终点击位置；根据窗口宽高动态计算订单区和发送区；复制后通过剪贴板变化验证动作；主流程形成“消息窗口、联系按钮、接待中心、订单状态、复制并发送”的业务步骤。

这说明真实业务中已经存在一条有效基础模式：**应用 / 窗口身份；局部感知；区域 / 目标；相对 Geometry；实际动作；结果验证。**

### 不应原样继承的实现债务

历史代码同时存在：`130`、`70`、`480`、`370`、`20`、`65` 等固定偏移和尺寸；大量 `sleep(500/800/1000)`；部分状态只依赖固定像素或单一颜色；`PageUp`、`End` 等实现性路径和业务语义混合；发送后缺少强业务验证；部分函数 `return true` 只能说明流程走完；状态准备、恢复、定位动作和正常业务步骤没有统一模型区分。

Recorder 应保留真实业务经验，但把固定偏移升级为窗口 / 区域 / 元素相对关系，把固定等待升级为状态等待，把单一定位升级为多候选和多信号定位，把弱成功判断升级为动作后和业务结果验证，并在生成正式代码前区分业务步骤、状态准备、探索、重试和恢复。

### 千牛案例直接提高的四项优先级

1. **窗口 / 区域相对坐标公共化**：真实业务已经反复需要局部截图坐标、窗口坐标和屏幕坐标之间转换，这不应继续由应用脚本手写。
2. **局部低成本感知优先**：已知窗口和区域后，颜色、OCR、Layout、局部截图往往已经足够；在线视觉模型不是默认路径。
3. **有效路径提炼必须成为正式阶段**：真实脚本天然混合状态准备、等待、重试、恢复和业务动作，不能机械转换成最终代码。
4. **动作后业务验证必须强化**：点击成功、函数未报错、等待结束都不能证明业务成功，关键步骤需要可独立观察的状态或结果。

千牛现阶段最适合用于发现通用 API 缺口、验证窗口 / 区域 / Geometry 设计、验证局部感知预算，以及检查 Recorder 能否把人工脚本中的脆弱实现提炼成更稳定的自动化模型，而不是用作最初级 Benchmark。

## 11. 需要逐步补齐的公共能力

- 窗口截图和指定窗口区域截图；多坐标空间和统一坐标转换；窗口相对、区域相对、元素相对动作。
- Accessibility / DOM / OCR / Layout / Image 的统一证据表达；页面、区域和元素状态模型；State / Layout Cache 与失效机制。
- Target Candidate Set；多 Locator 解析与排序；独立 Verifier / Oracle；Evidence、Confidence、Provenance。
- 可验证动作；Variable / Parameter 模型；Skill / Workflow 模型；Recorder 生成物到正式运行时 API 的稳定编译接口。

这些能力应优先进入 OpenDesk Automation Framework / Runtime 公共基础层，而不是在 Recorder 和每个具体应用脚本中重复实现。

## 12. 工程原则

1. Evidence 高于 Agent 自述；动作执行成功不等于业务成功。
2. 坐标不是元素身份；Locator 不是目标；一次目标优先保存候选集合。
3. 当前唯一的 Selector 不等于长期稳定的 Selector。
4. 第一次运行优先真正完成任务，同时保存足够证据和语义。
5. 正式脚本只保留有效成功路径，不复制探索过程。
6. 完整操作经验比裸 Event 更适合作为行为学习单位。
7. 稳定路径优先使用传统规则、结构化接口、缓存和局部低成本感知。
8. OCR、Layout、图色能够解决时，不调用在线视觉模型；Vision / Agent 主要处理结构不足、歧义、抽象、诊断和修复。
9. 正常稳定回放尽量不依赖在线大模型。
10. 窗口、区域、元素相对 Geometry 应由通用 API 提供，业务脚本不应长期手写坐标换算。
11. 固定等待、重复点击、状态准备、探索和恢复动作必须先分类，再决定是否进入正式成功路径。
12. 未能独立证明成功的关键步骤不能晋级正式自动化。
13. JavaScript 是派生产物，不是唯一事实源。
14. 先完成 Browser Recorder 低噪声闭环，再逐步增加 Desktop 不确定性。
15. 复杂应用用于后期综合验证，不能替代基础 Benchmark。
