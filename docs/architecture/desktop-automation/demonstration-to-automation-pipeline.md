# Agent 驱动的示范到自动化生成主链

## 状态与定位

- 文档性质：下一阶段架构基线 / 研究结论。
- 上位架构：`agent-first-recorder.md`。
- 配套框架：`docs/frameworks/automation-framework.md`、`app-development-framework.md`、`capability-development.md`。
- 本文不重新发明一级架构，而是把 Recorder 从“真实执行”到“高质量可重复自动化”的具体执行步骤补完整。
- 本文描述目标架构与开发方法，不代表所有能力已经实现。
- 本文已经使用 OpenDesk 历史真实应用代码 `examples/app/qianniu.js`（历史提交 `008d9d9726d4ab9ec215a73f6d30ec7e0f7e763e`）进行反向案例校准；案例证据用于强化二级执行原则，不用于证明通用 Recorder 已经完成。

## 一、一级主链：冻结

当前一级结构没有严重架构错误，建议冻结：

```text
任务来源：Agent / 人工 / 脚本
↓
真实任务执行
↓
多模态证据采集
↓
界面与状态重建
↓
元素、动作与语义落地
↓
行为规律归纳
↓
统一自动化模型
↓
工作流 / 技能合成
↓
健壮性工程
↓
编译生成
↓
真实回放与验证
↓
修复 / 晋级正式技能
```

核心目标不是生成普通宏，而是：

> 从一次真实成功的业务操作中，保留可核验证据，理解状态与目标，提炼真正有效的行为规律，最终生成接近人工编写质量、可重复执行、可验证、可维护的自动化程序。

## 二、最关键的十个执行步骤

1. 先让 Agent 真实完成一次任务。
2. 同时记录动作、语义、状态和证据。
3. 理解应用、窗口、页面、区域和元素。
4. 把语义目标对应到真实 UI，而不是只保存坐标。
5. 把完整执行轨迹提炼成真正有效的成功路径。
6. 把具体步骤抽象成业务步骤和可复用技能。
7. 把具体值提取成变量和参数。
8. 生成能够重复执行的代码。
9. 优化定位、坐标、验证、恢复和代码可读性。
10. 真实回放，通过后才晋级为正式自动化。

## 三、第一次运行：先真实完成任务

第一次运行的第一目标不是立即写出完美代码，而是先真正完成用户任务，并确认业务结果成立。

执行过程中同步保存：

- 用户目标与当前子目标；
- 当前准备完成什么操作；
- 操作目标是什么；
- 实际调用了什么工具或执行了什么动作；
- 动作前状态；
- 动作后状态；
- 预期变化；
- 实际变化；
- 是否成功；
- 是否重试；
- 是否进入恢复路径；
- 支撑以上判断的真实证据。

原则：

```text
真实证据
> 工具调用和实际结果
> Agent 的结构化提示
> Agent 的自然语言说明
```

Agent 提供的语义非常有价值，但只能作为提示、候选或假设，不能自动成为事实。

## 四、记录对象：不是鼠标键盘，而是完整操作经验

普通宏可能只记录：

```text
点击坐标
等待
输入文字
再次点击坐标
```

OpenDesk Recorder 应逐步形成：

```text
动作前状态
+
操作目标
+
实际动作
+
动作后状态
+
结果
+
验证
+
证据
```

例如不只记录“点击某坐标”，而要尽可能知道：

```text
当前处于联系人搜索状态
↓
目标是联系人搜索输入框
↓
输入联系人名称
↓
搜索结果发生变化
↓
选择目标联系人
↓
聊天区域切换到对应联系人
↓
通过页面状态和内容验证成功
```

这类完整经验才是后续行为归纳和技能生成的学习基础。

## 五、优先从浏览器录制建立简单环境下的完整链路

不要一开始从微信、千牛等复杂桌面软件推导全部架构。

优先顺序：

```text
可控网页测试环境
↓
真实浏览器网页
↓
简单桌面程序
↓
结构化桌面程序
↓
动态桌面程序
↓
复杂业务软件
↓
跨应用长期工作流
```

浏览器拥有 DOM、事件、节点属性、文字、层级关系等结构化信息，最适合先研究清楚：

> 怎样把“一次录制得到的粗糙轨迹和代码”，逐步优化成长期稳定、可读、可维护、可验证的自动化代码。

浏览器场景的核心处理链：

```text
真实操作
↓
记录 DOM / 事件
↓
确定实际操作元素
↓
生成多个候选定位方式
↓
判断候选的唯一性和稳定性
↓
删除容易变化的定位方式
↓
组合更可靠的定位条件
↓
转换成有业务语义的步骤
↓
删除探索和无效操作
↓
识别变量
↓
形成工作流
↓
生成高质量可读代码
↓
真实回放
↓
验证结果
```

核心判断：

```text
当前唯一
!=
长期稳定
```

普通 Recorder 的选择器和代码质量经常较低，本质上是因为它只需要找到“这一次操作的节点”，而长期自动化需要判断“哪些身份特征跨运行仍然稳定”。

## 六、从浏览器原理迁移到桌面应用

桌面端不能假设只有坐标，也不能假设永远能够获得完整 UI Tree。

默认逐级使用：

```text
结构化接口 / Accessibility
↓
角色、名称、文字和稳定标识
↓
页面、区域、父级和 Anchor
↓
OCR
↓
布局与相对空间关系
↓
图像 / 模板
↓
视觉模型
↓
坐标回退
```

因此：

```text
语义目标
!=
定位方式

定位方式
!=
坐标

坐标只是最终动作位置
```

一次目标应尽可能保存多个候选识别信号，而不是永久固化一个坐标。

## 七、先建立界面状态，再频繁操作

第一次进入陌生软件或陌生页面时，可以进行较完整的窗口分析：

```text
应用
└── 窗口
    └── 页面 / 状态
        └── 区域
            └── 元素
```

例如先识别：

- 左侧导航区域；
- 列表区域；
- 主内容区域；
- 输入区域；
- 按钮；
- 输入框；
- 文本和图标。

然后保存可复用的状态与布局信息。后续重复操作优先复用已有模型，只重新观察发生变化或置信度不足的区域。

## 八、控制截图和在线大模型成本

不能把正常路径设计成：

```text
每执行一步
→ 截全屏
→ 上传在线视觉模型
→ 重新理解整个桌面
```

建议按成本逐级升级：

```text
已有结构化信息和缓存
↓
Accessibility / DOM / 窗口信息
↓
OCR / Layout / 图色
↓
局部区域截图
↓
较大窗口区域视觉分析
↓
完整窗口视觉模型
↓
全屏视觉模型，仅困难情况
```

同时遵循：

- 初次进入陌生状态可以进行较完整分析；
- 已知状态优先使用缓存；
- 局部变化只分析局部区域；
- OCR、Layout、图色可以解决时，不请求在线大模型；
- 结构信号不足、歧义、抽象和修复时，再使用视觉模型 / Agent；
- 正常稳定回放尽量不依赖在线大模型。

千牛历史代码已经提供了一个真实佐证：它先确认 `AliWorkbench.exe` 和目标窗口，再针对窗口或窗口内部订单区域截图，并用 `ImageColor.pixel`、`hasColor`、`findColorBlocks` 等低成本感知完成状态判断和目标寻找。这说明“先窗口、再局部、再按需要升级感知”的方向具有真实应用基础，而不是只来自理论推演。

## 九、窗口相对坐标和 Geometry 必须成为通用基础能力

长期自动化不能主要依赖一次运行的全局屏幕坐标。

至少需要统一理解：

```text
屏幕坐标
显示器坐标
窗口坐标
窗口内容区坐标
区域坐标
元素坐标
归一化坐标
截图坐标
```

目标应该逐渐从：

```text
click(1532, 827)
```

转变为：

```text
目标应用
└── 目标窗口
    └── 当前页面
        └── 目标区域
            └── 目标元素
                └── 元素内部动作位置
```

执行时再完成各坐标空间之间的转换。

窗口截图、区域截图、相对坐标、坐标转换、目标定位与最终坐标解析应成为 OpenDesk 通用自动化基础能力，而不是只存在 Recorder 内部。

千牛历史代码已经手工实现过这种转换：先在局部截图中找到色块中心点，再加上截图区域偏移和窗口原点，最终转换为屏幕点击坐标；订单区域同样大量使用 `win.x`、`win.y`、`win.width`、`win.height` 与局部偏移组合计算目标位置。Recorder 不应该重新发明一套私有坐标体系，而应推动这些能力进入公共自动化 API。

## 十、完整执行轨迹必须经过有效路径提炼

Agent 第一次探索可能包含：

- 看界面；
- 尝试错误目标；
- 返回；
- 搜索；
- 输入错误内容；
- 修正；
- 重试；
- 最终成功。

这些不能全部进入正式脚本。

需要经过：

```text
完整执行轨迹
↓
动作归组
↓
识别探索行为
↓
识别错误和无效动作
↓
识别恢复动作
↓
提取真正成功路径
↓
合并连续操作
↓
形成最小必要步骤
```

正式自动化保留的是“完成任务所必需的可靠步骤”，不是第一次探索过程的录像。

千牛历史代码也说明真实业务脚本天然会混入实现性动作，例如点击订单区域、按 `PageUp` 回到顶部、固定等待、按 `End`、再次截图、移动鼠标后再等待等。它们有些是必要状态准备，有些只是当前实现策略。Recorder 必须区分“业务必需步骤”和“当前实现产生的探索、等待、重试或定位动作”，不能机械复制整条轨迹。

## 十一、从具体动作抽象为业务步骤和技能

例如：

```text
点击搜索框
输入联系人名称
等待搜索结果
选择联系人
验证聊天页面
```

可以逐渐抽象为：

```text
打开联系人(contactName)
```

再把：

```text
聚焦消息输入区
输入消息
发送
验证消息出现
```

抽象为：

```text
发送消息(message)
```

最后形成：

```text
发送消息给联系人(contactName, message)
```

判断是否应该形成 Skill，至少考虑：

- 是否具有明确业务语义；
- 是否有稳定输入和输出；
- 是否可以独立验证；
- 是否可以在其他工作流中复用；
- 是否具有相对稳定的开始和结束状态。

## 十二、在成功路径稳定后提取变量和参数

一次具体执行中，需要进一步判断：

```text
什么是流程结构？
什么只是本次运行的具体值？
```

例如：

- “张三” → 联系人变量；
- “你好” → 消息变量；
- 文件路径 → 文件变量；
- 日期 → 日期变量；
- 搜索关键词 → 搜索变量。

逐渐形成：

```text
稳定动作结构
+
可变输入参数
```

不参数化的结果更接近录像；经过可靠参数化以后才开始接近可复用 Skill。

## 十三、先生成正确可回放代码，再优化到人工质量

第一阶段先确保：

- 能够重复执行；
- 能够真正完成任务；
- 能够验证最终结果；
- 失败时不会继续假装成功。

第二阶段再进行代码质量优化：

- 整理函数边界；
- 提取变量；
- 使用业务语义命名；
- 优化定位方式；
- 减少固定坐标；
- 减少固定 sleep；
- 增加前置状态检查；
- 增加动作后验证；
- 增加明确的失败处理；
- 增加有限恢复；
- 删除录制产生的冗余步骤；
- 保留必要注释和来源关系。

最终目标不是：

```text
click
sleep
click
type
```

而是形成可读的：

```text
确认当前状态
↓
定位业务目标
↓
执行可验证动作
↓
确认业务结果
↓
必要时进入有限恢复
```

千牛代码进一步说明“动作执行成功”和“业务成功”必须分开。例如复制按钮操作后通过剪贴板变化进行了实际验证，这是值得继承的模式；但消息发送路径在点击发送按钮后主要依靠固定等待并直接返回成功，没有继续证明消息确实发送或业务结果成立，这类弱验证不应该被 Recorder 原样晋级为正式自动化。

## 十四、统一自动化模型位于代码之前

不要长期保持：

```text
Raw Trace
↓
Flow
↓
JavaScript
```

目标结构应逐渐演进为：

```text
原始证据
↓
完整操作经验
↓
语义行为
↓
统一自动化模型
↓
可执行工作流模型
↓
生成代码 / Skill / Playbook
```

统一自动化模型至少需要逐步表达：

- 应用；
- 窗口；
- 页面 / 状态；
- 区域；
- 元素；
- 目标；
- 多候选定位方式；
- Geometry；
- 变量；
- 可验证动作；
- Skill；
- Workflow；
- 条件和分支；
- Recovery；
- Evidence；
- Confidence；
- Provenance。

JavaScript 是可重新生成的交付物，而不是自动化知识的唯一事实源。

## 十五、真实回放与晋级

生成自动化后必须重新进入真实环境执行：

```text
识别应用
↓
识别当前状态
↓
解析变量
↓
定位目标
↓
解析最终动作位置
↓
执行动作
↓
重新观察
↓
验证动作结果
↓
继续下一步
```

失败时：

```text
定位失败
├── 尝试其他可靠候选
├── 更新状态 / 区域
├── 重新观察必要范围
└── 必要时再请求视觉模型 / Agent

验证失败
├── 判断动作是否真正失败
├── 判断 UI 是否发生预期外变化
├── 执行有限恢复
└── 无法证明成功时立即停止
```

只有经过真实回放和独立验证的结果才能晋级为正式 Skill。

## 十六、从简单到复杂的验证路线

### Level 1：可控 HTML Benchmark

验证：

- 事件记录；
- DOM 元素身份；
- 多选择器候选；
- 选择器优化；
- 动态位置；
- 输入和点击；
- 变量提取；
- 代码生成；
- 回放验证。

### Level 2：真实浏览器应用

增加：

- 动态 DOM；
- 异步状态；
- 滚动；
- Dialog；
- 多候选元素；
- 长期稳定选择器。

### Level 3：简单桌面应用

优先：

- Calculator；
- Settings；
- Text Editor。

验证：

- 窗口身份；
- Accessibility；
- 窗口相对坐标；
- OCR；
- 动作后验证。

### Level 4：普通结构化桌面应用

验证：

- 多区域；
- 多输入框；
- 列表；
- Tab；
- Dialog；
- 多页面状态。

### Level 5：动态桌面应用

验证：

- Resize；
- 滚动；
- DPI / 坐标变化；
- 动态布局；
- 虚拟列表；
- 自绘 UI；
- 不完整 Accessibility。

### Level 6：复杂业务应用

例如微信、千牛。

验证：

- 多区域；
- 多状态；
- 动态列表；
- OCR / Vision；
- 强业务验证；
- Recovery；
- 高风险动作保护。

### Level 7：跨应用、长期运行工作流

验证：

- 多应用切换；
- 多窗口；
- Clipboard / File；
- Checkpoint；
- Retry / Recovery；
- 长时间运行和状态恢复。

每一级都必须重复：

```text
真实执行
→ 理解
→ 生成
→ 回放
→ 验证
```

当前一级没有稳定证明之前，不用更复杂应用代替基础能力验证。

## 十七、需要逐步补齐的通用基础能力

优先检查并完善：

- 窗口截图和指定窗口区域截图；
- 多坐标空间及统一坐标转换；
- 窗口相对、区域相对、元素相对动作；
- Accessibility / DOM / OCR / Layout / Image 的统一证据表达；
- 页面、区域和元素状态模型；
- State / Layout Cache 与失效机制；
- Target Candidate Set；
- 多 Locator 解析与排序；
- 独立 Verifier / Oracle；
- Evidence、Confidence、Provenance；
- 可验证动作；
- Variable / Parameter 模型；
- Skill / Workflow 模型；
- Recorder 生成物到正式运行时 API 的稳定编译接口。

这些通用能力应优先进入 OpenDesk Automation Framework / Runtime 的公共基础层，而不是在每个具体应用脚本和 Recorder 中重复实现。

## 十八、工程原则

后续实现必须长期遵循：

1. Evidence 高于 Agent 自述。
2. 坐标不是元素身份。
3. 当前唯一的 Selector 不等于长期稳定的 Selector。
4. 一次目标优先保存候选集合，而不是单一定位结果。
5. 第一次运行优先真正完成任务，同时保存足够信息。
6. 正式脚本只保留有效路径，不复制探索过程。
7. 操作经验比裸 Event 更适合作为行为学习单位。
8. 稳定路径优先使用传统规则、结构化接口和缓存。
9. OCR、Layout、图色能够解决时，不调用在线视觉模型。
10. Vision / Agent 主要处理结构不足、歧义、抽象、诊断和修复。
11. 正常稳定回放尽量不依赖在线大模型。
12. 未能独立证明成功的关键步骤不能晋级正式自动化。
13. JavaScript 是派生产物，不是唯一事实源。
14. 先完成 Browser Recorder 的低噪声闭环，再逐步增加 Desktop 不确定性。
15. 复杂应用用于后期综合验证，不能替代基础能力 Benchmark。
16. 局部感知优先于整屏感知：先确定应用和窗口，再缩小到页面、区域和目标附近。
17. 窗口、区域、元素相对 Geometry 应由通用 API 提供，业务脚本不应长期重复手写坐标换算。
18. 真实轨迹中的固定等待、重复点击和恢复动作必须经过分类，不能机械进入正式成功路径。
19. 动作调用成功不等于业务成功，关键动作必须有独立的动作后状态或业务结果验证。

## 十九、千牛历史代码反向案例：已完成验证

### 19.1 证据范围

本节基于 OpenDesk 历史真实应用代码：

```text
examples/app/qianniu.js
历史提交：008d9d9726d4ab9ec215a73f6d30ec7e0f7e763e
```

该文件属于历史代码，不代表当前 `master` 仍保留相同路径或实现；这里使用它的目的，是检查真实桌面业务自动化曾经采用过哪些有效模式，以及哪些实现债务不应被 Recorder 学习。

### 19.2 已经验证的正确经验

千牛代码已经自然形成以下执行链：

```text
确认应用和目标窗口
↓
按窗口或窗口局部区域截图
↓
通过图色等低成本方式判断状态和目标
↓
在局部区域中找到色块 / 业务对象
↓
将局部坐标转换为窗口和屏幕坐标
↓
执行点击、键盘、剪贴板等动作
↓
对部分关键结果进行检查
```

具体已经出现：

- 使用 `exeName === 'AliWorkbench.exe'` 和窗口标题确认当前业务窗口；
- 对消息通知窗口和订单区域进行局部截图，而不是始终分析全屏；
- 使用像素颜色、颜色相似度、色块查找判断订单状态和按钮；
- 先获取色块相对坐标，再加截图区域偏移和窗口原点得到最终点击位置；
- 使用窗口宽高动态计算订单区域、发送区域等位置；
- 复制操作后通过剪贴板内容是否变化判断动作是否真正生效；
- 主流程已经具有“消息窗口 → 联系按钮 → 接待中心 → 订单状态 → 复制并发送”的业务步骤结构。

这些事实强化了以下架构判断：

```text
应用 / 窗口身份
↓
局部感知
↓
区域 / 目标
↓
相对 Geometry
↓
实际动作
↓
结果验证
```

这条链应成为桌面 Recorder 的重要基础模式。

### 19.3 不应该由 Recorder 原样继承的实现债务

千牛代码同时存在大量针对当时界面的手工实现细节：

- `130`、`70`、`480`、`370`、`20`、`65` 等固定偏移和尺寸；
- `sleep(500)`、`sleep(800)`、`sleep(1000)` 等固定等待；
- 某些状态依赖少量固定像素点或单一颜色；
- 订单区先点击、再 `PageUp`、再 `End` 等实现性路径与业务语义混合；
- 发送消息后主要依赖固定等待，缺少“消息已经真正发送”的强业务验证；
- 局部函数返回 `true` 有时只能说明函数流程走完，并不能独立证明最终业务目标完成；
- Recovery、状态准备、定位动作与正常业务步骤没有统一模型区分。

因此 Recorder 不应该学习成：

```text
记录什么
↓
原样生成什么
```

而应该：

```text
真实执行轨迹
↓
保存证据和业务语义
↓
区分业务步骤 / 状态准备 / 探索 / 重试 / 恢复
↓
提取有效成功路径
↓
把固定偏移升级为窗口 / 区域 / 元素相对关系
↓
把固定等待升级为状态等待
↓
把单一定位升级为候选目标与多信号定位
↓
补齐动作后和业务结果验证
↓
再生成正式自动化
```

### 19.4 对 Recorder 架构的直接校准

千牛案例没有要求修改一级主链，但把以下四项从“合理设计建议”提升为“已有仓库真实案例支持的高优先级能力”：

1. **窗口和区域相对坐标必须公共化**
   - 真实业务已经反复需要窗口原点、窗口宽高、局部截图坐标和最终屏幕坐标之间转换。
   - 这些转换不应继续由每个应用脚本手工计算。

2. **局部低成本感知必须优先**
   - 已知窗口和区域后，颜色、OCR、Layout、局部截图往往已经足够。
   - 在线视觉模型应该用于结构信号不足、歧义和修复，而不是成为每一步默认依赖。

3. **有效路径提炼必须是正式阶段**
   - 真实脚本会混合状态准备、定位、等待、重试、恢复和业务动作。
   - Recorder 必须先分类和蒸馏，再生成正式工作流。

4. **动作后业务验证必须强化**
   - “点击成功”“函数没有报错”“等待结束”都不能证明业务成功。
   - 关键步骤必须尽量观察可独立证明的状态变化或业务结果。

### 19.5 千牛案例在整体验证路线中的位置

千牛不应该被用作最初级 Recorder Benchmark。

正确顺序仍然是：

```text
可控网页环境
↓
真实浏览器
↓
简单桌面应用
↓
结构化桌面应用
↓
动态桌面应用
↓
千牛 / 微信等复杂业务应用
```

千牛当前最有价值的作用是：

- 反向发现通用 API 缺口；
- 验证窗口 / 区域 / Geometry 设计是否能够覆盖真实历史用法；
- 验证局部感知预算是否合理；
- 检查 Recorder 是否能把人工脚本中的脆弱实现提炼成更稳定的自动化模型；
- 在基础能力通过前，不承担“证明整个 Recorder 正确”的职责。

## 二十、当前推荐开发顺序

```text
P0  正确性门禁
    └── 未验证的关键动作不能晋级正式自动化

P1  浏览器 Recorder Benchmark
    └── 先证明录制 → 理解 → 提炼 → 参数化 → 生成 → 回放 → 验证完整闭环

P2  完整操作经验模型
    └── 原始 Trace 不再直接变成最终 Flow

P3  Target + State + Geometry 公共基础能力
    └── 尤其补齐窗口 / 区域 / 元素相对坐标和局部截图

P4  有效路径提炼 + 行为归纳 + 统一自动化模型
    └── 把一次具体操作真正转换为可复用行为

P5  高质量 Skill / Workflow / Codegen
    └── 先正确可回放，再优化成人工质量代码

P6  简单桌面应用验证
    └── Calculator / Settings / Text Editor

P7  普通和动态桌面应用

P8  千牛 / 微信等复杂业务应用综合验证
```

当前不建议因为千牛案例已经存在，就跳过浏览器和简单桌面 Benchmark。历史代码用于提供真实约束；从简单到复杂的验证梯度用于证明新架构是否真正可靠。
