# OpenDesk API Reference Documentation Rules

本文件定义 `docs/api/` 的强制文档格式。

目标是让 `docs/api/` 保持为一致、可检索、适合人类和 Agent 阅读的 SDK/API Reference，而不是源码分析、设计笔记或维护日志。

## 1. 文档单位

一个公开类、namespace 或主要全局对象原则上只使用一个主 API 文件。

例如：

- `UI` → `desktop-ui.md`
- `Geometry` → `geometry.md`
- `mouse` → `mouse.md`
- `page` → `page.md`

同一个类的方法不得仅因为 backend、平台或功能分类不同而拆成多个平行 API Reference 文件。

专题设计、实现原理和内部架构应放入 `docs/architecture/`、`docs/implementation/` 或其他对应目录。

## 2. Heading 层级

### 标题文字与目录导航

所有级别的标题（H1–H6）一律使用纯文本，不得用反引号包裹接口名、参数名、类型名或其他标题文字。不得用转义反引号、HTML 实体或 `<code>` 标签绕过此规则。

此规则适用于 `docs/api/` 及其全部子目录中的 Markdown 文档，也适用于本规则文件里的标题格式示例。

```markdown
## UI.getCapabilities()

### Scope：within

### relativeTo
```

手写目录和 API 导航链接的显示文字、可选 title 也必须使用纯文本，不得携带反引号；不能只清理正文标题而保留目录中的旧格式。

```markdown
- [UI.getCapabilities()](desktop-ui.md#uigetcapabilities "UI.getCapabilities()")
```

正文中的行内代码、参数表、签名和代码块仍保留正常代码格式。不得全局删除文档中的反引号，也不得改写 JavaScript 模板字符串。清理标题时保持原有接口名称、参数、标题级别及顺序；检查生成锚点和跨页链接，只有锚点确实变化时才同步调整链接目标。

### H1：对象或 API 页面

每个 API 文件只能有一个 H1。

```markdown
# UI
```

### H2：公开接口是主导航单位

每一个公开方法、函数、构造器或重要属性必须拥有独立的 H2。

```markdown
## UI.findTexts(text, options?)

## UI.findText(text, options?)

## UI.hasText(text, options?)
```

禁止：

```markdown
## UI.findTexts() / UI.findText() / UI.hasText()：文本接口
```

即使多个接口参数相同、属于同一功能族、互为别名或通常成对调用，也不能共享方法标题。

### 功能分组不得压低方法层级

Text APIs、Image APIs、Native Menu APIs 等分组不得通过 H2 包住方法并把方法降为 H3。

需要视觉分组时使用普通文本或粗体标签：

```markdown
**Text APIs**

## UI.findTexts(text, options?)
## UI.findText(text, options?)
```

### H2：允许的非方法主章节

只有真正的页面级 Reference 内容可以使用 H2，例如：

```markdown
## API 一览
## 公共约定
## 类型
## 错误
## 平台与能力
```

### H3：公共概念或共享选项

公共规则必须放在其所属 H2 下。

```markdown
## 公共约定

### Scope：within
### region
### relativeTo
### Capture mapping 与 DPI
```

不得让 `scope`、`region`、定位策略等概念章节处在公开 API 方法之上。

### H4：公共概念的子模式

```markdown
### relativeTo

#### Direction mode
#### Region mode
```

禁止无理由跳级。

## 3. API 一览

API 总览表中每个接口必须独占一行。

```markdown
| 方法 | 用途 |
| --- | --- |
| `UI.findTexts(text, options?)` | 返回全部匹配文本 |
| `UI.findText(text, options?)` | 返回唯一文本 |
| `UI.hasText(text, options?)` | 判断文本是否存在 |
```

禁止：

```markdown
| `findText / hasText / tapText` | 文本操作 |
```

别名也必须独占一行，并明确标记其 canonical method。

## 4. 方法 Reference 固定结构

每个公开方法按以下顺序描述：

1. 一句话用途
2. **签名**
3. **参数**
4. **返回值**
5. **行为与错误**
6. **示例**

这些内容默认使用粗体标签，不使用额外 heading，避免 TOC 被参数和示例淹没。

即使方法没有参数，也应明确写：

```markdown
**参数**

无。
```

即使返回 `void` / `undefined`，也必须明确描述。

## 5. 共享参数

多个方法共用参数时可以建立公共类型或公共选项章节，但每个方法仍必须独立说明其参数入口。

推荐：

```markdown
**参数**

`text`：目标文本。

`options`：`OpenDeskUITextOptions`，字段见 [文本选项](#文本选项)。
```

禁止只写：

```markdown
参数同上。
```

禁止因为共享参数而省略不同方法的返回值、错误、无结果行为、等待行为或副作用差异。

## 6. 参数表

一个参数或 option 字段一行。

推荐列：

```text
参数 | 类型 | 必填 | 默认值 | 说明
```

禁止把独立参数合并：

```markdown
| `provider` / `providerChain` / `lang` | ... |
| `timeout` / `polling` | ... |
```

应拆为：

```markdown
| `provider` | ... |
| `providerChain` | ... |
| `lang` | ... |
| `timeout` | ... |
| `polling` | ... |
```

联合类型不是多个参数，不得错误拆分：

```text
string | null
OpenDeskWindowInfo | OpenDeskDisplayInfo
```

Markdown 表格中的 `|` 必须正确转义。

## 7. 接口分类与实现边界

Stable、Experimental、Deprecated、Compatibility 等状态属于接口元数据，不应改变接口的 heading 层级。

例如原生菜单仍然属于 `UI`：

```markdown
**Native Menu APIs · Experimental**

## UI.getMenuItems(options)
## UI.findMenuItem(path, options)
## UI.tapMenuItem(path, options)
```

不要因为 native backend 不同而创建另一套层级模型。

## 8. 示例

标记为 JavaScript 的示例必须是可运行 JavaScript。

标记为 JSON 的示例必须是合法 JSON。

类型签名使用 `ts` 或明确的 signature block，不得伪装成可运行 JavaScript。

示例应明确工作目录和必要前置条件。

## 9. 页面内容边界

`docs/api/` 只包含用户调用 Reference 所需内容：

- API 用途
- 签名
- 参数
- 返回值
- 错误
- 状态
- 平台限制
- 权限
- 最小示例
- 必要的共享语义

以下内容不应占据 API Reference 主结构：

- 源码实现历史
- 大段架构推导
- 维护者构建过程
- 测试 harness 内部实现
- 迁移过程记录
- 未来规划

这些内容应链接到其他文档。

## 10. 修改前检查

修改 `docs/api/` 前必须确认：

- 当前 Runtime / 类型声明中的真实接口
- 是否已经存在同类或同 namespace 文档
- 是否会产生重复 API Reference 页面
- 是否影响现有锚点和跨页链接

## 11. 修改后检查

必须至少检查：

- 所有级别的标题是否均为纯文本，不含反引号或行内代码标签
- 手写目录和 API 导航链接的显示文字及 title 是否不含反引号
- 规则文档中的标题格式示例是否也符合上述约定
- 正文行内代码、参数表、签名和代码块是否被完整保留
- 每个公开接口是否独立一行
- 每个公开方法是否独立 H2
- 是否仍存在 `methodA / methodB / methodC` 式方法标题
- 参数是否一项一行
- Heading 是否没有跳级
- 概念章节是否没有压过方法层级
- Markdown table 是否能正确解析
- JavaScript / JSON 示例是否语法有效
- 页内和跨页链接是否有效
- API 一览与详细 Reference 是否一致

## 一句话规则

**一个类一个主文件；一个接口一个条目；一个方法一个 H2；标题使用纯文本；公共概念只能辅助方法，不能取代方法层级。**
