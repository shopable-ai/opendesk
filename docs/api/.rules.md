# OpenDesk API Documentation Rules

本文件定义 `docs/api/` 的强制文档规则。

目标是让这里同时适合人类与 Agent：既能稳定查到 canonical API Reference，也允许必要的用户 Guide、Concept、CLI 与 Protocol 文档，而不会再次把运行模式、产品入口、公共 API 和内部实现混成一页。

## 1. 文档类型

新增或进行实质性重构的 `docs/api/*.md` 应在 frontmatter 中声明 `docType`。允许值：

| docType | 用途 | 主要内容 |
| --- | --- | --- |
| `reference` | 一个公开对象/namespace/主要全局 API 的 canonical Reference | 签名、参数、返回值、错误、状态、平台限制、最小示例 |
| `guide` | 面向用户目标的工作流 | happy path、选择入口、必要概念，并链接 canonical Reference |
| `concept` | 解释公共关系或语义模型 | 概念边界、选择规则；不得复制完整 method contract |
| `protocol` | HTTP/MCP/transport 契约 | endpoint/tool、request、response、错误与 transport 约束 |
| `cli` | CLI 命令契约 | command、flags、stdout/stderr、exit code |
| `index` | 导航/机器索引说明 | 链接、分类、source-of-truth 规则 |

历史文件不要求一次性补齐 frontmatter；但只要某文件被实质性重构，就应确定其当前类型。仅用于旧名称或旧路径跳转的 Markdown 占位页不属于长期文档类型：仓库内引用迁移完成后直接删除，历史由 Git 保存。

## 2. Canonical Reference

一个公开类、namespace 或主要全局对象原则上只使用一个主 Reference 文件。

例如：

- `UI` → `desktop-ui.md`
- `ui` → `ui.md`
- `Geometry` → `geometry.md`
- `automation.app` → `automation-app.md`

运行模式、产品入口、实现 package 不因为名称相关就自动属于同一 Reference：

```text
opendesk -app <dir>        → Runtime/App Mode entry
opendesk.app.json          → package Manifest
App Shell                  → native host/lifecycle architecture
automation.app.*           → current App Mode execution JavaScript API
App.*                      → external desktop application API
```

Guide/Concept 可以解释它们的关系，但参数、返回值、错误等 method contract 只在 canonical Reference 维护。

专题设计、实现原理和内部架构放入 `docs/architecture/`、`docs/implementation/` 或其他对应目录。

## 3. Canonical 方法与兼容别名

兼容别名不得形成第二套完整 API Reference。

规则：

- canonical method 拥有完整 H2 Reference；
- alias 可以拥有独立 H2，但只说明兼容关系、差异和迁移目标，并链接 canonical method；
- 新示例、新 Guide、机器索引的 preferred method 必须使用 canonical method；
- 不要复制同一组参数/返回/错误数百行后只改方法名；
- 方法或名称兼容关系写在 canonical Reference 内，不为它单独创建旧文件名、旧路径 redirect Markdown。

例如：

```text
ui.toast()   = canonical
ui.notify()  = compatibility alias
notify()     = operating-system notification, another API
```

## 4. 主业务链路优先于诊断接口

`getCapabilities()` 默认属于诊断、环境适配与可选分支接口，不应被文档排版成每次业务调用的强制握手。

正常文档顺序优先展示真实业务入口，例如：

```text
LLM.generate()
Agent.run()
automation.app.onAction()
```

随后再说明 `getCapabilities()`。

只有具体 API 的安全/平台合同确实要求 preflight 时，才把 capability 检查加入主链路。

共享字段 `enabled`、`supported`、`configured`、`available`、`reason`、`checked`、`authenticated` 的语义由 [Runtime Capability Contract](../architecture/runtime-capability-contract.md) 统一定义。各 API 可以只暴露需要的子集，也可以增加自己的字段；不得复用同名字段表达另一种含义。

## 5. Heading 层级

### 标题文字与目录导航

所有级别标题使用纯文本，不用反引号、HTML `<code>` 或实体包裹接口名。

```markdown
## UI.getCapabilities()

### Scope：within
```

正文行内代码、参数表、签名、代码块仍正常使用反引号。

### H1：页面

每个 Markdown 页面只能有一个 H1。

### H2：Reference 的公开接口

`docType: reference` 中，每一个公开方法、函数、构造器或重要属性必须拥有独立 H2：

```markdown
## UI.findTexts(text, options?)
## UI.findText(text, options?)
## UI.hasText(text, options?)
```

禁止：

```markdown
## UI.findTexts() / UI.findText() / UI.hasText()
```

功能分组不得把方法降成 H3。需要分组时用普通文字或粗体标签。

允许的页面级 H2 包括 `API 一览`、`公共约定`、`类型`、`错误`、`平台与能力` 等。

### H3/H4：共享概念

公共参数、scope、region、relativeTo 等只能辅助方法，不得压过方法主导航；禁止无理由跳级。

## 6. API 一览

Reference 总览表中每个公开方法独占一行。兼容 alias 也独占一行，并标注 canonical method。

禁止把 `findText / hasText / tapText` 合成一个表项。

## 7. 方法 Reference 固定结构

canonical public method 默认按以下顺序描述：

1. 一句话用途
2. **签名**
3. **参数**
4. **返回值**
5. **行为与错误**
6. **示例**

方法没有参数也写“无”；返回 `undefined` 也明确写出。

共享参数可以链接公共类型/选项章节，但不得只写“参数同上”，也不得因此省略不同方法的返回、错误、无结果、等待或副作用差异。

## 8. 参数表

一个参数或 option 字段一行。推荐：

```text
参数 | 类型 | 必填 | 默认值 | 说明
```

不要把独立参数合并到同一行。联合类型不是多个参数。Markdown 表格中的 `|` 必须正确转义。

## 9. Guide / Concept / Protocol / CLI 边界

### Guide

围绕用户目标组织：入口 → happy path → 关键选择 → 验证 → 相关 Reference。不要重新维护完整 method contract。

### Concept

回答“这些概念是什么关系、什么时候选哪个”。不得因为概念页更容易发现就成为第二份参数/错误 Reference。

### Protocol

HTTP/MCP/transport endpoint 与数据模型可以独立于 JavaScript object Reference。协议页只拥有协议合同，不拥有其底层 Store、线程、SQLite driver 等实现历史。

### CLI

命令行参数、stdout/stderr、exit code 属于 CLI 文档；不要把 CLI 命令伪装成 JavaScript method。

### 旧名称与旧路径

Deprecated/Compatibility 方法或名称只在 canonical Reference 内保留最小迁移说明。仅用于“旧入口 → 新入口”的独立 Markdown 页面在内部引用更新后应删除；若公开站点确实需要保留历史 URL，应由发布/路由层做 redirect，而不是把空壳文档永久留在 `docs/api/`。

## 10. 用户边界与内部实现

`docs/api/` 可以说明用户必须知道的安全/生命周期约束，但以下内容不应占据 API/Guide 主结构：

- 源码实现历史；
- 大段架构推导；
- 内部数据库表、锁文件、driver 选择；
- 维护者构建过程；
- 测试 harness 内部实现；
- 迁移过程日志；
- 未来规划。

这些内容应移动到或链接 `docs/architecture/`、`docs/implementation/`、`docs/maintenance/`。

## 11. 示例

- `js` 示例必须是可运行 JavaScript；
- `json` 示例必须是合法 JSON；
- 类型签名用 `ts` 或明确 signature block；
- 示例说明工作目录和必要前置条件；
- 新示例不得继续扩散 Deprecated/Compatibility 名称。

## 12. 机器索引

`docs/api/runtime-api.ai.json` 是高密度机器索引，不是独立事实源。

它必须：

- 与当前 Runtime/类型声明/canonical Reference 一致；
- canonical `doc` 直接指向真正 Reference，不指向旧路径占位页面；
- 可以链接 Concept/Guide 作为补充，但不能用它们替代 API Reference；
- 不得把已支持能力写成 unsupported；
- preferred/keyMethods 应把正常业务方法放在诊断方法之前；
- compatibility alias 必须明确标记，不能伪装成首选接口。

## 13. 修改前检查

至少确认：

- 当前 Runtime / polyfill / 类型声明中的真实接口；
- 是否已经存在同 namespace 的 canonical Reference；
- 是否会产生重复 Reference；
- 当前页面属于哪一种 `docType`；
- 是否影响现有锚点、机器索引和跨页链接。

## 14. 修改后检查

至少检查：

- 标题层级、纯文本标题、参数表与 Markdown table；
- 每个公开方法是否独立 H2；
- alias 是否只在 canonical Reference 内保留最小兼容说明；
- 是否新增长期保留的旧路径/迁移占位页；
- API 一览与详细 Reference 是否一致；
- Guide/Concept 是否没有复制 method contract；
- 机器索引是否指向 canonical 文档；
- `getCapabilities()` 是否没有无理由抢占主业务链路；
- capability 共享字段是否遵守统一语义；
- JavaScript / JSON 示例语法；
- 页内与跨页链接。

仓库维护者还应运行：

```bash
node scripts/check_api_docs_contract.js
```

## 一句话规则

**一个公开对象一个 canonical Reference；一个方法一个 H2；兼容别名留在 canonical Reference、旧路径占位页迁完即删；业务入口优先于诊断入口；Guide/Concept/Protocol/CLI 与内部实现分层；机器索引不能与 Runtime 事实漂移。**
