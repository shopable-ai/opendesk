# 客户交付：先形成现金流，再沉淀复用资产

状态：本轮业务推进建议，不是已经获客、收入或投放效果的记录。执行广告、报价承诺、付费、发消息或发布之前需要实际授权。

## 目标与边界

优先跑通“明确服务 → 获得询盘 → 限定范围 → 付费试点 → 交付验收 → 实际回款 → 维护与复用”。这条商业流程按需调用 [Agent-to-Recipe](../agent-to-recipe/WORKFLOW.md)，不替换其技术十二阶段。

早期可以外包、项目制、人工辅助或 JS＋Agent 混合交付。客户购买的是可验收的业务结果，不是框架完整度。先限制一个场景、一个业务对象类型和少量应用；跨平台能力分别核验，不因为框架支持 Windows 就承诺每个客户流程已跨平台通过。

## 宣传与获客

先选能实际演示、输入和结果清楚、风险可控的服务。发布说明应包含面向谁、减少哪种重复工作、交付什么、适用范围、仍需人工的部分，以及提交样本／预约评估的入口。不使用尚未实现的无人值守能力或未经测量的节省比例作广告。

可用文案骨架：

> 为【具体人群】把【一项重复流程】做成可重复运行的桌面自动化。先看样本、约定结果与范围，再做小范围付费试点；交付运行说明、验证记录和约定维护。

宣传、转介与小额广告可以先开始，不必等待平台完成。广告开始前由负责人确定真实预算上限、渠道、目标客户与停止条件；按有效询盘、付费项目和实际回款复盘，而不是只看曝光。未形成可交付服务或无法追踪询盘来源时，不扩大投放。

## 各环节的输入、输出与完成条件

| 环节 | 需要什么 | 留下什么／怎样完成 |
| --- | --- | --- |
| 收到询盘 | 客户问题、联系方式、来源和必要授权 | 具体痛点、联系人与下一步，不收集无关账户或秘密 |
| 任务评估 | 脱敏样本、操作示范、应用／系统范围、频率与当前耗时 | 一页项目范围：目标、输入输出、验收、禁止动作、依赖与未决风险 |
| 报价与付费试点 | 可交付边界、预计工作量和维护责任 | 费用、里程碑、付款条件、变更规则、支持范围和复用约定；收款状态依据真实记录 |
| 开发与内部验证 | 已确认范围、实际授权及获准样本 | 按需调用 Agent-to-Recipe；保留已有资产，仅补交付缺口 |
| 客户验收 | 冻结版本、运行说明与约定场景 | 客户确认记录与未完成项；技术通过不能代替客户接受 |
| 结算与交接 | 验收情况、约定支付条件 | 实际到账记录、交付版本与维护联系人；账单或承诺不等于回款 |
| 维护与复盘 | 故障、人工介入、成本和客户反馈 | 范围内修复、超范围新需求、可复用候选及下一次报价依据 |

低价试点以小范围为前提。需求、应用、账号范围或维护期限变化时重新评估，不用无限免费追加来掩盖范围不清。没有真实客户或授权样本时，用明确标注的演示资料验证，不编造客户案例。

## 每单最少保留的数据

负责人维护一份项目记录即可，不必先开发 CRM：来源、任务与范围版本、报价、已收／待收、付款依据、开发和支持工时、实际外部成本、交付版本、客户验收、未决风险、维护边界及资产复用许可。客户身份、业务样本和付款资料保存在获准私有位置，不进入公共仓库。

分开观察：获客、开发、模型／外部服务和维护成本；同时记录人工时间。已回款扣除已付项目成本只是现金贡献口径，不能忽略人工和后续维护后宣称盈利。所有金额和收益填写实际值，未测就标未知。

每个完成项目复盘三个问题：客户是否愿意为该结果继续付费；下一单能否复用已验证部分并降低交付成本；故障和支持是否吞掉收益。得到答案再扩大广告与服务范围。

## 向他人学习与资产化

从公开产品演示、官方资料、获准案例和合作反馈学习获客、范围控制、交付与维护；记录来源、观察到的方法、在本项目的适用假设和试验结果。不能把别人的案例当 OpenDesk 已实现，也不把客户资料或许可不明的代码直接变成共享资产。

先沉淀项目内普通函数；当相似项目确实重复使用后，再提取应用操作或业务能力。可以把“三次相似交付后评估产品化”作为内部试验门槛，而非行业标准或成功保证。只有权限、版本、证据、维护者和支持范围清楚的内容才进入资产目录。

平台留到后面：出现重复购买／复用需求，资产可交接，维护成本可接受时，再评估检索、安装、版本管理、计费与分发。不把这些系统作为第一单的前置条件。

## 外部经验与本轮建议的区别

YC 关于早期客户和手工服务的经验支持“先做不能规模化的事”这一方向，但不能证明本项目已经存在付费需求。本文的广告范围、项目记录和交付门槛是本轮针对 OpenDesk 的建议，需要用真实询盘、交付和回款验证。
