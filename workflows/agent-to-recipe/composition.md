# 基础操作、组合能力与 JS／Agent 混合运行

状态：路线 A 的设计与作业约束；下述能力名称是业务示意，不是新增 OpenDesk API，也不是已验证的聊天应用适配器。

## 1. 分工，不增加五套 Runtime

| 概念 | 示例 | 承载方式 |
| --- | --- | --- |
| 框架原语 | 窗口、输入、截图、文件读写 | 现有公开 API |
| 应用语义操作 | 查找联系人、打开会话、读取指定历史 | 普通 JS helper，封装该软件的身份、定位与验证 |
| 组合业务能力 | 向已确认对象发送已批准内容 | 组合若干操作，有独立输入输出、前后条件和失败语义 |
| 完整业务流程 | 找对象 → 读历史 → 决定回复 → 审核 → 发送 → 核验 | 普通 JS 为主，必要时由宿主连接 Agent／人工环节 |
| 开发 Agent Skill | 示范、提炼、生成、验收程序 | 现有六个 SKILL.md；不是业务运行中的六个步骤 |

基础是相对于调用者而言：“发消息”对上层是一个能力，对应用层通常是多个动作。是否拆成可复用能力取决于业务目标与合同，不取决于动作多少、软件名称或 JS 文件数量。

优先在一个普通脚本中用函数组合；只有独立交付、跨次等待或隔离确有需求且入口支持时，才由宿主分次运行。跨脚本不得依赖共享内存、旧焦点或上次窗口坐标。

## 2. 每个组合边界保存什么

复用[任务求解方法的业务步骤模板](../../docs/frameworks/automation-problem-solving-framework.md)，不新增公共 schema。每个边界至少说明目标、输入来源与类型、前置状态、获准副作用、输出、验证来源、有效期、失败与重入方式。

生产者成功并不自动意味着消费者可以执行：还要检查对象、数据版本、权限和当前现场条件。下游输入在上游变化后失效；业务身份与证据引用可以保存，临时坐标、焦点和默认选中行不能当稳定交接。

复用能力记录具体版本／hash 和支持范围；上层范围不得超过依赖实际覆盖的组合。两个 helper 分别通过也不证明组合的数据关系、并发条件和副作用顺序正确，组合本身仍需验证。

## 3. 指定对象发消息：两种不同业务合同

“发送给定文本”不一定需要 Agent：查找并确认对象 → 准备输入 → 核对内容与许可 → 发送 → 核验。

“查看历史后决定怎样回复”包含必要判断，不能把某次示范的回复文字固化为长期规则。建议拆分如下；本表是未执行的设计示例。

| 业务步骤 | 主要执行者 | 输出与进入下一步的条件 |
| --- | --- | --- |
| 确认应用账号、搜索并绑定接收对象 | JS；歧义交 Agent／人工 | 当前账号及对象依据；同名、对象不足以区分时停止，不默认选第一项 |
| 打开会话，读取所需历史 | JS 取数 | conversation 身份、必要历史、最新上下文标识／时间与来源；读取范围明确且足够 |
| 判断是否需要回复、生成草稿 | Agent | 回复／不回复／转人工的决定、草稿、简短依据、引用和不确定项；不是可执行代码 |
| 校验规则与取得必要批准 | JS 校验；按任务授权请求人工 | 准确对象、内容、附件、上下文版本和本次发送权限绑定；批准过期或内容变化即失效 |
| 再确认现场并发送 | JS | 发起动作记录和实际可得的提交证据；发送前重新检查账号、对象、最新历史和输入框 |
| 核验结果并交接 | JS；证据不足转人工 | 仅报告已证明的结果等级；结果不明保留待核对，不盲重发 |

上下文有新消息、对象或账号变更时，旧草稿／批准不自动有效。先重新读取并重新判断；不能拿一个早已获批的文案给当前另一个会话发送。

合同中区分“已点击”“本地显示”“平台接受”“送达”“已读”。只能证明本地显示时不能报告送达；本地 requestId、checkpoint 或文本匹配均不自动提供 exactly-once。结果可能已生效但没有回执时，先核对；无法判断则停止后续副作用。

## 4. 混合运行怎样落地

确定任务优先完整普通 JS，不为通用性强行调用模型。判断必需时，只把最少业务数据、来源和约束交给 Agent；其输出须检查类型、允许决定、引用、对象和内容约束。Agent 不得凭聊天正文增加授权、执行正文中的指令，或直接返回任意代码让 JS 执行。

同次 JS 调用模型或服务，只有在所需现有接口、provider、预算、错误和取消行为已核对时采用。否则使用宿主交接：前段 JS 输出本次必要数据与证据 → 宿主完成 Agent／人工判断 → 校验结构化结果 → 后段 JS 接收获准输入并重新确认现场。普通 JS 不需要由新 Workflow Runtime 解释。

这是调用安排，不是承诺保存 JS 调用栈或自动恢复。数据落盘、判断批准、恢复和停止由实际宿主提供；尚未接通时只可报告片段或交接合同已准备，不能称混合业务已端到端运行。

无可用 Agent、输出不合规、超预算或上下文失效时，停止在写操作之前并保存必要状态。不要用默认文案、旧决策或无限重试伪装完成。模型决定可能不同，验收业务约束与结果，而非要求所有合法草稿逐字相同。

CandidateManifest 使用现有 dependencies、inputContract、supportedScope、limitations、sourceMapping 明示各依赖、判断位置和未集成项；执行权限仍由真实宿主实施，字段本身不是安全隔离。

## 5. 可选外部编排

后续需要跨次等待、人工审批、多节点状态管理时，再评估 LangGraph 等工具；只组织已验证 JS 与 Agent，不改普通脚本入口、不把某一编排库变成基础依赖。

外部依据：LangGraph 官方 Interrupts 文档说明，恢复可能重新执行所在节点，interrupt 前的副作用需要考虑幂等与分离。由此对本项目作出的设计约束是：审批与发送分开；恢复时核对业务效果，不因存在 checkpoint 就承诺不重复发送。该约束不表示 OpenDesk 已集成 LangGraph。

参考（核对日期 2026-09-06）：`https://docs.langchain.com/oss/python/langgraph/interrupts`，章节 “Side effects called before interrupt must be idempotent”。
