# 计算器案例｜任务、数据流与失败定位

本案例要解决的不是“会不会算出 660”，而是：**一次真实任务经过示范、提炼、过程建模、代码生成和独立验收后，关键动作与数据关系是否仍然正确；失败时能否找到最早有证据的错误交接。**

用小任务验证工作流，不另造工作流。正式阶段仍是 [S1—S12](../WORKFLOW.md)，业务脚本运行时不重新走十二阶段。本文是案例阅读入口，不是执行授权或完整作业输入包。

## 1. 任务与成功标准

### 先看这段业务

```text
第一次计算：
通过计算器按钮输入 25 × 4 + 10 =
从本次显示区实际读取 firstResult。

第二次计算前：
按已确认、已授权的应用规则清空计算器界面，
但保留任务数据中已经读取的 firstResult。

第二次计算：
点击“6”“×”，逐字符输入 firstResult，再点击“=”。

最终交付：
从本次显示区实际读取 finalResult，打印并返回它。
```

第一式按钮顺序是 `2 → 5 → × → 4 → + → 1 → 0 → =`。第二式的数字部分必须在读取后由 `firstResult` 产生，不能提前写成 `1 → 1 → 0`。

| 必须成立的要求 | 检查重点 |
| --- | --- |
| 两次运算确实通过计算器按钮完成 | 真实动作、目标和回执；不能用 JS 算术、整式键盘输入或后台求值替代 |
| 首值来自本次结果显示区 | 读取来源、原文、身份、时序；不使用历史值、剪贴板遗留值或推测值 |
| 第二式确实消费该首值 | 生产者、逐字符转换、实际按钮输入和消费者对应，而不只是变量同名 |
| 终值实际读取、打印并返回 | 返回值与日志来自终点读取；输出正确数字本身不证明过程正确 |
| 准备状态和异常处理符合授权 | 不清除无关历史、不改变权限、不关闭无关窗口；结果不明时不盲重试 |

本固定任务的验收期望是首值 `110`、终值 `660`。期望只参与核验，不能产生业务输入或冒充实际读数。首次读取缺失、身份不明、格式不支持、效果未知或合同要求的核验失败时，不继续正常的第二次输入。

## 2. 关键数据流：清空界面，不清除已经读取的数据

```text
第一式的按钮操作
    ↓
第一次结果显示区
    ↓ 实际读取：保留来源与原文
firstResult ───────────────┐
    ↓                     │ 任务数据继续有效
第二次获准状态准备         │
    ↓                     ↓
点击 6、× ← 逐字符展开 firstResult → 点击 =
    ↓
第二次结果显示区
    ↓ 实际读取
finalResult → 打印 / 返回
```

| 数据 | 从哪里来 | 谁使用 | 不允许的替代 |
| --- | --- | --- | --- |
| `25、4、10、6` 与运算要求 | 用户任务／固定 TaskContract | 对应按钮输入步骤 | 擅自扩大为任意表达式或参数化接口 |
| `firstResult` | 本次第一次结果读取 | 第二次按钮输入；必要的首值核验 | Expected `110`、旧值、JS 重算或调用者默认参数 |
| `finalResult` | 本次第二次结果读取 | 打印、返回、终值核验 | 固定返回 `660` |
| `110、660` | 本固定任务的独立验收期望 | 验证器与对应判据 | 回灌生产者、消费者或读取 API |

若某次有证据的实际读值为字符串 `"110"`，本次展开才是 `["1","1","0"]`；两个 `1` 不能去重。保存值与计算器显示状态是两件事；屏幕出现 `0` 也不自动证明内部待运算状态已经清除。

## 3. 从任务到 Recipe：各阶段到底交付什么

以下是开发／制备链，不是点击计算器的业务步骤。**阶段不等于 Skill，也不等于文件或 Agent。** 每行的独立输入、处理、输出、拒绝条件与反例见链接中的交接卡。

| 阶段与方法 | 计算器里解决的问题 | 交给下游的核心内容 |
| --- | --- | --- |
| [S1 · automation-plan](calculator-handoffs.md#s1) | 固定目标、授权、范围与成功标准 | TaskContract + WorkPlan：按钮、真实首值、第二次消费、最终交付、停止条件 |
| [S2 · application-engineer / discover](calculator-handoffs.md#s2) | 认识下一步必需的窗口、按钮、显示区及可行性 | 最小 AppProfile：有来源的对象认识、前提和 Unknown |
| [S3—S6 · task-demonstrate](calculator-handoffs.md#s3-s6) | 真实执行并同步记录事实 | Dossier + Raw Trace／Evidence：实际动作、观察、读值、消费者和副作用 |
| [S7 · trace-distill](calculator-handoffs.md#s7) | 从轨迹中判断必要步骤，不丢状态和数据 | DistilledSteps：逐原动作取舍、来源、顺序和生产／消费关系 |
| [S8—S9 · procedure-synthesize](calculator-handoffs.md#s8-s9) | 形成业务过程和可复用的数据关系 | SemanticProcedure：Business Steps、运行时值、转换、支持范围与能力决定 |
| [S10 · application-engineer / harden / repair](calculator-handoffs.md#s10) | 补强或复用真正需要的应用操作规则 | 有来源的定位、读取、等待、清空、停止规则及适用范围 |
| [S11 · recipe-build](calculator-handoffs.md#s11)；[按需 code-rebuild](calculator-handoffs.md#s11-optional) | 忠实实现过程，必要时独立改进代码 | 普通 JS + CandidateManifest：真实数据依赖、源码映射、入口和依赖 |
| [S12 · recipe-qualify](calculator-handoffs.md#s12) | 验收冻结的同一候选，而不是参考脚本 | QualificationRecord：实际运行、独立观察、逐范围结论和未测项 |

已有有效成果先核对版本与范围，从真实缺口接续；不为教学而重做整个任务。能力发现嵌入相关阶段，不增加 S13。具体方法和正式字段仍以各 Skill、[共享合同](../../../docs/frameworks/agent-to-recipe-skill-contract.md)为准，本文不另建 schema。

## 4. 失败时先查哪里

**发现错误的阶段，不一定是制造错误的阶段。** 先比较相邻交接，找到“输入还正确、输出已经错误”的最早证实位置。下面是诊断条件，不是对历史失败的断言。

| 证据显示的问题 | 返回责任与最小修复 | 哪些成果不能直接沿用 |
| --- | --- | --- |
| 合同漏掉“第二次使用实际首值” | S1 修合同；不改写用户原始来源 | 受目标变化影响的计划及下游 |
| 已有真实材料未随 request 交付 | 协调者补交获准固定材料，保留原 source owner | 未获得正确输入的下游；不因此重做示范 |
| 原始动作里没有首值读取，或事实本身缺失 | S3—S6 新建获准定向补采 | 依赖这项事实的提炼／过程；不得追补虚构历史 |
| 原始读取完整，S7 却删掉它或把 `1,1,0` 去重 | S7 修取舍与完整数据关系 | 受影响的 Procedure、Candidate 和资格 |
| S7 正确保留首值，Procedure 却把它设为默认常量 | S8—S9 修运行时值和消费者解释 | 受影响的代码与资格；不能由 S10 修定位掩盖 |
| Procedure 正确，JS 却硬编码 `110` 或返回 `660` | S11 修实现并冻结新候选 | 旧候选的资格不能授予新字节 |
| 目标歧义、读取不稳定、环境不在支持范围 | 先分辨现场前提、应用规则或 Runtime 缺口；有据再交 S2／S10／Runtime owner | 受影响规则、实现与资格；不默认全部重做 |
| 点击超时但输入可能已经发生 | 停止后续输入，保存 unknown／回执，交获准现场责任核对 | 当前正常路径；不能盲重放前缀或切换 backend 再点 |
| 验收使用另一份脚本、改了候选或漏跑 requested 场景 | S12 修验收；必要时上游发布新候选 | 相应通过声明；不能删减请求范围来变成 PASS |

失败摘要采用下面的**可读视图**；正式记录仍按共享合同保存：

```text
本次停止阶段：
最后已核实的正确输入／产物及版本：
最早已证实的问题交接（证据不足则写根因未定）：
观察到什么；依据是什么：
副作用：已知状态，或 unknown：
下一责任、所需材料／授权和最小修复：
受影响的下游与重验范围：
```

## 5. 分开验证，不让总分遮住缺口

**文档写清楚、Skill 方法可独立使用、固定候选真实通过，是三种不同结论。** 本轮文档的逐项评分与依据见[独立分项审阅](../../../docs/quality/agent-to-recipe/calculator-document-review-20260927.md)，不计算一个能掩盖短板的综合分。

| 验证对象 | 怎么检查 | 能说明什么 |
| --- | --- | --- |
| 案例与阶段交接说明 | 单独检查任务、数据、每个阶段、反例、责任和来源 | 文档在本案例范围内是否表达充分；不是 Skill 全能力认证 |
| 某个 Skill 的独立使用能力 | 新 Agent 只接收该 Skill 允许的输入，禁止偷看未来标准产物／最终 JS | 该方法是否能独立完成职责；未执行则记 not-run |
| 固定 Recipe 的真实资格 | 同一候选、已定范围、真实动作与读值、独立证据 | 一次运行／重复运行／参数化分别结论，不能互相替代 |

构造“删首读、删必要准备、去重数字、常量替换、漏终读、换候选”等反例，可检查方法和判据；必须标为教学或测试材料，不能冒充真机证据。变参 `12 × 3 + 4`、再 `6 × firstResult` 的期望为 `40、240`，仅是待验证场景；固定脚本改常量后再跑不算参数化。
