# 计算器案例｜工作流代入、设计记录与待验证事项

任务：通过桌面计算器按钮输入 `25 × 4 + 10 =`，读取结果，再点击 `6 × 上一步实际结果 =`，读取、打印并返回最终结果。此文件长期保留案例、设计理由、备选方案、反例和未决问题，不能仅放在会被清理的临时目录。

状态：2026-09-07 整理的需求与设计记录；本次没有运行计算器、生成生产 JS 或取得真实读数。`110`、`660` 是数学验收期望，不是本次观察结果。实际系统、应用版本、布局、按钮坐标、读数方式和候选脚本路径均须在获准执行时确认。

入口：[主工作流](../WORKFLOW.md)、[应用操作建模](../application-operations.md)、[code-rebuild](../../code-rebuild/WORKFLOW.md)。以下沿用主工作流的三种起点和五个结果层次；另完整保留讨论中的十三节点展开，使用 R1—R13 防止与共享合同 S1—S12 重名。它们是同一案例的不同阅读视图，不是两套可执行流程。

## 业务需求与不可替代的事实

- 必须通过计算器实际按钮完成两次计算，不用 JS 算术、键盘直接输入整式、后台计算接口或预写答案替代。
- 第二次操作数必须来自第一次显示区域的实际读取值，不来自期望 `110`、历史运行、剪贴板遗留值或模型推测。
- 最终打印与返回必须来自第二次实际读取；输出 `660` 本身不足以证明前面的操作和数据流成立。
- 允许的清空与状态准备在本次合同中确认；不能擅自清除无关历史、关闭用户窗口或改变系统权限。
- 本轮先支持所需的正整数及乘法、加法、等号；其他数字格式、模式和平台不自动获得支持资格。

## 按需求语义拆分本次业务任务

- 完成第一次计算并取得中间结果。
  - 确认正确计算器和可开始的状态。
  - 顺序点击 `2 → 5 → × → 4 → + → 1 → 0 → =`。
  - 从当前结果组件读取实际值，保存为 `firstResult`，再与独立期望 `110` 核对。
- 用中间结果完成第二次计算。
  - 保留任务数据里的 `firstResult`，准备新的计算起点。
  - 点击 `6 → ×`，按 `firstResult` 的真实数值表示逐位点击，再点击 `=`。
  - 第一次没读到、格式不支持或核验未通过时不得继续。
- 取得并交付最终结果。
  - 从当前结果组件读取 `finalResult`，与独立期望 `660` 核对。
  - 打印并返回实际读取值；失败时明确失败，不补出正确答案。

以上是生成后业务脚本要执行的子任务；下面的 Recorder 工作流负责怎样建立、提炼、生成并验证这段脚本，不应混为同一层。

## 三种入口与五个结果层次

- 选择本次真实起点。
  - Agent 新示范：真实完成上述业务并同步留下依据，再进入完整提炼和新生成。
  - 人工开发：用同一合同指导试验和代码，保存真实运行证据；不把人工试验追认成 Agent 示范。
  - 已有资产：先核对脚本路径、字节、来源和当前范围，原样复用或最小修复，不重复从零探索。
- 取得可信执行依据，映射主树 S1—S6。
  - 确认合同和应用起点，完成两次计算，保存真实读值、消费者、状态与验证。
  - 封存完整示范或指定补采范围；失败包和局部补证不冒充完整成功示范。
- 得到可解释的业务过程，映射 S7—S8。
  - 重建状态与操作，解释清空、读取、输入和验证的必要性。
  - 按“计算并读取中间值”“使用中间值再计算”“返回结果”组织业务步骤。
- 得到有依据的复用规格，映射 S9。
  - 确认参数、按钮转换、真实运行时值与支持范围，必要时补充变化样本。
  - 确定哪些步骤直接调用框架、哪些普通函数组合、哪些判断尚需 Agent。
- 形成可独立使用的普通程序，映射 S10—S11。
  - 确认应用操作规则，优先现有 UI／Geometry 等能力，不要求 `calc` 对象。
  - 采用已有或生成基础代码，执行 code-rebuild 检查，冻结真实候选。
- 证明资格并持续维护，映射 S12。
  - 独立新运行，验证读值来源、两次数据交接和打印结果。
  - 对变化输入、旧状态、定位异常和错误拒绝逐项验收，失败后定向修复。

## 十三节点工作流代入：保留讨论中的细化过程

- **R1｜目标与任务约束（Goal & Task Contract；对应主树 S1）**
  - 明确按钮完成两次计算，第二次消费第一次真实读值。
  - 明确最终读取、打印与返回，分别定义操作正确性、数据交接和结果期望。
  - 核对已有脚本、应用知识、证据、允许清空的范围和停止条件；未知信息不伪造。
- **R2｜真实任务尝试／应用发现（Execution Attempt / Discover；对应 S2—S6）**
  - 复用有效认识，确认窗口、计算模式、显示区和所需按钮，只探查未知部分。
  - 准备起点，按顺序输入第一式；每个关键动作后检查反馈和可继续条件。
  - 从结果区读取并核验第一值，保存 `firstResult` 和来源。
  - 保留该值，准备第二次起点，输入 `6 × firstResult` 对应的按钮序列并求值。
  - 读取、核验、打印并返回最终结果，用任务级证据关闭本次尝试；本步骤描述计划，不表示已经执行。
- **R3｜同步证据采集（Synchronized Evidence Capture；与 R2 同时进行）**
  - 保存关键动作前后状态、窗口身份、按钮定位依据、工具调用与实际反馈。
  - 记录第一读值来自哪个组件、哪次观察、何种解析，并记录实际进入第二次按钮输入的序列。
  - 保存结果读取到日志／返回值的消费者关系，期望值与实际值分开。
  - 探索、错误、重试和人工接管同样保留，不事后只留下成功叙述。
- **R4｜状态重建（State Reconstruction；对应 S7）**
  - 从证据还原计算起点、第一表达式输入、第一结果显示、第二次准备、第二表达式输入和最终结果显示。
  - 明确哪些状态是观察到的，哪些只是推断；缺失或矛盾状态列为未决，不补造中间画面。
  - 区分“结果已保存在任务数据中”与“计算器屏幕仍显示该值”。
  - 区分显示 0 与已清除完整待计算状态，不能默认二者等价。
- **R5｜动作分段（Action Segmentation；对应 S7／S8，利用 S5 分类）**
  - 将零散点击组成准备起点、输入第一式、读取中间值、准备第二式、输入第二式、读取和输出最终值。
  - 按子目标、数据依赖与状态变化划界，不按固定点击个数分段。
  - 区分正常操作、状态准备、探索、错误、重试和恢复，不能混成每次必做的点击列表。
- **R6｜语义落地与效果归因（Semantic Grounding / Attribute；对应 S7／S8）**
  - Where／What：确认操作的是哪个计算器窗口、哪个按钮区域、哪个显示组件。
  - Why／Effect：第一式产生中间值，读取使该值成为程序数据，第二式消费该数据，最后交付结果。
  - 解释清空、等待和读取为什么需要；必要操作不能因为不直接计算而删除。
  - 将每个保留／排除决定关联原始事实；“点过等号”不直接证明本次计算已完成，时间相邻也不自动证明归因。
- **R7｜行为抽象（Behavior Abstraction；对应 S9）**
  - 提炼准备计算状态、操作指定按钮、顺序输入、读取当前结果等应用操作。
  - 将同一子目标下操作归纳为“在计算器中执行表达式并读取结果”，但不强制创建 Calculator 类。
  - 区分业务输入、验证期望、运行时结果与临时坐标；`110` 不得变成后续业务常量。
  - 数字拆分、运算符映射、等号归属和可接受数字格式分别确认；没有证据的分支或循环标为候选。
- **R8｜工作流合成（Workflow Synthesis；对应 S8／S9）**
  - 组合首次计算、读取 `firstResult`、准备第二次、构造按钮输入、再次计算、读取、验证和输出。
  - 第二式的实际输入必须由第一次读值生成，不是“演示答案看起来相同”。
  - 第一读值缺失、格式不支持、身份不明或验证失败时停止，不让第二式继续。
  - 明确状态、数据、前后条件、允许恢复和完成条件；两次运算相似不证明任意表达式均受支持。
- **R9｜健壮性工程（Robustness Engineering；对应 S10）**
  - 确认当前布局与 UI 组件，再为按钮绑定语义身份和定位依据。
  - 优先现有可用能力；需要时比较区域文字定位、结构信号、图像和有依据的矩阵，不直接均分窗口。
  - 补齐清空语义、目标消歧、当前 Geometry、内部安全点击点、有界等待和结果读取验证。
  - 窗口移动重算位置，布局改变重认规则，读值不确定补观察；目标歧义、状态冲突和结果不符停止。
  - 不能把历史坐标、固定等待、重复等号或盲重试固化到正常流程。
- **R10｜自动化规范（Automation Specification；对应 S9—S11）**
  - 确认第一表达式、后续表达式模板、实际读值、业务步骤、按钮映射、定位与验证规则。
  - 区分“发生过什么”“为什么这样做”“以后怎样执行”，三者关联但不互相覆盖。
  - 保留业务步骤、应用操作、代码位置和原始证据的对应关系。
  - 普通 JS 路线用现有过程主产物和普通代码，不因节点叫规范就新增可执行 IR。
- **R11｜代码编译生成与质量改进（Code Compilation；对应 S11）**
  - 现有脚本适用则采用，有据缺口才修；没有代码时生成必要基础实现，不伪称从零。
  - 优先使用真实 OpenDesk API 和少量普通函数，检查表达式展开、等号归属和结果读取。
  - 按 code-rebuild 检查业务可读性、API 复用、实际数据流、顺序与错误处理，不强制 `calc.tapButton()`。
  - 每次真实读取中间值再生成第二式，不写死 `6 × 110`，最终打印真实读取值。
  - 冻结候选字节、入口、依赖、范围和未测项；节点名称不表示新增 Compiler，未接通能力不得伪装可执行。
- **R12｜分层验证（Validation Ladder；对应 S12）**
  - 分别验证组件身份与位置、按钮操作、输入转换、一次计算、两次数据交接及最终输出。
  - 基线新运行允许相同任务输入，但必须重新操作和读数；另用合法变参证明参数化。
  - 覆盖旧状态污染、支持范围内窗口变化、错误期望、目标缺失、读值失败和不支持格式拒绝。
  - 正确数值和正确数据来源分别证明；真实候选、参考脚本、模拟逻辑测试不能混为一份通过结论。
- **R13｜固化或修复（Promotion or Repair；对应 S12 后续闭环）**
  - 通过后保留代码、已确认规则、来源、支持范围、版本和维护责任。
  - 状态／语义解释错误回 R4／R6；抽象／组合错误回 R7／R8；定位问题回 R9；代码问题回 R11。
  - 缺事实回 R2／R3 定向补采，合同错误回 R1；验收设置有误修正并重验，不降低标准。
  - 修复后验证受影响部分并形成新候选资格，不默认全部推倒重来。

## 数据关系与按钮表示：不可用期望值替代现场

- 第一式业务输入是 `25`、乘法、`4`、加法、`10`；操作序列是 `2, 5, ×, 4, +, 1, 0, =`。
- 第一次显示读取产生原始文本，再按已确认规则得到 `firstResult`。本次没有实际读值；预期是 `110`。
- 第二式业务输入是 `6`、乘法、`firstResult`；按钮数字部分必须从该运行时值展开。在读值确为 `110` 的实际运行中，序列才应成为 `6, ×, 1, 1, 0, =`。
- 第二次显示读取产生 `finalResult`，打印和返回它。期望 `660` 只参与验证，不负责生成实际值。
- 用户提出的 `[25, *, 4, +, 10, =]` 在 JS 中应把运算符写成字符串，即 `[25, "*", 4, "+", 10, "="]`；这是候选输入表示，不是现有通用 API 的签名。
- `UI.tapTexts()` 需要已展开的字符串序列，不会自动把 `25` 拆位，也不求算术答案；结果读取和业务验证还要另做。
- 不直接把完整运行包装成一个返回常量的“计算函数”；准备状态、输入、实际读数和消费者必须都真实存在。

## 应用认识到 JS：保留的设计选择

- **优先普通脚本与框架 API，不强制应用对象。**
  - 早期 `calc.tapButton()` 只是封装示意，后续用户明确希望脚本优先复用 UI 能力。
  - 当前决策：能直接调用则直接调用；有真实组合、转换或校验价值才用普通函数。
  - 不把“必须有 calc 对象”写成质量要求；这不禁止未来确有复用需要的 adapter。
- **布局与组件分开认识，目标与坐标分开保存。**
  - 显示区、数字区、运算符区是区域；结果文本、数字键、乘号和清除键是组件目标。
  - 相同数字可能出现在表达式、结果、历史和按钮中，定位需要正确区域及上下文。
  - 按钮变量保存身份与规则，本次矩形／坐标只作运行投影。
- **按钮矩阵保留为候选，不当作事实。**
  - `3×4` 只是一种区域拆分设想；尚未证明当前系统计算器采用该布局。
  - 真正采用前确认区域、行列、留白、间距、跨列键和运算符是否独立；不能均分整个窗口。
  - 窗口平移后可重算位置，重排或模式切换后需要重新选规则；矩阵有效性必须能检查。
  - 失配后停止或重新识别，不点击邻近格子作为无证据 fallback。
- **比较直接文字定位与布局复用，不预先宣称哪种最优。**
  - 文字定位可复用框架，但逐键截图／识别有成本且须避免与显示区重名。
  - 已验证矩阵可能减少重复识别，但布局证明、当前窗口核对和结果验证不能省。
  - 当前可用结构化信号或其他识别也可作为候选；以实际权限、平台和证据决定。
- **分别定义单按钮、序列、表达式与一次计算的职责。**
  - 单按钮处理目标点击；序列处理顺序；表达式处理数字拆分和符号映射；一次计算增加起点、求值、等待和读数。
  - 不要求四层都形成函数，避免无用包装；等号只能由一个层级追加。
  - `UI.tap()` 目前只是讨论过的可能扩展方向，不能在交付代码中当作已实现方法。
- **清空和读取规则必须来自实际应用。**
  - `C`／`AC`、清除当前输入与清除全部运算不是可随意互换的概念。
  - 清空后屏幕 0 不必然证明运算器内部没有待处理表达式。
  - 读取应保留原文与规范化结果；空白、错误文字、溢出或不支持格式不能转成默认数字。
- **代码质量改进与业务资格验收分开。**
  - code-rebuild 检查真实读取、数据消费者、框架复用、异步顺序、错误处理和必要封装。
  - 普通脚本生成或静态通过不能替代本次真机回放；不创建新 Runtime 或 Compiler 来掩盖缺口。

## 待验证问题与最小补证任务

- 确认实际 OS、应用版本、计算模式、窗口身份和允许的清空范围；没有这些事实不固定按钮矩阵或坐标。
- 查明已有计算器脚本及历史证据的真实位置、内容 hash 和作用范围；旧文档路径或聊天称“已运行”不能替代文件和证据。
- 验证结果显示组件与历史／表达式的区别，选择真实可用的读取方式；不能只等待期望数字出现就把它当实际返回值。
- 验证清空、连续输入、等号、显示完成状态和允许的节奏；同值结果也可能需要状态或过程证据，不只比较文字是否变化。
- 核对全部被候选使用的按钮以及表达式展开规则；计划支持 0—9 时需相应覆盖，不能仅凭示范用过几个数字就宣称全覆盖。
- 比较适用定位方案在当前范围的正确性、观察成本和失效行为；没有实测时不报告“矩阵更快”或“纯离线”。
- 本例的乘加顺序不能证明所有混合表达式的运算优先级；涉及不同运算次序、负数、小数或指数时另立明确期望与补证。
- 无新发现时复用已确认知识，不重新从零截图探索；发现失效则只返回相关问题所需阶段。

## 后续验收场景：当前均未运行

- 基线 `25 × 4 + 10`，随后 `6 × firstResult`：独立期望 `110`、`660`，验证真实读值、输入和最终打印。
- 合法变参 `12 × 3 + 4`，随后 `6 × firstResult`：独立期望 `40`、`240`；这是设计测试输入，不是示范读数。
- 带有旧结果或未结束表达式开始：只做获准状态准备，不能把旧 `110` 当第一式结果。
- 窗口移动或支持范围内尺寸变化：重新定位后仍点对；超出布局范围应拒绝而非猜坐标。
- 数字文本重复、按钮遮挡或目标缺失：正确消歧或停止，不选第一个匹配。
- 第一读值为空、错误文字、不支持格式或证据丢失：停止第二次输入，不用默认值补齐。
- 故意错误期望：验收应拒绝；测试可以因正确拒绝而通过，但业务失败状态必须保留。
- 第二次仍硬编码 `110`：即使基线得到 `660`，数据流检查与变参测试也必须指出失败。
- 顺序中断、点击结果不明、重复等号：先核对实际状态，只有获准清空并确认起点时才能安全重做相关表达式。
- 对表达式展开的离线测试或 mock，只证明纯逻辑／接线，不证明真实点击、读数和跨步骤交接。
- 冻结候选与实际执行字节一致，运行命令、工作目录、依赖和构建来源有记录；不能用参考脚本成功替代。
