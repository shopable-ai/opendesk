# Agent-to-Recipe 工作流

状态：路线 A 的流程作业规范；六个 Skill 和十二阶段的组织入口，不是自动调度器或整链通过报告。

## 1. 何时进入，何时不进入

输入是真实用户任务、成功条件、授权、环境范围和已有资料；输出是普通 OpenDesk JS 候选及其明确范围的资格证据。业务仍需理解或判断时，同时交付明确的 Agent／人工接口与运行说明，不将这类任务伪称纯 JS 无人值守。

这是“开发自动化”的工作流，不是“给某人回复消息”的业务步骤。获客与收款见[客户交付](../client-delivery/WORKFLOW.md)，每次业务运行见[业务执行](../business-execution/WORKFLOW.md)。作者边界见[工作流入口](../README.md)。

先选择本次范围：仅文档／静态审阅、参考脚本基本测试、已有脚本接续，或完整新示范与新生成。范围记录在现有工作包与 gate.scope 中，不新造运行模式 API。基本测试不能升级为整链通过；原样复用不能改写为从零生成。

## 2. 单一依据

[主方法](../../docs/frameworks/demonstration-to-automation-pipeline.md)负责阶段含义；[共享合同](../../docs/frameworks/agent-to-recipe-skill-contract.md)负责调用、版本、权限、交接与恢复；[六个 Skill](../../prompts/automation/agent-to-recipe/README.md)负责专业判断；[阶段卡](stages/README.md)负责每一环节的输入、作业、输出、门槛和回退。

沿用 S1—S12。S11 采用路线 A：直接生成普通 JS，不采用 Recorder 路线的必经 IR／Compiler。业务能力与生产业务程序的六个 Agent Skill 是不同对象，不按业务动作数量增设专业 Skill。

补充作业入口：[组合能力与混合运行](composition.md)明确业务层次和消息示例；[资产生命周期](asset-lifecycle.md)约束长期复用与分享；[验收与推进](validation.md)区分静态检查、独立交接和真实业务验证。它们是本工作流的专项说明，不另建公共合同。

## 3. 先核对已有成果

核对根 AGENTS、当前分支／HEAD／修改范围、实际脚本与 hash、任务包、已发布交接、证据和构建来源。没有本地工作树访问能力时明确范围，不把远端快照当用户本地状态。已有代码、历史运行、Agent 示范和本次 Fresh Run 分开标明来源。

已有脚本可原样采用或做有依据的最小修复；只补实际缺口，不为凑齐十二阶段重跑整个应用。没有调用的环节是本次不适用，不是已经通过。输入、对象、版本或成功条件变化时，只将依赖它们的结果标为需重新验证。

核验时发现：基线中的计算器规程与 `scripts/test_ai_calculator_recipe.js` 仍引用 `workflows/macos/calculator/calculate-and-reuse-result.js`，但当时 `workflows/` 不存在。本轮不恢复或伪造该脚本；下一次获准基本测试前必须查明真实源码归属并同步规程与 runner。路径未查明时阻塞对应测试，不靠改命令或 mock 宣称通过。

## 4. 正常路径

```text
S1 合同与粗计划
→ S2 最小应用认识
→ S3 操作 ↔ S4 观察验证 ↔ S5 分类与安全决策
→ S6 用任务级证据关闭示范
→ S7 因果复盘 → S8 业务分段 → S9 参数与数据依赖
→ S10 按缺口工程化目标、定位、等待与验证
→ S11 生成／登记普通 JS 候选并冻结清单
→ S12 独立 Fresh Run、负向验证、限定范围结论
→ 交付并进入业务运行；失效时定向修复和重新验证
```

六个专业责任保持不变：automation-plan 负责 S1；application-engineer 负责 S2／S10；task-demonstrate 负责 S3—S6；procedure-synthesize 负责 S7—S9；recipe-build 负责 S11；recipe-qualify 负责 S12。各阶段详细产出见阶段卡，不复制 Skill 正文。

业务中间值必须保存真实来源与消费者。示范时读到的值是证据样本，不是以后运行的固定答案；后续程序按合同从本次现场重新读取。模型的解释不能覆盖观察事实，期望值不能伪装成观察值。

## 5. 怎样真正推进与接续

具备文件与工具能力的宿主／协调者先读取合同、计划与唯一 progress，核对当前输入就绪的工作包；只向责任 Skill 提供必要资料和实际授权。生产者保存输出与证据，最后发布 handoff；协调者核验后更新 progress；消费者再核对版本、范围与现场条件。

初次任务复用[现有任务包模板](../../prompts/automation/agent-to-recipe/templates/task-package.md)。用户给出业务意图和权限，可从仓库、环境或已有资产核对的技术细节由 Agent 补齐；模板占位符未替换不得派发。

任务产物沿用 `.runtime/automation-authoring/<task-id>/` 与 attempts 组织，字段、状态和证据根规则全部引用共享合同。一个任务一个进度写入者，一个桌面一个操作拥有者。离线分析可以并行，不并行抢占同一桌面的输入。

恢复前检查实际产物和副作用，而不是看到 running 就重做。发送／提交可能成功但回执丢失时先核对，不盲重试。停止和取消只承诺当次宿主与 Runtime 真正支持的方式；文件检查点不是 JS 调用栈恢复。

没有真实工具、权限、构建来源或必要证据就保存具体阻塞和已有部分成果。不能通过增加另一个“记录 Skill”事后猜测未保存的数据。

## 6. JS 与 Agent 的分工在生成前确定

在 S8／S9 标明哪些业务步骤可由已验证规则执行、哪些需要内容理解、哪些需要人工确认；这属于业务步骤说明，不扩展共享 JSON schema。对每个判断环节写清输入、输出约束、预算、失败与权限边界，并在 S11 的依赖和适用范围中体现。

最小混合运行可以是：JS 读当前数据并保存上下文，外层 Agent 生成受约束的建议，人或既定策略审核，再由普通 JS 校验并执行获准动作。无编排能力时显式分段交接，不假装脚本能自动等待 Agent 或恢复。不要直接执行模型返回的任意 JS。

S12 分别检查确定步骤正确性、判断质量和整体任务结果。正确读写不能证明回复内容正确；正确回复也不能证明发给了正确对象。依赖 Agent 的候选必须声明在线条件、成本上限、内容评价标准和人工接管方式。

开发和运行分为两条闭环。运行时失败只产生证据与修复请求，不自行改写已发布代码或降低标准后继续发送／提交；修改回到开发链，新候选重新验收。确定控制流不等于离线运行；模型、OCR／Vision 或外置服务依赖均须明示。

长任务在工作包开始、完成、阻塞和计划修订时报告。预算耗尽、身份歧义或副作用无法确认时停止；没有新证据不得盲重试。

## 7. 失败返回哪里

目标／授权／范围问题返回 S1；应用状态、定位和等待问题返回 S2／S10；缺少现场事实返回 S3—S6 的定向补采；业务解释、数据来源或分段问题返回 S7—S9；实现错误返回 S11。修复后生成新候选并重跑受影响验收，不能修改原证据或降低成功条件。

正式 Gate 和失败分类沿用共享合同引用的 G0—G7／F0—F10。每次报告明确 scope，不在这里增设另一套评分或放行编号。

## 8. 最小验证与交付

先静态核对文件、链接、阶段映射与输入输出；再分别检验专业交接；最后才进行获准的真实整链。六个独立验收关注点分别是：规划能处理输入变化；应用工程能识别过期定位；示范能留住真实关键值；提炼能在缺证据时拒绝确认；生成能保留真实数据流并给出普通入口；验收能拒绝错误期望和脚本伪成功。

至少覆盖正常输入、变化输入、旧状态污染、关键证据缺失、错误目标／错误期望，以及副作用结果不明时停止。高风险反例先使用离线材料或获准测试对象，不通过破坏用户现场制造故障。真正换独立上下文才可声称无历史聊天交接通过。

计算器作为技术基线按[既有规程](../../docs/quality/agent-to-recipe/calculator-validation.md)核对当前路径后执行，不由本文件复制命令。客户任务另有业务结果和验收，不以计算器成功代替商业交付。

最终交付：冻结候选与必要 helper、输入／配置／Secret 引用说明、真实入口与依赖、QualificationRecord、适用范围与未测项、操作与停止说明、维护归属。技术通过、客户接受、实际收款和允许共享是四个不同事实。没有真实证据时不填写 95 分或“整链已通过”。
