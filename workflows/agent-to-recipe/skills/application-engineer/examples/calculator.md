# application-engineer 示例｜Calculator 的认识、补强与维修

> 案例解释方法，不定义方法或通用 Calculator 规则。业务来自 [Calculator 案例](../../../cases/calculator.md)：点击 `25 × 4 + 10 =`，读取 firstResult，再点击 `6 × 本次 firstResult =`，读取、打印并返回终值。110/660 是此业务的期望，不是可预填的运行时值。
>
> 以下 C-OBS/C-RULE 编号是明确标注的教学材料，不是仓库历史 actionId 或本次真机证据。已有案例/质量报告记录过限定环境运行，但不等于本次重新观察；可清理的原任务包缺失时应报告不可复核，不能从最终 JS 重建它。本文不宣称完成新的模型提取、现场运行或独立资格。
>
> 本文含参考实现分析与未来阶段答案，只用于方法维护/教学，或冻结 Candidate 后获准的 Evaluator。独立 Producer 的 S1—S11 不读取本文补答案，仍从当前 request、方法与固定上游进入。

## 一、discover：未知应用 → 最小认识

### 输入与进入条件

输入是上述用户任务、只能用实际按钮/实际读值的约束、获准观察范围，以及“旧 Profile 尚未提供”。不输入 calculator-current.js、标准 Procedure 或预制按钮表。不知道当前应用是否打开、窗口身份、模式、输入区/显示区、当前状态和可用观察能力；不要求先有完整 SemanticProcedure。

先把任务翻译为认识问题，而不是猜控件：

| 任务需求 | 必须认识什么 | 应取得的现场材料 | 不能据此宣称 |
| --- | --- | --- | --- |
| 点击第一式 | 正确应用/窗口、当前模式、数字/运算/等号目标与父区 | 当前窗口身份与获准截图；必要原生属性 | 同名窗口就是目标；按钮外观证明动作成功 |
| 读取 firstResult | 哪个区域表示本次结果，怎样与当前窗口/运算关联 | 显示区及关系观察、可用读取渠道 | 当前显示数字就是本次计算结果 |
| 第二式依赖首读 | 读取区与后续输入区属于同一业务对象，状态准备影响什么 | 同窗关系、模式/状态、允许清空范围 | 可预填 110；可清除无关历史 |
| 正确停止 | 歧义目标、异常模式、不可读状态和阻塞物 | 与必要目标相关的当前观察 | 没有看到错误就一定可继续 |

假设本次获准材料**实际提供**以下内容，才能作右列判断；没有提供时相应字段保持 unknown。

| 教学观察 | 可支持的认识 | 仍然未知 |

| C-OBS-1：当前窗口身份材料与截图对应 Calculator、基本模式 | 此观察范围内的应用身份/模式 | 下一次运行是否相同；动作权限是否齐全 |
| C-OBS-2：图中输入区域可辨认任务需要的数字、乘/加/等号及清空目标，包含父区 | 必要 targets/regions 及可见关系 | 安全点击区、定位唯一性、当前 API 动作能力 |

## 二、harden：已确认过程 → 操作规则

此时输入已有过程明确“准备首式 → 输入 → 读取 firstResult → 准备第二式 → 使用 firstResult → 读取终值”，且有当前 Profile。不要再问是否应该做两次计算，也不要把本 Skill 变成 S7/S9。

| 工程缺口 | 本 Skill 应补的规则 | 下游职责仍保留什么 |
| --- | --- | --- |
| 目标如何可靠找到 | C-RULE-LOC：限定正确窗口/父区，重新定位、唯一性与漂移检查，失败不点击 | S11 按规则实现；不复制 Runtime 定位算法 |
| 结果如何读 | C-RULE-READ：绑定当前结果区、返回原始文本/实际值与来源，异常/歧义时停止 | firstResult 的业务含义和使用方式由过程固定 |
| 何时可读/点击下一项 | C-RULE-WAIT：明确可观察 ready 条件及已授权时间/次数上限，超时停止 | 不用恒定等待时间冒充 ready 证据 |
| 清空如何安全做 | C-RULE-PREP：仅清空获准输入状态，检查回执和实际干净后置 | 第二次准备是否为必要历史步骤由 S7 取舍 |
| 如何处理首读 | 操作合同交付真实读取来源与类型；后续调用保持绑定 | digit expansion 的业务决定属 S8—S9，不在 Profile 预写答案 |

规则编号只是教学说明。实际采用 API 前读取当前 canonical 和公共约束；未实测写 not-run。当前案例曾采用 `232×321` 环境限制，它只能作为有来源的**案例环境约束**，不能写成通用 Skill 前提，不能从宽高反推出 S2 已完成。

### 完整操作样本：为下一段独立计算清空当前计算状态

**来源性质：**下表实现部分来自 `928515d98849143973124990c12cd8b4c66547d9` 的[参考 JavaScript](../../../../../examples/agent-to-recipe/calculator.js)静态阅读，不是新发现记录；验证设计来自本 Skill 方法。本轮该样本没有新的桌面执行证据，所有拟实测项为 not-run。代码不能倒证历史候选选择；未选方案的理由只作为本次方法审阅判断。

| 阅读项 | 本例具体正文 |
| --- | --- |
| 目的与输入 | 给下一段独立计算准备 Calculator；输入为本次已经确认的窗口。第二次清空不得丢弃任务数据中的实际 firstResult |
| 不可替代要求 | 真实按钮操作、真实结果读取；不能用 JS 算出答案代替 UI，也不能清除无关应用/未授权历史 |
| 代码限定范围 | 参考代码检查 Calculator 标题、Basic 的 232×321 布局、前台与焦点、中文清除标签。OS/app 精确版本需另取现场证据，不从尺寸推断 |
| 执行入口 | 参考采用 `UI.tapTargets`；当前方法是否适用仍须核对对应 canonical 契约与本次环境 |
| 观察来源与目标绑定 | `window.current` 复核窗口；`Accessibility.snapshot` 检查树完整性，在当前窗口找唯一、enabled 且支持 invoke 的清除目标 |
| 选择理由 | 语义点击与应用结构预检组合保留当前目标约束；高层动作并不取代业务准备语义验证 |
| 未选候选 | 固定坐标无必要且会增加布局依赖；不为样本增加 OCR-only/图像路径。它们未在本轮执行，不记 failed |
| 动作策略 | 每次根据真实观察到的“清除/全部清除”名称调用；参考实现最多两次，典型为 C 后 AC，不是无条件重复点击 |
| 直接后置 | 实际执行“全部清除”后通过读取函数读回并要求显示 0；无法取得全部清除或读值异常则抛错停止 |
| 读取限制 | 读取函数两次 `UI.readText` 相等且符合数字格式，只提供采样/格式检查；必须另证读到正确结果区，不能由这两项倒证来源 |
| 仍需证明 | 显示 0 不单独证明所有会干扰下一段计算的残留效果均已排除；需有区分性后续操作和局部证据 |
| 切换与停止 | 本参考没有备用实现；窗口失效、目标歧义、读取异常或副作用不明时停止，不换坐标/后端继续点击 |
| 兼容与失效 | 环境超出参考限制、目标/读取语义变化或 helper 变化后按实际依赖重验；拒绝范围外环境不等于兼容该环境 |
| 下游消费 | AppProfile/局部验证引用所用规则与 helper；S11 实现已确认过程；S12 核验冻结 Candidate。示例不发布 Qualification |

### 预先定义验证，再取得 Actual

下面只是可执行验证设计。执行者须先固定真实应用/版本、允许输入与清空的窗口及预算；没有授权不做探针。

| 场景 | 预设输入与检查 | Expected | Actual / 当前状态 |
| --- | --- | --- | --- |
| 正常准备 | 在获准窗口执行目标清空操作，再按按钮输入 `2 + 5 =`，从正确结果区读回 | 7；回执、目标和实际读值各自有证据 | 未采集 / not-run |
| 可能残留运算 | 从真实按钮输入 `9 × 4` 但不按等号，保存当前观察；执行目标清空，再输入 `2 + 5 =` | 独立第二式仍为 7；不得用 Expected 回填 Actual | 未采集 / not-run |
| 区分性对照 | 在隔离获准测试中，对照只检查显示 0 的不足规则与完整准备规则；选能实际暴露残留的序列 | 不足规则被观察证据否定；若两者没有差异，此反例无区分力，不能据此宣称覆盖 | 未采集 / not-run |
| 任务数据保留 | 按真实第一式读取 firstResult，清空 UI 后核对任务变量及第二式实际输入 | 第二式使用本次读取的全部字符；任务值不被 UI 清空覆盖 | 未采集 / not-run |
| 歧义或输入结果未知 | 受控反例验证目标歧义/unknown 后停止；分别记录 mock 层与 live 层 | 无后续依赖输入，不重放前缀、不自动换方法 | 未采集 / not-run |

一次区分性探针只支持该版本、模式及操作序列，不认证所有内部状态。Raw observation、时间顺序和实际动作应当随执行保存；不能为了形成“完整样本”事后编造。

### 怎样映射到代码而不过度封装

`currentCalculator` 是窗口/状态检查 helper；`inspectCalculator` 是只读应用预检；`clearCalculator`、`clickCalculatorButtons`、`readCalculatorResult` 是有合同的应用操作；`main` 组织两段计算与真实数据交接。它们不是新的 Runtime 原语。当前任务可保持单文件，不因为“应用操作”名词而强制创建 class、Adapter Registry 或多个模块。

## 三、repair：具体失败 → 局部维修

教学输入：某次已记录的失败显示同名按钮候选有两个，旧规则仅按文字匹配；当前父区证据足以区分目标，且尚无输入副作用。输出应只增加有来源的父区/窗口约束，保留读取与等待等仍有效规则，记录旧/新版、受影响操作与定位/动作重验。未完成重验时不得称“修好且通过”。

另一个反例：第二式点击超时但可能已输入。正确返回是保留回执及 unknown、停止后续输入、核对实际界面；不是再次清空并重放整式。若失败实为 S9 把 firstResult 写成常量，则返回 S8—S9，不能用定位补丁掩盖。

### 首错与最小返工的阅读示例

以下是诊断分支模板，不是本轮已发生的失败。当前任务 `stage-review.md` 应当从真实记录填写：最后确认正确的输入 → 首个有证据的错误输出 → failure owner → 漏检责任 → 保留上游 → 受影响下游 → 下一安全动作。

若过程正确规定保留 firstResult，而操作规则把 UI 清空与任务数据清除混同，首先修应用规则；若规则正确但代码清除了变量，修 S11；若验证把日志中的期望值当实际值，修 S12。定位、读取或动作效果证据不足时先待诊断，不能仅因失败出现在 Calculator 就断言 application-engineer 是根因。

## 四、错误链与正确链

错误：读取 `calculator-current.js` → 看见宽高/按钮表/helper → 声称“历史 Agent 在 S2 发现了这些事实” → AppProfile。代码只证明当前实现，不能证明历史观察、选型或副作用。

正确：任务需求 → 需要认识的问题 → 获准现场观察 → 有来源且有限制的 AppProfile → 受控示范/已确认过程 → 按缺口 harden → S11 实现 → S12 对冻结候选核验。

没有现场材料时正确输出是具体缺口与只读认识范围，不是按熟悉 Calculator 布局填答案。移植到工单系统时，只替换目标/结果区/状态证据，仍使用相同问题—观察—主张—限制方法；不携带数字按钮、窗口尺寸或清空规则。
