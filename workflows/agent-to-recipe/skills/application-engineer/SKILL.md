# application-engineer｜应用认识与规则补强（S2/S10）

## 定位与责任边界

把“本任务需要知道什么”转为有来源、有限定范围、能被下一职责消费的应用认识或规则。维持唯一 AppProfile，不建立第二个 UIProfile、应用类、Registry、执行引擎或平行 Workflow。S2 与 S10 不是同一工作重复两次，也不是由代码完成度决定的阶段。

| 模式 | 已知输入 → 本次问题 → 交付 | 不应要求或代做 |
| --- | --- | --- |
| discover（S2） | 任务需求＋未知/局部已知应用 → 需要认识什么、现场能证明什么 → 最小 AppProfile、审阅、缺口 | 不要求未来 Procedure/JS；不提前解决全部工程问题 |
| harden（S10） | 已确认过程＋现有认识＋明确工程缺口 → 怎样可靠定位、读取、等待和动作 → 有界操作规则或有效规则复用 | 不重新定义业务目的、参数、数据关系或原动作取舍 |
| repair（按原失败责任返回） | 失败证据＋旧规则＋影响范围 → 哪个局部约定失效 → 新规则、影响分析、重验请求 | 不把所有失败归因于定位；不重规划、不重造历史、不扩大成功标准 |

三模式按输入选择，不强制 discover → harden → repair。仅界面认识与审阅是范围，不是第四模式。Skill 是专业方法，不是另一个 Agent；返回某职责不要求更换 Agent。

## 开始作业时读取

必读本文件及 [input-spec](references/input-spec.md)、[output-spec](references/output-spec.md)、[validation](references/validation.md)、[failure-handling](references/failure-handling.md)。四者分别回答能否进入、必须交付、怎样发现错误、失败交给谁；不得用案例替代规则。

按工作读取 [操作专业约束](references/operating-guidance.md)。认识包用 [AppProfile 成果模板](templates/app-profile.md)，操作增量用 [规则与维修模板](templates/operation-rules.md)。[Calculator](examples/calculator.md) 只解释方法；[独立审阅基线](references/independent-review.md) 只检查本 Skill。原 [io-spec](references/io-spec.md) 保留为兼容导航，不维护第二套正文。

正式 JSON 字段、引用、发布及状态沿用 [共享合同](../../../../docs/frameworks/agent-to-recipe-skill-contract.md)。模板是生成前的填写清单和同版可读视图，不是新 schema。执行前固定实际方法、四项规格、合同及输入的内容版本；不读取隐含 latest 或用完整聊天补接口缺口。

## 方法

### discover：先提出认识问题，再观察

从任务合同列出近期必需操作和结果，逐项写出必须确认的应用身份、页面/模式、目标、父区/锚点、结果区、进入条件与阻塞项。先复核获准旧资料，只补影响近期任务的缺口；不要先盘点整个软件，也不要把必需目标降级来换通过。

取得与问题对应的获准观察，记录来源、时间或未知、应用/窗口/页面、原图和坐标映射。逐项分开可见事实、模型解释、待验证假设和未知；把字段关联到具体证据。截图可支持认识，不自动支持点击；按钮外观不证明可操作，显示值不证明业务已成功。

整理最小 AppProfile，检查身份、关系、几何、来源和支持范围，生成同版审阅材料。对每项原始认识问题写出已回答、仍未知及下一安全动作。仅认识足以支持受控示范时可以交付，不以缺少完整执行规则拒绝 S2；阻塞核心任务的未知不得隐藏。

### harden：从已确认过程逐项补操作合同

固定所消费的过程版本和目标，不重新推导业务。建立“过程步骤 → 所需操作 → 现有规则 → 具体缺口”映射；无缺口则复核并引用原版，不强制改版或重跑。

每个待补操作明确输入输出、目标身份、定位范围与唯一性、读取来源/类型、等待条件/上限、动作顺序、运行门禁、后置、失效和停止/恢复约定。把 Target、Locator、Geometry、Coordinate 分开。先确认当前能力及 canonical 契约，再选择可实现策略；未实现接口只能交付缺口。

按授权层级验证定位、读取、等待、动作和必要变化。设计完成、结构正确、动作回执、真实后置及业务资格分别记录。发布规则增量及未测部分；不生成最终 Recipe，不替 S9 改数据流。

### repair：先确认效果与责任，再改局部

冻结原失败、旧规则、已知实际效果及受影响对象。若动作可能已经发生而结果未知，先停止依赖副作用并定向观察，不重放前缀、不换 backend 再提交。

按 failure-handling 判断是事实、取舍、语义、规则、代码还是验收问题。只有应用规则缺陷由本 Skill 修改；其余保持有效 Profile 并准确返回原责任。修订写出旧/新值、证据、原因、依赖和重验范围，保留旧失败和资格。

先冻结新 Profile/helper，再让审阅/验证记录引用它，最后发布 handoff，避免 hash 环。没有重验只能交付“修订待验证”；影响 Candidate 的改动交原 S11/S12 接续，不沿用旧资格。

## 不负责什么

S1 拥有目标、授权及成功标准；S3—S6 拥有实际动作/读值；S7 拥有原动作 retain/merge/omit/recovery；S8—S9 拥有 Business Step、参数、业务变换及复用政策；S11 拥有普通 JS；S12 拥有冻结候选资格。本 Skill 可发现这些缺陷，但不静默替它们改成果。

既有代码可以作为当前 harden/repair 的实现参考，不能证明首次发现过程、真实观察或历史选型。正常下游只得到明确交付的必要材料，不因 lineage 就获准重读全量 Dossier/Raw Trace。Human 来源保持 Human 来源，按 failure-handling 路由。

## 完成条件

交付物必须同时通过输入范围、逐主张证据、方法边界、失败停止和下游消费审阅；不以文件数量、检查器 PASS 或整链成功代替。未知、未运行和超范围项目保留原状态。按 output-spec 发布真实局部成果及后续请求，未取得现场/模型/人工证据不得宣布对应能力通过。
