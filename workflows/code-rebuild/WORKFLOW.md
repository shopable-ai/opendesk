# code-rebuild｜普通 JavaScript 构建与质量改进

将已有脚本或已生成的基础代码，依据真实需求、应用规则和当前 OpenDesk API，改进为可理解、可维护、可验证的普通 JS。已经满足要求的代码可以原样采用；rebuild 不是推倒重写。

状态：独立专业环节的框架，尚不是安装完成的 Skill，也不是代码质量通过报告。返回[工作流入口](../README.md)，在[主流程](../agent-to-recipe/WORKFLOW.md)中对应 S11。对照[计算器案例](../agent-to-recipe/cases/calculator.md)。

## 何时进入与职责边界

- 已有普通 JS 需要审查、局部修复、结构整理或可靠性改进时，可以直接进入，不要求先重新执行整条 Agent 示范链。
- 主流程已批准业务过程并准备所需应用操作，但还没有代码时，在 S11 先形成必要基础实现，再做本环节检查；不是故意先写差代码，也不是跳过过程理解直接从 Trace 生成。
- 已有资产仍需本次需求、当前 API、来源及范围。代码本身只能证明实现结构，不能独立证明业务意图、历史成功或现场正确。
- 本环节负责代码，不自行改变目标、授权、成功标准、平台支持声明或上游观察事实；应用认识缺口返回[应用操作环节](../agent-to-recipe/application-operations.md)。
- 以[现有 recipe-build](../../prompts/automation/agent-to-recipe/recipe-build/SKILL.md)和[共享合同](../../docs/frameworks/agent-to-recipe-skill-contract.md)为当前作业依据。本轮不新增第二份 `SKILL.md`、不改调用枚举、不移动原目录。
  - code-rebuild 是拟升级名称；迁移前正式请求仍引用现有 recipe-build，交接也使用原有合法字段。
  - 后续独立细化并评估详细 Skill，再同步名称、文档和消费者，不长期维护两套重叠正文。

## 工作流任务分解树

- **明确代码必须完成什么、保持什么**
  - 冻结本次基线与目标范围。
    - 核对源脚本、依赖、内容 hash、来源、当前入口及工作目录。
    - 保存必须保留的用户修改与范围外代码，不自动格式化整个仓库或改写无关部分。
    - 对照业务任务树确认对象、参数、状态准备、真实操作、读取、消费者、输出与成功条件。
  - 区分行为、证据与未知项。
    - 已验证行为、设计意图、已知缺陷、推断和未验证范围分开记录。
    - 原代码缺少读取或存在错误答案时，不以“行为保持”为由保留缺陷；修复必须有需求或证据依据。
    - 缺少目标、关键数据来源或应用操作依据时列出具体缺口，返回对应环节，不通过猜测补全。
  - 明确本次允许的修改类别。
    - 结构重构以保持约定可观察行为为目标。
    - 缺陷修复明确哪些错误行为要改变，依据什么判定正确。
    - 可靠性增强明确支持条件、等待与失败行为的改变。
    - 性能改进先明确测量范围与资源代价，不能仅因代码更短就声称更快。
- **找出真正需要修改的问题**
  - 从业务阅读体验检查结构。
    - 主流程是否能看出任务目标和数据关系，而不是只有点击、sleep 和截图路径。
    - 函数是否承担单一清楚的职责，返回值是否便于下一步使用，命名是否表达业务意图。
    - 是否存在复制代码、死分支、无依据的抽象或只为套模式创建的类和对象。
  - 从正确性检查隐患。
    - 现场读值是否被示范常量覆盖，期望值是否参与生成本次业务结果。
    - 是否依赖旧窗口、焦点、剪贴板、截图、位置或未声明全局状态。
    - 是否吞掉错误、默认成功、无界等待、盲重试，或把日志 passed 当业务证明。
  - 从 API 与运行条件检查重复和虚构能力。
    - 对照[当前 API](../../docs/api/README.md)、类型及必要源码核对签名、返回值、错误与平台范围。
    - 不从工具名、示意代码或已有 import 写法推定当前 Runtime 支持 Node、模块加载或某个全局对象。
    - 框架已提供定位、坐标、点击或等待时，不再写功能重叠且语义更弱的一套实现。
  - 为每项建议说明问题位置、依据、预期收益和验证方式。
    - 不是每项建议都必须修改；没有证据或收益时保持原样。
    - 先消除会导致错误业务和假成功的问题，再处理可读性与性能，不以平均分抵消硬缺口。
- **选择最小足够的代码结构**
  - 优先直接复用现有 OpenDesk 能力。
    - 当前 `UI.tapText()`、`UI.tapTexts()` 等是否适用，以[Desktop UI 文档](../../docs/api/desktop-ui.md)和实际平台为准。
    - 不假定通用 `UI.tap()` 存在，不在业务脚本中给全局 UI 临时挂方法后称为正式扩展。
    - 不因计算器是桌面应用就必须创建 `Calculator` 类或 `calc.tapButton()`。
  - 必要时使用普通函数与规则数据。
    - 普通函数只承担必要的组合、参数转换、状态准备、读数或业务验证。
    - 布局、区域和按钮语义可以是明确的规则数据；一次解析出的矩形与点是本次运行值。
    - 多层职责不等于多层包装；任务简单时同文件函数足够，文件拆分以当前加载能力和真实复用价值为依据。
  - 让业务流程、应用约定与底层机制分开。
    - 业务流程表达目标顺序及数据交接，不散布行列号和坐标换算。
    - 应用约定表达布局适用性、按钮含义、清空和读取规则。
    - 通用定位、Geometry、鼠标和日志优先调用现有机制；缺少必要原语才按[扩展框架](../../docs/frameworks/runtime-api-extension-framework.md)提出独立任务。
- **保持完整、可追溯的业务数据流**
  - 分类所有参与业务的关键值。
    - 分开业务输入、Config、Secret 引用、不变量、验证期望、运行时读取值与临时坐标。
    - 明确数据产生者、消费者、类型、单位／精度、有效期与重新获取条件。
    - 通过参数和返回值表达交接，不依赖隐含可变全局状态。
  - 保留实际读取与必要格式转换。
    - 第二次计算消费本次读取的 `firstResult`，不能写死 `110`；最终打印实际读值，不能固定 `660`。
    - 将 `25` 拆成数字按钮、把 `"*"` 映射乘法键属于输入适配，不是 JS 求值。
    - 解析与规范化保留原始读值及来源；不以默认值、宽松解析或“纠错到期望值”掩盖失败。
    - 输入格式、范围和操作符在副作用前检查；未知能力拒绝，不顺便生成通用表达式引擎。
  - 保护执行方式和授权约束。
    - 任务要求 UI 点击和读取时，不用 `eval`、`Function`、JS 算术、键盘输入或后台查询偷偷替代。
    - 单独测试可使用已知期望作为 Oracle，但不得把 Oracle 答案注入被测业务链。
    - 模型只接收必要业务数据并返回受约束的结果；JS 校验后执行获准动作，不执行模型生成的任意代码。
- **补齐执行可靠性和失败诊断**
  - 核对当前对象与新鲜状态。
    - 动作前重新确认正确窗口、区域、布局和业务资格。
    - 相对坐标同样需要适用性验证；Geometry 返回对象不会自动跟随窗口。
    - 图像坐标、屏幕逻辑坐标和父区域保持明确来源，不为方便省略标记或自行猜测 DPI 转换。
  - 保持顺序和有界同步。
    - 桌面点击、输入、读取与依赖步骤按正确顺序执行，核对必要异步等待。
    - 不并行点击同一应用，不用固定 sleep 当结果证明，不无限轮询或循环重试。
    - 批量操作中途失败时保留步骤位置和已执行部分，不吞错后继续剩余序列。
  - 明确失败语义与恢复权限。
    - 区分目标缺失、歧义、状态不符、观察失败、动作结果未知和业务验证失败。
    - 读取失败可按预算补观察；动作可能生效时先对账，不能自动重放数字串、等号、发送或提交。
    - 只有授权且状态可确认时，才从安全起点重做当前子任务；不能把文件 checkpoint 当作回滚或 exactly-once 保证。
    - 取消与超时按实际 Runtime 能力描述；外层 Promise 结束不表示原生工作停止。
  - 保留足够而不泄露的诊断信息。
    - 错误能定位到业务步骤、目标、输入摘要、预期与实际状态及证据索引。
    - 日志失败不应覆盖原业务错误；清理不应破坏可复核事实或用户资源。
    - 不输出 Secret、环境变量全集、无关屏幕内容和不必要本机路径。
- **检查是否真的提高了质量**
  - 对照改前改后检查需求和行为。
    - 必要的读取、状态准备、验证和输出没有因“精简”被删除。
    - 修复与结构重构分别有理由；支持范围没有被静默扩大，成功标准没有被降低。
    - 代码行数、函数数、类数或统一命名不能单独证明质量。
  - 执行本次允许的检查并标明边界。
    - 静态审阅覆盖语法结构、API、参数、异步顺序、数据流、失败路径和依赖。
    - 有授权时对纯转换逻辑做独立测试，如数字拆分、映射、非法词元拒绝与读数规范化；不以这些测试代替真实按钮操作。
    - 需要桌面事实时交给独立验收；没有实际权限或工具则明确 not-run／blocked，不生成模拟成功报告。
    - 每项检查关联代码位置与依据；未证明项仍保留，不只给笼统“质量不错”或无证据分数。
  - 形成可解释的处置。
    - 无需改动：保留原 ref／hash，说明为何满足本次范围。
    - 需要改动：保存最小变更、新代码版本和受影响的回归场景。
    - 依据不足：保存已完成分析、具体问题与责任阶段，不以“生成完了”掩盖阻塞。
- **冻结候选并交接独立验收**
  - 沿用 CandidateManifest 保存实际脚本／hash、合同与过程引用、应用资料、API 依据、entryCommand、workingDirectory、inputContract、dependencies、supportedScope、sourceMapping 和 limitations。
  - 原样采用既有脚本可以只引用，不复制成新生成；修改则新候选、新 hash，不继承旧版本资格。
  - 用业务步骤到函数／代码区域的简表保留来源，不为此开发 Compiler 或 source-map 系统。
  - 新候选及诊断放在本次获准 attempt；原样复用维持获准来源位置。仅在成果完备后按共享合同发布 handoff。
  - 列出真实完成的检查、未测场景、外部依赖、未集成 Agent 环节和必要运行说明。
  - 交给[recipe-qualify](../../prompts/automation/agent-to-recipe/recipe-qualify/SKILL.md)验证指定字节与业务结果；验收者不改标准或代码后宣布原候选通过。

## 独立质量门槛与责任返回

- 保持任务正确性与数据真实性。
  - 绕过指定 UI 过程、硬编码示范结果、未读数即继续、假成功，均阻止依赖此结果的正式交付。
- 保持接口与状态可执行性。
  - 不存在 API、来源不明坐标、缺依赖、目标歧义或无界控制，须修正或明确阻塞。
- 保持可维护而不过度设计。
  - 只有带来清楚职责、实际复用或必要校验的封装才保留，原本良好代码不为了名字重写。
- 按问题返回，不扩大重构范围。
  - 目标与授权回 S1；真实事实回 S3—S6；业务解释和参数关系回 S7—S9；布局和操作规则回 S2／S10；代码实现留在本环节修复。
  - Oracle／测试设置错误单独修正并重验，不降低业务成功标准。
- 正式 Gate、Failure、handoff 与状态沿用[共享合同](../../docs/frameworks/agent-to-recipe-skill-contract.md)及其引用的既有质量体系，本文件不增加另一套评分编号或放行枚举。

## 用反例评估此环节，而不只评价输出文风

以下是后续 Skill 评估任务，尚未运行：

- 给出读取 `firstResult` 却仍使用固定 `110` 的脚本，要求指出实际消费者错误并保留读数证据。
- 给出读取失败后默认答案、吞错打印成功或省略验证的脚本，要求拒绝假成功。
- 给出把 `25` 当单按钮、重复等号、并行点击或遗漏异步等待的代码，要求定位具体顺序问题。
- 给出旧坐标改名为按钮变量、未确认即均分 `3×4` 矩阵的代码，要求返回应用依据缺口，不凭想象补坐标。
- 给出自造 `UI.tap()`、Node 环境假设或不完整 helper 调用，要求核对 API 并拒绝未实现能力。
- 给出已经使用真实 API、业务步骤清楚、数据流和验证完整的脚本，要求允许不改，不能强制引入 `calc`、类或更多文件。
- 分别检查“发现问题是否正确”“改动是否最小且符合需求”“新代码是否实际通过”，不能只因一次计算器结果正确就宣布 Skill 成熟。

## 后续细化与迁移

- 先拿实际获准脚本形成保留项、问题、最小修改和回归范围；不在本框架文件中塞入未运行生产代码。
- 再编写详细 Skill、必要检查清单和少量对照案例，测试其能发现坏代码也能保留好代码。
- 迁移时统一修改原 recipe-build 的名称、消费者与共享合同引用；本轮不执行迁移、不注册新 Skill、不修改 Runtime。
- 计算器设计选择与未决项继续维护在案例中；试验结果、截图和日志按实际执行保存，不用设计摘要替代原始证据。
