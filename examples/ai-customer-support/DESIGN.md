# OpenDesk Desktop · AI 客服助手｜产品设计基线

> 2026-10-28 · 产品需求与交互设计（不是功能验收报告）
>
> 仓库：shopable-ai/opendesk · 唯一正式浏览器原型：`examples/ai-customer-support/preview/index.html`（当前 R1.3 Compact Copilot）。本文记录后续产品目标，不能把待设计能力写成已实现。

## 1. 核心定位与决策

**一句话目标：** 给用户明确授权的 macOS 聊天窗口附加一个轻量 AI 客服助手，让客服在原聊天软件内完成“看消息 → 找可靠知识/商品 → 选回复 → 修改/填入草稿 → 人工发送”；只有经过独立安全准入才考虑真实自动发送。

- **产品形态：** 独立桌面侧附助手，跟随授权聊天窗口；不是浏览器扩展、完整 CRM、第二套聊天应用或新的 Runtime。
- **主界面：** “推荐回复 / 知识库”两个主页面；设置由右上角图标打开抽屉；当前会话和人工接管在主页面可见。不因新增商品功能再增加第三个主 Tab。
- **回复原则：** 只提供有业务差异的 1–3 个候选，例如“直接答复 / 补充信息 / 人工核实”；**礼貌、简洁、专业**属于同一答案的润色，不算三个独立答案。不强行凑满三条。
- **匹配重点：** 将文字问答、商品资料、商品链接作为 MVP 核心；将图片匹配列为 P1 重点。多商品比较和推荐按实际数据条件渐进实现。
- **最小可运行闭环：** 先在自有模拟聊天客户端和本地示例数据上完成确定性匹配、推荐与草稿读回；之后才扩展真实微信/企业微信与受控自动发送。
- **安全底线：** 会话不确定、知识冲突、订单/库存/价格来源不可靠、图片候选不确定或发送回执未知时，不猜测、不补发、不自动承诺。

## 2. 用户主链路

1. 用户选择并授权唯一的目标聊天窗口；助手在旁边停靠，显示当前客户与观察状态。
2. 识别客户新消息及其会话/消息身份；识别一条消息里的多个独立问题，去重并保留必要上下文。
3. 按消息内容同时检索问答知识、商品目录与可信商品链接；图片消息在 P1 才参与识别。
4. 显示匹配结果、依据和适用范围；对未知、冲突或敏感请求明确提示“需要人工核实”。
5. 同屏显示 1–3 条**处理策略不同**的推荐回复；点击选用，可就地展开编辑、复制、填入聊天草稿。
6. 人工确认后在原聊天软件发送；如未来启用受控托管，也须逐条满足授权、身份、知识与去重条件并回读结果。
7. 随时单击“人工接管”；保留未发送草稿、停止当前会话自动动作，不自动补发历史消息。

## 3. 功能优先级：先让核心流程可用

| 阶段 | 必须解决的用户需求 | 可验收结果 | 不应提前扩张 |
| --- | --- | --- | --- |
| **P0-A · 会话与窗口** | 选择/解绑目标、跟随窗口、识别当前会话和新消息 | 移动、缩放、切换会话、最小化或撤权时不串会话、不误填 | 多平台同时管理 |
| **P0-B · 知识匹配** | 导入本地 JSON/Markdown、搜索和筛选、精确/相似/未命中、引用来源 | 有效政策可回答；停用、冲突、范围不符不得自动作为可信依据 | 自建大型 RAG 系统 |
| **P0-C · 商品与链接匹配** | 按名称/SKU/型号/别名/规格查商品；解析可信商品链接到商品身份 | 识别正确商品，展示候选、规格与来源；没有实时数据不承诺库存、价格或配送 | 自动抓取所有电商平台 |
| **P0-D · 多策略回复与草稿** | 同时查看不同业务策略，选用、展开、编辑、复制、填入草稿 | 一次回答覆盖已识别问题；切换会话或异步完成不覆盖已有草稿 | 大量话术风格与编辑器工具 |
| **P0-E · 人工接管与异常** | 区分观察/会话托管；一键接管、明确交还；发送回执与去重 | 无依据/高风险/授权失效时安全停止，结果未知不重试 | 真实无人值守发送 |
| **P1 · 体验与商品增强** | 图片识别/以图找同款、商品比较和替代推荐；摘要、快捷话术、翻译/润色、待人工队列 | 图片候选可核对；商品比较有明确属性依据；摘要不虚构事实 | 把所有 P1 功能塞进 MVP |
| **P2 · 业务系统** | 真实订单/库存/物流查询、CRM/工单、多人协作、服务质量统计 | 由合法外部系统返回有来源的结果，授权和错误路径可核验 | 未取得接口就模拟“实时查询成功” |

**MVP 数据：** 先准备约 10–30 件本地演示商品（商品 ID/SKU、名称、别名、型号、规格、图片引用、官方链接、资料来源和更新时间）以及少量售后知识。资料中的价格、库存、物流如果不是可信实时值，只能显示“示例/待核实”，不可生成实时承诺。

## 4. 四类匹配能力及边界

| 类型 | 用户输入示例 | 匹配方式与结果 | 安全边界 |
| --- | --- | --- | --- |
| **问答知识（P0）** | “签收后几天可以退款？” | 按标准问题、别名、关键词和适用范围找到政策，展示来源与必要条件 | 相似候选、停用/冲突或范围不符不得认定为已核实事实 |
| **商品资料（P0）** | “A100 黑色 L 码有吗？” | 先识别商品 ID/SKU/名称，再关联颜色、尺码等变体；多候选时请用户/客服确认 | 型号、规格、库存是不同事实；有商品资料不代表有实时库存 |
| **商品链接（P0）** | “这个商品链接可以买吗？” | 在允许的域名和链接格式内提取商品 ID/路径，映射本地商品目录；显示来源链接 | 不默认访问任意第三方地址，不信任链接里的自由文本，不把短链/陌生域名当可信商品 |
| **商品图片（P1）** | “图片里的这款有吗？” | 经允许读取图片，用已验证的图片识别/相似检索产生商品候选，并在面板显示图片、商品信息和依据 | 视觉相似不等于同款；没有可靠结果则要求人工确认，不虚构 SKU |

**匹配结果统一表达：** 至少包含“匹配类型、候选对象、依据来源、适用条件、确认/候选/无结果/冲突状态、是否必须人工核实”。可以按一个客户问题聚合多个知识与商品证据，但必须分别标明哪些事实已证实。

**检索技术决策：** MVP 先复用现有知识数据模型与确定性检索，商品目录用独立结构化数据并共享统一的回复/来源展示。只有在真实问题证明检索不足时，再评估语义检索/RAG；不新建第二套 AI 引擎或 Desktop Runtime。

## 5. 页面信息架构与视觉约束

### 推荐回复（默认首页）

- 固定头部：AI 助手、全局观察状态、设置入口；下方显示**当前会话**及其人工接管状态。
- 内容顺序：最新客户消息/多个意图 → 匹配知识与商品（可展开依据）→ 1–3 张策略候选 → 当前选中答案的按需编辑和草稿动作。
- 回复卡片保留可阅读正文；窄面板默认最多显示两行并提供明确“展开全部”，不可让点击卡片无意覆盖人工草稿。
- 商品候选作为推荐页面内的紧凑模块（商品图片、名称、SKU、规格、匹配状态），不新建常驻“商品”主选项卡。
- 高风险或没有可靠依据时，允许只显示“澄清/转人工”，不能为了视觉整齐而制造直接回答。

### 知识库（第二主页面）

- 搜索问题、答案、同义词及商品信息；用一个筛选入口展开类型、启停、来源和适用范围。
- 紧凑列表以**加粗问题/商品名称 + 简短答案/商品描述**为核心，默认两行省略，点击原位展开全文和必要来源；不要将文件路径作为醒目主内容。
- 导入区域按需展开，支持选择文件与拖拽；展示格式校验、重复/错误和导入结果。
- **只读浏览**表示不可在此任意修改、删除或覆盖正式知识。导入的临时预览数据与已批准可用于托管的正式知识必须区分；不因为导入成功就自动成为自动回复依据。

### 设置（图标进入抽屉）

- 仅放低频配置：目标与授权、窗口跟随、工作模式/托管范围、知识来源和隐私。
- 观察状态与会话托管状态不能混为一谈；人工接管不可藏在设置里。
- 优先覆盖 320/360/380/400/440/520px、200% 缩放、深浅色、键盘/触屏可操作及底部主要动作可达性；正式 Mac 仍要单独实测。

## 6. 工作模式、授权与防误操作

- **全局观察：** 未授权 / 观察中 / 暂停 / 窗口失效。决定是否可以读取新消息，不等于当前会话可以自动发送。
- **每会话处理：** 手动 / 半自动 / 受控托管 / 人工接管。人工接管一键生效，仍允许阅读建议、人工编辑/复制；显式交还后只处理新消息。
- **当前消息动作：** 待分析 / 建议待审 / 已填入草稿 / 已发送且回读确认 / 结果未知。填写草稿不等于发送；提交成功不等于已被对方收到。
- **受控托管前置条件：** 独立授权、已绑定且未变化的窗口/会话/消息身份、受认可的启用知识及正确适用范围、无敏感承诺或业务冲突、幂等去重。任一失败立刻降级人工。
- **草稿安全：** 收到新消息和切换会话不得清空尚未发送的人工草稿；旧 AI 请求晚到时禁止写入新会话。
- **回执安全：** 无法判定是否已发送时显示“结果未知”，不自动重试，不伪造成功。
- **隐私：** 最小化读取，默认本地处理；外部模型和图片上传须在对应授权与数据范围内运行，不隐性传输客户内容。

## 7. 最少应覆盖的验收场景

| 场景 | 预期结果 |
| --- | --- |
| 准确退款政策 | 命中来源可靠的政策，生成可核对回复；不推断具体订单资格 |
| 相似知识 / 多问题 | 标识“待核实”；组合已知答复与待补充问题，不漏掉第二个咨询点 |
| SKU + 规格 | 找到商品及相应变体；无实时库存时不声称“有货” |
| 商品链接 | 允许的示例链接定位正确商品；未知/恶意/不支持链接安全降级 |
| 商品图片（P1） | 显示一项或多项可确认候选，不把相似图片当确定同款 |
| 客户询问物流或特殊赔偿 | 必要时请求订单号或交人工，不伪造查询结果与赔偿承诺 |
| 生成中切换会话 | 旧建议不进入新会话，原草稿保留 |
| 托管时人工接管 | 停止后续自动动作、不补发历史消息；可继续人工使用建议 |
| 窗口最小化/关闭/撤权/回执未知 | 观察停止或身份复核；不串会话、不重复发送 |

## 8. 当前仓库状态与后续推进

截至 2026-10-28 的 `master`：

- **当前主原型：** R1.3 Compact Copilot，`preview/index.html`。已有紧凑推荐、知识搜索/筛选/导入、模拟接管与浏览器交互回归记录。
- **历史 R1.1：** 曾有双窗口拖动和跟随的浏览器模拟；**当前 R1.3 主文件已不包含完整双窗口交互**，不能把历史能力算成当前版本已实现。
- **未实现 / NOT_TESTED：** 原生 Desktop 双窗口 Execution、微信/企业微信真实读取与写入、真实窗口跟随、正式知识持久化、图片识别、商品链接真实来源接入、实际发送及外部回执、Mac 实窗与 200% 系统缩放。
- **第一步（设计确认后）：** 只在唯一主原型 `preview/index.html` 中增量展示商品与链接的安全模拟匹配，保留已经认可的 Compact UI 和知识功能，不制作第二套平行 Mock。
- **第二步：** 复用 OpenDesk Runtime，在自有模拟聊天客户端上实现真实 Desktop 窗口、会话、知识/商品匹配、草稿填入与读回。
- **第三步：** 在可信输入和数据准备好后，实施图片匹配；真实平台接入与受控发送另设安全验收门槛。

**质量原则：** 八个设计维度（目标、架构、空间、多答案、知识/商品检索、安全、桌面适配、工程复用）独立以 100 分评估，目标各 ≥95，综合为算术平均。设计评分不等于代码 PASS；没有实机证据的部分必须标 `NOT_TESTED`。
