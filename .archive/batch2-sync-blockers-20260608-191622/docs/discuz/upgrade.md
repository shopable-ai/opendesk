# testMonkey-go 升级讨论纪要（2026-03-02）

## 0. 讨论范围与背景
- 本文基于当前仓库代码（约 16 个月前完成的主要设计）进行升级构思。
- 讨论前提：2026 年环境下，AI 自动化能力显著增强，用户期待从“脚本执行器”升级为“可治理的 Agent 自动化平台”。
- 参考趋势：OpenClaw 在开发者群体中热度上升，但其当前仍以 CLI/桌面侧半自动化为主，面向技术用户更友好，尚未天然覆盖企业级治理与业务流程抽象。
- 目标：
  1. 找出现有设计中不合理之处。
  2. 用 5 位软件专家 + 3 位 AI 专家 + 2 位产品专家开展 50 轮主讨论。
  3. 对争议点追加 10 轮争论式讨论。
  4. 明确项目定位、架构升级路径与可执行落地计划。
  5. 回答“是否可直接生成 `AGENTS.md/agent.md` 帮助 AI 提升准确率”。

## 2. 当前项目设计的主要不合理点（2026 视角）

### 2.1 架构与职责边界
1. `main.go` 过重：启动逻辑、HTTP 控制器、脚本执行、状态管理、CORS、页面回退都在同一入口文件中，维护成本高。
2. 全局状态较多：`jsRuntime`、`scriptStatus` 等全局变量直接共享，缺少隔离与并发控制。
3. 运行模式耦合：CLI 与 HTTP 模式代码路径交织，导致功能演进时容易互相影响。

### 2.2 并发与可靠性
1. Goja runtime 并发风险：HTTP 收到脚本后启动 goroutine 直接执行全局 runtime，多个请求并发时有潜在竞态。
2. 脚本状态共享无锁：`scriptStatus` 没有 mutex/atomic 保护。
3. 执行完成判定依赖全局 `__scriptComplete` 轮询，天然不适合多任务并发。

### 2.3 能力重复与一致性漂移
1. HTTP 请求层重复：`http.go` 与 `axios.go` 功能重叠。
2. 定时器重复：`timer.go` 与 `js.go` 都在处理 timer 语义，行为一致性风险高。
3. 类型声明与实现漂移风险：`types/*.d.ts` 靠人工维护，易与 Go 能力不一致。

### 2.4 安全与治理
1. HTTP API 默认开放 CORS `*`，且执行任意脚本，缺少鉴权、租户隔离、审计。
2. 未形成“能力白名单/沙箱”模型，难以在企业场景落地。
3. 无标准审计事件模型（谁在何时执行了什么脚本、影响什么对象）。

### 2.5 可移植性与发布
1. `loadPolyfills/loadJSLibs` 依赖可执行目录，部署到受限路径时可能失败。
2. `gocv` 硬依赖导致构建环境门槛高。
3. HTTP 端口配置参数存在但与实际常量端口行为不一致（配置感知弱）。

### 2.6 测试与工程化
1. 缺少可分层测试（单元/契约/集成/冒烟）闭环。
2. 缺少“能力契约自动生成 + 变更检测”流水线。
3. 缺少面向 AI 时代的“任务成功率、误操作率、回放可复现性”指标体系。

## 4. 各专家“完整立场卡”（覆盖优点/缺点/迁移性/升级性/AI相关性/维护性/质疑）

### SW1 平台架构师
- 优点：当前以 Go 为核心，单机执行链路短，原型迭代快。
- 缺点：入口层过重，模块边界不清，技术债累积快。
- 可迁移性：从 `automation/*` 可抽出核心能力包到 `internal/engine`，迁移可行。
- 可升级性：建议“单体内分层优先”，后续再做进程拆分。
- AI相关性：缺少显式工具契约，AI 难做稳定 tool-calling。
- 维护性：中期将因耦合导致变更成本指数上升。
- 关键质疑：如果不先治理边界，任何 AI 升级都会放大系统风险。

### SW2 跨平台系统工程师
- 优点：已具备 Windows/macOS 分支实现基础。
- 缺点：Linux 为 stub，平台能力不对称。
- 可迁移性：可基于 `windowManagerPlatform` 补 Linux/X11/Wayland 适配。
- 可升级性：应先定义“能力分级矩阵”（L1/L2/L3），避免承诺过度。
- AI相关性：AI 需要知道平台能力差异，否则规划会失败。
- 维护性：统一接口 + 平台能力标记可显著降低维护难度。
- 关键质疑：如果平台差异不显式暴露，线上 bug 将不可控。

### SW3 可靠性与测试专家
- 优点：脚本执行链路清晰，便于做最小冒烟。
- 缺点：并发模型脆弱、状态全局化、缺少系统性测试。
- 可迁移性：先引入 `Session` 模型再迁移执行器。
- 可升级性：可建立从单元到端到端的测试金字塔。
- AI相关性：AI 自动化必须可回放、可复现、可审计。
- 维护性：没有自动化评测与回归门禁，维护会越来越依赖人工。
- 关键质疑：当前结构是否能承受并发 10+ 的任务负载？

### SW4 安全架构专家
- 优点：当前部署简单、接入门槛低。
- 缺点：执行任意脚本 + 开放 CORS + 无鉴权是高风险组合。
- 可迁移性：可快速引入 token、IP allowlist、操作白名单。
- 可升级性：后续可拓展到 RBAC、审计、审批流。
- AI相关性：AI 误操作风险必须靠策略层兜底。
- 维护性：安全左移后反而降低事故维护成本。
- 关键质疑：没有审计链路，出事后如何归因？

### SW5 性能与运维专家
- 优点：单机工具响应路径短，适合轻量场景。
- 缺点：无队列、无背压、无资源治理，峰值不稳定。
- 可迁移性：可引入轻量任务队列和 Worker 池。
- 可升级性：后续可接入调度器、分片执行、灰度发布。
- AI相关性：AI 任务波动大，必须有可观测与限流。
- 维护性：SLO/SLA 没有定义，运维无法量化交付质量。
- 关键质疑：当任务超时或卡死时，自动恢复策略在哪？

### AI1 Agent 系统专家
- 优点：现有 API 足够做工具调用原型。
- 缺点：缺“计划-执行-验证-回滚”闭环，不适合复杂 Agent。
- 可迁移性：可先封装 Tool Registry + Executor。
- 可升级性：可演进为单 Agent -> 多 Agent 协作。
- AI相关性：工具描述、前置条件、失败语义要结构化。
- 维护性：无规范会导致 prompt 变更就引发行为漂移。
- 关键质疑：同一任务的幂等与补偿机制如何定义？

### AI2 模型与提示专家
- 优点：已有 `types/*.d.ts` 与示例脚本，适合作提示素材。
- 缺点：上下文文件分散，不利于模型稳定理解项目能力边界。
- 可迁移性：可自动汇总为 `AGENTS.md` 与 `agent.schema.json`。
- 可升级性：后续可做“动态上下文注入 + 版本锁定”。
- AI相关性：强烈建议引入“任务模板 + 安全提示 + 失败重试策略”。
- 维护性：提示资产未版本化会形成隐性债务。
- 关键质疑：当 API 改了但提示没改，如何阻断错误上线？

### AI3 评测与数据专家
- 优点：脚本执行天然可记录步骤，具备数据化基础。
- 缺点：缺标准事件模型，无法形成高质量训练/评测集。
- 可迁移性：先定义事件协议，再打点采集。
- 可升级性：可做离线 benchmark + 在线实验平台。
- AI相关性：没有评测，就无法判断“AI 变强还是变危险”。
- 维护性：数据闭环建立后，维护从“猜问题”变“看指标”。
- 关键质疑：业务成功率如何定义与计算？

### PM1 平台产品专家
- 优点：当前面向技术用户，学习成本可控。
- 缺点：对非技术用户不友好，业务配置能力不足。
- 可迁移性：可通过“任务模板市场 + 表单化参数”扩展人群。
- 可升级性：支持“个人开发者 -> 小团队 -> 企业”梯度升级。
- AI相关性：AI 价值应体现在“少写脚本也能稳定完成任务”。
- 维护性：产品边界清晰后，需求优先级更稳定。
- 关键质疑：未来到底是“自动化引擎”还是“AI 代理平台”？

### PM2 商业化与生态专家
- 优点：Go + JS 技术栈有生态基础，扩展空间大。
- 缺点：没有插件协议和生态分发机制。
- 可迁移性：可先定义插件 manifest 与能力签名。
- 可升级性：可形成 ClawHub 类似的“能力注册中心”。
- AI相关性：生态越完善，AI 可调用工具越丰富。
- 维护性：生态治理（审核/评分/风控）是长期维护重点。
- 关键质疑：不开生态就难增长，开生态又会带来安全风险，如何平衡？

## 5. 50 轮主讨论纪要

> 说明：每轮都包含优点、缺点、可迁移性、可升级性、AI 相关性、维护性、质疑与回应。为可读性采用压缩记录。

1. **R01 / SW1 / 主题：是否先重构入口层**
   优点：`main.go` 易定位问题；缺点：职责过载；迁移：提炼 `cmd/server` + `internal/app`; 升级：支持多入口；AI：工具生命周期更清晰；维护：降低改动爆炸半径；质疑(SW5)：会不会拖慢交付？回应(SW1)：分两期“切路由不改能力”。
2. **R02 / SW2 / 主题：跨平台能力矩阵**
   优点：已有 `windowManagerPlatform`; 缺点：Linux 缺实现；迁移：先输出 capability map；升级：按等级补齐；AI：避免模型调用不存在能力；维护：减少平台特判散落；质疑(PM1)：会不会降低宣传口径？回应(SW2)：透明能力反而减少投诉。
3. **R03 / SW3 / 主题：并发执行安全**
   优点：当前单任务路径简单；缺点：全局 runtime 并发风险；迁移：每任务独立 Session/runtime；升级：可加队列；AI：并发 agent 才可行；维护：线上故障定位更清楚；质疑(SW1)：成本？回应(SW3)：先单机队列 + session 池。
4. **R04 / SW4 / 主题：HTTP 安全基线**
   优点：开放接口便于调试；缺点：执行任意脚本风险高；迁移：默认仅 localhost + token；升级：RBAC + 审计；AI：防止误操作放大；维护：事故率下降；质疑(PM2)：门槛会升高？回应(SW4)：提供 dev 模式一键放开。
5. **R05 / SW5 / 主题：任务队列与背压**
   优点：当前实时执行延迟低；缺点：无背压；迁移：引入 in-memory queue；升级：可替换外部队列；AI：任务激增时稳定；维护：可观测指标清晰；质疑(AI1)：是否影响交互速度？回应(SW5)：交互任务走高优先级队列。
6. **R06 / AI1 / 主题：Agent 执行闭环**
   优点：现有工具接口足够多；缺点：缺计划与回滚；迁移：加入 `Plan -> Act -> Verify`; 升级：多 agent 编排；AI：减少“做了但没验证”；维护：失败可复现；质疑(SW3)：验证成本高？回应(AI1)：优先覆盖高风险动作。
7. **R07 / AI2 / 主题：上下文文件治理**
   优点：已有 d.ts 与示例；缺点：分散且人工更新；迁移：自动生成 `AGENTS.md`; 升级：上下文版本化；AI：显著降低幻觉；维护：文档与代码一致性提升；质疑(SW1)：自动生成准确吗？回应(AI2)：加 CI diff 审核。
8. **R08 / AI3 / 主题：评测体系设计**
   优点：脚本步骤可采集；缺点：无统一事件模型；迁移：定义 `task_run/event/action/result`; 升级：离线+在线评测；AI：可量化改进；维护：回归可自动阻断；质疑(PM1)：初期收益？回应(AI3)：先做前 20 高频任务。
9. **R09 / PM1 / 主题：产品定位**
   优点：技术用户可快速上手；缺点：业务用户难用；迁移：模板化任务；升级：流程编排 UI；AI：自然语言到任务模板；维护：需求边界更稳；质疑(SW1)：是否偏离内核？回应(PM1)：先 API-first，不急做重 UI。
10. **R10 / PM2 / 主题：生态战略**
    优点：工具链丰富可形成市场；缺点：无插件规范；迁移：先内部插件接口；升级：公开 registry；AI：工具可发现性提升；维护：生态治理成本上升；质疑(SW4)：供应链风险？回应(PM2)：签名与审核分级。
11. **R11 / SW1 / 主题：目录重构方案**
    优点：结构清晰后研发效率更高；缺点：短期改动面大；迁移：`cmd/ internal/ pkg/`; 升级：便于拆服务；AI：更容易抽取能力图谱；维护：新人学习曲线下降；质疑(SW5)：影响发布？回应：分支灰度。
12. **R12 / SW2 / 主题：窗口能力抽象**
    优点：接口已存在；缺点：行为语义平台差异大；迁移：返回 `unsupported_reason`; 升级：平台策略可插拔；AI：模型可动态降级；维护：减少 if-else；质疑(AI1)：会不会太复杂？回应：复杂性封装到 adapter。
13. **R13 / SW3 / 主题：状态机化执行**
    优点：可明确生命周期；缺点：需要改现有流程；迁移：`queued/running/verifying/succeeded/failed`; 升级：可恢复执行；AI：支持自愈重试；维护：排障可视化；质疑(PM1)：用户是否理解？回应：UI 展示简化状态。
14. **R14 / SW4 / 主题：权限模型**
    优点：最小权限可控风险；缺点：初期配置复杂；迁移：按动作分组权限；升级：项目级策略中心；AI：限制高危调用；维护：安全策略可审计；质疑(PM2)：会阻碍生态？回应：提供“受限沙盒插件”。
15. **R15 / SW5 / 主题：可观测性 MVP**

## 7. 关于“是否可直接生成 agent.md/AGENTS.md”

结论：**必须做，且应作为本项目 AI 能力升级的第一优先级之一。**

### 7.1 目标
- 让 AI 在执行前读取统一、准确、可版本化的项目事实。
- 降低因上下文缺失导致的误调用、幻觉调用、错误参数生成。
- 将“知识正确性”从人工记忆转为机器可校验产物。

### 7.2 推荐产物
1. `AGENTS.md`（给 AI 的人类可读总览）
2. `agent.context.json`（结构化事实，供工具与校验）
3. `docs/ai/tool-catalog.md`（能力说明与示例）
4. `docs/ai/migration-notes.md`（版本变更提示）

### 7.3 自动生成输入源
- Go AST：导出方法、参数、返回值、注释。
- `types/*.d.ts`：面向脚本开发者的声明。
- `examples/*.js`：真实调用示例。
- 配置与入口：CLI flags、HTTP 路由、默认端口与权限模式。
- 平台能力：Windows/macOS/Linux 支持矩阵。

### 7.4 生成规则（关键）
- 只输出白名单字段，禁止泄露密钥、路径敏感信息。
- 每次生成都写入 `generated_at`、`git_commit`、`schema_version`。
- 生成后与仓库版本进行 diff，CI 不通过时阻断合并。
- 为每个工具生成：
  - `name`
  - `description`
  - `args_schema`
  - `side_effect`
  - `preconditions`
  - `failure_modes`
  - `examples`

### 7.5 使用方式（建议）
- 本地：`go run ./cmd/agentdoc -write`
- CI：`go run ./cmd/agentdoc -check`
- 发布：在 release pipeline 强制执行 `-check`。

### 7.6 预期收益
- AI 首轮任务成功率提升。
- 平均修复轮次下降。
- 新成员接入速度提升。
- 接口变更导致的隐性回归显著减少。

## 8. 建议的目标架构（v2）

### 8.1 分层
- `cmd/cli`：命令行入口。
- `cmd/server`：HTTP 服务入口。
- `internal/app`：应用编排层（任务、会话、权限、策略）。
- `internal/engine`：执行引擎（脚本、动作、状态机、回放）。
- `internal/adapters`：平台适配（window/input/screen/http）。
- `internal/ai`：agent 上下文、提示模板、评测与策略。
- `pkg/sdk`：对外稳定 SDK（可选）。

### 8.2 核心对象
- `Session`：每次任务独立上下文（runtime/状态/日志）。
- `Task`：可排队可重试的执行单元。
- `ToolRegistry`：能力注册与 schema。
- `PolicyEngine`：权限、审计、风控。
- `Evaluator`：任务结果验证与评分。

### 8.3 关键非功能要求
- 安全：默认 localhost + token，生产模式强鉴权。
- 可靠：有队列、有超时、有幂等、有补偿。
- 可观测：结构化日志 + 指标 + 回放。
- 可迁移：平台能力矩阵 + 降级策略。

## 9. 路线图（30/90/180 天）

### 9.1 30 天（止血期）
- 完成入口层瘦身（不改业务能力）。
- 引入 `Session`，去除全局 runtime 并发共享。
- 收敛 HTTP 能力到单实现，保留兼容层。
- 落地 `AGENTS.md` 自动生成最小版本。
- 加 20 条核心评测 case（发布硬门禁）。

### 9.2 90 天（重构期）
- 完成 `internal/engine` 与 `adapters` 拆分。
- 建立权限模型、审计事件、错误码体系。
- 建立跨平台能力矩阵与降级路径。
- 引入任务队列与资源限额。
- 评测扩展到 100+ 场景，支持 A/B 比较。

### 9.3 180 天（平台期）
- 上线插件协议与私有 registry。
- 引入多 Agent（执行 + 验证）协作模式。
- 输出企业版治理能力（RBAC、审批、审计查询）。
- 形成可对外合作的 API/SDK 体系。

## 10. 最终结论
1. 当前项目具备良好自动化能力基础，但在 2026 AI 自动化背景下，架构与治理能力明显滞后。
2. 不是“推倒重来”，而是“分阶段重构”：先稳内核、再建治理、后扩生态。
3. `AGENTS.md/agent.md` 自动生成是必须项，不是可选项；它将直接提升 AI 任务准确率与可维护性。
4. 对标 OpenClaw 的方向可以借鉴，但本项目应形成自己的差异化：
   - 更强的可治理与审计能力
   - 更稳的企业级运行可靠性
   - 更清晰的业务模板化与可迁移策略
