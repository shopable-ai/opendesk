# OpenDesk：直接落地面向 Agent 的分层 Markdown API 阅读入口

## 目标需求

直接在 `shopable-ai/opendesk` 当前 `master` 完成面向 Agent 的 API 文档消费入口，使下面的链路真实可用：

短 Markdown 入口
→ 按当前业务需要选择能力分组
→ 比较候选方法
→ 取得选中方法的完整契约和必要公共约束
→ 通过现有 OpenDesk CLI／JavaScript 脚本入口正确调用
→ 将经过验证的调用用于普通 JavaScript Recipe。

日常能力发现与编写代码，不再要求全文读取 `docs/api/runtime-api.ai.json`，也不要求先通读全部 Reference、类型、框架设计和历史案例。

本轮交付是直接写入仓库并提交的 Markdown、必要只读辅助工具、测试和最小引用接入。不是压缩包、附件、补丁下载、审计报告，也不是再次生成执行提示词。完成必要核验后直接实施，不反复等待技术细节确认。

仅改造文档发现与读取层；不接管另一对话正在完善的 `workflows/agent-to-recipe/` 业务流程。

## 本轮执行

先遵守最新 `AGENTS.md` 和 `docs/api/.rules.md`，定向核查现有导航、相关 Workflow／Skill／提示词及读取工具。分别记录“程序解析什么”“工具返回什么”“模型实际得到什么”，不要把三者混为一谈，也不要为了审计把全部 API 返回给模型。

### 1. 建立唯一短入口

默认位置为 `docs/api/agent/README.md`。已有同职责入口则收敛复用，不建立竞争入口。

只包含能力概览、最小共用执行约束、能力分组直达链接、取得完整方法契约的实际方式，以及缺失／冲突处理。

明确停止展开条件：当前步骤的方法、输入输出、必要类型、权限、平台、错误、等待／取消与副作用已清楚，且无未决依赖，即停止阅读无关材料；新问题出现时再定向补读。引用不等于递归必读。

### 2. 按真实能力建立 Markdown 方法目录

按语义和使用时机分组，不机械照搬 JSON 字段、平均切文件或每个方法建一个文件。

每个方法至少提供：用途、精确名称、主要输入输出、副作用、关键适用条件，以及完整契约取得方式。目录负责选型，不手工复制另一套参数和错误正文。

覆盖当前正式 JavaScript Runtime 能力，不只覆盖 CLI，也不能只列熟悉方法或以机器索引的 keyMethods 冒充全部覆盖。根据当前公开 Reference、类型和必要实现建立可检查的覆盖依据；兼容别名、实验能力、文档缺口和未实现规划应明确区分，不能悄悄遗漏或伪装可调用。

`UI.tapTexts` 只是举例，不设为全局优先 API；应用局部经验不升级为框架默认选型顺序。

### 3. 确保选中后真的取得完整契约

第三层优先复用 canonical Markdown Reference，取得签名、参数、返回值、前置条件、权限、平台、错误、等待、取消、副作用、必要公共类型和最小正确示例。

先核实真实读取工具是否支持章节或行范围。支持则给出可执行的范围读取路径；不支持或不能可靠包含依赖时，补最小只读提取工具，或从唯一正文确定性生成小型 Markdown 片段。宿主侧文档工具与 OpenDesk 业务脚本要明确区分。

必须处理：公共约束位于其他章节、跨页类型、别名指向 canonical 方法、工具截断和来源漂移。保留来源路径、章节／范围、来源版本或内容 hash，能判断是否完整、是否过期；不能静默截断、漏读或靠聊天常识补全。无法确认关键合同的项目明确标为阻塞，不生成确定调用。

若正文确实缺少必要行为说明，依据当前实现／类型／测试做最小补齐，写回唯一 canonical Reference，不把未经核实的规则写入目录。不得建立第二份人工维护的完整合同。

### 4. 最小接入并保留执行体系

- 总体 API 导航及相关 Workflow／Skill／提示词接入新入口和明确触发条件；保留必要授权、真实数据依赖、安全停止与原业务阶段。详细设计、历史案例和无关专项资料不列为日常默认必读。
- `runtime-api.ai.json` 退出日常默认全文阅读路径，继续保留程序消费者；不预设删除、拆分或改变格式。`types/*.d.ts` 仅按需核对类型和重载，不替代行为合同。
- 已有适合的 CLI 命令继续使用；需要 JavaScript API 时走现有脚本入口，不能因为没有同名 CLI 命令就重写能力。
- 修正本轮相关的过时路径、重复入口和冲突指令，给出替代位置；没有真实失效依据不批量删除。
- 上一轮仅为搬运资料新增的 CI 上传步骤，核实没有新增有效依赖后移除该步骤；保留已有检查和其他会话修改，不回退整个文件或提交，也不继续围绕压缩包建设流程。

### 5. 完成离线检查和三组阅读演示

保留并运行适用的现有 API 文档检查，包括 `node scripts/check_api_docs_contract.js`；为新增目录／提取方式补充离线测试，覆盖链接、锚点、方法覆盖、来源一致性、必要依赖、截断／失效处理和确定性。既有失败与本轮引入失败分开记录，不弱化断言伪造通过。

提供三组不预先指定 API 的输入：

A. 从指定桌面窗口中取得某个业务值，不改变窗口内容。
B. 读取一份配置数据，校验后另存结果，不覆盖原文件。
C. 已有 Recipe 某个局部步骤失败，只修复该步骤，保持其他业务行为。

演示只进行文档发现与读取，不执行这些业务。分别展示从入口进入哪个分组、比较哪些方法、选中理由、实际取得的契约与依赖、停止展开的位置，以及没有要求读取的无关资料。

记录实际文件、章节／行范围及返回内容是否完整。有真实 token 数据才报告 token；否则记录字节、字符或明确标注的估算方法。维护工具读取量与模型上下文量分开；不能仅因文件变小就宣称效率或成功率已提升。

## 完成标准

从新入口出发，Agent 无需全文读取大型 JSON 就能发现相关能力、选择方法、实际取得完整契约及必要依赖；不需要用户手工挑选文件。

目录覆盖可检查，既不是只有名称的索引，也不是另一套完整 Reference。现有机器索引消费者、类型、公开文档、CLI／Runtime 入口和执行协议不被破坏。

最终先展示可直接理解的阅读链路，再给出：

1. 文件调整表：新增、修改、保留、退出默认阅读、删除；删除说明失效依据。
2. 实际提交 SHA、写入／推送状态及本轮修改范围。
3. 离线检查命令与真实结果、三组阅读演示和读取范围记录。
4. 分别报告文件已调整、离线检查、阅读演示、真实 Agent 加载是否验证、尚未验证部分；文件存在或模拟通过不等于真实 Agent 已加载。
5. 一段简短、可复制的后续 Agent-to-Recipe 调用示例，让 Agent 自行沿新入口按需阅读，不再要求用户列出待读文件。

全部交付直接留在仓库；不能把“已生成压缩包”当成“已修改仓库”，也不能把缺少真实 Agent 环境说成已验证。

## 必要边界

- 只使用 `shopable-ai/opendesk` 当前 `master`；不创建新分支，不 reset、不 force push。开始、重要写入前和提交前核对最新 HEAD 并重读目标文件。本地可见时检查 git status；只有 GitHub 工具时明确无法观察用户未提交工作区，利用当前文件 SHA 防止覆盖并行修改。
- 不改写 Agent-to-Recipe 的整体阶段、合同和专业职责；不增加 Skill 集群、检索平台、编译器、Runtime、业务 API 或执行框架，不改变工具调用协议和 JSON 返回格式。
- 不执行真实桌面操作、客户业务或生产接口变更。授权仅包括相关仓库修改、必要只读核验和离线测试。
- 不为减少上下文删掉必要契约，不隐藏错误与未知状态，不把历史或规划材料当成当前可调用能力。
- 工具或环境确有阻塞时，保留已完成的仓库交付并明确最小阻塞；不要转向压缩包交付、虚假完成或只留下新的计划。
