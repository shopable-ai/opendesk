# 任务规划

## 入口与边界

用于新建任务、计划修订、输入变化后的影响分析和已有任务接续。对应方法 S1，包含先定目标、再拆关键步骤的工作。只阅读本文不会授权桌面操作。

先读[共享合同](../../../../docs/frameworks/agent-to-recipe-skill-contract.md)与当前根 [AGENTS.md](../../../../AGENTS.md)。按需读[任务求解方法](../../../../docs/frameworks/automation-problem-solving-framework.md)，不要重新发明第二套业务分段模型。

## 输入

接收共享合同的 `request.json`。新建时需要用户任务和实际授权来源；此时允许 contractRef／planRevision 为空。修订／接续时必须提供当前合同、计划、进度及已发布交接引用。

需要的信息：业务目标及对象、输入来源、成功证据、允许和禁止的副作用、平台／应用范围、探索与验证预算。任务不明确且可能造成副作用时输出阻塞，不自行补充授权。

## 工作方法

1. 区分开发自动化的工作流与最终业务流程；确定本次是文档、参考脚本 smoke，还是完整 Agent-to-Recipe 验收，防止把低范围结果升级为整链通过。
2. 建立 TaskContract：稳定 criterionId、期望、观察来源和证明强度；分离业务输入、Config、Secret 引用、运行时派生值、初始状态和停止条件。
3. 先产生完整的粗粒度 WorkPlan，临近工作包细化。每包明确 ID、责任 Skill、依赖、输入、现场前提、输出、验收、允许副作用、预算与恢复策略。不预编造尚未观察的坐标和全部点击。
4. 未知应用先给一个有明确问题和退出条件的探测包；已经可复用的成果先核对版本与适用范围，不默认从零开始。
5. 计划变更保留稳定 ID，记录新增／取消／修改理由、受影响输入和下游。把结果标 needs-revalidation，不删除旧事实。
6. 修改账号、业务对象、内容、金额、费用、权限或成功标准前重新核对授权；普通低风险细化在既有边界内进行。
7. 接续时先核对已有产物；running／done 标签不能代替文件和证据。副作用结果不明时输出核对工作包，不能自动重复动作。

## 必须保存的输出

- `task-contract.json`：按共享合同的 TaskContract 字段；期望与事实分开，不能把用户期望写作已观察结果。
- `work-plan.json`：revision、contractRef、工作包、依赖、预算、变更记录；每包至少有一个明确消费者或终止交付。
- `handoff.json`：引用以上产物、实际输入版本、Gate 与未解决项；最后发布。

输出保存到本次 attempt 或协调者指定的版本目录，再通过引用消费。生产者只提出 planDelta；全局 progress 由协调者单独更新。下一个 Skill 只需要合同、分配给它的工作包、必要引用，不需要整段历史聊天。

## 通过、失败与权限

通过意味着合同和计划可以安全推进，不意味着业务已经完成。无法确定成功证据、任务对象或执行授权时 gate 为 warn／fail，并注明 F0 或 F9 等实际原因。格式或引用错误映射 F7。

默认不调用桌面写操作、不修改业务脚本、不填写虚构验证成绩。预算必须有本次实际上限；不允许“无限重试直到成功”。

## 最小独立验收

只给一个新 Agent 用户任务与获准边界，能输出可交接的合同和计划；给已有计划及一个上游输入变化，能指出受影响工作包而不重做全部任务。缺失授权时明确停止。实际测试结果另存，不在本 Skill 中写“已通过”。
